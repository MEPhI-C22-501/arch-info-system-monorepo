# Переход модулей на назначения Keycloak и профили Reference Manager

В realm `arch-info-system` корневой каталог определяет роли пяти прикладных клиентов, допустимые role scope mappings и audiences. Администраторы Keycloak управляют назначениями после создания учётки. Конвергенция восстанавливает схему клиентов, а назначения тестовым людям и служебным клиентам создаёт только при их первичном создании. Право модуля проверяется по роли его клиента и условиям матрицы модуля.

| Клиент | Существующее право | Назначение после переноса |
| --- | --- | --- |
| Task Tracker | `local_access` с `allowed=true` | `task-tracker`: `MEMBER`, `LEAD`, `ADMIN` |
| Planning | `R-01`…`R-06` или одноимённая роль Planning из realm | `planning-system`: `PORTFOLIO_OWNER`, `PLANNER`, `PROJECT_MANAGER`, `RESOURCE_MANAGER`, `TEAM_MEMBER`, `MODULE_ADMIN` соответственно |
| Reference Manager | `reference-reader`, `reference-admin`, `reference-hr-reader`, `reference-hr-admin` из realm | Те же имена в `reference-manager` |
| QA | `qa-viewer`, `qa-tester`, `qa-automation`, `qa-lead`, `qa-admin` по матрице 070 | Те же имена в `qa-system` по согласованным назначениям. Demo-логины не переносятся автоматически. |
| Reports | `reports-*` из client roles | Существующие назначения сохраняются. Право `cost.read` назначается отдельно после сверки прежних допусков. |

Служебные полномочия перечислены в `realm/desired.json` по целевому клиенту. Области Planning задаются атрибутами `portfolio_ids`, `project_ids` и `employee_ids`. Их редактирует только администратор Keycloak. Scope `cost.read` и роль, которая его разрешает, проверяются вместе в клиенте модуля. Reports проверяет ту же роль в фоне и заново проверяет права обеих сторон перед чтением готовой подписки. `reports-directory` читает статусы и эффективные назначения учёток через Admin API в режиме `client_credentials`.

## Прогон и переключение

1. Настройте realm и проверьте клиентские роли, audiences и scopes. В рабочем режиме токены действуют до 300 секунд плюс допуск времени проверяющего сервиса. После отзыва проверяйте отсутствие роли в новом токене. Действующий токен истекает в пределах этого окна. Проверьте, что отключённая учётка не обновляет токен.
2. На время переноса приостановите изменение локальных назначений. Выгрузите существующие назначения в JSON. Для Task Tracker исходные поля берутся из `local_access`: `external_user_id` → `sub`, `role`, `allowed`. Добавьте подтверждённый `iss`, `client: "task-tracker"` и `source: "local_access"`. Для ролей из realm используйте `source: "realm"` и укажите модуль. Если требуется дополнить существующую служебную учётку, укажите согласованный grant из каталога, `source: "service"` и `serviceClient`. Никогда не восстанавливайте настройки допуска по email, ФИО или логину.
3. Укажите адрес Keycloak в `KEYCLOAK_INTERNAL_URL` и учётные данные администратора миграции в `KC_BOOTSTRAP_ADMIN_USERNAME` и `KC_BOOTSTRAP_ADMIN_PASSWORD`. Выполните `python3 infra/scripts/migrate_keycloak_roles.py --issuer "$ISSUER" preview legacy.json > preview.json`. Сверьте `ready`, `present`, `blocked`, `conflict`, прямые и унаследованные назначения. Унаследованные старые роли переносите по согласованным группам в Admin Console. Отключённым пользователям access не выдаётся. После согласования примените `... --issuer "$ISSUER" apply preview.json --journal migration.jsonl`. Сохраните один журнал на realm. Если в нём есть `attempted` без `applied`, вручную сверяйте назначение в Keycloak перед продолжением. Повторный запуск пропускает уже обработанные назначения, включая позднее отозванные.
4. Для сверки профилей подготовьте JSON с `kind: "userId" | "employeeId"`, строковым `id` и меткой исходного объекта. Для известных связок укажите `expectedEmployeeId`. Запустите `python3 infra/scripts/check_profile_links.py --issuer "$ISSUER" subjects.json`. OAuth берётся из `RM_BASE_URL` (с `/v1`), `RM_TOKEN_URL`, `RM_CLIENT_ID`, `RM_CLIENT_SECRET`. Устранение конфликтов выполняется у владельца данных. Инструмент не изменяет назначения и не подбирает совпадения по имени.
5. Заполните проекции профилей и проверьте новый токен каждого модуля. Затем переключите сервисы. При сбое чтения справочника отображение использует последнюю удачную копию, а новое назначение проверяет свежесть до одного часа. Источники обновляются каждые 15 минут. В акторе и доменных ссылках сохраняются прежние ID. В API профиля почта отдаётся при запросе своего профиля, кадровые сценарии используют уже ограниченный HR API.
6. Старые таблицы оставьте до подтверждения перехода. При откате сначала сверяйте текущие назначения и отзывы с аудитом Keycloak. Вернуть старый путь доступа можно только после удаления из него отозванных назначений и сверки действующих; старый снимок ролей целиком не восстанавливайте. Проекции справочников можно повторно заполнить без правок исторических ссылок.

Административный аудит Keycloak доступен Infra через раздел Events, вкладку Admin events. Записываются автор, время и путь изменённого ресурса. Срок хранения 90 дней. Тела административных запросов не сохраняются. Файлы предпросмотра и журналы миграции с идентификаторами храните в закрытом месте, вне репозитория.

Для локального прогона используйте отдельный Compose-проект с файлами `compose.yaml`, `compose.dev.yaml`, `compose.modules.yaml` и профилем `modules`. QA и Reports работают с общим Keycloak, а процессы `reports-load-qa` и `reports-load-profiles` читают реальные API. Для изолированного BI сохранён стенд Reports с собственным realm и служебным секретом `REPORTS_DIRECTORY_CLIENT_SECRET`.
