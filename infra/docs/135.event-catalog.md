# 135. Каталог внешних событий

В каталог попали только события, которые команда предлагает наружу. Внутренние шаги не копируются. Reference Manager издателем Kafka не назначается: его текущий контракт — REST.

Статус `draft` означает, что издатель или потребитель ещё не подтвердили пару. Инфраструктура создала топики, чтобы стенд мог проверять ACL, и этим не объявляет контракт согласованным.

`NotificationCreated` Task Tracker в этот каталог не включён: издатель сам просит не учитывать его как изменение часов.

## Конфликт `TimeLogged`

Один и тот же `eventType` у Task Tracker несёт одну запись списания (`timeLogId`, `hours`, `loggedDate`). Planning в `planning-system/docs/contracts/events/TimeLogged.schema.json` ждёт полный срез задачи, `sourceRevision` и строковую `schemaVersion`. Reports считает часы только из `TimeLogged` издателя и не суммирует их с `WorkItemFieldsChanged`. Пока издатель не примет схему Planning, потребитель не может считать своё ожидание контрактом.

## DLQ

QA пишет, что отдельный топик ошибок не нужен, потому что издатель повторяет отправку. Это закрывает только повтор публикации. Ошибка потребителя после успешной публикации остаётся у потребителя. Эталон инфраструктуры использует `dev.infra.examples.v1.dlq`. Для бизнес-топиков отдельное имя DLQ не создано и остаётся вопросом D-DLQ.
