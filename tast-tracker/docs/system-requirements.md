

## 1. Общая информация

### 1.2. Цель системы

Система должна предоставлять команде единое пространство, в котором можно:
- регистрировать задачи и ошибки;
- планировать сроки и трудоёмкость работ;
- назначать ответственных;
- управлять приоритетами и статусами;
- планировать итерации и контролировать их выполнение;
- отслеживать фактически затраченное и оставшееся время;
- обмениваться данными через файлы Excel.

### 1.3. Границы системы

В состав системы входят:

- бэклог задач;
- канбан-доска;
- карточка задачи и комментарии;
- иерархия задач;
- учёт трудозатрат;
- управление итерациями;
- импорт и экспорт данных в формате Excel.

## 2. Термины

| Термин                   | Определение                                                                                          |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| Бэклог                   | Общий упорядоченный список задач, которые зарегистрированы в системе.                                |
| Задача                   | Единица работы, для которой задаются описание, сроки, исполнитель, трудоёмкость, приоритет и статус. |
| Ошибка                   | Вид задачи, описывающий дефект или некорректное поведение.                                           |
| Итерация                 | Ограниченный период или этап выполнения работ; может использоваться как спринт или веха.             |
| Плановая трудоёмкость    | Оценка времени, необходимого для выполнения задачи.                                                  |
| Фактическая трудоёмкость | Время, фактически затраченное на выполнение задачи.                                                  |
| Оставшееся время         | Расчётное количество часов, которое осталось затратить на задачу.                                    |
| Дочерняя задача          | Задача, созданная в рамках декомпозиции другой, родительской задачи.                                 |

## 3. Пользователи и роли

Предварительно выделяются следующие роли:

| Роль                       | Основные возможности                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Участник команды           | Просмотр задач, изменение доступных задач, добавление комментариев и фактических трудозатрат, настройка статусов                     |
| Руководитель / планировщик | Ведение бэклога, назначение исполнителей, управление приоритетами, планирование и контроль итераций, настройка статусов, типов задач |
| Администратор              | пользователей и прав доступа.                                                                                                        |

## 4. Функциональные требования

### 4.1. Управление бэклогом

- Система должна хранить единый бэклог задач.
- Пользователь с соответствующими правами должен иметь возможность создать, просмотреть, изменить и удалить либо архивировать задачу.
- Система должна поддерживать как минимум два вида задач: «Задача» и «Ошибка».
- Для каждой задачи система должна хранить уникальный идентификатор.
- Пользователь должен иметь возможность отбирать и сортировать задачи как минимум по виду, статусу, приоритету, исполнителю и итерации.
- Пользователь должен иметь возможность открыть карточку задачи из бэклога.

### 4.2. Карточка задачи

- Карточка задачи должна содержать следующие поля:
  - идентификатор;
  - наименование;
  - описание (в виде markdown);
  - вид задачи;
  - статус;
  - приоритет;
  - исполнитель;
  - дата начала;
  - срок выполнения;
  - плановая трудоёмкость в часах;
  - фактическая трудоёмкость в часах;
  - оставшееся время в часах;
  - итерация;
  - родительская задача, если она существует;
  - комментарии.

- Наименование задачи должно быть обязательным для заполнения.
- Плановая и фактическая трудоёмкость не должны принимать отрицательные значения.
- Срок выполнения задачи не должен быть раньше даты её начала.
- Пользователь должен иметь возможность назначить на задачу одного ответственного исполнителя.
- Система должна сохранять изменения карточки задачи.

### 4.3. Статусы и канбан-доска

- Система должна отображать задачи на канбан-доске.
- Каждому статусу задачи должна соответствовать колонка канбан-доски.
- Пользователь должен иметь возможность изменить статус задачи путём её перемещения между колонками.
- После перемещения задачи система должна сохранить новый статус и отобразить задачу в соответствующей колонке.
- Администратор должен иметь возможность создавать, переименовывать, упорядочивать и деактивировать статусы.
- Канбан-доска должна поддерживать фильтрацию как минимум по исполнителю, приоритету и итерации.

### 4.4. Приоритеты

- Каждой задаче должен назначаться приоритет.
- Пользователь с соответствующими правами должен иметь возможность изменить приоритет задачи.
- Система должна позволять сортировать и фильтровать задачи по приоритету.
- Перечень значений приоритета должен быть единым для всех задач.

### 4.5. Декомпозиция задач

- Пользователь должен иметь возможность создать дочернюю задачу для существующей задачи.
- Система должна отображать родительскую задачу и список её непосредственных дочерних задач.
- Дочерняя задача должна иметь собственные статус, исполнителя, сроки и трудоёмкость.
- Система не должна допускать циклических связей в иерархии задач.

### 4.6. Комментарии

- Пользователь должен иметь возможность добавить текстовый комментарий к задаче.
- Для каждого комментария система должна отображать автора, дату и время создания.
- Комментарии должны отображаться в карточке задачи в хронологическом порядке.
- Правила изменения и удаления комментариев должны определяться правами пользователя.

### 4.7. Учёт трудоёмкости

- Пользователь должен иметь возможность задать плановую трудоёмкость задачи в часах.
- Пользователь должен иметь возможность регистрировать фактически затраченное на задачу время.
- **FR-TM-03.** Каждая запись о затраченном времени должна содержать количество часов, дату и пользователя, зарегистрировавшего время.
- **FR-TM-04.** Фактическая трудоёмкость задачи должна рассчитываться как сумма всех зарегистрированных затрат времени.
- **FR-TM-05.** Система должна рассчитывать оставшееся время по формуле: `плановая трудоёмкость − фактическая трудоёмкость`.
- **FR-TM-06.** Если фактическая трудоёмкость превышает плановую, система должна показывать перерасход часов, а не скрывать его.
- **FR-TM-07.** Плановая, фактическая и оставшаяся трудоёмкость должны отображаться в карточке задачи.

### 4.8. Управление итерациями

- **FR-IT-01.** Пользователь с соответствующими правами должен иметь возможность создать, просмотреть, изменить и завершить итерацию.
- **FR-IT-02.** Для итерации должны храниться наименование, описание, дата начала, дата окончания и состояние.
- **FR-IT-03.** Система должна поддерживать как минимум состояния итерации «Запланирована», «Активна» и «Завершена».
- **FR-IT-04.** Пользователь должен иметь возможность включать задачи из бэклога в итерацию и исключать их из неё.
- **FR-IT-05.** Одна задача не должна одновременно входить более чем в одну незавершённую итерацию.
- **FR-IT-06.** Система должна отображать для итерации:

  - перечень входящих задач;
  - количество задач по статусам;
  - суммарную плановую трудоёмкость;
  - суммарную фактическую трудоёмкость;
  - суммарное оставшееся время;
  - долю завершённых задач.

- **FR-IT-07.** При завершении итерации система должна сохранить сведения о составе итерации и результатах её выполнения.
- **FR-IT-08.** Незавершённые задачи завершённой итерации должны оставаться в бэклоге и быть доступными для последующего планирования.

### 4.9. Импорт и экспорт Excel

- **FR-EX-01.** Пользователь с соответствующими правами должен иметь возможность экспортировать задачи в файл формата `.xlsx`.
- **FR-EX-02.** Экспорт должен включать все поля задачи, необходимые для последующего восстановления данных посредством импорта.
- **FR-EX-03.** В экспорт должны включаться уникальные идентификаторы задач и связанные справочные значения.
- **FR-EX-04.** Пользователь должен иметь возможность импортировать ранее экспортированный системой файл `.xlsx`.
- **FR-EX-05.** При импорте система должна создавать новые задачи и обновлять существующие задачи по их уникальным идентификаторам.
- **FR-EX-06.** Перед применением импорта система должна проверить структуру файла, обязательные поля, форматы значений и ссылки на связанные сущности.
- **FR-EX-07.** При наличии ошибок система не должна частично применять некорректные строки без явного уведомления пользователя.
- **FR-EX-08.** После импорта система должна показать количество созданных, обновлённых и отклонённых записей, а также перечень ошибок.
- **FR-EX-09.** Экспортированный файл без изменений должен быть пригоден для обратного импорта без потери поддерживаемых данных.

## 5. Основные бизнес-правила

- **BR-01.** Каждая задача в любой момент времени имеет ровно один статус.
- **BR-02.** Каждая задача имеет ровно один вид и один приоритет.
- **BR-03.** Исполнитель может отсутствовать у задачи, находящейся в бэклоге, если иное не будет определено правилами процесса.
- **BR-04.** Завершение задачи не удаляет её из системы.
- **BR-05.** Значения времени хранятся и отображаются в часах.
- **BR-06.** Оставшееся время вычисляется автоматически и не вводится пользователем вручную.
- **BR-07.** Удаление пользователя, статуса, приоритета или итерации не должно приводить к потере связанных задач.
- **BR-08.** Родительская и дочерняя задачи не могут быть одной и той же задачей.

## 6. Пользовательские сценарии

### 6.1. Недельное планирование

1. Руководитель создаёт новую итерацию и задаёт её сроки.
2. Руководитель просматривает и при необходимости фильтрует бэклог.
3. Руководитель уточняет приоритеты, сроки и плановую трудоёмкость задач.
4. Руководитель назначает исполнителей.
5. Руководитель включает выбранные задачи в итерацию.
6. Система показывает суммарную плановую нагрузку итерации.
7. Руководитель переводит итерацию в активное состояние.

### 6.2. Выполнение задачи

1. Исполнитель открывает назначенную ему задачу.
2. Исполнитель переводит её в рабочий статус.
3. Исполнитель регистрирует затраченное время и при необходимости добавляет комментарии.
4. Система пересчитывает фактическое и оставшееся время.
5. После выполнения исполнитель переводит задачу в завершающий статус.

### 6.3. Декомпозиция

1. Пользователь открывает крупную задачу.
2. Пользователь создаёт одну или несколько дочерних задач.
3. Пользователь задаёт для них исполнителей, сроки и оценки.
4. Система отображает созданные задачи в иерархии родительской задачи и в бэклоге.

### 6.4. Контроль итерации

1. Руководитель открывает активную итерацию.
2. Система показывает распределение задач по статусам и показатели трудоёмкости.
3. Руководитель выявляет просроченные задачи и задачи с перерасходом времени.
4. По окончании периода руководитель завершает итерацию.
5. Незавершённые задачи возвращаются в доступный для планирования бэклог.

### 6.5. Обмен данными через Excel

1. Пользователь экспортирует задачи в файл `.xlsx`.
2. Пользователь изменяет допустимые значения в файле.
3. Пользователь загружает файл обратно в систему.
4. Система проверяет файл и показывает результат проверки.
5. При успешной проверке система создаёт или обновляет задачи и формирует отчёт об импорте.

## 7. Требования к интерфейсу

### 7.1. Страница бэклога

Страница должна содержать:

- таблицу или список задач;
- основные поля задачи: идентификатор, наименование, вид, статус, приоритет, исполнитель, срок, плановые, фактические и оставшиеся часы, итерация;
- элементы фильтрации и сортировки;
- действие создания задачи;
- действия импорта и экспорта Excel;
- переход к карточке выбранной задачи.

### 7.2. Канбан-доска

Страница должна содержать:

- колонки, соответствующие активным статусам;
- карточки задач в колонках;
- возможность перемещения карточек между колонками;
- фильтры по исполнителю, приоритету и итерации;
- краткие сведения на карточке: идентификатор, наименование, исполнитель, приоритет, срок и оставшиеся часы.

### 7.3. Карточка задачи

Страница должна содержать:

- все поля задачи;
- блок родительской и дочерних задач;
- историю зарегистрированных трудозатрат;
- форму добавления трудозатрат;
- список комментариев и форму нового комментария;
- действия сохранения изменений и смены статуса.

### 7.4. Страница итерации

Страница должна содержать:

- реквизиты и состояние итерации;
- список включённых задач;
- показатели плановой, фактической и оставшейся трудоёмкости;
- количество и долю завершённых задач;
- распределение задач по статусам;
- действия добавления и исключения задач;
- действие завершения итерации.

## 8. Требования к данным

Система должна хранить как минимум следующие сущности и связи:

| Сущность | Основные данные и связи |
|---|---|
| Задача | Поля карточки; связь с видом, статусом, приоритетом, исполнителем, итерацией и родительской задачей. |
| Пользователь | Идентификатор, отображаемое имя, состояние учётной записи и роль. |
| Статус | Идентификатор, наименование, порядок на доске и признак активности. |
| Приоритет | Идентификатор, наименование, порядок и признак активности. |
| Вид задачи | Идентификатор, наименование и признак активности. |
| Итерация | Наименование, описание, даты, состояние и связанные задачи. |
| Запись трудозатрат | Задача, пользователь, дата, количество часов и необязательный комментарий. |
| Комментарий | Задача, автор, текст, дата и время создания. |

## 9. Нефункциональные требования

- **NFR-01. Целостность данных.** Операции сохранения задачи и импорта должны либо завершаться согласованно, либо возвращать понятное сообщение об ошибке.
- **NFR-02. Аудит.** Система должна хранить автора и время создания и последнего изменения задачи. Необходимость полной истории изменений подлежит согласованию.
- **NFR-03. Безопасность.** Доступ к операциям должен определяться ролью пользователя; система не должна полагаться только на скрытие элементов интерфейса.
- **NFR-04. Удобство использования.** Сообщения об ошибках должны объяснять причину и указывать, какие данные необходимо исправить.
- **NFR-05. Совместимость.** Файлы экспорта должны открываться в актуальных версиях Microsoft Excel и совместимых табличных редакторах.
- **NFR-06. Локализация времени.** Даты и время должны отображаться в согласованном часовом поясе и однозначном формате.
- **NFR-07. Сохранность данных.** Требования к резервному копированию и восстановлению должны быть определены до ввода системы в эксплуатацию.

Целевые показатели производительности, доступности, объёма данных и времени восстановления пока не заданы.

## 10. Критерии приёмки первой версии

Первая версия может считаться соответствующей исходным пожеланиям, если одновременно выполняются следующие условия:

1. Пользователь может создать задачу или ошибку со всеми обязательными атрибутами и увидеть её в бэклоге.
2. Задачу можно назначить исполнителю, приоритизировать, оценить в часах и привязать к итерации.
3. Задача отображается на канбан-доске и меняет статус при перемещении между колонками.
4. Для задачи можно создать дочернюю задачу, добавить комментарий и зарегистрировать фактические трудозатраты.
5. Система корректно показывает плановые, фактические и оставшиеся часы, включая перерасход.
6. Пользователь может сформировать итерацию, контролировать её показатели и завершить её без потери незавершённых задач.
7. Задачи можно экспортировать в `.xlsx`, а полученный файл — импортировать обратно без потери поддерживаемых данных.
8. Некорректный файл импорта не приводит к незаметной частичной порче данных и сопровождается отчётом об ошибках.

5. Каков исходный набор приоритетов?
6. Являются ли «спринт» и «веха» одним типом итерации или разными сущностями с различным поведением?
7. Может ли задача входить одновременно в спринт и веху?
8. Нужно ли автоматически суммировать оценки и фактические часы дочерних задач в родительской задаче?
9. Следует ли разрешать ручную корректировку оставшегося времени независимо от плановых и фактических часов?
10. Нужно ли учитывать трудозатраты дробно, например с шагом 0,25 часа?
11. Какие поля и связанные данные должны переноситься через Excel: комментарии, трудозатраты, иерархия, итерации и справочники?
12. Как разрешать конфликты, если данные одной задачи были изменены и в системе, и в экспортированном файле?
13. Требуется ли полная история изменений задач, статусов, назначений и оценок?
14. Нужны ли уведомления о назначении, приближении срока, просрочке и новых комментариях?
15. Требуются ли поиск, отчёты, диаграммы, ограничения незавершённой работы (WIP) и учёт доступной ёмкости команды?
16. Каковы ожидаемые число пользователей, количество задач и требования к скорости работы?
17. Какие требования предъявляются к развёртыванию, резервному копированию, доступности и защите данных?

## 12. Предлагаемые границы первой версии

В первую версию рекомендуется включить:

- карточку задачи и бэклог;
- виды «Задача» и «Ошибка»;
- одного исполнителя на задачу;
- настраиваемые статусы и фиксированный справочник приоритетов;
- канбан-доску;
- дочерние задачи одного или нескольких уровней;
- комментарии;
- плановые и фактические часы;
- итерации и основные показатели их выполнения;
- двусторонний обмен задачами через `.xlsx`;
- базовые роли и контроль доступа.

Уведомления, расширенная аналитика, WIP-лимиты, планирование ёмкости команды и интеграции целесообразно рассматривать после согласования базовых процессов.
