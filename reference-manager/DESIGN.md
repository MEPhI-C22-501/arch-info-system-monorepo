| Поле | Значение |
| --- | --- |
| Проект | arch-info-system - учебная ERP-система (НИЯУ МИФИ, группа C22-501) |
| Подсистема | Reference Manager ("Справочник"), сервис НСИ |
| Команда | команда справочников |
| Версия документа | 0.4 (черновик) |
| Дата | 2026-09-14 |
| Основание | .specify/memory/vision.md v0.2 (FEAT-01..11), .specify/memory/constitution.md v1.0.0, решения команды от 2026-09-14 |

## 1. Назначение документа

Документ фиксирует требования к сервису "Справочник" и его технический стек. Требования пронумерованы: функциональные - FR-RM-NN, нефункциональные - NFR-RM-NN; каждое ссылается на возможность FEAT-NN из .specify/memory/vision.md и на срез, в котором реализуется. Детальные технические решения (модель данных, контракт API, раскладка пакетов) оформляются в спецификациях spec-kit и ADR в `.specify/memory/` по мере реализации срезов и в этот документ не входят.

Термины совпадают с разделом 1.3 vision. Принципы I-VII - из конституции проекта.

## 3. Функциональные требования

### 3.1. Справочники

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-01 | Сервис создаёт справочник с полями `code`, `name`, `description`; `code` уникален в своей области (системные справочники; справочники одного арендатора) и не совпадает с кодом системного справочника; статус по умолчанию ACTIVE. | 1 | 01 |
| FR-RM-02 | Сервис возвращает справочник по `code`, включая неактивные и удалённые. | 1 | 01 |
| FR-RM-03 | Сервис частично изменяет `name`, `description`, `status` справочника. | 1 | 01 |
| FR-RM-04 | Сервис возвращает список справочников с фильтрами по статусу, поиском по коду и названию, флагом показа удалённых и постраничным выводом. | 1 | 01 |

### 3.2. Элементы справочника

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-05 | Сервис создаёт элемент справочника с полями `code`, `name`, `attributes`; `code` уникален в пределах справочника, включая удалённые элементы. | 1 | 02, 03 |
| FR-RM-06 | Сервис возвращает элемент по `id` и по `code`, включая неактивные и удалённые. | 1 | 02 |
| FR-RM-07 | Сервис частично изменяет `name`, `status`, `attributes` элемента; попытка изменить `id`, `code` или служебные поля отклоняется с кодом 422. | 1 | 02, 03 |
| FR-RM-08 | Сервис возвращает список элементов справочника с фильтром по статусу (по умолчанию ACTIVE), поиском по префиксу кода и вхождению в название, флагом показа удалённых, фильтром `updated_since` (изменённые после момента, включая неактивные и удалённые), постраничным выводом и сортировкой по `code`, `name`, `updated_at`. | 1 | 02 |

### 3.3. Статус, удаление и восстановление

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-09 | Справочники и элементы имеют статус ACTIVE или INACTIVE; неактивные записи не попадают в списки без явного фильтра, но доступны по `id` и `code`. | 1 | 04 |
| FR-RM-10 | Удаление справочника или элемента - мягкое: запись получает отметку `deleted_at`, ответ 204; повторное удаление отвечает 409. | 1 | 04 |
| FR-RM-11 | Удалённая запись не попадает в списки без флага показа удалённых, доступна по `id` и `code` с заполненным `deleted_at`; изменение удалённой записи отклоняется с кодом 409 до восстановления. | 1 | 04 |
| FR-RM-12 | Восстановление снимает отметку удаления и возвращает запись; восстановление неудалённой записи отвечает 409. | 1 | 04 |
| FR-RM-13 | Для удалённого справочника все вложенные операции отвечают 404, кроме получения самого справочника и восстановления; отметки удаления его элементов не меняются. | 1 | 04 |
| FR-RM-14 | Каждая операция записи, включая удаление и восстановление, увеличивает `version` записи и обновляет `updated_at` и `updated_by`. | 1 | 03 |

### 3.4. Схемы атрибутов

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-15 | Справочник имеет версионируемую схему атрибутов в формате JSON Schema draft 2020-12; версии не изменяются и не удаляются; текущей считается последняя. | 1 | 05 |
| FR-RM-16 | Создание версии схемы проверяет её компиляцию; ссылки `$ref` на внешние ресурсы запрещены. | 1 | 05 |
| FR-RM-17 | Новая версия схемы принимается, только если ей соответствуют все активные неудалённые элементы справочника; иначе ответ 409 с перечнем нарушающих элементов (до 20). | 1 | 05 |
| FR-RM-18 | Атрибуты элемента проверяются текущей схемой при создании и изменении; несоответствие отвечает 422 со списком ошибок по путям; в элементе сохраняется версия схемы, по которой прошла проверка. | 1 | 05 |
| FR-RM-19 | Сервис возвращает текущую схему справочника и список всех её версий. | 1 | 05 |
| FR-RM-20 | При отсутствии схемы атрибуты принимаются как любой JSON-объект. | 1 | 05 |

### 3.5. Аутентификация и авторизация (срез 2)

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-21 | Каждый запрос к API несёт Bearer-токен Keycloak; сервис проверяет подпись, издателя, получателя, срок действия; иначе ответ 401. | 2 | 07 |
| FR-RM-22 | Роли `reference-reader`, `reference-editor`, `reference-admin` читаются из claim токена; reader читает, editor создаёт, изменяет, удаляет и восстанавливает записи и схемы в границах своего арендатора, admin делает то же для всех арендаторов и системных справочников. | 2 | 07 |
| FR-RM-23 | Права проверяются в сервисном слое перед каждой операцией; недостаточные права отвечают 403. | 2 | 07 |
| FR-RM-24 | Изменение и удаление требуют заголовка `If-Match` с текущей версией: несовпадение отвечает 412, отсутствие - 428; получение возвращает `ETag` и поддерживает `If-None-Match`. | 2 | 03 |

### 3.6. Мультиарендность (срез 2)

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-25 | Арендатор определяется из claim токена; системные справочники не принадлежат арендатору. | 2 | 06 |
| FR-RM-26 | Арендаторские справочники видны и изменяемы только пользователям своего арендатора; обращение к чужому справочнику отвечает 404; администратор видит все. | 2 | 06 |
| FR-RM-27 | Код справочника разрешается сначала среди справочников арендатора вызывающего, затем среди системных; совпадение кода арендаторского и системного справочника запрещено при создании. | 2 | 06 |

### 3.7. Интерфейс администрирования (срез 3)

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-28 | Сервис отдаёт веб-интерфейс администрирования по пути `/admin/` из того же процесса и образа; вход через Keycloak (OIDC Authorization Code с PKCE); доступные действия определяются ролями токена, сервер проверяет права независимо. | 3 | 09 |
| FR-RM-29 | Интерфейс содержит: список справочников с поиском, фильтром по статусу и показом удалённых; карточку справочника с текущей схемой и её версиями и редактором схемы; таблицу элементов с поиском, фильтрами и постраничным выводом; форму элемента, поля атрибутов которой строятся по схеме; действия деактивации, удаления и восстановления с подтверждением; отображение ошибок API с привязкой к полям. | 3 | 09 |

### 3.8. Служебные точки

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-30 | `GET /health` отвечает 200, пока процесс жив. | 1 | 08 |
| FR-RM-31 | `GET /ready` отвечает 200, если база данных отвечает на ping и версия схемы миграций не ниже ожидаемой приложением; иначе 503. | 1 | 08 |
| FR-RM-32 | По флагу конфигурации сервис отдаёт метрики в формате Prometheus на `/metrics`. | 1 | 08 |

## 4. Нефункциональные требования

### 4.1. Архитектурные ограничения

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-01 | Сервис принимает только входящие вызовы; исходящие соединения ограничены собственной PostgreSQL, коллектором OpenTelemetry и Keycloak (ключи проверки токенов). Обращений к другим модулям ERP нет. | I |
| NFR-RM-02 | Сервис хранит только НСИ: справочники, элементы, схемы атрибутов. Бизнес-сущности не хранятся. | I |
| NFR-RM-03 | К базе данных сервиса обращается только сам сервис; потребители работают через REST API. | I |
| NFR-RM-04 | Физическое удаление данных не реализуется ни в API, ни в миграциях. | II |
| NFR-RM-05 | `id` и `code` неизменяемы после создания; код удалённой записи остаётся занятым. | II |
| NFR-RM-06 | Контракт API обратно совместим в пределах мажорной версии `/v1`; несовместимые изменения выпускаются как `/v2`. | II |
| NFR-RM-07 | Все операции записи выполняются сервисным слоем в одной транзакции; обработчики HTTP не обращаются к хранилищу напрямую. | III |
| NFR-RM-08 | Приложение не хранит состояния между запросами, кроме кэшей схем и ключей; допускает несколько одновременно работающих экземпляров. | VI |

### 4.2. Контракт API

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-09 | REST поверх HTTP, `application/json`, UTF-8, время в RFC 3339 UTC, базовый путь `/api/reference-data/v1`. | IV |
| NFR-RM-10 | Частичное изменение - `PATCH` в формате JSON Merge Patch (RFC 7386). | IV |
| NFR-RM-11 | Ошибки - RFC 9457 `application/problem+json` с полями `request_id`, `trace_id` и списком `errors[]` для ошибок валидации. | IV |
| NFR-RM-12 | Контракт описан в `api/openapi.yaml` (OpenAPI 3.x), обновляется до реализации и проверяется контрактными тестами. | IV |
| NFR-RM-13 | Каждый ответ содержит `X-Request-Id` и `X-Trace-Id`; входящий `traceparent` продолжает трассу вызывающего. | VI |

### 4.3. Данные

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-14 | Идентификаторы - UUID v7. | VI |
| NFR-RM-15 | Ограничения размера: тело запроса 1 МБ, `attributes` 64 КБ, схема 256 КБ, размер страницы не более 200 (по умолчанию 50). | VII |
| NFR-RM-16 | Роль приложения в базе данных не имеет прав DDL и `DELETE`; DDL выполняет только задание миграций. | II, VII |
| NFR-RM-17 | Каждая миграция обратима, проверяется последовательностью up-down-up в CI и совместима с предыдущей версией приложения. | V |

### 4.4. Производительность и доступность

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-18 | p95 времени отклика чтения не более 100 мс при 100 запросах в секунду; записи - не более 300 мс, включая проверку схемы. | - |
| NFR-RM-19 | Доступность 99,5% на стенде (целевое значение согласуется с Infra). | - |
| NFR-RM-20 | Списки возвращают общее количество записей; запросы списков, поиска по коду и `updated_since` покрыты индексами. | - |

### 4.5. Эксплуатация

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-21 | Миграции применяет отдельное задание (job) до запуска новой версии приложения: локально - цель Taskfile, в Kubernetes - Job; сервиса миграций в Docker Compose нет. | VI |
| NFR-RM-22 | Конфигурация читается из каталога YAML-файлов или переменных окружения без пересборки; секреты не хранятся в репозитории. | VI |
| NFR-RM-23 | Остановка корректная: текущие запросы завершаются, соединения и экспортёры телеметрии закрываются с таймаутом. | VI |
| NFR-RM-24 | Один образ содержит API и интерфейс администрирования; версия сервиса передаётся в бинарник при сборке. | VI |

### 4.6. Наблюдаемость

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-25 | Трассы, метрики и журналы собираются через OpenTelemetry и отправляются по OTLP в коллектор; ресурс несёт `service.name`, `service.version`, `service.instance.id`, `deployment.environment`. | VI |
| NFR-RM-26 | Трассируются каждый HTTP-запрос, каждый запрос к базе данных (без параметров), операции сервисного слоя и проверка схемы; сэмплирование parent-based с долей из конфигурации. | VI |
| NFR-RM-27 | Метрики: HTTP по семантическим соглашениям OpenTelemetry, пул соединений, runtime Go, счётчики операций записи и проверок схем, количество справочников и элементов по статусам. | VI |
| NFR-RM-28 | Журналы структурированные через `log/slog` с `trace_id`, `span_id`, `request_id`, `actor_id`; отдельный обработчик отправляет их по OTLP; токены, пароли и тела запросов не пишутся. | VI, VII |
| NFR-RM-29 | Недоступность коллектора не замедляет и не отклоняет запросы; при отключённой телеметрии используются no-op провайдеры. | VI |

### 4.7. Безопасность

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-30 | В срезе 1 сервис доступен только из внутренней сети стенда; порт наружу не публикуется. | VII |
| NFR-RM-31 | Все запросы к базе данных параметризованы. | VII |
| NFR-RM-32 | В Kubernetes исходящий трафик ограничен сетевой политикой адресами из NFR-RM-01. | I, VII |
| NFR-RM-33 | Ответы с ошибками не раскрывают внутренние детали; подробности только в журналах и трассах. | VII |
| NFR-RM-34 | Зависимости проверяются `govulncheck` в CI. | VII |
| NFR-RM-35 | Статика интерфейса отдаётся с `Content-Security-Policy` без inline-скриптов и `X-Frame-Options: DENY`; интерфейс и API работают на одном origin, CORS не требуется. | VII |

### 4.8. Качество кода и тестирование

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-36 | Код проходит golangci-lint v2 с конфигурацией репозитория без предупреждений. | V |
| NFR-RM-37 | Модульные тесты доменной логики и сервисного слоя, интеграционные тесты хранилища на реальном PostgreSQL, контрактные тесты API, тесты наличия телеметрии, сквозной сценарий на стенде; покрытие доменной логики и хранилища не ниже 80 процентов строк. | V |
| NFR-RM-38 | `task lint` и `task tests` проходят на каждом pull request; исправление дефекта сопровождается регрессионным тестом. | V |

## 5. Технический стек

| Область | Технология | Примечание |
| --- | --- | --- |
| Язык | Go (версия из `go.mod`, сейчас 1.27) | Статический бинарник, `CGO_ENABLED=0` |
| HTTP | `net/http`, маршрутизатор chi v5 | Middleware: request id, otelhttp, recover, логирование, лимит тела, таймаут; со среза 2 - аутентификация |
| Конфигурация | cleanenv, каталог YAML через `--configs` или переменные окружения | Файлы `transport.yaml`, `databases.yaml`, `log.yaml`, `limits.yaml`, `telemetry.yaml`; срез 2 - `auth.yaml` |
| База данных | PostgreSQL 18 | Единственное хранилище; JSONB для атрибутов и схем |
| Драйвер БД | pgx v5 с пулом pgxpool | Трассировка через otelpgx |
| Миграции | golang-migrate, SQL-файлы с последовательной нумерацией в `deployments/migrations/` | Запуск отдельным заданием (образ `migrate/migrate`, цель Taskfile, Kubernetes Job) |
| Проверка атрибутов | JSON Schema draft 2020-12, библиотека `santhosh-tekuri/jsonschema` | Схемы компилируются и кэшируются |
| Идентификаторы | UUID v7 (`google/uuid`) | - |
| Контракт API | OpenAPI 3.x в `api/openapi.yaml`; ошибки RFC 9457; `PATCH` по RFC 7386 | Контрактные тесты на kin-openapi |
| Телеметрия | OpenTelemetry SDK для Go: трассы, метрики, журналы; экспорт OTLP (gRPC, при необходимости HTTP) | Инструментирование otelhttp, otelpgx, `contrib/instrumentation/runtime`, мост `otelslog`; опционально Prometheus-экспортёр |
| Журналирование | `log/slog` с обработчиками `console`, `file`, `otel` из `log.yaml` | Существующий реестр обработчиков `pkg/log` |
| Аутентификация (срез 2) | Keycloak, OIDC, JWT; проверка подписи по JWKS или ключам из конфигурации | Библиотека JWT выбирается ADR |
| Интерфейс (срез 3) | Одностраничное приложение, статика встроена в бинарник через `embed`, путь `/admin/`; вход OIDC с PKCE | Стек фронтенда выбирается ADR; сборка статики в `task generate` |
| Сборка и задачи | Taskfile: `generate`, `build`, `lint`, `tests`, `migration`, `images`, `up`, `down`; golangci-lint v2 | - |
| Контейнеры | Образы distroless static (рабочий и отладочный с busybox) | Один образ на API и интерфейс |
| Запуск | Docker Compose на стенде (`deployments/docker-compose.yaml`), Kubernetes в целевом окружении силами Infra | Readiness на `/ready`, liveness на `/health`, egress ограничен сетевой политикой |
| Тестирование | `testing`, testcontainers-go (PostgreSQL), kin-openapi, in-memory экспортёры OpenTelemetry | Интеграционные и контрактные тесты в `tests/` |
| CI/CD | GitHub Actions по изменениям `reference-manager/**` | Lint, тесты, up-down-up миграций, govulncheck, сборка образов |
| Процесс | spec-kit (артефакты в `.specify/memory/`), Conventional Commits, CODEOWNERS | Конституция проекта |
