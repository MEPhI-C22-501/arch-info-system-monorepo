## 1. Назначение документа

Документ фиксирует требования к сервису "Справочник" и его технический стек. Требования пронумерованы: функциональные - FR-RM-NN, нефункциональные - NFR-RM-NN. Каждое ссылается на возможность FEAT-NN из .specify/memory/vision.md и на срез, в котором реализуется. Детальные технические решения (структура таблиц, контракт API, раскладка пакетов, способ переиспользования кода обработчиков) оформляются в спецификациях spec-kit и ADR в `.specify/memory/` по мере реализации срезов и в этот документ не входят.

Идентификаторы требований стабильны. Требование, потерявшее смысл после смены модели, не удаляется и не переиспользуется: оно перечислено в разделе 6 с причиной. Новые требования получают следующие номера.

Термины совпадают с разделом 1.3 vision. Принципы I-VII - из конституции проекта.

## 3. Функциональные требования

### 3.1. Справочники

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-33 | Справочник добавляет команда справочников по заявке: миграция golang-migrate создаёт таблицу с общими столбцами (FR-RM-34) и столбцами справочника (FR-RM-35); в сервисе регистрируются пять обработчиков (FR-RM-37); `api/openapi.yaml` и тесты дополняются в том же pull request. | 1 | 01 |
| FR-RM-34 | Таблица каждого справочника содержит общие столбцы `id` (UUID v7), `code`, `name`, `status`, `version`, `created_at`, `created_by`, `updated_at`, `updated_by`, `deleted_at`; `code` уникален в пределах таблицы, включая удалённые записи. Состав, типы и индексы общих столбцов одинаковы во всех таблицах справочников. | 1 | 01, 03 |
| FR-RM-35 | Столбцы справочника типизированы; обязательность, диапазоны, уникальность и ссылки на записи других справочников заданы ограничениями таблицы (NOT NULL, CHECK, UNIQUE, FOREIGN KEY). Сервис проверяет запись до обращения к базе данных и отвечает 422 со списком ошибок по полям; нарушение ограничения базы данных также отвечает 422. | 1 | 12 |
| FR-RM-36 | Состав столбцов меняется только новой миграцией: новый столбец необязателен или имеет значение по умолчанию; столбцы не удаляются и не меняют тип. Справочник не удаляется: таблица и обработчики остаются, ненужные записи деактивируются. | 1 | 01, 12 |
| FR-RM-37 | Каждый справочник имеет ровно пять операций API: `POST /{catalog}` - создание записи, `GET /{catalog}` - постраничное чтение, `GET /{catalog}/{id}` - чтение одной записи, `PATCH /{catalog}/{id}` - частичное изменение, `DELETE /{catalog}/{id}` - удаление; `{catalog}` - код справочника, например `currencies`. Через API справочники не создаются, не изменяются и не удаляются. | 1 | 01, 02 |
| FR-RM-38 | Состав справочников и их столбцов описан в `api/openapi.yaml`: по одной схеме записи на справочник. Потребители и интерфейс администрирования узнают справочники из контракта. | 1 | 01 |
| FR-RM-39 | Заявка на справочник оформляется как issue по шаблону команды справочников и содержит: код и название справочника, назначение, столбцы с типами и ограничениями, признак арендаторского справочника, начальные данные. Заявка на бизнес-сущности (сотрудники, проекты, календарь) отклоняется со ссылкой на принцип I. | 1 | 01 |

### 3.2. Записи справочника

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-05 | Сервис создаёт запись справочника с полями `code`, `name` и столбцами справочника; `code` уникален в пределах справочника, включая удалённые записи; статус по умолчанию ACTIVE. | 1 | 02, 03 |
| FR-RM-06 | Сервис возвращает запись по `id`, включая неактивные и удалённые. Чтение по `code` - фильтр `code` постраничного чтения с точным совпадением. | 1 | 02 |
| FR-RM-07 | Сервис частично изменяет `name`, `status` и столбцы справочника; попытка изменить `id`, `code`, `version`, `created_at`, `created_by`, `updated_at`, `updated_by` отклоняется с кодом 422. Для `deleted_at` допустимо только значение null (восстановление, FR-RM-12). | 1 | 02, 03 |
| FR-RM-08 | Постраничное чтение поддерживает фильтр по статусу (по умолчанию ACTIVE), точное совпадение `code`, поиск по префиксу кода и вхождению в название, флаг показа удалённых, фильтр `updated_since` (изменённые после момента, включая неактивные и удалённые), `limit`/`offset` и сортировку по `code`, `name`, `updated_at`. Справочник может добавлять фильтры по своим столбцам; они описаны в OpenAPI. | 1 | 02 |

### 3.3. Статус, удаление и восстановление

| ID | Требование | Срез | FEAT |
| --- | --- | --- | --- |
| FR-RM-09 | Записи имеют статус ACTIVE или INACTIVE; неактивные записи не попадают в списки без явного фильтра, но доступны по `id` и `code`. | 1 | 04 |
| FR-RM-10 | Удаление записи - мягкое: запись получает отметку `deleted_at`, ответ 204; повторное удаление отвечает 409. | 1 | 04 |
| FR-RM-11 | Удалённая запись не попадает в списки без флага показа удалённых, доступна по `id` и `code` с заполненным `deleted_at`; изменение удалённой записи отклоняется с кодом 409, кроме восстановления. | 1 | 04 |
| FR-RM-12 | Восстановление - `PATCH` с телом `{"deleted_at": null}`: отметка снимается, запись возвращается в ответе; восстановление неудалённой записи отвечает 409. | 1 | 04 |
| FR-RM-14 | Каждая операция записи, включая удаление и восстановление, увеличивает `version` записи и обновляет `updated_at` и `updated_by`. | 1 | 03 |

| ID | Требование | Срез | FEAT |

## 4. Нефункциональные требования

### 4.1. Архитектурные ограничения

| ID | Требование | Принцип |
| --- | --- | --- |
| NFR-RM-01 | Сервис принимает только входящие вызовы; исходящие соединения ограничены собственной PostgreSQL, коллектором OpenTelemetry и Keycloak (ключи проверки токенов). Обращений к другим модулям ERP нет. | I |
| NFR-RM-02 | Сервис хранит только НСИ: справочники и их записи. Бизнес-сущности не хранятся. | I |
| NFR-RM-03 | К базе данных сервиса обращается только сам сервис; потребители работают через REST API. | I |
| NFR-RM-04 | Физическое удаление данных не реализуется ни в API, ни в миграциях данных. | II |
| NFR-RM-05 | `id` и `code` неизменяемы после создания; код удалённой записи остаётся занятым. | II |
| NFR-RM-06 | Контракт API обратно совместим в пределах мажорной версии `/v1`; несовместимые изменения выпускаются как `/v2`. | II |
| NFR-RM-07 | Все операции записи выполняются сервисным слоем в одной транзакции; обработчики HTTP не обращаются к хранилищу напрямую. | III |
| NFR-RM-08 | Приложение не хранит состояния между запросами, кроме кэша ключей проверки токенов; допускает несколько одновременно работающих экземпляров. | VI |
| NFR-RM-39 | Добавление справочника или столбца - обратно совместимое изменение API: новые пути и необязательные поля. Удаление столбца или изменение его типа не выполняется (FR-RM-36). | II |
| NFR-RM-40 | Пять обработчиков всех справочников ведут себя одинаково: те же коды ответов, формат ошибок, фильтры и заголовки. Отличия справочников - только состав столбцов и их фильтров, описанных в OpenAPI. | VI |

## 5. Технический стек

| Область | Технология | Примечание |
| --- | --- | --- |
| Язык | Go (версия из `go.mod`, сейчас 1.27) | Статический бинарник, `CGO_ENABLED=0` |
