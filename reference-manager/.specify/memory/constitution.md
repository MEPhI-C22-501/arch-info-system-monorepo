# Конституция проекта Reference Manager

## Основные принципы

### I. Единственный источник НСИ, только входящие вызовы

Сервис "Справочник" хранит только нормативно-справочную информацию (НСИ): справочники, их записи и историю изменений записей. Каждый справочник - отдельная таблица с типизированными столбцами и пять одинаковых операций API. Бизнес-сущности - User, Employee, Product, Invoice и подобные - в сервисе НЕ хранятся, даже если их удобно "положить рядом".

Другие подсистемы ERP получают данные ТОЛЬКО через REST API. Прямой доступ к базе данных сервиса из других сервисов запрещён; схема БД - внутренняя деталь и может меняться без уведомления потребителей.

Сервис НЕ выполняет исходящих вызовов к другим модулям ERP и не подписывается на их данные. Разрешённые внешние обращения: собственная PostgreSQL, получение ключей проверки токенов Keycloak, отправка телеметрии в коллектор OpenTelemetry.

Обоснование: сервис существует ради устранения копий и расхождений справочных данных; любой обходной путь возвращает исходную проблему. Отсутствие исходящих зависимостей делает сервис самым простым и самым доступным компонентом ERP.

### II. Стабильные ключи, только мягкое удаление

`id` и `code` записи задаются один раз и НЕ изменяются. Физическое удаление строк НЕ реализуется ни в API, ни в миграциях данных. `DELETE` в API - мягкое удаление: запись получает `deleted_at`, исчезает из списков, но остаётся доступной по `id` и `code` и может быть восстановлена. Код удалённой записи остаётся занятым: повторно создать запись с тем же `code` нельзя, нужно вернуть в работу существующую. Состояний два: ACTIVE и DELETED.

Публичный контракт REST API обратно совместим в пределах мажорной версии: поля не удаляются и не меняют тип, новые поля необязательны. Несовместимое изменение оформляется новой мажорной версией пути (`/v2`).

Обоснование: на справочные данные ссылаются документы других подсистем; сломанная ссылка - потерянные данные у чужой команды. Мягкое удаление даёт "убрать ошибочно созданное" без потери ссылок.

### III. Каждое изменение проходит через сервисный слой

Любая операция записи выполняется сервисным слоем в одной транзакции БД; обработчики HTTP не обращаются к репозиторию напрямую. Каждая запись имеет поле `version`, увеличиваемое при изменении, и поля `updated_at` / `updated_by`. В той же транзакции снимок записи после изменения сохраняется в историю (`record_history`); история не изменяется и не удаляется. Начиная со среза 2 изменение принимается только с ожидаемой версией (оптимистическая блокировка через `If-Match`); несовпадение отклоняется.

Обоснование: единая точка записи держит инварианты (уникальность кодов, проверка схемы, правила удаления) в одном месте и делает добавление новых проверок локальным изменением.

### IV. Контракт прежде кода

Изменение поведения начинается со спецификации: OpenAPI в `api/`, по одной схеме записи на справочник. Спецификация проходит ревью до реализации. Обработчики проверяются на соответствие OpenAPI автоматически (контрактные тесты). Значения столбцов проверяются ограничениями таблицы (NOT NULL, CHECK, UNIQUE, FOREIGN KEY), заданными в миграции, и предварительной проверкой в сервисном слое; данные, не прошедшие проверку, не сохраняются. Столбцы только добавляются, справочники не удаляются.

Обоснование: потребители и интерфейс администрирования интегрируются по контракту, а не по коду; расхождение контракта и реализации - дефект сервиса.

### V. Тесты и проверки обязательны

Доменная логика и сервисный слой покрываются модульными тестами; работа с БД - интеграционными тестами на реальном PostgreSQL в `tests/`. Исправление дефекта сопровождается регрессионным тестом. `task lint` и `task tests` проходят на каждом pull request; код с предупреждениями линтера не сливается. Каждая миграция имеет рабочий `down` и проверяется последовательностью up-down-up.

Обоснование: сервис - зависимость всех подсистем; регресс в нём ломает всех сразу.

### VI. Простота и наблюдаемость

Стандартная раскладка Go: `cmd/`, `internal/`, `pkg/`; `pkg/` не импортирует `internal/`. Новые слои, абстракции и внешние зависимости добавляются только под потребность, зафиксированную в spec или plan. Конфигурация - файлы YAML в каталоге `--configs` или переменные окружения, без пересборки.

Вся телеметрия - трассы, метрики, журналы - собирается через OpenTelemetry и отправляется по OTLP в коллектор; журналы пишутся в stdout форматом и уровнем из `telemetry.yaml`. Каждый запрос несёт идентификатор и идентификатор трассы, которые попадают в журналы и ответ. Проверки работоспособности и готовности обязательны. Секреты не хранятся в репозитории.

Обоснование: маленькая команда и короткий семестр; сложность, которую нельзя объяснить в одном абзаце ADR, не нужна. Единый формат телеметрии - требование Infra.

### VII. Безопасность по умолчанию

Начиная со среза 2 каждый запрос к API аутентифицирован токеном Keycloak (проверка подписи, срока действия, издателя, получателя); права проверяются на сервере для каждой операции. Уровни доступа create, read, update, execute, delete распределены между двумя ролями: reader имеет read и execute, admin - все пять; права действуют на все справочники и записи, ограничений по организации нет. До этого сервис доступен только из внутренней сети стенда и не публикуется наружу. В любой версии: токены и секреты не попадают в журналы и сообщения об ошибках; параметризованные запросы; ограничения размера тела и атрибутов.

Обоснование: сервис общий для всех подсистем ERP; несанкционированное изменение справочника ломает документы во всех модулях.

## Технологические ограничения

- Язык: Go (версия из `go.mod`). HTTP: `net/http` и chi. БД: PostgreSQL 18, драйвер pgx, миграции golang-migrate (SQL, последовательная нумерация). Идентификация: Keycloak по OIDC, токены JWT. Телеметрия: OpenTelemetry SDK для Go, экспорт OTLP.
- Поставка: статический бинарник в образах distroless (`deployments/docker/`); Docker Compose (`deployments/docker-compose.yaml`) для локального стенда; Kubernetes силами команды Infra. Миграции - отдельное задание (job) до запуска приложения, не сервис.
- Инструменты: Taskfile (`task generate|lint|tests|migration|build|up|down`; `generate` - oapi-codegen, `build` - сборка образа), golangci-lint v2 с конфигурацией `.golangci.yaml`.
- Хранение: таблица на справочник с типизированными столбцами и ограничениями в миграции; история изменений в общей таблице `record_history` со снимками JSONB, заполняемой в транзакции изменения.
- API: REST/JSON под `/api/reference-data/v1`; частичное изменение через `PATCH`; ошибки в формате RFC 9457 (`application/problem+json`).
- Интерфейс администрирования: отдельный срез; статика встраивается в бинарник сервиса (`embed`) и отдаётся тем же процессом, отдельного контейнера и релиза нет; стек фронтенда выбирается ADR до начала среза.

## Процесс разработки

- Изменения вносятся через pull request в `main`; обязательно ревью владельцев из CODEOWNERS. Прямые коммиты в `main` запрещены.
- Коммиты: Conventional Commits со scope `reference-manager`, например `feat(reference-manager): add catalog items api`.
- Функциональность вводится срезами. Границы срезов и требования каждого среза (FR-RM-NN, NFR-RM-NN) фиксируются в `docs/system-requirements.md`, раздел 13. Срез 1 - CRUD НСИ: порядок добавления справочника, пять обработчиков на справочник, история изменений, БД, проверки и телеметрия. Срез 2 - защита API. Срез 3 - интерфейс администрирования.
- Новая функциональность проходит spec-kit: `$speckit-specify` -> `$speckit-plan` -> `$speckit-tasks` -> `$speckit-implement`; все артефакты (спецификации, планы, задачи, модели данных, контракты) хранятся в `.specify/memory/`. `plan.md` содержит раздел Constitution Check с проверкой принципов I-VII; нарушение фиксируется в Complexity Tracking с обоснованием и отвергнутой альтернативой, иначе план не утверждается.
- Проектные документы: `docs/system-requirements.md` (функциональные и нефункциональные требования, бизнес-правила), `docs/vision.md` (видение), ADR в `.specify/memory/adr/`. Документы на русском языке, идентификаторы, код и пути на латинице; дефис вместо тире, прямые кавычки.

## Управление

Конституция имеет приоритет над остальными практиками и договорённостями команды. Поправка вносится pull request с изменением этого файла, обоснованием и, при необходимости, планом приведения существующего кода в соответствие; требуется одобрение обоих владельцев CODEOWNERS.

Версионирование семантическое: MAJOR - удаление или несовместимое переопределение принципа; MINOR - новый принцип или существенно расширенное руководство; PATCH - уточнение формулировок без изменения смысла. Каждое ревью pull request проверяет соответствие принципам; каждый `plan.md` проходит Constitution Check до начала реализации.
