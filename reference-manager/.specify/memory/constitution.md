# Конституция проекта Reference Manager

## Основные принципы

### I. Единственный источник НСИ и кадровых мастер-данных

Сервис "Справочник" хранит нормативно-справочную информацию (НСИ) и кадровые мастер-данные: справочники, их записи и историю изменений записей. К кадровым мастер-данным относятся сотрудники (HR-профили), организационная структура, должности, датированные назначения, оклады и отсутствия. Учётные записи, пароли и роли доступа хранит Keycloak. Бизнес-сущности других модулей - проекты, задачи, планы, счета и подобные - в сервисе НЕ хранятся, даже если их удобно "положить рядом".

Другие подсистемы ERP получают данные ТОЛЬКО через REST API. Прямой доступ к хранилищу сервиса запрещён; его устройство - внутренняя деталь и может меняться без уведомления потребителей.

Сервис НЕ вызывает другие модули ERP, не подписывается на их данные и не публикует события. Разрешённые внешние обращения: собственное хранилище, отправка телеметрии в коллектор OpenTelemetry и Keycloak: получение ключей проверки токенов и Admin REST API для создания, изменения и блокировки учётных записей сотрудников.

HR-профиль и учётная запись не существуют друг без друга. Профиль хранится в сервисе, учётная запись в Keycloak, связь поддерживается интеграцией, а не общей базой. Обращение к Keycloak выполняется вне транзакции хранилища: сначала сохраняется намерение, затем выполняется вызов, затем сохраняется результат. Повтор операции не создаёт вторую учётную запись.

Состав справочников определяет команда справочников по постановке проекта и подтверждённым потребностям команд-потребителей; процесса заявок и самообслуживания нет. Справочник без подтверждённого потребителя в сервис не добавляется.

Обоснование: сервис существует ради устранения копий и расхождений справочных и кадровых данных; любой обходной путь возвращает исходную проблему. Единственная исходящая интеграция с изменением данных - учётные записи в Keycloak, потому что постановка проекта называет сервис владельцем HR-профилей.

### II. Стабильные имена, только мягкое удаление

Имя записи (`name`, например `currencies/EUR`) задаётся один раз и НЕ изменяется. Физическое удаление НЕ реализуется. Датированное значение - назначение, оклад, отсутствие - НЕ перезаписывается: новое значение создаётся новой записью с периодом действия. `Delete` - мягкое удаление по AIP-164: запись получает состояние DELETED и `delete_time`, исчезает из списков без `show_deleted`, остаётся доступной по имени и восстанавливается методом `Undelete`. Идентификатор удалённой записи остаётся занятым. Состояний два: ACTIVE и DELETED.

Публичный контракт обратно совместим в пределах мажорной версии: поля не удаляются и не меняют тип, новые поля необязательны, новый справочник - новая коллекция. Несовместимое изменение оформляется новой мажорной версией пути (`/v2`).

Обоснование: на справочные данные ссылаются документы других подсистем; сломанная ссылка - потерянные данные у чужой команды.

### III. Каждое изменение оставляет ревизию

Любая операция записи выполняется сервисным слоем в одной транзакции, меняет `etag` записи и создаёт ревизию в истории своего справочника: действие, актор, время, изменённые поля с прежними и новыми значениями. Ревизии не изменяются и не удаляются. Обработчики HTTP не обращаются к хранилищу напрямую. Начиная со второго среза операции записи принимают `etag` и отклоняют несовпадение (AIP-154).

Обоснование: единая точка записи держит инварианты в одном месте; история отвечает на вопрос "кто, когда и что изменил" без отдельного журнала аудита.

### IV. Контракт прежде кода, по принципам Google AIP

API проектируется по AIP: ресурсно-ориентированный дизайн, коллекция на справочник, стандартные методы List, Get, Create, Update, Delete, кастомные методы для восстановления и истории, `filter`, `order_by`, `page_token`, `update_mask`, `etag`, ошибки `google.rpc.Status`. Изменение поведения начинается со спецификации OpenAPI, по одной коллекции и схеме записи на справочник. Спецификация проходит ревью до реализации и проверяется контрактными тестами. Значения полей проверяются по схеме справочника; данные, не прошедшие проверку, не сохраняются. Поля только добавляются, справочники не удаляются.

Обоснование: потребители и интерфейс администрирования интегрируются по контракту, а не по коду; единые правила AIP избавляют от споров о форме каждого нового метода.

### V. Тесты и проверки обязательны

Доменная логика и сервисный слой покрываются модульными тестами; хранилище - интеграционными тестами на реальной базе в `tests/`. Общий набор тестов стандартных методов выполняется для каждого справочника без копирования. Исправление дефекта сопровождается регрессионным тестом. Линтер и тесты проходят на каждом pull request. Каждое изменение схемы хранилища обратимо.

Обоснование: сервис - зависимость всех подсистем; регресс в нём ломает всех сразу.

### VI. Простота и наблюдаемость

Стандартная раскладка Go: `cmd/`, `internal/`, `pkg/`; `pkg/` не импортирует `internal/`. Новые слои, абстракции и внешние зависимости добавляются только под потребность, зафиксированную в spec или plan. Конфигурация - файлы YAML в каталоге `--configs` или переменные окружения, без пересборки.

Вся телеметрия - трассы, метрики, журналы - собирается через OpenTelemetry и отправляется по OTLP в коллектор; журналы пишутся в stdout форматом и уровнем из `telemetry.yaml`. Каждый запрос несёт идентификатор и идентификатор трассы, которые попадают в журналы и ответ. Проверки работоспособности и готовности обязательны. Секреты не хранятся в репозитории.

Обоснование: маленькая команда и короткий семестр; сложность, которую нельзя объяснить в одном абзаце ADR, не нужна. Единый формат телеметрии - требование Infra.

### VII. Безопасность по умолчанию

С первой версии каждый запрос аутентифицирован токеном Keycloak (проверка подписи, срока действия, издателя, получателя); права проверяются на сервере для каждой операции. Работы без аутентификации нет. Уровни доступа create, read, update, execute, delete задаются по группам справочников: общие классификаторы, кадровые справочники, оклады и отсутствия. Ролей четыре: reader читает первые две группы, hr-reader читает все три, admin ведёт классификаторы, hr-admin ведёт кадровые справочники, включая оклады и отсутствия. В любой версии: токены, пароли, секреты, оклады и отсутствия не попадают в журналы и сообщения об ошибках; пароли не хранятся; параметризованные запросы; ограничения размера тела и страницы. Перед приёмкой модуль проходит проверку безопасности по чек-листу с отчётом.

Обоснование: сервис общий для всех подсистем ERP и хранит персональные данные; несанкционированное изменение справочника ломает документы во всех модулях, а открытые оклады недопустимы.

## Технологические ограничения

- Язык: Go (версия из `go.mod`). HTTP: `net/http` и chi. Хранилище: PostgreSQL 18, драйвер pgx, изменения схемы golang-migrate. Идентификация: Keycloak по OIDC, токены JWT. Телеметрия: OpenTelemetry SDK для Go, экспорт OTLP.
- Хранение: отдельное хранилище записей и отдельная история на каждый справочник; типизированные поля с ограничениями на уровне хранилища.
- Поставка: статический бинарник в образах distroless (`deployments/docker/`); Docker Compose (`deployments/docker-compose.yaml`) для локального стенда; локальный кластер minikube для приёмки: манифесты Deployment, Service, ConfigMap, Secret, PersistentVolumeClaim и маршрутизация. Изменения схемы - отдельное задание до запуска приложения.
- Инструменты: Taskfile (`task generate|lint|tests|migration|build|up|down`; `generate` - oapi-codegen, `build` - сборка образа), golangci-lint v2.
- API: REST/JSON под `/v1` по Google AIP; ошибки в формате AIP-193.
- Интерфейс администрирования: отдельный срез и отдельный компонент со своим образом; с сервисом общается только через REST API; первый шаг - админ-панель на имитированных данных; стек фронтенда выбирается ADR до подключения к API.

## Процесс разработки

- Изменения вносятся через pull request в `main`; обязательно ревью владельцев из CODEOWNERS. Прямые коммиты в `main` запрещены.
- Коммиты: Conventional Commits со scope `reference-manager`.
- Функциональность вводится срезами. Границы срезов фиксируются в `documents/system-requirements.md`, раздел 13. Срез 1 - первая версия: справочники, включая кадровые, методы на каждый справочник, история, хранилище, проверка токена и ролей, учётные записи в Keycloak, проверки и телеметрия. Срез 2 - `etag` в операциях записи и сетевая политика. Срез 3 - интерфейс администрирования. Пакетные операции и загрузка из файла выполняются в конце, если останется время.
- Новая функциональность проходит spec-kit: `$speckit-specify` -> `$speckit-plan` -> `$speckit-tasks` -> `$speckit-implement`; артефакты хранятся в `.specify/memory/`. `plan.md` содержит раздел Constitution Check с проверкой принципов I-VII.
- Проектные документы: `documents/system-requirements.md`, `documents/vision.md`, комплект `documents/010..165` по составу документов курсового проекта (`documents/documents-composition.md`), ADR в `.specify/memory/adr/`. Документы на русском языке, идентификаторы, код и пути на латинице; дефис вместо тире, прямые кавычки; без привязки к деталям реализации там, где состав документа этого не требует.

## Управление

Конституция имеет приоритет над остальными практиками и договорённостями команды. Поправка вносится pull request с изменением этого файла, обоснованием и, при необходимости, планом приведения существующего кода в соответствие; требуется одобрение обоих владельцев CODEOWNERS.

Версионирование семантическое: MAJOR - удаление или несовместимое переопределение принципа; MINOR - новый принцип или существенно расширенное руководство; PATCH - уточнение формулировок без изменения смысла. Каждое ревью pull request проверяет соответствие принципам; каждый `plan.md` проходит Constitution Check до начала реализации.
