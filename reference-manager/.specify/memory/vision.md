## 1. Введение

### 1.1. Цель документа

Документ фиксирует общее видение сервиса "Справочник": какую проблему он решает, для кого предназначен, какие возможности предоставляет и в каких границах работает. Он служит отправной точкой для детальных требований, архитектурного проектирования и планирования работ команды.

Документ отвечает на вопросы "что" и "зачем". Требования и технический стек фиксируются в DESIGN.md, детальные решения - в спецификациях и ADR в .specify/memory/.

### 1.2. Область применения

Документ относится к сервису Reference Manager в составе монорепозитория arch-info-system-monorepo. Смежные компоненты (Core, Keycloak, Infra) упоминаются только в части их взаимодействия с сервисом.

### 1.3. Термины и сокращения

| Термин | Определение |
| --- | --- |
| НСИ | Нормативно-справочная информация - данные, которые классифицируют или описывают бизнес-сущности, но сами бизнес-сущностями не являются. Синоним - справочные данные. |
| Справочник (Catalog) | Именованный набор однотипных справочных значений, например "валюты" (currencies) или "страны" (countries). Реализуется отдельной таблицей в базе данных сервиса и пятью обработчиками HTTP. Код справочника совпадает с именем таблицы и сегментом пути в API. |
| Запись справочника | Одно значение внутри справочника, например EUR в справочнике валют. Состоит из общих столбцов и столбцов справочника. |
| Общие столбцы | Столбцы, которые есть в таблице каждого справочника: id, code, name, status, version, created_at, created_by, updated_at, updated_by, deleted_at. |
| Столбцы справочника | Типизированные столбцы, которые есть только у данного справочника, например числовой код валюты. Задаются миграцией при добавлении справочника. |
| Пять обработчиков | Набор операций API каждого справочника: создание записи, чтение одной записи, постраничное чтение, частичное изменение записи, удаление записи. |
| Заявка на справочник | Обращение команды-потребителя к команде справочников: код и название справочника, состав столбцов, начальные данные. |
| Идентификатор (id) | Суррогатный ключ, генерируется сервисом, никогда не меняется. |
| Код (code) | Человекочитаемый ключ записи, уникальный в пределах справочника, задаётся при создании и не меняется. |
| Статус (status) | Состояние записи: ACTIVE (используется) или INACTIVE (выведена из оборота, ссылки остаются корректными). |
| Мягкое удаление | Запись помечается удалённой (deleted_at), исчезает из списков, но остаётся доступной по id и code и может быть восстановлена. Физическое удаление не предусмотрено. |
| Системный справочник | Справочник, записи которого общие для всех арендаторов. |
| Справочник арендатора | Справочник, записи которого принадлежат арендаторам: каждая запись видна только своему арендатору. |
| Арендатор (tenant) | Обособленная организация, работающая в ERP; признак арендатора передаётся в токене пользователя. |
| Версия записи | Порядковый номер состояния записи; увеличивается при каждом изменении. |
| Телеметрия | Трассы, метрики и журналы сервиса, собираемые через OpenTelemetry. |
| ERP | Enterprise Resource Planning - система управления ресурсами предприятия; в проекте - совокупность подсистем arch-info-system. |
| API | Application Programming Interface - программный интерфейс сервиса (в проекте - REST поверх HTTP с JSON). |
| IdP | Identity Provider - провайдер идентификации; в проекте - Keycloak. |
| OIDC | OpenID Connect - протокол аутентификации поверх OAuth 2.0. |
| ADR | Architecture Decision Record - запись об архитектурном решении. |

## 2. Позиционирование

### 2.1. Возможности бизнеса

Любая ERP-система опирается на десятки общих классификаторов: валюты, страны, языки, единицы измерения, типы оплаты, налоговые категории. Они нужны каждой подсистеме - при оформлении документов, ведении контрагентов, расчёте цен и налогов.

Если единого сервиса нет, каждая команда заводит собственную копию справочников. Копии расходятся, изменения вносятся вручную и несинхронно. Централизованный сервис даёт один источник истины, сокращает усилия на интеграцию и делает ведение справочных данных управляемым.

### 2.2. Формулировка проблемы

| Аспект | Описание |
| --- | --- |
| Проблема | Справочные данные дублируются в каждой подсистеме ERP, ведутся вручную и расходятся между сервисами. |
| Затрагивает | Команды подсистем ERP, пользователей, формирующих документы и отчёты, администраторов данных. |
| Следствие | Несогласованные документы и отчёты, ошибки при обмене данными между сервисами, ручная синхронизация копий. |
| Успешное решение | Единый сервис, который хранит справочники и их значения, предоставляет их через API и интерфейс администрирования и разграничивает доступ. |

### 2.3. Позиционирование продукта

| Аспект | Описание |
| --- | --- |
| Для | Команд и сервисов ERP-системы arch-info-system, а также администраторов справочных данных. |
| Которые | Нуждаются в согласованных, стабильных и проверяемых справочных данных. |
| Сервис "Справочник" | Является централизованным сервисом НСИ ERP. |
| Который | Хранит каждый справочник в отдельной типизированной таблице со стабильными идентификаторами, поддерживает статус, мягкое удаление и восстановление записей, предоставляет REST API из пяти операций на справочник и интерфейс администрирования. |
| В отличие от | Локальных таблиц-справочников в каждом сервисе и ручного ведения в файлах Excel. |
| Наш продукт | Даёт единый источник истины для справочных данных и не требует от потребителей прямого доступа к базе данных. Новый справочник появляется по заявке команды-потребителя силами команды справочников. Сам сервис ни к каким модулям ERP не обращается: все читают его, он не читает никого. |

### 3.3. Среда пользователей

- Администраторы работают через интерфейс администрирования справочников (отдельный срез, раздел 8) или через API. Читатели используют интерфейсы своих подсистем. Вход выполняется через Keycloak (единый вход).
- Заявки на справочники оформляются как issue в репозитории по шаблону команды справочников.
- Сервисы-потребители - контейнеры в одном кластере с сервисом. Они обращаются к нему по HTTP внутри сети.
- Сервис развёртывается командой Infra: на стенде через Docker Compose, в целевом окружении - в Kubernetes. Миграции БД, включая таблицы новых справочников, выполняются отдельным заданием (job) перед запуском приложения.

## 4. Обзор продукта

### 4.1. Место продукта в системе

Сервис "Справочник" - самостоятельная подсистема ERP со своей базой данных и интерфейсом администрирования. Интерфейс поставляется вместе с сервисом в одном образе и по одному адресу. Каждый справочник хранится в отдельной таблице этой базы и обслуживается пятью обработчиками HTTP. Сервис принимает запросы от подсистем и пользователей, проверяет токены Keycloak и работает с PostgreSQL. Исходящих обращений к другим модулям ERP у сервиса нет. Телеметрия передаётся в коллектор OpenTelemetry, который предоставляет Infra.

```mermaid
flowchart LR
    T[Команда-заказчик справочника] -->|Заявка: код, столбцы, данные| RT[Команда справочников]
    RT -->|Pull request: миграция и пять обработчиков| RM
    RT -->|Наполнение записей| RM
    U[Администратор справочников] -->|Вход| K[Keycloak]
    K -->|Токен| U
    U -->|Интерфейс администрирования в браузере| RM
    S[Подсистемы ERP] -->|REST с токеном, чтение| RM
    subgraph RM[Сервис "Справочник"]
        A[Приложение: REST API и Web UI] --> DB[(PostgreSQL: таблица на справочник)]
    end
    A -->|Ключи для проверки токенов| K
    A -->|Телеметрия| OT[OpenTelemetry Collector]
    I[Infra: CI/CD, Compose, Kubernetes] -.->|Развёртывание, job миграций| RM
```

Типовой сценарий: команда-заказчик присылает заявку на справочник. Команда справочников пишет миграцию с таблицей, регистрирует пять обработчиков, дополняет контракт OpenAPI и тесты, выпускает изменение через pull request. После развёртывания администратор наполняет справочник через интерфейс администрирования или API. Подсистемы-потребители читают значения по API и кэшируют их у себя.

### 4.2. Краткое описание возможностей

| Выгода для пользователя | Возможность сервиса |
| --- | --- |
| Все подсистемы используют одни и те же значения | Хранение справочников и записей, REST API для чтения |
| Ссылки на значения не ломаются со временем | Неизменяемые id и code, статус и мягкое удаление вместо физического |
| Ошибочно созданное можно убрать и вернуть | Мягкое удаление и восстановление |
| Новый справочник появляется по заявке, потребители ничего не переделывают | Регламент добавления: миграция и пять обработчиков, новый путь в API |
| Данные справочника типизированы и проверены | Отдельная таблица на справочник, ограничения в схеме базы данных |
| Справочники удобно вести людям | Интерфейс администрирования |
| Доступ получают только уполномоченные | Аутентификация через Keycloak, роли |
| Сбои видны и объяснимы | Телеметрия OpenTelemetry: трассы, метрики, журналы |

### 4.3. Предположения и зависимости

- Keycloak развёрнут и выдаёт токены с ролями. Состав ролей согласуется с командой Keycloak. Получение ключей для проверки токенов - единственное сетевое обращение сервиса за пределы своей БД, кроме отправки телеметрии.
- Хранилище - PostgreSQL. Миграции схемы, включая таблицы справочников, применяются отдельным заданием до запуска приложения.
- Коллектор OpenTelemetry предоставляется командой Infra. При его отсутствии сервис работает, телеметрия не отправляется.
- Сервис не обращается к другим модулям ERP и не подписывается на их данные. Потребители читают справочники по API и сами решают, как кэшировать.
- Состав справочников определяется заявками команд-потребителей. Команда справочников решает, является ли запрошенный набор данных НСИ (вопрос 12 раздела 11).
- Начальное наполнение справочников выполняет команда справочников через интерфейс администрирования или API. Способ поставки стандартных данных (ISO-коды) не выбран (вопрос 13 раздела 11).

### 4.4. Стоимость и лицензирование

Проект учебный. Используются открытые компоненты: Go, PostgreSQL, Keycloak, OpenTelemetry. Установка выполняется средствами Infra из версионированных образов через Docker Compose или Kubernetes. Отдельной процедуры установки у пользователей нет.

## 5. Возможности продукта

Каждая возможность имеет идентификатор FEAT-NN. Идентификаторы стабильны: отклонённая возможность сохраняет номер со статусом "Отклонено", новая получает следующий номер. Приоритеты и план версий сведены в разделе 8.

### FEAT-01. Ведение справочников

Справочник добавляет команда справочников по заявке. Миграция создаёт таблицу с общими столбцами и столбцами справочника, в сервисе регистрируются пять обработчиков, контракт OpenAPI и тесты дополняются в том же pull request. Состав справочников фиксирован кодом сервиса и известен потребителям из OpenAPI. Через API справочники не создаются и не удаляются. Справочник не удаляется и после ввода в эксплуатацию: таблица и обработчики остаются, ненужные записи деактивируются.

### FEAT-02. Ведение записей справочника

Для каждого справочника: создание записи, чтение записи по id, постраничное чтение с фильтрами (статус, точное совпадение code, поиск по коду и названию, изменённые после момента, показ удалённых) и сортировкой, частичное изменение (name, status, столбцы справочника), удаление. Чтение по code выполняется фильтром постраничного чтения. По умолчанию возвращаются только активные неудалённые записи.

### FEAT-03. Стабильные идентификаторы

id генерируется сервисом при создании, code задаётся создателем. Оба неизменяемы после создания. code уникален в пределах справочника и остаётся занятым даже у удалённых записей. Попытка изменить id или code отклоняется.

### FEAT-04. Статус и мягкое удаление

Запись переводится между ACTIVE и INACTIVE: неактивная запись не предлагается для выбора, но остаётся доступной по id и code. Мягкое удаление помечает запись удалённой: она исчезает из списков, остаётся доступной по id и code и восстанавливается снятием отметки удаления через операцию изменения. Физического удаления нет.

### FEAT-05. Расширяемые атрибуты со схемой

Отклонено 2026-09-17. JSON-атрибуты записей и версионируемые схемы JSON Schema заменены типизированными столбцами справочника (FEAT-12). Идентификатор сохранён, чтобы ссылки в ранних документах оставались однозначными.

### FEAT-06. Системные и арендаторские справочники

Справочник объявляется системным или арендаторским при добавлении (миграцией). Записи системного справочника общие для всех арендаторов. Записи арендаторского справочника несут признак арендатора и видны только своему арендатору, который определяется из токена пользователя. Записи обоих видов ведёт команда справочников.

### FEAT-07. Аутентификация и авторизация

Каждый запрос содержит токен Keycloak. Сервис проверяет подпись, срок действия, издателя и получателя токена, затем проверяет право на действие. Ролей две: reference-reader читает записи всех справочников, reference-admin (команда справочников) создаёт, изменяет, удаляет и восстанавливает записи. Проверки выполняются на стороне сервера.

### FEAT-08. Телеметрия и эксплуатация

Сервис отдаёт трассы, метрики и журналы через OpenTelemetry (OTLP в коллектор), предоставляет проверку работоспособности и готовности (включая доступность БД). Конфигурация задаётся файлами или переменными окружения без пересборки. Остановка выполняется корректно: текущие запросы завершаются, соединения закрываются.

### FEAT-09. Интерфейс администрирования

Веб-интерфейс для команды справочников: список справочников из контракта сервиса, таблица записей с поиском и фильтрами, создание и изменение записей в форме, поля которой строятся по столбцам справочника, деактивация, удаление и восстановление. Работает поверх REST API сервиса и входа через Keycloak. Поставляется внутри сервиса: тот же образ, тот же адрес, отдельного компонента нет.

### FEAT-10. Локализованные наименования

Название записи может задаваться на нескольких языках (как минимум русский и английский). Потребитель запрашивает нужный язык. Возможность отложена до подтверждения потребности.

### FEAT-11. Массовый импорт и экспорт

Загрузка записей справочника из файла (CSV или JSON) с проверкой ограничений и выгрузка справочника в файл. Возможность отложена до подтверждения потребности.

### FEAT-12. Типизированные столбцы справочника

Каждый справочник хранит свои поля в типизированных столбцах своей таблицы. Типы, обязательность, диапазоны и уникальность задаются ограничениями базы данных в миграции и проверяются сервисом при записи с понятным ответом об ошибке по каждому полю. Новый столбец добавляется новой миграцией как необязательный или со значением по умолчанию. Столбцы не удаляются и не меняют тип, чтобы контракт API оставался обратно совместимым. Примеры: для валют - числовой код и число знаков после запятой, для стран - трёхбуквенный и числовой коды.

## 6. Ограничения

### 6.1. Технологические

- Язык реализации - Go, хранилище - PostgreSQL, провайдер идентификации - Keycloak по OIDC, телеметрия - OpenTelemetry.
- Каждый справочник - отдельная таблица PostgreSQL, созданная миграцией golang-migrate, и пять обработчиков HTTP в коде сервиса.
- Поставка - контейнерные образы, запуск через Docker Compose на стенде и Kubernetes в целевом окружении, миграции - отдельное задание, CI/CD - GitHub Actions. Эти решения заданы монорепозиторием и командой Infra.
- API - REST с JSON под префиксом /api/reference-data/v1. Обратная совместимость сохраняется в пределах мажорной версии API.
- Интерфейс администрирования поставляется внутри сервиса (один образ, один адрес). Стек фронтенда определяется отдельно (раздел 11).

### 6.2. Архитектурные

- Сервис владеет своей базой данных. Другие подсистемы получают данные только через API. Прямой доступ к БД запрещён.
- Сервис не выполняет исходящих вызовов к другим модулям ERP. Разрешённые внешние обращения: собственная БД, получение ключей Keycloak, отправка телеметрии в коллектор.
- Сервис хранит только НСИ. Бизнес-сущности (User, Employee, Product, Invoice и подобные) в нём не хранятся, даже если команда-заказчик просит завести их как справочник.
- Состав справочников меняет только команда справочников через pull request. Через API справочники не создаются и не удаляются.
- Физическое удаление справочников и записей не предусмотрено, только статус и мягкое удаление.
- id и code неизменяемы.

### 6.3. Организационные

- Проект учебный, команда справочников - два разработчика. Объём каждого среза ограничен сроками семестра.
- Изменения вносятся через pull request с ревью владельцев кода (CODEOWNERS).
- Секреты не хранятся в репозитории. На стенде трафик защищён HTTPS.

## 9. Прочие требования

### 9.1. Стандарты

- API описывается спецификацией OpenAPI 3.x, которая хранится в репозитории и обновляется вместе с кодом. В ней описана схема записи каждого справочника.
- Аутентификация - OIDC, токены в формате JWT.
- Телеметрия - OpenTelemetry, протокол OTLP, семантические соглашения OpenTelemetry для HTTP и БД.
- Коды стандартных справочников, если администраторы их заводят, соответствуют ISO 4217, ISO 3166-1, ISO 639-1.

### 9.2. Системные требования

- Приложение поставляется статическим бинарником в минимальном контейнерном образе.
- Требуется PostgreSQL 18 или совместимая версия.
- Конфигурация задаётся каталогом файлов YAML или переменными окружения.

### 9.3. Требования к среде

- Стенд - Docker Compose, общая конфигурация в корне монорепозитория.
- Целевое окружение - Kubernetes. HTTPS завершается на входном шлюзе.
- Порядок запуска: база данных, задание миграций, приложение. Трафик подаётся после проверки готовности.
