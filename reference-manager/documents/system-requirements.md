# Системные требования Reference Manager

## 1. Общая информация

### 1.1. Цель системы

Система должна предоставлять подсистемам ERP arch-info-system единый источник нормативно-справочной информации и кадровых мастер-данных, в котором можно:

- вести справочники сотрудников, организационной структуры и должностей с датированными назначениями, окладами и отсутствиями
- создавать учётную запись сотрудника в Keycloak при приёме и блокировать её при увольнении
- вести справочники общих классификаторов: валюты, страны, проектные роли, грейды
- получать записи справочников по стабильным идентификаторам, которые не меняются со временем
- убирать запись, которая больше не используется, без разрыва ссылок
- просматривать историю изменений каждой записи: кто, когда и что изменил
- выгружать содержимое справочника в файл для работы вне системы
- разграничивать доступ на чтение и на ведение записей

Каждый справочник - отдельный ресурс API со своим набором методов и отдельным хранилищем. API строится по принципам Google AIP (ресурсно-ориентированный дизайн, стандартные методы, фильтрация, постраничный вывод, мягкое удаление, ревизии). Решения приняты командой 2026-09-17 и 2026-09-27. Состав модуля приведён к постановке 2026-10-02 по замечаниям руководителя проекта от 2026-10-01: модуль ведёт сотрудников, оргструктуру и должности и владеет HR-профилями.

### 1.2. Границы системы

В состав системы входят:

- кадровые справочники: сотрудники (HR-профили), подразделения, должности, назначения на должность, оклады, отсутствия
- справочники общих классификаторов первой версии (раздел 9.2) и их записи
- интеграция с Keycloak по учётным записям: создание при приёме сотрудника, блокировка при увольнении
- REST API: для каждого справочника пять стандартных методов, выгрузка и чтение истории
- история изменений записей, отдельная для каждого справочника
- выгрузка записей справочника в файл `.xlsx`
- аутентификация и проверка прав по токену Keycloak с первой версии
- веб-интерфейс администрирования отдельным компонентом
- служебные точки проверки работоспособности и готовности, телеметрия OpenTelemetry

За границами системы остаются: учётные записи, пароли и роли доступа (их ведёт Keycloak), проекты, задачи, планы и расчётная ёмкость, статусы и приоритеты задач, серьёзность дефектов, мультиарендность, публикация событий, предзаполнение справочников стандартными данными, создание справочников потребителями или через API, процесс заявок на справочники.

Пакетные операции и загрузка записей из файла не входят в основной объём. Они выполняются в конце, если останется время (раздел 4.12).

## 2. Термины

| Термин | Определение |
| --- | --- |
| НСИ | Нормативно-справочная информация. Данные, которые классифицируют или описывают бизнес-сущности, но сами бизнес-сущностями не являются. |
| Кадровые мастер-данные | Сведения о сотрудниках, организационной структуре и должностях, общие для всех подсистем ERP. Единственный владелец - Reference Manager. |
| HR-профиль | Запись справочника сотрудников: ФИО, табельный номер, логин, адрес почты, состояние занятости, связь с учётной записью Keycloak. Текущие подразделение и должность берутся из действующего назначения. |
| Учётная запись | Запись пользователя в Keycloak: логин, пароль, роли доступа. Сервис её не хранит, а создаёт и блокирует по интеграции. |
| Подразделение | Узел организационной структуры: отдел или команда. Подразделения образуют иерархию. |
| Должность | Наименование должности из справочника должностей. Сотрудник занимает должность по назначению. |
| Датированная запись | Запись с датой начала и датой окончания действия: назначение на должность, оклад, отсутствие. Новое значение оформляется новой записью, прежняя сохраняется. |
| Назначение | Датированная запись о том, что сотрудник занимает должность в подразделении с даты по дату. |
| Оклад | Датированная запись о размере оклада сотрудника в валюте с даты по дату. |
| Отсутствие | Датированная запись о периоде, когда сотрудник не работает: отпуск, болезнь, другое. |
| Справочник | Именованный набор однотипных справочных записей, например валюты или сотрудники. В API - коллекция ресурсов со своим путём, например `/v1/countries`. |
| Запись справочника | Одна справочная единица внутри справочника, например страна RU. В API - ресурс с именем вида `countries/RU`. |
| Идентификатор записи | Целое число, которое назначает сервис при создании; путь записи - коллекция и идентификатор, например `/v1/currencies/5`. Стабилен, не меняется. |
| Идентификатор записи | Последний сегмент имени, например `EUR`. Уникален в пределах справочника, включая удалённые записи, и не меняется. Задаётся при создании, а для датированных записей назначается сервисом. |
| Общие поля записи | Поля, одинаковые во всех справочниках и доступные только для чтения: `id`, `is_deleted`, `revision`, `last_changer`, `created_at`, `updated_at`, `deleted_at`. Наименование `name` - собственное поле справочника, у датированных записей его нет. |
| Поля справочника | Типизированные поля, которые есть только у данного справочника, например числовой код валюты. |
| Состояние записи | ACTIVE или DELETED. Возвращается в поле `state`, только для чтения. |
| Состояние занятости | EMPLOYED (работает) или DISMISSED (уволен). Поле `employment_state` записи сотрудника. |
| Состояние учётной записи | PENDING (операция с учётной записью не завершена), ENABLED (создана и включена), DISABLED (заблокирована). Поле `account_state` записи сотрудника. |
| Удаление | Пометка записи удалённой (`is_deleted`): запись остаётся, получает `deleted_at`, исчезает из списков по умолчанию, остаётся доступной по идентификатору с `allowDeleted=true`. Физического удаления в штатной работе нет; `force=true` удаляет запись с историей. |
| Ревизия | Элемент истории изменений записи: кто, когда, какое действие, какие поля изменились и с какого значения на какое. Неизменяема. |
| История изменений | Ревизии записей справочника в обратном хронологическом порядке. Ведётся для каждого справочника отдельно. |
| Стандартные методы | List, Get, Create, Update, Delete по AIP-131..135. |
| Фильтр | Выражение отбора записей в параметре `filter` списка по AIP-160, например `is_deleted = false AND name : "евро"`. |
| Выгрузка | Файл `.xlsx` с записями, отобранными теми же параметрами, что и список. |
| Уровни доступа | Операции над записями: create, read, update, execute, delete. Набор уровней роли зависит от группы справочников (раздел 3). |

## 3. Пользователи и роли

Справочники делятся на три группы доступа: общие классификаторы, кадровые справочники (сотрудники, подразделения, должности, назначения) и кадровые данные ограниченного доступа (оклады, отсутствия).

| Роль | Основные возможности |
| --- | --- |
| Администратор справочников (reference-admin) | Участник команды справочников. Создаёт, изменяет, удаляет и восстанавливает записи общих классификаторов. Кадровые справочники читает. Оклады и отсутствия недоступны. |
| HR-администратор (reference-hr-admin) | Сотрудник кадровой службы. Создаёт, изменяет, удаляет и восстанавливает записи кадровых справочников, включая оклады и отсутствия, принимает и увольняет сотрудников. Общие классификаторы читает. |
| Читатель (reference-reader) | Любой аутентифицированный пользователь или сервис ERP. Читает общие классификаторы и кадровые справочники, их историю, выгружает в файл. Оклады и отсутствия недоступны. |
| Читатель кадровых данных (reference-hr-reader) | Пользователь или сервис, которому нужны оклады и отсутствия, например планирование ресурсов. Читает все справочники, включая оклады и отсутствия. |

Уровни доступа по группам:

| Роль | Общие классификаторы | Кадровые справочники | Оклады и отсутствия |
| --- | --- | --- | --- |
| reference-reader | read, execute | read, execute | нет |
| reference-hr-reader | read, execute | read, execute | read, execute |
| reference-admin | create, read, update, execute, delete | read, execute | нет |
| reference-hr-admin | read, execute | create, read, update, execute, delete | create, read, update, execute, delete |

Мультиарендности нет: права роли действуют на все записи справочников своей группы (2026-09-26). Роли `reference-hr-admin` и `reference-hr-reader` введены 2026-10-02 вместе с кадровыми справочниками.

## 4. Функциональные требования

### 4.1. Справочники

- **FR-RM-33.** Состав справочников определяется постановкой проекта и потребностями команд-потребителей (раздел 9.2) и реализуется в сервисе. Добавление справочника позже - новая версия сервиса: хранилище, ресурс API со своими методами, спецификация и тесты в одном изменении.
- **FR-RM-34.** Каждая запись любого справочника должна содержать общие поля только для чтения: `id` (идентификатор, назначает сервис), `is_deleted` (признак удаления), `revision` (номер последней ревизии), `last_changer` (актор последнего изменения), `created_at`, `updated_at`, `deleted_at` (время создания, последнего изменения и удаления, вычисляются по истории). Наименование - собственное поле справочника `name`. У датированных записей его нет.
- **FR-RM-35.** Поля справочника должны быть типизированы. Обязательность, диапазоны, уникальность и ссылки на записи других справочников проверяются при создании и изменении. Запись с недопустимыми значениями отклоняется ошибкой `INVALID_ARGUMENT` с перечнем полей и причин и не сохраняется.
- **FR-RM-36.** Состав полей справочника должен меняться только новой версией сервиса. Новое поле необязательно либо имеет значение по умолчанию. Поля не удаляются и не меняют тип.
- **FR-RM-37.** Каждый справочник должен иметь собственную коллекцию ресурсов `/v1/{справочник}/` и пять стандартных методов: `List` (`GET /v1/countries/`), `Get` (`GET /v1/countries/{countryID}`), `Create` (`POST /v1/countries/`), `Update` (`PATCH /v1/countries/{countryID}`), `Delete` (`DELETE /v1/countries/{countryID}`), а также выгрузку (`POST /v1/countries/export`) и чтение истории (`GET /v1/countries/{countryID}/revisions`, `GET /v1/countries/{countryID}/revisions/{revisionNumber}`). Единого пути для всех справочников нет.
- **FR-RM-38.** Через API справочники не должны создаваться, изменяться и удаляться. Перечень справочников и схема записи каждого описаны спецификацией OpenAPI; потребители и интерфейс администрирования узнают справочники из спецификации.

### 4.2. Записи справочника

- **FR-RM-05.** Пользователь с правом записи должен иметь возможность создать запись методом `Create`, указав поля справочника. Идентификатор записи назначает сервис. Деловые ключи справочника (коды, табельный номер, логин, адрес почты) уникальны в пределах справочника, включая удалённые записи. Повторное значение отклоняется ответом 409. Новая запись не удалена (`is_deleted: false`) и получает ревизию 1.
- **FR-RM-06.** Метод `Get` должен возвращать запись по идентификатору. Удалённая запись возвращается только с параметром `allowDeleted=true`, иначе ответ 404.
- **FR-RM-07.** Пользователь с правом записи должен иметь возможность частично изменить поля справочника методом `Update` с указанием изменяемых полей в параметре `updateMask`. Общие поля, поля, которые ведёт сервис, и неизменяемые поля (логин сотрудника, сотрудник датированной записи) в маске отклоняются ответом 400.
- **FR-RM-08.** Метод `List` должен поддерживать фильтр по AIP-160 (`filter`) по общим полям и полям справочника, сортировку (`order_by`) по тем же полям и постраничный вывод (`pageSize`, `pageToken`, `nextPageToken` в ответе). По умолчанию возвращаются только неудалённые записи. `allowDeleted=true` включает удалённые. Общее число записей в ответе не возвращается.

### 4.3. Жизненный цикл записи

- **FR-RM-09.** Каждая запись должна быть либо действующей, либо удалённой. Признак возвращается в поле `is_deleted` и не изменяется напрямую.
- **FR-RM-10.** Метод `Delete` должен помечать запись удалённой, создавать ревизию и возвращать запись. Повторное удаление отвечает 404: удалённая запись не видна методам записи. С параметром `force=true` метод удаляет запись вместе с историей без возврата. Это право администратора группы справочника.
- **FR-RM-11.** Удалённая запись не должна попадать в `List` без `allowDeleted`. Она доступна методом `Get` с `allowDeleted=true`. Изменение её полей невозможно: методы записи отвечают 404.
- **FR-RM-12.** Отозвано 2026-10-20: восстановления удалённой записи нет (ADR-022). Запись, удалённая по ошибке, создаётся заново.
- **FR-RM-14.** Каждая операция записи, включая удаление, должна создавать ревизию в истории справочника. Номер ревизии записи растёт на единицу. Операция, которая обнаруживает занятый номер ревизии, отвечает 409: запись изменена параллельно, клиент повторяет запрос.

### 4.4. Выгрузка в файл

- **FR-RM-40.** Пользователь с правом чтения должен иметь возможность получить записи справочника в виде файла `.xlsx` методом `POST /v1/{справочник}/export`. Формат `.xlsx` подтверждён руководителем проекта (зафиксировано 2026-10-02), способ - кастомный метод выгрузки (решение 2026-10-20, ADR-022).
- **FR-RM-41.** Выгрузка должна охватывать все неудалённые записи справочника в порядке создания. Параметры отбора и удалённые записи в выгрузку не входят.
- **FR-RM-42.** Файл выгрузки должен содержать строку заголовков и по одной строке на запись: собственные поля справочника, затем номер ревизии, актор последнего изменения, время создания и изменения. Коды выводятся текстом, даты - датами без времени, время - в согласованном формате. Выгружаются только записи справочника: история изменений (ревизии) в файл не входит, выгрузки истории нет.
- **FR-RM-43.** Отозвано 2026-10-20: предела объёма выгрузки нет, справочники первой версии малы и выгружаются целиком (ADR-022).

### 4.5. Аутентификация и авторизация

Требования этого раздела входят в первую версию: единый вход через Keycloak обязателен для модуля (решение 2026-10-02 по замечаниям от 2026-10-01).

- **FR-RM-21.** Каждый запрос к API должен нести Bearer-токен Keycloak. Сервис проверяет подпись, издателя, получателя и срок действия токена, иначе отвечает ошибкой `UNAUTHENTICATED`.
- **FR-RM-22.** Система должна читать роли `reference-reader`, `reference-hr-reader`, `reference-admin` и `reference-hr-admin` из claim токена. Уровни доступа: create, read, update, execute, delete. Набор уровней роли задан по группам справочников в разделе 3. Уровень read покрывает `List`, `Get` и чтение истории, execute - выгрузку, create - `Create`, update - `Update`, `Dismiss` и `SyncAccount`, delete - `Delete`.
- **FR-RM-23.** Права должны проверяться на сервере перед каждой операцией. Недостаточные права отвечают ошибкой `PERMISSION_DENIED`.
- **FR-RM-24.** Отозвано 2026-10-20: вместо `etag` параллельные изменения обнаруживаются по номеру ревизии (FR-RM-14), ответ 409 (ADR-022).

### 4.6. Разделение по арендаторам

Отозвано 2026-09-26. Мультиарендности нет, права ролей действуют на все записи справочников своей группы (FR-RM-22, BR-RM-13).

### 4.7. Интерфейс администрирования

- **FR-RM-28.** Веб-интерфейс администрирования должен поставляться отдельным компонентом со своим образом и развёртыванием и работать с сервисом только через REST API. Вход выполняется через Keycloak по протоколу OIDC Authorization Code с PKCE. Доступные действия определяются ролями токена, сервер проверяет права независимо от интерфейса. Первый шаг - админ-панель на имитированных данных без обращения к API. Решение об отдельном компоненте принято 2026-10-02.
- **FR-RM-29.** Интерфейс должен содержать список справочников из спецификации OpenAPI, таблицу записей с фильтром, сортировкой, показом удалённых и постраничным выводом, форму записи с полями по схеме справочника, действия удаления и восстановления с подтверждением, выгрузку в файл, историю изменений записи с различиями между ревизиями, отображение ошибок API с привязкой к полям.

### 4.8. Служебные точки

- **FR-RM-30.** `GET /v1/health/livez` должен отвечать кодом 200, пока процесс жив.
- **FR-RM-31.** `GET /v1/health/readyz` должен отвечать кодом 200, если хранилище доступно и его схема соответствует версии сервиса, иначе кодом 503 с перечнем неуспешных проверок.
- **FR-RM-32.** По флагу конфигурации сервис должен отдавать метрики в формате Prometheus на пути `/metrics`.

Имена служебных точек приведены к коду и спецификации 2026-10-02 (расхождение K-02).

### 4.9. История изменений

- **FR-RM-44.** Каждая операция записи (создание, изменение, удаление, увольнение, закрытие периода) должна вместе с изменением создавать ревизию: номер, актор, время и изменение в формате JSON Patch (RFC 6902) относительно предыдущего состояния записи. Ревизия создаётся в той же транзакции, что и изменение.
- **FR-RM-45.** История должна вестись для каждого справочника отдельно. Ревизии не изменяются и не удаляются.
- **FR-RM-46.** Пользователь с правом чтения должен получать историю записи методом `GET /v1/{справочник}/{id}/revisions`: ревизии постранично в порядке номеров, с фильтром и сортировкой по номеру, актору и времени. Отдельная ревизия доступна по пути `.../revisions/{revisionNumber}`.
- **FR-RM-47.** Отозвано 2026-10-20: состояние записи на ревизию сервис не восстанавливает, потребитель применяет операции JSON Patch ревизий сам (ADR-022).

### 4.10. Кадровые справочники

- **FR-RM-48.** Сервис должен вести справочники сотрудников (`employees`), подразделений (`org_units`) и должностей (`positions`). К ним применяются те же стандартные методы, восстановление, история и выгрузка, что и к остальным справочникам.
- **FR-RM-49.** Запись сотрудника должна содержать табельный номер как идентификатор, ФИО, логин, адрес почты, дату приёма, состояние занятости `employment_state` (EMPLOYED или DISMISSED), дату увольнения и сведения об учётной записи. Текущие подразделение и должность сотрудника возвращаются в записи только для чтения и берутся из назначения, действующего на дату запроса.
- **FR-RM-50.** Подразделения должны образовывать иерархию: запись подразделения может ссылаться на вышестоящее подразделение. Ссылка, которая образует цикл, отклоняется ошибкой `INVALID_ARGUMENT`.
- **FR-RM-51.** Сервис должен вести датированные справочники: назначения на должность (`assignments`), оклады (`salaries`) и отсутствия (`absences`). Каждая запись ссылается на сотрудника и имеет дату начала `start_date` и дату окончания `end_date`. Пустая дата окончания назначения или оклада означает, что запись действует сейчас. Идентификатор датированной записи назначает сервис.
- **FR-RM-52.** Периоды назначений одного сотрудника не должны пересекаться, то же относится к окладам. Запись с пересекающимся периодом или с датой окончания раньше даты начала отклоняется ошибкой `INVALID_ARGUMENT`. Смена должности или оклада оформляется закрытием действующей записи и созданием новой, прежние периоды сохраняются.

### 4.11. Учётные записи сотрудников

- **FR-RM-53.** При создании записи сотрудника сервис должен создать для него учётную запись в Keycloak: логин, временный пароль с обязательной сменой при первом входе, роли по умолчанию. Идентификатор учётной записи сохраняется в записи сотрудника. `Create` отвечает успехом только после того, как учётная запись создана и включена.
- **FR-RM-54.** Метод `Dismiss` (`POST /v1/employees/{id}:dismiss`) должен переводить сотрудника в состояние DISMISSED с датой увольнения, закрывать этой датой действующие назначение и оклад и блокировать учётную запись в Keycloak.
- **FR-RM-55.** Запись сотрудника должна показывать состояние учётной записи `account_state`. Пока операция с учётной записью не подтверждена, состояние равно PENDING. При недоступности Keycloak или тайм-ауте запись остаётся в PENDING, а метод отвечает ошибкой `UNAVAILABLE` с именем записи.
- **FR-RM-56.** Метод `SyncAccount` (`POST /v1/employees/{id}:syncAccount`) должен повторять незавершённую операцию с учётной записью по сохранённому идентификатору операции. Повтор не создаёт вторую учётную запись.
- **FR-RM-57.** Изменение ФИО или адреса почты сотрудника должно передаваться в его учётную запись тем же обменом, что и создание.
- **FR-RM-58.** Сервис не должен хранить пароли и управлять ролями доступа других модулей. Запись сотрудника с включённой учётной записью нельзя удалить: `Delete` отклоняется ошибкой `FAILED_PRECONDITION`, пока сотрудник не уволен.

### 4.12. Возможности вне основного объёма

Выполняются в конце, если останется время (ответ руководителя проекта, зафиксирован 2026-10-02). В критерии приёмки первой версии не входят.

- **FR-RM-59.** Пакетные операции: создание, изменение и удаление нескольких записей одного справочника одним запросом. Запрос выполняется целиком или отклоняется целиком.
- **FR-RM-60.** Загрузка записей справочника из файла `.xlsx`. Формат файла совпадает с форматом выгрузки (FR-RM-42). Строки проверяются так же, как при `Create` и `Update`, ошибки возвращаются по строкам и полям.

## 5. Требования к интеграциям

### 5.1. Общие правила обмена

- **INT-RM-01.** Потребители должны получать справочные данные только через REST API под префиксом `/v1`. Прямой доступ к хранилищу сервиса запрещён.
- **INT-RM-02.** Контракт обмена должен быть описан спецификацией OpenAPI, по одной коллекции и схеме записи на справочник, в соответствии с принципами Google AIP. Спецификация обновляется до реализации и проверяется контрактными тестами.
- **INT-RM-03.** Контракт должен оставаться обратно совместимым в пределах версии `/v1`: новый справочник появляется как новая коллекция, новое поле как необязательное. Потребитель не должен переделывать интеграцию при расширении состава справочников.
- **INT-RM-04.** Сервис не должен вызывать другие модули ERP и подписываться на их данные. Разрешены обращения к собственному хранилищу, к коллектору OpenTelemetry и к Keycloak: за ключами проверки токенов и к Admin REST API для создания, изменения и блокировки учётных записей сотрудников.
- **INT-RM-05.** Сервис не должен публиковать события. Потребитель, которому нужна локальная копия справочника, перечитывает его по API и сам выбирает срок жизни кэша. Целевой интервал перечитывания - не реже раза в час. Отказ от событий подтверждён документами потребителей, перечень приведён в [135](135.event-catalog.md).
- **INT-RM-06.** Ошибки должны возвращаться телом `{"message": "...", "details": [{"field": "...", "message": "..."}]}` с кодом HTTP по разделу 6 документа [130](130.api-contracts.md); `details` заполняются для ошибок проверки полей (ADR-022).
- **INT-RM-11.** Обмен с Keycloak по учётным записям должен выполняться синхронно в рамках запроса HR-администратора через Admin REST API под служебной учётной записью клиента, выданной Infra. Сервис сохраняет идентификатор операции до вызова Keycloak, чтобы повтор не создавал дублей. Связь профиля и учётной записи хранится с обеих сторон: идентификатор учётной записи в записи сотрудника, имя записи сотрудника в атрибуте учётной записи.
- **INT-RM-12.** Сервис является источником для аналитического хранилища отчётности. Данные извлекает задание ETL команды Reports по REST: `List` постранично с `allowDeleted`. Сервис сам данные в хранилище не отправляет.
- **INT-RM-13.** Сервис не участвует в обмене файлами через объектное хранилище. Файл выгрузки формируется по запросу, отдаётся в ответе и не сохраняется. Бакет сервису не нужен.

Справочник без подтверждённого потребителя в первую версию не входит.

## 6. Основные бизнес-правила

- **BR-RM-01.** Один справочник равен одной коллекции ресурсов со своим хранилищем и своим набором методов.
- **BR-RM-02.** Идентификатор записи назначается один раз и никогда не меняется.
- **BR-RM-03.** Деловые ключи удалённой записи остаются занятыми: повторно создать запись с тем же кодом, логином или адресом нельзя.
- **BR-RM-04.** Физического удаления записей в штатной работе нет. Удаление с `force=true` доступно администратору группы справочника для записей, созданных по ошибке, и уносит историю записи.
- **BR-RM-05.** Запись либо действует, либо удалена (`is_deleted`). Промежуточных состояний нет.
- **BR-RM-06.** Поля справочника только добавляются. Удаление поля или смена его типа несовместимы с контрактом API.
- **BR-RM-07.** Справочник не удаляется после ввода в эксплуатацию. Ненужные записи удаляются по BR-RM-05.
- **BR-RM-08.** Сервис хранит НСИ и кадровые мастер-данные: сотрудников, подразделения, должности, назначения, оклады и отсутствия. Учётные записи, пароли и роли доступа хранит Keycloak. Проекты, задачи, планы, расчётная ёмкость, статусы и приоритеты задач, серьёзность дефектов принадлежат другим модулям и в сервисе не хранятся.
- **BR-RM-09.** Сервис не вызывает другие модули ERP. Обращения к Keycloak за ключами и по учётным записям - интеграция с инфраструктурой, а не с модулем.
- **BR-RM-10.** Каждая операция записи выполняется в одной транзакции вместе с созданием ревизии и увеличивает номер ревизии записи.
- **BR-RM-11.** Потребители получают данные только через REST API.
- **BR-RM-12.** Каждая операция записи оставляет ревизию в истории своего справочника. Ревизии не изменяются и не удаляются.
- **BR-RM-13.** Права роли действуют на все записи справочников своей группы: общие классификаторы, кадровые справочники, оклады и отсутствия. Ограничений по организации или отдельной записи нет.
- **BR-RM-14.** Состав справочников определяет команда справочников по постановке и потребностям команд. Потребители справочники не создают.
- **BR-RM-15.** Учётная запись не существует без HR-профиля, а действующий HR-профиль без учётной записи. Профиль хранится в сервисе, учётная запись в Keycloak, связь между ними поддерживается интеграцией, а не общей базой.
- **BR-RM-16.** Датированное значение не перезаписывается. Новое назначение, новый оклад и новое отсутствие создаются отдельной записью, прежние периоды остаются в справочнике.

## 7. Пользовательские сценарии

### 7.1. Добавление справочника

1. Команда справочников уточняет у команды-потребителя состав полей и начальные данные справочника из перечня 9.2.
2. Разработчик добавляет хранилище справочника, его коллекцию и методы API, схему записи в спецификации и подключает справочник к общему набору тестов.
3. Изменение проходит ревью, вливается и развёртывается новой версией сервиса.
4. Администратор наполняет справочник записями через интерфейс администрирования или API.
5. Потребители читают данные по API.

### 7.2. Ведение записей

1. Администратор открывает справочник в интерфейсе администрирования.
2. Администратор создаёт запись, задавая идентификатор, наименование и поля справочника.
3. Система проверяет поля и сохраняет запись в состоянии ACTIVE вместе с ревизией создания.
4. При ошибке система показывает перечень полей и причины отклонения, запись не сохраняется.

### 7.3. Удаление и восстановление записи

1. Администратор удаляет запись, которая больше не нужна или создана по ошибке.
2. Система помечает запись удалённой (`is_deleted: true`), создаёт ревизию и возвращает запись.
3. Запись исчезает из списков по умолчанию, её идентификатор остаётся занятым, ссылки подсистем по имени продолжают работать.
4. Запись, удалённая по ошибке, создаётся заново: восстановления нет.

### 7.4. Выгрузка справочника в файл

1. Пользователь отбирает записи фильтром и запрашивает результат в формате `.xlsx`.
2. Система проверяет объём отбора.
3. При превышении предела система отвечает отказом и предлагает сузить отбор.
4. При допустимом объёме система формирует файл со строкой заголовков и строками записей и отдаёт его пользователю.

### 7.5. Просмотр истории записи

1. Пользователь открывает запись и запрашивает её ревизии.
2. Система возвращает ревизии от новой к старой: действие, кто и когда, изменённые поля с прежними и новыми значениями.
3. При необходимости пользователь запрашивает запись в состоянии на выбранную ревизию.

### 7.6. Приём сотрудника

1. HR-администратор создаёт запись сотрудника: табельный номер, ФИО, логин, адрес почты, дата приёма.
2. Система проверяет поля, сохраняет профиль с состоянием учётной записи PENDING и идентификатором операции.
3. Система создаёт в Keycloak отключённую учётную запись с логином, временным паролем, требованием сменить пароль и ссылкой на профиль, сохраняет её идентификатор и включает учётную запись.
4. Система переводит состояние учётной записи в ENABLED и возвращает запись сотрудника.
5. HR-администратор создаёт назначение на должность в подразделении и оклад с датой начала.
6. Сотрудник входит через Keycloak и меняет временный пароль.

Если Keycloak недоступен или не ответил вовремя, профиль остаётся с состоянием PENDING, а HR-администратор получает ошибку с именем записи. После восстановления Keycloak он повторяет операцию методом `SyncAccount`.

### 7.7. Увольнение сотрудника

1. HR-администратор вызывает `Dismiss` с датой увольнения.
2. Система переводит сотрудника в состояние DISMISSED, закрывает датой увольнения действующие назначение и оклад и создаёт ревизии.
3. Система блокирует учётную запись в Keycloak и переводит её состояние в DISABLED.
4. Запись сотрудника остаётся доступной по имени, ссылки подсистем продолжают работать. Уже выданный токен действует до истечения срока.

### 7.8. Смена должности или оклада

1. HR-администратор закрывает действующее назначение или оклад датой окончания.
2. HR-администратор создаёт новую запись с датой начала на следующий день.
3. Система проверяет, что периоды не пересекаются, и сохраняет запись. Прежний период остаётся в справочнике.

## 8. Требования к интерфейсу

### 8.1. Список справочников

Страница должна содержать перечень справочников сервиса с кодом и названием и переход к записям выбранного справочника.

### 8.2. Таблица записей справочника

Страница должна содержать таблицу записей с общими полями и полями справочника, строку фильтра, сортировку, флаг показа удалённых записей, постраничный вывод, действие создания записи, действие выгрузки отобранных записей в файл и переход к форме записи.

### 8.3. Форма записи

Страница должна содержать поля записи, построенные по схеме справочника из спецификации OpenAPI, сведения о состоянии и времени удаления, действия сохранения, удаления и восстановления с подтверждением, отображение ошибок API с привязкой к полям, историю изменений записи: ревизии с действием, актором, временем и различиями.

### 8.4. Карточка сотрудника

Форма записи сотрудника дополнительно должна показывать состояние занятости и состояние учётной записи, действующие назначение и оклад, списки назначений, окладов и отсутствий сотрудника по периодам, действия "Уволить" и "Повторить операцию с учётной записью". Оклады и отсутствия видны только ролям с доступом к ним.

## 10. Нефункциональные требования

### 10.1. Архитектурные ограничения

- **NFR-RM-01.** Сервис не должен вызывать другие модули ERP. Исходящие соединения ограничены собственным хранилищем, коллектором OpenTelemetry и Keycloak.
- **NFR-RM-02.** Сервис должен хранить только НСИ и кадровые мастер-данные: справочники, их записи и историю изменений.
- **NFR-RM-03.** К хранилищу сервиса должен обращаться только сам сервис.
- **NFR-RM-04.** Физическое удаление данных не должно реализовываться.
- **NFR-RM-05.** Имя записи должно быть неизменяемо после создания. Идентификатор удалённой записи остаётся занятым.
- **NFR-RM-06.** Контракт API должен быть обратно совместим в пределах мажорной версии `/v1`. Несовместимые изменения выпускаются как `/v2`.
- **NFR-RM-07.** Все операции записи должны выполняться сервисным слоем в одной транзакции вместе с созданием ревизии.
- **NFR-RM-08.** Приложение не должно хранить состояния между запросами, кроме кэша ключей проверки токенов. Допускается работа нескольких экземпляров одновременно.
- **NFR-RM-39.** Добавление справочника или поля должно быть обратно совместимым изменением API: новая коллекция и необязательные поля.
- **NFR-RM-40.** Методы всех справочников должны вести себя одинаково: те же коды ошибок, формат ошибок, параметры списка. Отличия справочников ограничены составом полей и фильтров по ним. У справочника сотрудников дополнительно есть методы `Dismiss` и `SyncAccount`.

### 10.2. Контракт API

- **NFR-RM-09.** API должен следовать принципам Google AIP: ресурсно-ориентированный дизайн (AIP-121, 122), стандартные методы (AIP-131..135), кастомные методы (AIP-136), постраничный вывод (AIP-158), фильтрация (AIP-160), ревизии (AIP-162), мягкое удаление (AIP-164). Отклонения зафиксированы в ADR-015 и ADR-022. Формат `application/json`, UTF-8, время в RFC 3339 UTC, префикс `/v1`.
- **NFR-RM-10.** Частичное изменение должно выполняться методом `Update` (`PATCH`) с `updateMask`.
- **NFR-RM-11.** Ошибки должны возвращаться в формате AIP-193 с `ErrorInfo`, `BadRequest` для ошибок полей и `RequestInfo` с идентификаторами запроса и трассы.
- **NFR-RM-12.** Контракт должен быть описан спецификацией OpenAPI, обновляться до реализации и проверяться контрактными тестами.
- **NFR-RM-13.** Каждый ответ должен содержать заголовки `X-Request-Id` и `X-Trace-Id`. Входящий заголовок `traceparent` продолжает трассу вызывающего.

### 10.3. Данные

- **NFR-RM-14.** Идентификатор записи задаётся создателем и должен соответствовать формату, заданному схемой справочника. Для стандартных классификаторов это код стандарта, для сотрудника табельный номер. Идентификатор датированной записи назначает сервис.
- **NFR-RM-15.** Размер тела запроса не должен превышать 1 МБ, `pageSize` не должен превышать 100 при значении по умолчанию 20.
- **NFR-RM-16.** Учётная запись сервиса в хранилище не должна иметь прав на изменение схемы и физическое удаление; ревизии для неё доступны только на добавление и чтение.
- **NFR-RM-17.** Каждое изменение схемы хранилища должно быть обратимо, проверяться в CI и быть совместимым с предыдущей версией сервиса.
- **NFR-RM-42.** Одна выгрузка не должна превышать 50 000 записей. Предельное значение задаётся конфигурацией.
- **NFR-RM-46.** Ведение истории не должно замедлять операции над записями сверх 10 процентов; чтение истории записи должно выполняться по индексу.

### 10.4. Производительность и доступность

- **NFR-RM-18.** Время отклика чтения не должно превышать 100 мс для 95 процентов запросов при нагрузке 100 запросов в секунду. Время отклика записи не должно превышать 300 мс. Операции с обращением к Keycloak в этот порог не входят.
- **NFR-RM-19.** Доступность на стенде должна составлять 99,5 процента. Целевое значение согласуется с командой Infra.
- **NFR-RM-20.** Запросы списков и чтения по идентификатору должны покрываться индексами.
- **NFR-RM-43.** Выгрузка предельного объёма должна формироваться не дольше 60 секунд и не должна удерживать соединение с хранилищем на всё это время.
- **NFR-RM-47.** Каждый вызов Keycloak Admin REST API должен быть ограничен тайм-аутом из конфигурации, значение по умолчанию 5 секунд. Недоступность Keycloak Admin REST API не должна влиять на чтение справочников и на операции записи, не связанные с учётными записями.

### 10.5. Совместимость выгрузок

- **NFR-RM-44.** Файл выгрузки должен открываться в актуальных версиях Microsoft Excel и совместимых табличных редакторах без предупреждений о повреждении.
- **NFR-RM-45.** Идентификаторы и коды в выгрузке должны сохраняться как текст.

### 10.6. Эксплуатация

- **NFR-RM-21.** Изменения схемы хранилища должно применять отдельное задание до запуска новой версии сервиса: локально цель Taskfile, в Kubernetes объект Job.
- **NFR-RM-22.** Конфигурация должна читаться из каталога файлов YAML или переменных окружения без пересборки. Секреты не хранятся в репозитории.
- **NFR-RM-23.** Остановка должна быть корректной: текущие запросы завершаются, соединения и экспортёры телеметрии закрываются с таймаутом.
- **NFR-RM-24.** Сервис и интерфейс администрирования должны поставляться двумя образами: образ сервиса с API и образ интерфейса со статикой. Версия передаётся в каждый образ при сборке.
- **NFR-RM-49.** Модуль должен развёртываться в локальном кластере minikube манифестами: Deployment, Service, ConfigMap, Secret, PersistentVolumeClaim и маршрутизация входящих запросов. Развёртывание в minikube - окружение приёмки.

### 10.7. Наблюдаемость

- **NFR-RM-25.** Трассы, метрики и журналы должны собираться через OpenTelemetry и отправляться по протоколу OTLP в коллектор. Ресурс несёт атрибуты `service.name`, `service.version`, `service.instance.id` и `deployment.environment`.
- **NFR-RM-26.** Трассироваться должны каждый запрос HTTP, каждый запрос к хранилищу без значений параметров и операции сервисного слоя.
- **NFR-RM-27.** Метрики должны включать показатели HTTP по семантическим соглашениям OpenTelemetry, состояние пула соединений, показатели среды выполнения, счётчики операций записи по справочникам, число записей по состояниям и число выгрузок.
- **NFR-RM-28.** Журналы должны быть структурированными с полями `trace_id`, `span_id`, `request_id` и `actor_id`. Токены, пароли и тела запросов в журналы не пишутся.
- **NFR-RM-29.** Недоступность коллектора не должна замедлять и отклонять запросы.

### 10.8. Безопасность

- **NFR-RM-30.** Отозвано 2026-10-02. Сервис не работает без аутентификации: проверка токена и ролей входит в первую версию (раздел 4.5).
- **NFR-RM-31.** Все запросы к хранилищу должны быть параметризованы.
- **NFR-RM-32.** В Kubernetes исходящий трафик должен быть ограничен сетевой политикой адресами из NFR-RM-01.
- **NFR-RM-33.** Ответы с ошибками не должны раскрывать внутренние детали.
- **NFR-RM-34.** Зависимости должны проверяться на известные уязвимости в CI.
- **NFR-RM-35.** Статика интерфейса должна отдаваться с заголовками `Content-Security-Policy` без inline-скриптов и `X-Frame-Options: DENY`. Интерфейс и API публикуются под одним адресом через маршрутизацию входящих запросов, поэтому междоменные запросы не нужны.
- **NFR-RM-48.** Оклады, отсутствия, временные пароли и секрет служебного клиента Keycloak не должны попадать в журналы, трассы и сообщения об ошибках. Временный пароль не сохраняется в хранилище.
- **NFR-RM-50.** Перед приёмкой модуль должен пройти проверку безопасности по чек-листу: XSS, CSRF, инъекции, заголовки статики, секреты в журналах. Результат оформляется отчётом в [документе проверки безопасности](security-check.md).

### 10.9. Качество и тестирование

- **NFR-RM-36.** Код должен проходить линтер репозитория без предупреждений.
- **NFR-RM-37.** Доменная логика и сервисный слой должны покрываться модульными тестами, хранилище интеграционными тестами, API контрактными тестами по спецификации. Покрытие доменной логики и хранилища не ниже 80 процентов строк.
- **NFR-RM-38.** Линтер и тесты должны проходить на каждом pull request. Исправление дефекта сопровождается регрессионным тестом.
- **NFR-RM-41.** Общий набор тестов стандартных методов должен выполняться для каждого справочника. Новый справочник подключается к набору без копирования тестов.

## 11. Критерии приёмки первой версии

1. Справочники первой версии из раздела 9.2 заведены, каждый со своей коллекцией и методами.
2. Для любого справочника работают пять стандартных методов, выгрузка и чтение истории с одинаковыми кодами и форматом ошибок.
3. Запись с недопустимым значением поля отклоняется ошибкой `INVALID_ARGUMENT` с перечнем полей и не сохраняется.
4. Повторный идентификатор записи отклоняется, в том числе если запись с таким идентификатором удалена.
5. Удаление переводит запись в DELETED и убирает её из списков по умолчанию, чтение по имени сохраняется; восстановление возвращает ACTIVE.
6. `List` поддерживает `filter`, `order_by`, `pageSize`, `pageToken`, `allowDeleted` и возвращает `nextPageToken`.
7. Каждая операция записи создаёт ревизию; история записи читается через `revisions` и содержит действие, актора, время и изменения.
8. Отобранные записи выгружаются в `.xlsx`, файл открывается в Excel, идентификаторы сохранены как текст.
9. `/v1/health/readyz` отвечает кодом 503, пока хранилище недоступно или его схема не соответствует версии сервиса.
10. Трассы, метрики и журналы поступают в коллектор OpenTelemetry.
11. Запрос без токена отклоняется ошибкой `UNAUTHENTICATED`, запрос без нужного уровня доступа ошибкой `PERMISSION_DENIED`. Оклады и отсутствия недоступны ролям `reference-reader` и `reference-admin`.
12. Создание записи сотрудника создаёт учётную запись в Keycloak, сотрудник входит с временным паролем и меняет его. Увольнение блокирует учётную запись.
13. При недоступном Keycloak профиль остаётся в состоянии PENDING, повтор методом `SyncAccount` завершает операцию без второй учётной записи.
14. Смена должности и оклада сохраняет прежние периоды. Пересекающиеся периоды отклоняются.
15. К приёмке модуля (веха M5): модуль развёртывается в minikube манифестами из NFR-RM-49, проходит проверку готовности и проверку безопасности по чек-листу (NFR-RM-50).

## 13. Предлагаемые границы первой версии

В первую версию рекомендуется включить:

- кадровые справочники: сотрудники, подразделения, должности, назначения, оклады, отсутствия
- создание и блокировку учётных записей в Keycloak
- справочники валют и стран как образцы, проектные роли и грейды
- пять стандартных методов, выгрузку и историю на каждый справочник, общий набор тестов
- проверку значений полей с ответом по полям
- мягкое удаление записи без восстановления
- `List` с фильтром, сортировкой, постраничным выводом и показом удалённых
- выгрузку записей справочника в файл `.xlsx`
- аутентификацию Keycloak и проверку ролей
- хранилище и задание изменений схемы
- служебные точки `/v1/health/livez` и `/v1/health/readyz`, телеметрию OpenTelemetry

Во вторую очередь предлагается сетевая политика исходящего трафика. Проверка `etag` снята, параллельные изменения обнаруживаются по номеру ревизии. В третью очередь интерфейс администрирования отдельным компонентом: сначала админ-панель на имитированных данных, затем работа с API. К приёмке модуля готовятся манифесты для minikube и отчёт проверки безопасности. В конце, если останется время, пакетные операции и загрузка из файла. Инкрементальная выдача изменений и локализованные наименования рассматриваются после подтверждения потребности.
