Редакция 2026-10-20: контракт приведён к реализации справочника валют (ADR-022). Прежняя редакция описывала имена ресурсов вида `currencies/EUR`, поля `name`, `display_name`, `state`, `etag`, `delete_time`, параметры `page_size` и `show_deleted`, метод `Undelete`, выгрузку через заголовок `Accept` и ошибки `google.rpc.Status`. Всё это заменено формой, которую реализует код.

## 1. Спецификация

Источник истины - OpenAPI в `backend/api/openapi/v1/`: на каждый ресурс своя спецификация и своя конфигурация генерации кода. Спецификация `health/openapi.yaml` описывает служебные точки, `currency/openapi.yaml` - валюты, остальные девять спецификаций (`country`, `project_role`, `grade`, `org_unit`, `position`, `employee`, `assignment`, `salary`, `absence`) порождает генератор `backend/tools/gencatalog` из описания полей справочника. Генератор выпускает также доменный пакет, адаптер обработчиков и миграцию справочника, поэтому форма методов у всех справочников одна (NFR-RM-40). Серверный код, модели и клиент собираются из спецификаций командой `task generate`.

Версия каждой спецификации в `info.version`: `1.0.0` у всех спецификаций первой версии. Мажорная версия совпадает с версией в пути (`/v1`), minor растёт при добавлении поля, метода или параметра, patch - при уточнении описаний. Несовместимое изменение выпускается как `/v2` со спецификацией `2.0.0` (INT-RM-03, NFR-RM-06).

## 2. Общие правила

| Правило | Значение |
| --- | --- |
| Ресурсы | Коллекция на справочник: `/v1/currencies/`, `/v1/employees/`. Запись адресуется целочисленным идентификатором, который назначает сервис: `/v1/currencies/{currencyID}` |
| Стандартные методы | `POST` создание, `GET` список, `GET` чтение, `PATCH` изменение, `DELETE` удаление; дополнительно `POST .../export` выгрузка, `GET .../revisions` и `GET .../revisions/{revisionNumber}` история |
| Общие поля записи | `id`, `is_deleted`, `revision`, `last_changer`, `created_at`, `updated_at`, `deleted_at`; все только для чтения, вычисляются по истории. Собственные поля справочника описаны в его схеме |
| Список | `pageSize` (1..100, по умолчанию 20), `pageToken`, `filter` (AIP-160), `order_by` (AIP-132), `allowDeleted`; ответ: массив записей под именем коллекции и `nextPageToken`, которого нет на последней странице. Общего числа записей в ответе нет |
| Создание | Тело - схема справочника без общих полей; идентификатор назначает сервис. Поля, которые ведёт сервис (например `employment_state`), в теле не принимаются |
| Изменение | `PATCH` с параметром `updateMask`: список полей через запятую; пустая маска или `*` - все изменяемые поля. Поле вне перечня изменяемых отклоняется как INVALID_ARGUMENT. Неизменяемые поля: `username` сотрудника, `employee_id` датированных записей |
| Конкурентность | Номер ревизии: запись читается в транзакции, следующая ревизия получает номер `revision + 1`; если его уже занял другой запрос, ответ 409 |
| Удаление | `DELETE` помечает запись `is_deleted: true` и возвращает её; `?force=true` удаляет запись вместе с историей без возврата (204). Восстановления нет: удалённая запись остаётся в хранилище и читается с `allowDeleted=true` |
| Ревизии | Каждая операция записи даёт ревизию с номером, автором, временем и изменением в формате JSON Patch (RFC 6902) относительно предыдущего состояния; ревизия 1 описывает создание относительно пустого документа |
| Ошибки | Тело `{"message": "...", "details": [{"field": "...", "message": "..."}]}`; `details` заполнены для ошибок проверки полей. Коды HTTP - в разделе 6 |
| Формат | `application/json`, UTF-8, время RFC 3339 UTC, календарные даты `YYYY-MM-DD` |
| Выгрузка | `POST /v1/{коллекция}/export` возвращает файл `.xlsx` со всеми активными записями справочника в порядке создания; параметров отбора нет. В файл входят только записи, ревизии не выгружаются |
| Права | Роли из токена Keycloak проверяются на сервере по группе справочника и уровню (раздел 3 требований, [070](070.role-matrix.md)); в спецификации роли перечислены в `x-required-roles` каждой операции |

## 3. Методы справочника

На примере `countries`. У всех справочников набор одинаков.

| Метод | HTTP | Роль | Успех | Ошибки |
| --- | --- | --- | --- | --- |
| Create | `POST /v1/countries/` | admin | 201: запись | 400 проверка полей с `details`; 409 занятое уникальное значение |
| List | `GET /v1/countries/?pageSize=20&filter=...&order_by=...&allowDeleted=false` | reader | 200: `countries[]`, `nextPageToken` | 400 фильтр, сортировка, `pageToken` |
| Export | `POST /v1/countries/export` | reader | 200: файл `countries.xlsx` | 401, 403 |
| Get | `GET /v1/countries/{countryID}?allowDeleted=false` | reader | 200: запись | 404, в том числе для удалённой без `allowDeleted` |
| Update | `PATCH /v1/countries/{countryID}?updateMask=name,currency_id` | admin | 200: запись | 400 поля, маска; 404; 409 уникальность или параллельное изменение |
| Delete | `DELETE /v1/countries/{countryID}` | admin | 200: запись с `is_deleted: true` | 404 уже удалена; 409 параллельное изменение |
| Purge | `DELETE /v1/countries/{countryID}?force=true` | admin | 204 | 404 |
| ListRevisions | `GET /v1/countries/{countryID}/revisions` | reader | 200: `revisions[]`, `nextPageToken` | 404 |
| GetRevision | `GET /v1/countries/{countryID}/revisions/{revisionNumber}` | reader | 200: ревизия | 404 запись или ревизия |

Для `currencies` набор тот же с идентификатором `currencyID`. В таблице указана наименьшая роль для классификаторов. У кадровых справочников писать может только `reference-hr-admin`, а оклады и отсутствия читают только `reference-hr-reader` и `reference-hr-admin` (раздел 3 требований).

### Кадровые справочники

| Справочник | Отличие |
| --- | --- |
| `employees` | Поля `employment_state` и `dismissal_date` ведёт сервис: новая запись получает `EMPLOYED`, метод `POST /v1/employees/{employeeID}/dismiss` с телом `{"dismissal_date": "2026-10-31"}` переводит в `DISMISSED` и закрывает этой датой действующие назначение и оклад. Поля `org_unit_id` и `position_id` только для чтения: берутся из назначения, действующего сегодня. Логин `username` после создания не меняется. Поля `account_state` и `account_user_id` только для чтения: учётную запись в Keycloak ведёт сервис (раздел 8), метод `POST /v1/employees/{employeeID}/syncAccount` без тела повторяет незавершённую операцию с ней и отвечает записью сотрудника |
| `org_units` | Ссылка `parent_id` на существующее неудалённое подразделение; ссылка на себя или на подчинённое подразделение отклоняется |
| `assignments`, `salaries` | Ссылка `employee_id` не меняется; новая запись принимается только для работающего сотрудника; периоды одного сотрудника не пересекаются; `end_date` не раньше `start_date`; пустой `end_date` означает "действует сейчас" |
| `absences` | Обе даты обязательны, `end_date` не раньше `start_date` |
| `salaries`, `absences` | Чтение требует роли `reference-hr-reader` или `reference-hr-admin` |

Учётные записи сотрудников в Keycloak (FR-RM-53..58) реализованы 2026-10-29: запись сотрудника несёт `account_state` и `account_user_id`, метод `POST /v1/employees/{employeeID}/syncAccount` повторяет незавершённую операцию. Исходящий контракт - в разделе 8.

### Фильтры

Поля фильтра и сортировки - собственные поля справочника и общие поля `is_deleted`, `revision`, `last_changer`, `created_at`, `updated_at`, `deleted_at`. Строки сравниваются операторами `=`, `!=`, `<`, `<=`, `>`, `>=` и оператором вхождения `:` (без учёта регистра), `поле:*` проверяет наличие значения, даты сравниваются как строки `YYYY-MM-DD`, время - как RFC 3339.

| Задача потребителя | Запрос |
| --- | --- |
| Работающие сотрудники подразделения | `GET /v1/employees/?filter=employment_state = "EMPLOYED" AND org_unit_id = 2` |
| Подчинённые подразделения | `GET /v1/org_units/?filter=parent_id = 1` |
| Только команды | `GET /v1/org_units/?filter=kind = "TEAM"` |
| Назначение сотрудника на дату | `GET /v1/assignments/?filter=employee_id = 1 AND start_date <= "2026-06-15" AND (end_date >= "2026-06-15" OR NOT end_date:*)` |
| Отсутствия сотрудника за период | `GET /v1/absences/?filter=employee_id = 1 AND start_date <= "2026-12-31" AND end_date >= "2026-10-01"` |
| Страна по названию | `GET /v1/countries/?filter=name : "kazakh"&order_by=alpha2` |
| Полная выгрузка для кэша или ETL | `GET /v1/employees/?allowDeleted=true&pageSize=100` постранично до ответа без `nextPageToken` |

## 4. Схемы

Каждая запись содержит общие поля `id`, `is_deleted`, `revision`, `last_changer`, `created_at`, `updated_at`, `deleted_at` (пустое значение `0001-01-01T00:00:00Z`, если запись не удалялась) и собственные поля:

| Справочник | Собственные поля |
| --- | --- |
| `currencies` | `code` (три заглавные буквы, уникально), `number` (три цифры, уникально), `name`, `decimals` (0..4) |
| `countries` | `alpha2` (уникально), `alpha3` (уникально), `numeric_code` (три цифры, уникально), `name`, `currency_id` (необязательно, ссылка на валюту) |
| `project_roles` | `code` (строчные латинские буквы, цифры и дефис, уникально), `name`, `description` (необязательно) |
| `grades` | `code` (уникально), `name`, `rank` (1..100) |
| `org_units` | `code` (уникально), `name`, `kind` (`DEPARTMENT` или `TEAM`), `parent_id` (необязательно) |
| `positions` | `code` (уникально), `name` |
| `employees` | `personnel_number` (1..10 цифр, уникально), `family_name`, `given_name`, `middle_name` (необязательно), `email` (уникально), `username` (уникально, не меняется), `hire_date`; только для чтения `employment_state`, `dismissal_date`, `org_unit_id`, `position_id`, `account_state`, `account_user_id` |
| `assignments` | `employee_id`, `org_unit_id`, `position_id`, `start_date`, `end_date` (необязательно) |
| `salaries` | `employee_id`, `amount` (больше нуля, два знака), `currency_id`, `start_date`, `end_date` (необязательно) |
| `absences` | `employee_id`, `kind` (`VACATION`, `SICK_LEAVE`, `OTHER`), `start_date`, `end_date` |

Ревизия: `id`, `{справочник}_id` (например `country_id`), `revision_number`, `change` (массив операций JSON Patch), `changed_by` (UUID актора из токена), `changed_at`.

Ошибка: `message`, необязательный `details[]` из `{field, message}`.

## 5. Примеры

### 5.1. Создание, успех

```http
POST /v1/countries/
Content-Type: application/json
Authorization: Bearer <token>

{"alpha2": "RU", "alpha3": "RUS", "numeric_code": "643", "name": "Russia", "currency_id": 1}
```

```http
HTTP/1.1 201 Created

{"id": 1, "alpha2": "RU", "alpha3": "RUS", "numeric_code": "643", "name": "Russia", "currency_id": 1, "is_deleted": false, "revision": 1, "last_changer": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "created_at": "2026-10-20T09:00:00Z", "updated_at": "2026-10-20T09:00:00Z", "deleted_at": "0001-01-01T00:00:00Z"}
```

### 5.2. Создание, ошибка по полям

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"message": "validation failed", "details": [{"field": "alpha2", "message": "must match ^[A-Z]{2}$"}, {"field": "currency_id", "message": "currencies 99 does not exist"}]}
```

### 5.3. Занятое уникальное значение

```http
HTTP/1.1 409 Conflict

{"message": "country already exists"}
```

### 5.4. Список с фильтром и выгрузка

```http
GET /v1/countries/?filter=name%20%3A%20%22kazakh%22&order_by=alpha2&pageSize=20
```

```http
HTTP/1.1 200 OK

{"countries": [{"id": 2, "alpha2": "KZ", "alpha3": "KAZ", "numeric_code": "398", "name": "Kazakhstan", "is_deleted": false, "revision": 1, "last_changer": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "created_at": "2026-10-20T09:01:00Z", "updated_at": "2026-10-20T09:01:00Z", "deleted_at": "0001-01-01T00:00:00Z"}]}
```

На странице, за которой есть следующая, в ответе появляется `nextPageToken`. Его передают в `pageToken` с теми же `filter`, `order_by` и `allowDeleted`, иначе ответ 400.

Выгрузка:

```http
POST /v1/countries/export
```

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
Content-Disposition: attachment; filename=countries.xlsx
```

Лист `Countries`: столбцы собственных полей, затем `Revision`, `Last changer`, `Created at`, `Updated at`. Числовые коды выгружаются текстом, даты - датами без времени.

### 5.5. Изменение и удаление

```http
PATCH /v1/countries/1?updateMask=name,currency_id
Content-Type: application/json

{"alpha2": "XX", "alpha3": "XXX", "numeric_code": "000", "name": "Russian Federation", "currency_id": 1}
```

```http
HTTP/1.1 200 OK

{"id": 1, "alpha2": "RU", "alpha3": "RUS", "numeric_code": "643", "name": "Russian Federation", "currency_id": 1, "is_deleted": false, "revision": 2, "last_changer": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "created_at": "2026-10-20T09:00:00Z", "updated_at": "2026-10-20T09:05:00Z", "deleted_at": "0001-01-01T00:00:00Z"}
```

Поля вне маски не изменились. Удаление возвращает запись с `is_deleted: true` и заполненным `deleted_at`. `DELETE /v1/countries/1?force=true` отвечает 204 и удаляет запись с историей.

### 5.6. История записи

```http
GET /v1/countries/1/revisions/2
```

```http
HTTP/1.1 200 OK

{"id": 2, "country_id": 1, "revision_number": 2, "change": [{"op": "replace", "path": "/name", "value": "Russian Federation"}, {"op": "replace", "path": "/currency_id", "value": 1}], "changed_by": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "changed_at": "2026-10-20T09:05:00Z"}
```

`GET /v1/countries/1/revisions` возвращает `revisions[]` в порядке номеров и `nextPageToken`. Состояние записи на ревизию сервис не восстанавливает: потребитель применяет операции JSON Patch ревизий 1..N сам.

### 5.7. Приём сотрудника

```http
POST /v1/employees/
Content-Type: application/json

{"personnel_number": "1024", "family_name": "Петрова", "given_name": "Мария", "email": "m.petrova@example.org", "username": "m.petrova", "hire_date": "2026-11-02"}
```

```http
HTTP/1.1 201 Created

{"id": 2, "personnel_number": "1024", "family_name": "Петрова", "given_name": "Мария", "email": "m.petrova@example.org", "username": "m.petrova", "hire_date": "2026-11-02", "employment_state": "EMPLOYED", "is_deleted": false, "revision": 1, "last_changer": "d81f4b6c-2e9a-4c35-b7d0-6a5e4f3c2b1d", "created_at": "2026-10-20T09:10:00Z", "updated_at": "2026-10-20T09:10:00Z", "deleted_at": "0001-01-01T00:00:00Z"}
```

Поля `org_unit_id` и `position_id` появляются после создания назначения с датой начала не позже сегодняшней. Создание сотрудника создаёт и включает его учётную запись в Keycloak (FR-RM-53): в ответе `account_state` ENABLED, `account_user_id` заполнен, `revision` 2, потому что результат операции с учётной записью - отдельная ревизия. При недоступном Keycloak ответ 503 с сообщением `employee 2 (m.petrova) is stored, the operation with its account is pending, repeat it with SyncAccount: dependency is unavailable`, запись сохранена с `account_state` PENDING (FR-RM-55). Логин, занятый чужой учётной записью (почта не совпадает), - 400 с сообщением `employee 2: account conflict: username "m.petrova" belongs to another account: failed precondition`. Удаление работающего сотрудника с учётной записью - 400 с сообщением `employee 2 has an account, dismiss the employee before the deletion: failed precondition` (FR-RM-58).

### 5.8. Увольнение

```http
POST /v1/employees/1/dismiss
Content-Type: application/json

{"dismissal_date": "2026-10-31"}
```

```http
HTTP/1.1 200 OK

{"id": 1, "personnel_number": "1001", "family_name": "Иванов", "given_name": "Иван", "middle_name": "Иванович", "email": "i.ivanov@example.org", "username": "i.ivanov", "hire_date": "2024-01-15", "employment_state": "DISMISSED", "dismissal_date": "2026-10-31", "org_unit_id": 2, "position_id": 1, "account_state": "DISABLED", "account_user_id": "9b2f1c4e-6d3a-4b8e-9f10-2a7c5d8e1b34", "is_deleted": false, "revision": 3, "last_changer": "d81f4b6c-2e9a-4c35-b7d0-6a5e4f3c2b1d", "created_at": "2026-10-01T10:00:00Z", "updated_at": "2026-10-20T09:20:00Z", "deleted_at": "0001-01-01T00:00:00Z"}
```

Действующие назначение и оклад получают `end_date: "2026-10-31"` и по ревизии каждый. Сам сотрудник получает две ревизии: состояние занятости с датой и `account_state` PENDING в транзакции увольнения, затем DISABLED после блокировки учётной записи в Keycloak (FR-RM-54). Повторное увольнение отвечает 400 с сообщением `employee 1 is already dismissed on 2026-10-31: failed precondition`, дата раньше приёма - 400 с `details` по полю `dismissal_date`.

### 5.9. Назначение с пересечением периода

```http
POST /v1/assignments/
Content-Type: application/json

{"employee_id": 1, "org_unit_id": 1, "position_id": 1, "start_date": "2026-10-01"}
```

```http
HTTP/1.1 400 Bad Request

{"message": "invalid start_date, end_date: period overlaps another record of the employee"}
```

Сначала действующее назначение закрывается `PATCH /v1/assignments/1?updateMask=end_date` с `end_date: "2026-09-30"`, затем создаётся новое (BR-RM-16).

### 5.10. Отказ в доступе к окладам

Чтение `GET /v1/salaries/` ролью `reference-reader`:

```http
HTTP/1.1 403 Forbidden

{"message": "permission denied"}
```

Запрос без токена отвечает 401 с заголовком `WWW-Authenticate: Bearer error="invalid_token"` и телом `{"message": "unauthenticated"}`.

## 6. Соответствие ошибок

| Ситуация | HTTP | `message` |
| --- | --- | --- |
| Нет токена или недействителен | 401 | `unauthenticated` |
| Нет уровня доступа на группу справочника | 403 | `permission denied` |
| Запись не найдена, удалена без `allowDeleted`, повторное удаление | 404 | `{справочник} not found` |
| Ревизия не найдена | 404 | `{справочник} revision not found` |
| Занятое уникальное значение | 409 | `{справочник} already exists` |
| Параллельное изменение, номер ревизии занят | 409 | `{справочник} was modified concurrently, retry the request` |
| Неверные поля, ссылки, период, цикл в иерархии | 400 | `validation failed` с `details` по полям |
| Пересечение периодов, нарушение ограничения хранилища | 400 | `invalid start_date, end_date: period overlaps another record of the employee` |
| Фильтр, сортировка, маска, токен страницы, параметры пути | 400 | `invalid {параметр}: ...` или `invalid request parameters` |
| Операция недопустима в текущем состоянии (повторное увольнение) | 400 | текст причины с окончанием `failed precondition` |
| Тело не разобрано | 400 | `failed to decode request` |
| Внутренняя ошибка | 500 | `internal server error` |

## 8. Исходящий контракт: Keycloak Admin REST API

Контракт учётных записей сотрудников (FR-RM-53..58, ADR-019), реализован 2026-10-29: клиент Admin REST API в `backend/pkg/keycloak/admin.go`, координация в `backend/internal/services/employee`. Сервис вызывает Keycloak под служебным клиентом `reference-manager-provisioner` с ролями `manage-users`, `view-users`, `query-users` и `view-realm` клиента `realm-management`; на общем стенде клиент создаёт Infra (`infra/keycloak/realm/desired.json`, [vision Infra, раздел 3](../../infra/vision.md)), в локальном realm модуля он есть, секрет подставляется из `KEYCLOAK_PROVISIONER_SECRET` при старте Keycloak.

| Назначение | Запрос к Keycloak | Когда | Ответ и обработка |
| --- | --- | --- | --- |
| Служебный токен | `POST /realms/{realm}/protocol/openid-connect/token`, `grant_type=client_credentials` | Перед операцией, токен кэшируется до истечения срока | Ошибка - 503, состояние PENDING |
| Найти учётную запись | `GET /admin/realms/{realm}/users?username={username}&exact=true` | Перед созданием и при повторе | Запись со связью читает учётную запись по `account_user_id` (`GET /admin/realms/{realm}/users/{id}`); без связи найденная по логину учётная запись с той же почтой присваивается (прерванное создание), с другой почтой - 400 FAILED_PRECONDITION |
| Создать учётную запись | `POST /admin/realms/{realm}/users`: логин, ФИО, адрес почты, `enabled: false`, случайный временный пароль, обязательное действие смены пароля | Создание сотрудника, повтор | 201 - идентификатор из заголовка `Location`; 409 - 400 FAILED_PRECONDITION |
| Роли по умолчанию | `GET /admin/realms/{realm}/roles/{name}`, `POST /admin/realms/{realm}/users/{id}/role-mappings/realm` | Сразу после создания, роли из конфигурации `auth.keycloak.provisioner.default_realm_roles` (локально `reference-reader`) | 204 |
| Включить, заблокировать, изменить | `PUT /admin/realms/{realm}/users/{id}`: `enabled: true` или `false`, `firstName` = `given_name`, `lastName` = `family_name`, адрес почты (отчество в Keycloak не передаётся) | Завершение создания; увольнение; изменение ФИО или почты | 204 - операция подтверждена; 404 - учётная запись удалена в Keycloak, ищется по логину и создаётся заново |

Тайм-аут каждого вызова - из конфигурации, по умолчанию 5 секунд (NFR-RM-47). Секрет клиента, временный пароль и служебный токен в журналы и ошибки не попадают (NFR-RM-48). Состояние после операции: ENABLED пока сотрудник работает, DISABLED после увольнения, PENDING при любой ошибке Keycloak; `syncAccount` повторяет операцию по состояниям записи, отдельный идентификатор операции не хранится. Доставка временного пароля сотруднику - вопрос 18.

## 9. Методы вне основного объёма

Выполняются в конце, если останется время (FR-RM-59, FR-RM-60). В спецификации первой версии не входят.

| Метод | HTTP | Правило |
| --- | --- | --- |
| Пакетные операции | `POST /v1/{справочник}/batch` | Несколько записей одного справочника; запрос выполняется целиком или отклоняется целиком; на каждую запись своя ревизия |
