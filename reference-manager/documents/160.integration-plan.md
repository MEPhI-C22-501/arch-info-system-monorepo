## 2. Порядок реализации

```mermaid
flowchart LR
    M1["И-M1: хранилище, первая миграция, задание схемы, CI с реальными тестами"] --> M2["И-M2: телеметрия, спецификация по AIP, контракт учётных записей с Infra, устранение K-02, K-04, K-07..K-13"]
    M2 --> M3["И-M3: срез 1 выпущен: вход Keycloak, кадровые справочники, учётные записи, потребители, выгрузки, ETL"]
    M3 --> M4["И-M4: etag, NetworkPolicy"]
    M4 --> M5["И-M5: интерфейс отдельным компонентом, Core, minikube, проверка безопасности"]
    Q["Согласования: вопросы 2, 4, 6-9, 12, 13, 18-22"] -.-> M3
    Q -.-> M4
```

| Веха | Шаги | Выход |
| --- | --- | --- |
| И-M1 | Учётные записи хранилища; первая миграция по 120; цель Taskfile для изменений схемы; удаление сервиса из Compose; секреты из переменных окружения; workflow CI с реальными тестами | Хранилище и конвейер готовы к первому справочнику |
| И-M2 | Спецификация OpenAPI по AIP для справочников первой версии; экспорт телеметрии, `X-Request-Id`, `X-Trace-Id`; ограничения в конфигурацию; транспорт OTLP; согласование с Infra профиля, идентификатора связи, состояний и способа выдачи временного пароля | Контракт и наблюдаемость готовы, расхождения с требованиями закрыты, контракт учётных записей согласован |
| И-M3 | ADR-011; методы по описанию справочника; история как ревизии; проверка токена и ролей; кадровые справочники; создание и блокировка учётных записей; классификаторы; выгрузка; общий набор тестов; чтение из сред потребителей; задание ETL Reports | Первая версия по критериям 1-14 раздела 11 требований |
| И-M4 | NetworkPolicy | Исходящий трафик ограничен |
| И-M5 | Админ-панель на имитированных данных, стек интерфейса, интерфейс отдельным компонентом; потребности Core; манифесты и развёртывание в minikube; отчёт проверки безопасности; отложенные вопросы 3, 11, 13, 16 | Полный контур, приёмка по критерию 15 |

Админ-панель на имитированных данных от API не зависит и может выполняться параллельно с И-M1..И-M3.

### 4.3. Роли служебных входов на общем стенде

Проверка руководителя проекта 2026-11-23 получила от сервиса 403 для Planning System и Reports. 2026-11-24 причина воспроизведена на Keycloak и конвергенции Infra из корневого `compose.yaml` в отдельном проекте Compose. Токен каждого клиента получен по client credentials:

| Состояние тома Keycloak | `planning-service` | `reports-client` | `tracker-directory` | `qa-executor` |
| --- | --- | --- | --- | --- |
| Пустой том, одна конвергенция по текущему `desired.json` | `reference-hr-reader` | `reference-reader` | `reference-reader` | `reference-profile-reader` |
| Том создан конвергенцией до #194, затем текущая конвергенция | нет ролей | нет ролей | `reference-reader` | нет ролей |

Во втором случае у всех четырёх клиентов в токене есть аудитория `reference-manager`, поэтому сервис принимает токен и отвечает 403. `infra/scripts/keycloak_converge.py` назначает роли служебной учётной записи только при создании клиента (`if created and grants`). Это правило Infra записано в `infra/keycloak/migration.md`: конвергенция не восстанавливает отозванные назначения. Поэтому клиенты, созданные до #194, ролей не получают, а `tracker-directory`, созданный позже, получает. Проверка воспроизводит механизм, а не сам стенд руководителя проекта. Решение за Infra: пересоздать том Keycloak стенда или один раз выдать роли, вопрос задан в #163.

### 4.4. Потребитель без роли

Сервис отвечает такому потребителю 403 с перечнем ролей, которые дают нужный доступ, и пишет отказ в журнал строкой `access denied` с `sub`, `azp`, ролями токена, методом и путём (FR-RM-65, [130, раздел 5.10](130.api-contracts.md)). По ответу команда потребителя видит, какую роль просить, а Infra по журналу находит служебный вход без роли. Роль выдаёт Infra по заявке в задаче команды.

Изменение #194 (влито 2026-11-16 без проверки владельцами кода модуля) изменило код модуля: убрало роль новой учётной записи, перевело роли в роли клиента, добавило профили и пятую роль. 2026-11-24 изменения описаны (ADR-024, ADR-025), сломанный сценарий приёма и начальное наполнение стенда, которое падало без файла `profiles.sql`, исправлены.

## 5. Состав проектных ролей и грейдов

Владелец перечня - команда справочников, значения ведёт роль `reference-admin` (группа G-1). Planning System читает их по REST: `GET /v1/project_roles/` и `GET /v1/grades/` с `allowDeleted=true`, постранично, вместе с кадровыми справочниками не реже раза в час (INT-RM-05). Перечень первой версии - набор `deployments/seed/demo.sql`:

| Справочник | Код | Наименование | Порядок |
| --- | --- | --- | --- |
| `project_roles` | `developer` | Разработчик | - |
| `project_roles` | `qa-engineer` | Тестировщик | - |
| `project_roles` | `analyst` | Аналитик | - |
| `project_roles` | `project-manager` | Руководитель проекта | - |
| `project_roles` | `devops` | Инженер DevOps | - |
| `grades` | `junior` | Junior | 1 |
| `grades` | `middle` | Middle | 2 |
| `grades` | `senior` | Senior | 3 |
| `grades` | `lead` | Lead | 4 |

Правила пополнения и чтения:

- Новое значение команда, которой оно нужно, просит задачей с меткой `reference-manager`, администратор справочников заводит запись. Изменения редкие, отдельного расписания у них нет.
- Ключ значения у потребителя - `id`. Код и наименование могут измениться, `id` не меняется.
- Удалённое значение остаётся читаемым с `allowDeleted=true` и `is_deleted: true`, его `id` не переиспользуется.
- Если Planning System нужна роль или грейд, которых нет в перечне, она не заводит значение у себя, а просит его добавить. До добавления значение в планировании не используется.
- Если Planning System встретила `id`, которого нет в её копии, она читает запись `GET /v1/project_roles/{id}` или `GET /v1/grades/{id}`. Ответ 404 значит, что запись удалена окончательно, ссылка на неё показывается как неизвестная.

Перечень и правила переданы Planning System в #143, вопрос 2 закрывается после их подтверждения.
