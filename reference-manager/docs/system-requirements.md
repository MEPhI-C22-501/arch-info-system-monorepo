# Системные требования Reference Manager

## 1. Общая информация

### 1.1. Цель системы

Система должна предоставлять подсистемам ERP arch-info-system единый источник нормативно-справочной информации, в котором можно:

- вести справочники общих классификаторов: валюты, страны, единицы измерения, языки, статьи затрат и другие
- получать записи справочников по стабильным именам, которые не меняются со временем
- убирать запись, которая больше не используется, без разрыва ссылок, и возвращать её
- просматривать историю изменений каждой записи: кто, когда и что изменил
- выгружать содержимое справочника в файл для работы вне системы
- разграничивать доступ на чтение и на ведение записей

Каждый справочник - отдельный ресурс API со своим набором методов и отдельным хранилищем. API строится по принципам Google AIP (ресурсно-ориентированный дизайн, стандартные методы, фильтрация, постраничный вывод, мягкое удаление, ревизии). Решения приняты командой 2026-09-17 и 2026-09-27.

### 1.2. Границы системы

В состав системы входят:

- справочники первой версии, состав которых собран у команд-потребителей один раз (раздел 9.2), и их записи
- REST API: для каждого справочника пять стандартных методов, восстановление и чтение истории
- история изменений записей, отдельная для каждого справочника
- выгрузка записей справочника в файл `.xlsx`
- аутентификация и проверка прав по токену Keycloak
- веб-интерфейс администрирования внутри сервиса
- служебные точки проверки работоспособности и готовности, телеметрия OpenTelemetry

За границами системы остаются: бизнес-сущности любой подсистемы, мультиарендность, обмен событиями, загрузка записей из файла, предзаполнение справочников стандартными данными, создание справочников потребителями или через API, процесс заявок на справочники.

### 1.3. Идентификаторы требований

Функциональные требования нумеруются как FR-RM-NN, требования к интеграциям как INT-RM-NN, бизнес-правила как BR-RM-NN, нефункциональные как NFR-RM-NN. Номер закрепляется за требованием навсегда.

Отозваны и не переиспользуются: FR-RM-01, 02, 03, 04, 13, 15, 16, 17, 18, 19, 20 (смена модели хранения 2026-09-17), FR-RM-25, 26, 27 (мультиарендность отменена 2026-09-26), INT-RM-07, 08, 09, 10 (процесс заявок отменён 2026-09-27).

Состояний записи два: ACTIVE и DELETED (решение 2026-09-17). История изменений включена в границы 2026-09-26; с 2026-09-27 она ведётся для каждого справочника отдельно и хранит различия, а не снимки.

## 2. Термины

| Термин | Определение |
| --- | --- |
| НСИ | Нормативно-справочная информация. Данные, которые классифицируют или описывают бизнес-сущности, но сами бизнес-сущностями не являются. |
| Справочник | Именованный набор однотипных справочных записей, например валюты или страны. В API - коллекция ресурсов со своим путём, например `/v1/countries`. |
| Запись справочника | Одна справочная единица внутри справочника, например страна RU. В API - ресурс с именем вида `countries/RU`. |
| Имя записи | Имя ресурса по AIP-122: путь коллекции и идентификатор записи, например `currencies/EUR`. Стабильно, задаётся один раз. |
| Идентификатор записи | Последний сегмент имени, например `EUR`. Задаётся при создании, уникален в пределах справочника, включая удалённые записи, и не меняется. |
| Общие поля записи | Поля, одинаковые во всех справочниках: `name`, `display_name`, `state`, `etag`, `delete_time`. |
| Поля справочника | Типизированные поля, которые есть только у данного справочника, например числовой код валюты. |
| Состояние записи | ACTIVE или DELETED. Возвращается в поле `state`, только для чтения. |
| Удаление | Перевод записи в состояние DELETED: запись остаётся, получает `delete_time`, исчезает из списков по умолчанию, остаётся доступной по имени. Физического удаления нет. |
| Восстановление | Перевод удалённой записи обратно в ACTIVE методом `Undelete`. |
| Ревизия | Элемент истории изменений записи: кто, когда, какое действие, какие поля изменились и с какого значения на какое. Неизменяема. |
| История изменений | Ревизии записей справочника в обратном хронологическом порядке. Ведётся для каждого справочника отдельно. |
| Стандартные методы | List, Get, Create, Update, Delete по AIP-131..135. |
| Фильтр | Выражение отбора записей в параметре `filter` списка по AIP-160, например `state = ACTIVE AND display_name:"евро"`. |
| Выгрузка | Файл `.xlsx` с записями, отобранными теми же параметрами, что и список. |
| Уровни доступа | Операции над записями: create, read, update, execute, delete. Роль reader имеет read и execute, роль admin - все пять. |

## 3. Пользователи и роли

| Роль | Основные возможности |
| --- | --- |
| Администратор справочников (reference-admin) | Участник команды справочников. Создаёт, изменяет, удаляет и восстанавливает записи всех справочников, читает историю, выгружает. Уровни доступа: create, read, update, execute, delete. |
| Читатель (reference-reader) | Любой аутентифицированный пользователь или сервис ERP. Читает записи всех справочников и их историю, выгружает в файл. Уровни доступа: read, execute. |

Роли редактора нет: записи ведёт только команда справочников (2026-09-15). Мультиарендности нет: права роли действуют на все записи всех справочников (2026-09-26).

## 4. Функциональные требования

### 4.1. Справочники

- **FR-RM-33.** Состав справочников определяется командой справочников один раз по потребностям команд-потребителей (раздел 9.2) и реализуется в сервисе. Добавление справочника позже - новая версия сервиса: хранилище, ресурс API со своими методами, спецификация и тесты в одном изменении.
- **FR-RM-34.** Каждая запись любого справочника должна содержать общие поля: `name` (имя ресурса), `display_name` (наименование), `state` (состояние), `etag` (признак версии), `delete_time` (время удаления, заполнено только в состоянии DELETED). `name`, `state`, `etag`, `delete_time` доступны только для чтения.
- **FR-RM-35.** Поля справочника должны быть типизированы. Обязательность, диапазоны, уникальность и ссылки на записи других справочников проверяются при создании и изменении. Запись с недопустимыми значениями отклоняется ошибкой `INVALID_ARGUMENT` с перечнем полей и причин и не сохраняется.
- **FR-RM-36.** Состав полей справочника должен меняться только новой версией сервиса. Новое поле необязательно либо имеет значение по умолчанию. Поля не удаляются и не меняют тип.
- **FR-RM-37.** Каждый справочник должен иметь собственную коллекцию ресурсов `/v1/{справочник}` и пять стандартных методов: `List` (`GET /v1/countries`), `Get` (`GET /v1/countries/{id}`), `Create` (`POST /v1/countries`), `Update` (`PATCH /v1/countries/{id}`), `Delete` (`DELETE /v1/countries/{id}`), а также методы `Undelete` (`POST /v1/countries/{id}:undelete`) и чтения истории (`GET /v1/countries/{id}/revisions`). Единого пути для всех справочников нет.
- **FR-RM-38.** Через API справочники не должны создаваться, изменяться и удаляться. Перечень справочников и схема записи каждого описаны спецификацией OpenAPI; потребители и интерфейс администрирования узнают справочники из спецификации.

### 4.2. Записи справочника

- **FR-RM-05.** Пользователь с правом записи должен иметь возможность создать запись методом `Create`, указав идентификатор записи, `display_name` и поля справочника. Идентификатор уникален в пределах справочника, включая удалённые записи; повторный идентификатор отклоняется ошибкой `ALREADY_EXISTS`. Новая запись получает состояние ACTIVE.
- **FR-RM-06.** Метод `Get` должен возвращать запись по имени, включая записи в состоянии DELETED.
- **FR-RM-07.** Пользователь с правом записи должен иметь возможность частично изменить `display_name` и поля справочника методом `Update` с указанием изменяемых полей в `update_mask`. Попытка изменить `name`, `state`, `etag` или `delete_time` отклоняется ошибкой `INVALID_ARGUMENT`.
- **FR-RM-08.** Метод `List` должен поддерживать фильтр по AIP-160 (`filter`) по общим полям и полям справочника, сортировку (`order_by`) по `display_name` и полям справочника, постраничный вывод (`page_size`, `page_token`, `next_page_token`) и общее число записей (`total_size`). По умолчанию возвращаются только записи в состоянии ACTIVE; `show_deleted` включает удалённые.

### 4.3. Жизненный цикл записи

- **FR-RM-09.** Каждая запись должна находиться в одном из двух состояний: ACTIVE или DELETED. Состояние возвращается в поле `state` и не изменяется напрямую.
- **FR-RM-10.** Метод `Delete` должен переводить запись в состояние DELETED, заполнять `delete_time` и возвращать запись. Повторное удаление отклоняется ошибкой `FAILED_PRECONDITION`.
- **FR-RM-11.** Запись в состоянии DELETED не должна попадать в `List` без `show_deleted`. Она доступна методом `Get`. Изменение её полей отклоняется ошибкой `FAILED_PRECONDITION`, пока запись не восстановлена.
- **FR-RM-12.** Метод `Undelete` должен переводить удалённую запись в ACTIVE, очищать `delete_time` и возвращать запись. Восстановление неудалённой записи отклоняется ошибкой `FAILED_PRECONDITION`.
- **FR-RM-14.** Каждая операция записи, включая удаление и восстановление, должна менять `etag` записи и создавать ревизию в истории справочника.

### 4.4. Выгрузка в файл

- **FR-RM-40.** Пользователь с правом чтения должен иметь возможность получить отобранные записи справочника в виде файла `.xlsx`. Формат выбирается заголовком `Accept` в запросе `List`; отдельного метода выгрузки нет.
- **FR-RM-41.** Выгрузка должна применять те же `filter`, `order_by` и `show_deleted`, что и `List`, и охватывать весь отбор, а не одну страницу.
- **FR-RM-42.** Файл выгрузки должен содержать строку заголовков и по одной строке на запись: общие поля, включая имя, наименование и состояние, и поля справочника. Даты и время выводятся в согласованном формате.
- **FR-RM-43.** Объём одной выгрузки должен быть ограничен. При превышении предела сервис отвечает ошибкой `FAILED_PRECONDITION` с указанием предела.

### 4.5. Аутентификация и авторизация

- **FR-RM-21.** Каждый запрос к API должен нести Bearer-токен Keycloak. Сервис проверяет подпись, издателя, получателя и срок действия токена, иначе отвечает ошибкой `UNAUTHENTICATED`.
- **FR-RM-22.** Система должна читать роли `reference-reader` и `reference-admin` из claim токена. Уровни доступа: create, read, update, execute, delete. Читатель имеет read и execute: методы `List`, `Get`, чтение истории, выгрузка. Администратор имеет все уровни: дополнительно `Create`, `Update`, `Delete`, `Undelete`. Права действуют на все справочники и все записи.
- **FR-RM-23.** Права должны проверяться на сервере перед каждой операцией. Недостаточные права отвечают ошибкой `PERMISSION_DENIED`.
- **FR-RM-24.** Методы `Update`, `Delete` и `Undelete` должны принимать `etag` записи; несовпадение с текущим отклоняется ошибкой `ABORTED`. Ответы `Get` и `List` содержат `etag` каждой записи.

### 4.6. Разделение по арендаторам

Отозвано 2026-09-26. Мультиарендности нет, права ролей действуют на все записи всех справочников (FR-RM-22, BR-RM-13).

### 4.7. Интерфейс администрирования

- **FR-RM-28.** Сервис должен отдавать веб-интерфейс администрирования по пути `/admin/` из того же процесса и образа. Вход выполняется через Keycloak по протоколу OIDC Authorization Code с PKCE. Доступные действия определяются ролями токена, сервер проверяет права независимо от интерфейса.
- **FR-RM-29.** Интерфейс должен содержать список справочников из спецификации OpenAPI, таблицу записей с фильтром, сортировкой, показом удалённых и постраничным выводом, форму записи с полями по схеме справочника, действия удаления и восстановления с подтверждением, выгрузку в файл, историю изменений записи с различиями между ревизиями, отображение ошибок API с привязкой к полям.

### 4.8. Служебные точки

- **FR-RM-30.** `GET /health` должен отвечать кодом 200, пока процесс жив.
- **FR-RM-31.** `GET /ready` должен отвечать кодом 200, если хранилище доступно и его схема соответствует версии сервиса, иначе кодом 503.
- **FR-RM-32.** По флагу конфигурации сервис должен отдавать метрики в формате Prometheus на пути `/metrics`.

### 4.9. История изменений

- **FR-RM-44.** Каждая операция записи (создание, изменение, удаление, восстановление) должна вместе с изменением создавать ревизию: действие, актор, время, изменённые поля с прежними и новыми значениями. Ревизия создаётся в той же транзакции, что и изменение.
- **FR-RM-45.** История должна вестись для каждого справочника отдельно. Ревизии не изменяются и не удаляются.
- **FR-RM-46.** Пользователь с правом чтения должен получать историю записи методом `GET /v1/{справочник}/{id}/revisions`: ревизии от новой к старой, постранично, каждая с действием, актором, временем и списком изменений. Отдельная ревизия доступна по имени `{запись}/revisions/{ревизия}`.
- **FR-RM-47.** Пользователь с правом чтения должен получать запись в состоянии на заданную ревизию; сервис восстанавливает его по цепочке ревизий.

## 5. Требования к интеграциям

### 5.1. Общие правила обмена

- **INT-RM-01.** Потребители должны получать справочные данные только через REST API под префиксом `/v1`. Прямой доступ к хранилищу сервиса запрещён.
- **INT-RM-02.** Контракт обмена должен быть описан спецификацией OpenAPI, по одной коллекции и схеме записи на справочник, в соответствии с принципами Google AIP. Спецификация обновляется до реализации и проверяется контрактными тестами.
- **INT-RM-03.** Контракт должен оставаться обратно совместимым в пределах версии `/v1`: новый справочник появляется как новая коллекция, новое поле как необязательное. Потребитель не должен переделывать интеграцию при расширении состава справочников.
- **INT-RM-04.** Сервис не должен выполнять исходящих вызовов к другим модулям ERP и подписываться на их данные. Разрешены обращения к собственному хранилищу, к Keycloak за ключами проверки токенов и к коллектору OpenTelemetry.
- **INT-RM-05.** Сервис не должен публиковать события. Потребитель, которому нужна локальная копия справочника, перечитывает его по API и сам выбирает срок жизни кэша.
- **INT-RM-06.** Ошибки должны возвращаться в формате AIP-193 (`google.rpc.Status`): код, сообщение, статус и детали, включая `ErrorInfo`, `BadRequest` для ошибок полей и `RequestInfo` с идентификатором запроса.

### 5.2. Состав интеграций

| Система | Что получает от сервиса | Что передаёт сервису | Способ обмена | Режим | Критичность |
| --- | --- | --- | --- | --- | --- |
| Keycloak | - | Ключи проверки токенов и роли в токене пользователя | OIDC, JWKS | Чтение ключей | Критичная со среза защиты API |
| Хранилище (PostgreSQL) | - | Хранение справочников, записей и истории | Отдельная база сервиса | Чтение и запись | Критичная: без хранилища сервис не готов |
| Infra: Kubernetes и CI/CD | Образ сервиса и задание миграций схемы | Конфигурацию окружения, порядок запуска, проверки готовности | Конфигурация Infra | - | Критичная для развёртывания |
| Infra: коллектор OpenTelemetry | Трассы, метрики и журналы | - | OTLP | Запись | Средняя: недоступность коллектора не влияет на обработку запросов |
| Core | Справочные значения для форм и проверок | - | REST с токеном | Чтение | Высокая |
| Task Tracker | Справочные значения для полей задач | - | REST с токеном | Чтение | Средняя, зависит от согласования владельца статусов и приоритетов |
| Planning System | Валюты, единицы измерения, типы финансирования, статьи затрат, проектные роли, грейды, языки, налоговые категории | - | REST с токеном | Чтение | Высокая: без классификаторов не считаются бюджет и потребность в людях |
| Reports | Классификаторы для разрезов отчётов, в том числе компетенции | - | REST с токеном, кэш на стороне отчётов | Чтение | Высокая: без них невозможны разрезы отчётов |
| Потребители выгрузок | Файл `.xlsx` с записями справочника | Параметры отбора | REST с токеном, заголовок `Accept` | Чтение | Средняя |

Planning System в своих документах рассчитывает получать классификаторы событиями. Сервис событий не публикует (2026-09-14); ожидание нужно согласовать.

### 5.3. Состав справочников

Перечень справочников собирается у команд-потребителей один раз перед реализацией и фиксируется в разделе 9.2. Процесса заявок нет (2026-09-27): потребители не создают справочники и не подают запросы через API или трекер; новый справочник появляется новой версией сервиса по решению команды справочников.

## 6. Основные бизнес-правила

- **BR-RM-01.** Один справочник равен одной коллекции ресурсов со своим хранилищем и своим набором методов.
- **BR-RM-02.** Имя записи задаётся один раз и никогда не меняется.
- **BR-RM-03.** Идентификатор удалённой записи остаётся занятым. Повторно создать запись с тем же идентификатором нельзя, нужно восстановить существующую.
- **BR-RM-04.** Физического удаления записей нет.
- **BR-RM-05.** Запись находится в одном из двух состояний: ACTIVE или DELETED. Промежуточных состояний нет.
- **BR-RM-06.** Поля справочника только добавляются. Удаление поля или смена его типа несовместимы с контрактом API.
- **BR-RM-07.** Справочник не удаляется после ввода в эксплуатацию. Ненужные записи удаляются по BR-RM-05.
- **BR-RM-08.** Сервис хранит только НСИ. Бизнес-сущности других подсистем, например сотрудники, проекты, задачи и календари рабочего времени, в нём не хранятся.
- **BR-RM-09.** Сервис не выполняет исходящих вызовов к другим модулям ERP.
- **BR-RM-10.** Каждая операция записи выполняется в одной транзакции вместе с созданием ревизии и меняет `etag` записи.
- **BR-RM-11.** Потребители получают данные только через REST API.
- **BR-RM-12.** Каждая операция записи оставляет ревизию в истории своего справочника. Ревизии не изменяются и не удаляются.
- **BR-RM-13.** Права ролей действуют на все справочники и все записи. Ограничений по организации или отдельному справочнику нет.
- **BR-RM-14.** Состав справочников определяет команда справочников; потребители справочники не создают.

## 7. Пользовательские сценарии

### 7.1. Добавление справочника

1. Команда справочников уточняет у команды-потребителя состав полей и начальные данные справочника из перечня 9.2.
2. Разработчик добавляет хранилище справочника, его коллекцию и методы API, схему записи в спецификации и подключает справочник к общему набору тестов.
3. Изменение проходит ревью, вливается и развёртывается новой версией сервиса.
4. Администратор наполняет справочник записями через интерфейс администрирования или API.
5. Потребители читают данные по API.

### 7.2. Ведение записей

1. Администратор открывает справочник в интерфейсе администрирования.
2. Администратор создаёт запись, задавая идентификатор, наименование и поля справочника.
3. Система проверяет поля и сохраняет запись в состоянии ACTIVE вместе с ревизией создания.
4. При ошибке система показывает перечень полей и причины отклонения, запись не сохраняется.

### 7.3. Удаление и восстановление записи

1. Администратор удаляет запись, которая больше не нужна или создана по ошибке.
2. Система переводит запись в состояние DELETED, заполняет `delete_time`, создаёт ревизию и возвращает запись.
3. Запись исчезает из списков по умолчанию, её идентификатор остаётся занятым, ссылки подсистем по имени продолжают работать.
4. При необходимости администратор восстанавливает запись методом `Undelete`.

### 7.4. Выгрузка справочника в файл

1. Пользователь отбирает записи фильтром и запрашивает результат в формате `.xlsx`.
2. Система проверяет объём отбора.
3. При превышении предела система отвечает отказом и предлагает сузить отбор.
4. При допустимом объёме система формирует файл со строкой заголовков и строками записей и отдаёт его пользователю.

### 7.5. Просмотр истории записи

1. Пользователь открывает запись и запрашивает её ревизии.
2. Система возвращает ревизии от новой к старой: действие, кто и когда, изменённые поля с прежними и новыми значениями.
3. При необходимости пользователь запрашивает запись в состоянии на выбранную ревизию.

## 8. Требования к интерфейсу

### 8.1. Список справочников

Страница должна содержать перечень справочников сервиса с кодом и названием и переход к записям выбранного справочника.

### 8.2. Таблица записей справочника

Страница должна содержать таблицу записей с общими полями и полями справочника, строку фильтра, сортировку, флаг показа удалённых записей, постраничный вывод, действие создания записи, действие выгрузки отобранных записей в файл и переход к форме записи.

### 8.3. Форма записи

Страница должна содержать поля записи, построенные по схеме справочника из спецификации OpenAPI, сведения о состоянии и времени удаления, действия сохранения, удаления и восстановления с подтверждением, отображение ошибок API с привязкой к полям, историю изменений записи: ревизии с действием, актором, временем и различиями.

## 9. Требования к данным

### 9.1. Состав хранимых данных

| Сущность | Основные данные и связи |
| --- | --- |
| Справочник | Отдельное хранилище записей и отдельное хранилище истории. Состав полей задаётся схемой справочника. |

## 10. Нефункциональные требования

### 10.1. Архитектурные ограничения

- **NFR-RM-01.** Сервис должен принимать только входящие вызовы. Исходящие соединения ограничены собственным хранилищем, коллектором OpenTelemetry и Keycloak.
- **NFR-RM-02.** Сервис должен хранить только НСИ: справочники, их записи и историю изменений.
- **NFR-RM-03.** К хранилищу сервиса должен обращаться только сам сервис.
- **NFR-RM-04.** Физическое удаление данных не должно реализовываться.
- **NFR-RM-05.** Имя записи должно быть неизменяемо после создания. Идентификатор удалённой записи остаётся занятым.
- **NFR-RM-06.** Контракт API должен быть обратно совместим в пределах мажорной версии `/v1`. Несовместимые изменения выпускаются как `/v2`.
- **NFR-RM-07.** Все операции записи должны выполняться сервисным слоем в одной транзакции вместе с созданием ревизии.
- **NFR-RM-08.** Приложение не должно хранить состояния между запросами, кроме кэша ключей проверки токенов. Допускается работа нескольких экземпляров одновременно.
- **NFR-RM-39.** Добавление справочника или поля должно быть обратно совместимым изменением API: новая коллекция и необязательные поля.
- **NFR-RM-40.** Методы всех справочников должны вести себя одинаково: те же коды ошибок, формат ошибок, параметры списка. Отличия справочников ограничены составом полей и фильтров по ним.

### 10.2. Контракт API

- **NFR-RM-09.** API должен следовать принципам Google AIP: ресурсно-ориентированный дизайн (AIP-121, 122), стандартные методы (AIP-131..135), кастомные методы (AIP-136), стандартные поля (AIP-148), `etag` (AIP-154), постраничный вывод (AIP-158), фильтрация (AIP-160), ревизии (AIP-162), мягкое удаление (AIP-164), ошибки (AIP-193). Формат `application/json`, UTF-8, время в RFC 3339 UTC, префикс `/v1`.
- **NFR-RM-10.** Частичное изменение должно выполняться методом `Update` (`PATCH`) с `update_mask`.
- **NFR-RM-11.** Ошибки должны возвращаться в формате AIP-193 с `ErrorInfo`, `BadRequest` для ошибок полей и `RequestInfo` с идентификаторами запроса и трассы.
- **NFR-RM-12.** Контракт должен быть описан спецификацией OpenAPI, обновляться до реализации и проверяться контрактными тестами.
- **NFR-RM-13.** Каждый ответ должен содержать заголовки `X-Request-Id` и `X-Trace-Id`. Входящий заголовок `traceparent` продолжает трассу вызывающего.

### 10.3. Данные

- **NFR-RM-14.** Идентификатор записи задаётся создателем и должен соответствовать формату, заданному схемой справочника; для стандартных классификаторов это код стандарта.
- **NFR-RM-15.** Размер тела запроса не должен превышать 1 МБ, `page_size` не должен превышать 200 при значении по умолчанию 50.
- **NFR-RM-16.** Учётная запись сервиса в хранилище не должна иметь прав на изменение схемы и физическое удаление; ревизии для неё доступны только на добавление и чтение.
- **NFR-RM-17.** Каждое изменение схемы хранилища должно быть обратимо, проверяться в CI и быть совместимым с предыдущей версией сервиса.
- **NFR-RM-42.** Одна выгрузка не должна превышать 50 000 записей. Предельное значение задаётся конфигурацией.
- **NFR-RM-46.** Ведение истории не должно замедлять операции над записями сверх 10 процентов; чтение истории записи должно выполняться по индексу.

### 10.4. Производительность и доступность

- **NFR-RM-18.** Время отклика чтения не должно превышать 100 мс для 95 процентов запросов при нагрузке 100 запросов в секунду. Время отклика записи не должно превышать 300 мс.
- **NFR-RM-19.** Доступность на стенде должна составлять 99,5 процента. Целевое значение согласуется с командой Infra.
- **NFR-RM-20.** Списки должны возвращать общее число записей. Запросы списков и чтения по имени должны покрываться индексами.
- **NFR-RM-43.** Выгрузка предельного объёма должна формироваться не дольше 60 секунд и не должна удерживать соединение с хранилищем на всё это время.

### 10.5. Совместимость выгрузок

- **NFR-RM-44.** Файл выгрузки должен открываться в актуальных версиях Microsoft Excel и совместимых табличных редакторах без предупреждений о повреждении.
- **NFR-RM-45.** Идентификаторы и коды в выгрузке должны сохраняться как текст.

### 10.6. Эксплуатация

- **NFR-RM-21.** Изменения схемы хранилища должно применять отдельное задание до запуска новой версии сервиса: локально цель Taskfile, в Kubernetes объект Job.
- **NFR-RM-22.** Конфигурация должна читаться из каталога файлов YAML или переменных окружения без пересборки. Секреты не хранятся в репозитории.
- **NFR-RM-23.** Остановка должна быть корректной: текущие запросы завершаются, соединения и экспортёры телеметрии закрываются с таймаутом.
- **NFR-RM-24.** Один образ должен содержать API и интерфейс администрирования. Версия сервиса передаётся в бинарник при сборке.

### 10.7. Наблюдаемость

- **NFR-RM-25.** Трассы, метрики и журналы должны собираться через OpenTelemetry и отправляться по протоколу OTLP в коллектор. Ресурс несёт атрибуты `service.name`, `service.version`, `service.instance.id` и `deployment.environment`.
- **NFR-RM-26.** Трассироваться должны каждый запрос HTTP, каждый запрос к хранилищу без значений параметров и операции сервисного слоя.
- **NFR-RM-27.** Метрики должны включать показатели HTTP по семантическим соглашениям OpenTelemetry, состояние пула соединений, показатели среды выполнения, счётчики операций записи по справочникам, число записей по состояниям и число выгрузок.
- **NFR-RM-28.** Журналы должны быть структурированными с полями `trace_id`, `span_id`, `request_id` и `actor_id`. Токены, пароли и тела запросов в журналы не пишутся.
- **NFR-RM-29.** Недоступность коллектора не должна замедлять и отклонять запросы.

### 10.8. Безопасность

- **NFR-RM-30.** До ввода аутентификации сервис должен быть доступен только из внутренней сети стенда.
- **NFR-RM-31.** Все запросы к хранилищу должны быть параметризованы.
- **NFR-RM-32.** В Kubernetes исходящий трафик должен быть ограничен сетевой политикой адресами из NFR-RM-01.
- **NFR-RM-33.** Ответы с ошибками не должны раскрывать внутренние детали.
- **NFR-RM-34.** Зависимости должны проверяться на известные уязвимости в CI.
- **NFR-RM-35.** Статика интерфейса должна отдаваться с заголовками `Content-Security-Policy` без inline-скриптов и `X-Frame-Options: DENY`. Интерфейс и API работают на одном origin.

### 10.9. Качество и тестирование

- **NFR-RM-36.** Код должен проходить линтер репозитория без предупреждений.
- **NFR-RM-37.** Доменная логика и сервисный слой должны покрываться модульными тестами, хранилище интеграционными тестами, API контрактными тестами по спецификации. Покрытие доменной логики и хранилища не ниже 80 процентов строк.
- **NFR-RM-38.** Линтер и тесты должны проходить на каждом pull request. Исправление дефекта сопровождается регрессионным тестом.
- **NFR-RM-41.** Общий набор тестов стандартных методов должен выполняться для каждого справочника. Новый справочник подключается к набору без копирования тестов.

## 11. Критерии приёмки первой версии

1. Справочники первой версии из раздела 9.2 со статусом "подтверждено" заведены, каждый со своей коллекцией и методами.
2. Для любого справочника работают пять стандартных методов, `Undelete` и чтение истории с одинаковыми кодами и форматом ошибок.
3. Запись с недопустимым значением поля отклоняется ошибкой `INVALID_ARGUMENT` с перечнем полей и не сохраняется.
4. Повторный идентификатор записи отклоняется, в том числе если запись с таким идентификатором удалена.
5. Удаление переводит запись в DELETED и убирает её из списков по умолчанию, чтение по имени сохраняется; восстановление возвращает ACTIVE.
6. `List` поддерживает `filter`, `order_by`, `page_size`, `page_token`, `show_deleted` и возвращает `total_size`.
7. Каждая операция записи создаёт ревизию; история записи читается через `revisions` и содержит действие, актора, время и изменения.
8. Отобранные записи выгружаются в `.xlsx`, файл открывается в Excel, идентификаторы сохранены как текст.
9. `/ready` отвечает кодом 503, пока хранилище недоступно или его схема не соответствует версии сервиса.
10. Трассы, метрики и журналы поступают в коллектор OpenTelemetry.

## 12. Вопросы, требующие согласования

1. Владелец справочников статусов задач, приоритетов задач и серьёзности дефектов: Reference Manager или Task Tracker.
2. Состав значений проектных ролей и грейдов для Planning System.
3. Нужна ли потребителям инкрементальная выдача изменившихся записей и каким механизмом.
4. Нужны ли Reports компетенции отдельным справочником и каков состав их значений.
5. Снят 2026-09-26: мультиарендности нет.
6. Состав ролей Keycloak для сервиса и их соответствие правам.
7. Допустимо ли обращение сервиса к Keycloak за ключами проверки токенов или ключ передаётся через конфигурацию.
8. Транспорт OTLP на стенде и адрес коллектора.
9. Целевые показатели доступности и производительности со стороны команды Infra.

## 13. Предлагаемые границы первой версии

В первую версию рекомендуется включить:

- справочники валют и стран как образцы, затем остальные подтверждённые из раздела 9.2
- пять стандартных методов, `Undelete` и историю на каждый справочник, общий набор тестов
- проверку значений полей с ответом по полям
- два состояния записи, удаление и восстановление
- `List` с фильтром, сортировкой, постраничным выводом и показом удалённых
- выгрузку отобранных записей в файл `.xlsx`
- хранилище и задание изменений схемы
- служебные точки `/health` и `/ready`, телеметрию OpenTelemetry

Во вторую очередь предлагается защита API: аутентификация Keycloak, роли, `etag` в операциях записи. В третью очередь интерфейс администрирования внутри сервиса. Инкрементальная выдача изменений, загрузка из файла и локализованные наименования рассматриваются после подтверждения потребности.
