## ADR-001 Отдельное хранилище и отдельные методы на каждый справочник

- **Статус:** принято 2026-09-17, уточнено 2026-09-27.
- **Контекст:** первая модель хранила все справочники в одной таблице элементов с JSON-атрибутами и общей ручкой `/{catalog}`; проверка данных выполнялась приложением, ссылки между справочниками и типы полей не контролировались хранилищем.
- **Решение:** каждый справочник - отдельная коллекция API со своим путём (`/v1/countries`), своим хранилищем с типизированными полями и ограничениями и своим набором методов; общей ручки для всех справочников нет.
- **Последствия:** плюс - проверка данных средствами хранилища, явный контракт на каждый справочник, схема записи в спецификации; минус - новая версия сервиса на каждый справочник. Связано с FR-RM-33..38, NFR-RM-39, NFR-RM-40.

## ADR-002 Мягкое удаление и два состояния записи

- **Статус:** принято 2026-09-14, уточнено 2026-09-17 и 2026-09-27.
- **Контекст:** на справочные значения ссылаются документы всех подсистем; физическое удаление ломает ссылки, третье состояние INACTIVE дублировало удаление.
- **Решение:** `Delete` по AIP-164: состояние DELETED, `delete_time`, запись остаётся доступной по имени и восстанавливается `Undelete`; идентификатор удалённой записи остаётся занятым; состояний два; учётная запись сервиса без прав на удаление.
- **Последствия:** плюс - ссылки не ломаются, ошибочное удаление обратимо; минус - хранилище растёт только вверх, потребители обязаны понимать `state: DELETED`. Связано с BR-RM-02..05, NFR-RM-04, NFR-RM-16.

## ADR-003 Только входящие вызовы, без событий

- **Статус:** принято 2026-09-14.
- **Контекст:** команда не планирует взаимодействовать с другими модулями; шина событий добавила бы исходящие зависимости и вторую модель согласованности.
- **Решение:** сервис не публикует и не потребляет события, не вызывает другие модули; исходящие соединения только к хранилищу, коллектору OpenTelemetry и Keycloak. Потребители перечитывают данные по API.
- **Последствия:** плюс - самый простой и доступный компонент ERP; минус - потребители узнают об изменениях с задержкой кэша, ожидание Planning System не выполнено. Связано с BR-RM-09, INT-RM-04, INT-RM-05.

## ADR-005 OpenTelemetry для всей телеметрии

- **Статус:** принято 2026-09-14.
- **Контекст:** Infra собирает телеметрию всех подсистем в общем формате.
- **Решение:** трассы, метрики и журналы через OpenTelemetry с экспортом OTLP; журналы в stdout форматом и уровнем из конфигурации; каждый ответ несёт `X-Request-Id` и `X-Trace-Id`; отказ коллектора не влияет на запросы.
- **Последствия:** плюс - один протокол, выбор бэкенда за Infra; минус - транспорт OTLP не согласован (вопрос 8). Связано с NFR-RM-13, NFR-RM-25..29.

## ADR-006 Интерфейс администрирования внутри сервиса

- **Статус:** принято 2026-09-14.
- **Контекст:** отдельный контейнер со статикой означал бы второй образ, второй релиз и CORS.
- **Решение:** статика встраивается в бинарник и отдаётся тем же процессом по `/admin/`; один origin с API; стек фронтенда - отдельный ADR перед срезом 3.
- **Последствия:** плюс - один артефакт и одна версия; минус - релиз интерфейса совпадает с релизом сервиса. Связано с FR-RM-28, NFR-RM-24, NFR-RM-35.

## ADR-007 Изменения схемы хранилища отдельным заданием

- **Статус:** принято 2026-09-14; в Compose ещё не выполнено (K-04).
- **Контекст:** сервис изменений схемы в Compose не соответствует Kubernetes, где схему обновляет Job перед Deployment.
- **Решение:** изменения схемы применяет задание до запуска приложения; приложение в проверке готовности сравнивает версию схемы с ожидаемой; учётная запись сервиса без прав на схему.
- **Последствия:** плюс - одинаковый порядок на стенде и в кластере; минус - локальный запуск требует отдельного шага. Связано с NFR-RM-16, 17, 21, FR-RM-31.

## ADR-008 Выгрузка `.xlsx` через заголовок `Accept` на методе List

- **Статус:** принято 2026-09-17; подтверждение против `:export` - вопрос 13.
- **Контекст:** потребителям и администраторам нужна выгрузка отобранных записей; отдельный метод увеличил бы набор методов справочника.
- **Решение:** `List` с `Accept` для `.xlsx` возвращает файл по тем же `filter`, `order_by`, `show_deleted`; предел объёма в конфигурации; идентификаторы как текст.
- **Последствия:** плюс - параметры отбора едины; минус - согласование содержимого нестандартно для части клиентов, AIP-136 предлагает кастомный метод. Связано с FR-RM-40..43, NFR-RM-42..45.

## ADR-010 Контракт прежде кода: OpenAPI и генерация из спецификации

- **Статус:** принято; генерация реализована в `main` (`task generate`).
- **Контекст:** потребители и интерфейс интегрируются по контракту; ручное поддержание обработчиков и спецификации расходится.
- **Решение:** спецификация OpenAPI - источник истины; серверные интерфейсы и модели генерируются из неё; контрактные тесты проверяют ответы; совместимость `/v1` проверяется сравнением спецификаций в CI.
- **Последствия:** плюс - спецификация не расходится с кодом; минус - зависимость от генератора; текущая спецификация не по AIP (K-10). Связано с NFR-RM-12, INT-RM-02, INT-RM-03.

## ADR-011 Способ переиспользования кода методов между справочниками

- **Статус:** предложено; решение до начала реализации среза 1 (вопрос 12).
- **Контекст:** NFR-RM-40 требует одинакового поведения методов всех справочников, NFR-RM-41 - общего набора тестов без копирования; при этом у каждого справочника свои пути и своя схема записи.
- **Предлагаемое решение:** обобщённая логика операций, параметризованная описанием справочника (схема записи, поля, фильтры), и тонкие адаптеры на каждую коллекцию; генерация адаптеров - при появлении третьего справочника, если они окажутся однообразными.
- **Последствия при принятии:** плюс - один путь исполнения для всех справочников; минус - обобщённый код сложнее читать.

## ADR-014 Авторизация: две роли, уровни CRUXD, без арендаторов

- **Статус:** принято 2026-09-26.
- **Контекст:** решался вопрос разграничения прав при интеграции с Keycloak; мультиарендность признана ненужной.
- **Решение:** уровни create, read, update, execute, delete; роль `reader` - read и execute, роль `admin` - все пять; права на все справочники и записи; проверка роли против уровня операции на сервере.
- **Последствия:** плюс - одна проверка на операцию, нет фильтров по строкам; минус - при появлении второй организации потребуется отдельное решение. Связано с FR-RM-22, FR-RM-23, BR-RM-13.

## ADR-015 API по принципам Google AIP

- **Статус:** принято 2026-09-27.
- **Контекст:** нужны единые правила формы API для всех справочников; собственные соглашения (merge patch, `limit`/`offset`, RFC 9457, `If-Match`) требовали отдельных решений на каждый вопрос.
- **Решение:** ресурсно-ориентированный дизайн: коллекция на справочник, имена ресурсов, стандартные методы List, Get, Create, Update, Delete, кастомные Undelete и ListRevisions, `filter` по AIP-160, `order_by`, `page_size`/`page_token`, `total_size`, `show_deleted`, `update_mask`, `etag` с ABORTED, ошибки `google.rpc.Status`. Отклонения зафиксированы: в записи нет `create_time`/`update_time` (они в ревизиях), ревизия несёт различия, выгрузка через `Accept`.
- **Последствия:** плюс - предсказуемая форма каждого нового метода, готовые правила для потребителей; минус - спецификацию и сгенерированный код нужно переписать (K-10), команда должна знать AIP. Связано с NFR-RM-09..11, FR-RM-05..12, 24.

## ADR-016 История как ревизии с различиями, отдельно на справочник

- **Статус:** принято 2026-09-27; заменяет ADR-013.
- **Контекст:** нужна история изменений; рассматривались одна таблица со всеми версиями записи и актуальная таблица плюс история. Команда выбрала вторую и уточнила: история на каждый справочник, хранятся различия, а не снимки.
- **Решение:** для каждого справочника отдельная история; каждая операция записи в той же транзакции создаёт ревизию: действие, актор, время, идентификатор запроса, список изменённых полей с прежними и новыми значениями; ревизии неизменяемы; чтение через `revisions` записи; состояние на ревизию восстанавливается применением различий.
- **Отклонённый вариант:** одна таблица со всеми версиями записи. Ломает уникальность идентификатора среди актуальных записей и ссылки между справочниками, каждое чтение превращается в выбор последней версии поверх фильтров.
- **Последствия:** плюс - таблица записей без служебных столбцов времени и автора, история изолирована по справочникам, различия компактны; минус - состояние на ревизию требует восстановления по цепочке, при добавлении поля старые ревизии его не содержат. Связано с FR-RM-44..47, BR-RM-12, NFR-RM-46.
