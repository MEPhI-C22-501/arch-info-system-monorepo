# 145 - Архитектурные решения Reference Manager

**Блок H.** Редакция 1.0 от 2026-09-25, к ревью команды.
Основания: решения команды 2026-09-14, 2026-09-15, 2026-09-17; [Системные требования](../system-requirements.md); [конституция](../../.specify/memory/constitution.md); текущий код `main`.

Шаблон: контекст -> решение -> последствия. Статусы: принято, предложено. Последующие ADR хранятся в `.specify/memory/adr/` по конституции; здесь сводный реестр.

## ADR-001 Таблица на справочник вместо обобщённой модели

- **Статус:** принято 2026-09-17.
- **Контекст:** первая модель хранила все справочники в одной таблице элементов с JSON-атрибутами и версионируемой JSON Schema. Проверка данных при этом выполнялась приложением, ссылки между справочниками и типы столбцов не контролировались базой.
- **Решение:** каждый справочник - отдельная таблица с общими столбцами и типизированными столбцами справочника; ограничения NOT NULL, CHECK, UNIQUE, FOREIGN KEY задаются в миграции; пять одинаковых обработчиков на справочник; справочники не создаются через API.
- **Последствия:** плюс - проверка данных средствами базы, простой предсказуемый сервис, схема записи в OpenAPI на каждый справочник; минус - миграция и код на каждый новый справочник, добавление справочника требует pull request и развёртывания. Отозваны FR-RM-01..04, 13, 15..20, 27. Конституция, принцип IV, требует поправки (K-05). Связано с NFR-RM-39, NFR-RM-40, вопросом 12.

## ADR-002 Мягкое удаление и два состояния записи

- **Статус:** принято 2026-09-14, уточнено 2026-09-17.
- **Контекст:** на справочные значения ссылаются документы всех подсистем; физическое удаление ломает ссылки, а третье состояние INACTIVE дублировало смысл удаления.
- **Решение:** `DELETE` ставит `deleted_at`, запись остаётся доступной по `id` и `code`, код остаётся занятым, возврат в работу через `PATCH {"deleted_at": null}`; состояний два - ACTIVE и DELETED; `status` вычисляется; роль приложения не имеет `DELETE`.
- **Последствия:** плюс - ссылки не ломаются никогда, ошибочное удаление обратимо; минус - таблицы растут только вверх, потребители обязаны понимать `status: DELETED`. Связано с BR-RM-02..05, NFR-RM-04, NFR-RM-16.

## ADR-003 Только входящие вызовы, без событий

- **Статус:** принято 2026-09-14.
- **Контекст:** команда не планирует взаимодействовать с другими модулями; Kafka и outbox добавили бы исходящие зависимости и вторую модель согласованности.
- **Решение:** сервис не публикует и не потребляет события, не вызывает другие модули; исходящие соединения только к PostgreSQL, коллектору OpenTelemetry и Keycloak. Потребители перечитывают данные по API.
- **Последствия:** плюс - самый простой и доступный компонент ERP, нет шины и её эксплуатации; минус - потребители узнают об изменениях с задержкой кэша, ожидание Planning System о событиях не выполнено, инкрементальная выдача остаётся открытым вопросом 3. Связано с BR-RM-09, INT-RM-04, INT-RM-05.

## ADR-004 Без журнала аудита с историей значений

- **Статус:** принято 2026-09-14.
- **Контекст:** история значений требовала отдельной таблицы, роста объёма и API истории; потребность не заявлена.
- **Решение:** хранится только текущее состояние с `version`, `updated_at`, `updated_by`; факты изменений видны в трассах и журналах.
- **Последствия:** плюс - меньше таблиц и кода; минус - ответить "каким было значение месяц назад" нельзя; при появлении требования - отдельный срез и новый ADR.

## ADR-005 OpenTelemetry для всей телеметрии

- **Статус:** принято 2026-09-14.
- **Контекст:** Infra собирает телеметрию всех подсистем в общем формате; отдельные интеграции с Prometheus, Jaeger и файлами журналов создавали бы три протокола.
- **Решение:** трассы, метрики и журналы через OpenTelemetry SDK для Go с экспортом OTLP в коллектор; журналы также пишутся обработчиками из `log.yaml`; каждый ответ несёт `X-Request-Id` и `X-Trace-Id`; при отказе коллектора запросы не страдают.
- **Последствия:** плюс - один SDK, один протокол, выбор бэкенда за Infra; минус - зависимость от SDK и коллектора, транспорт OTLP ещё не согласован (вопрос 8). Связано с NFR-RM-13, NFR-RM-25..29.

## ADR-006 Интерфейс администрирования внутри бинарника сервиса

- **Статус:** принято 2026-09-14.
- **Контекст:** отдельный контейнер со статикой означал бы второй образ, второй релиз, CORS и отдельную выкладку.
- **Решение:** статика встраивается в бинарник (`embed`) и отдаётся тем же процессом по `/admin/`; сборка статики в `task generate`; один origin с API; стек фронтенда - отдельный ADR перед срезом 3.
- **Последствия:** плюс - один артефакт и одна версия, без CORS; минус - релиз интерфейса совпадает с релизом сервиса, бинарник растёт. Связано с FR-RM-28, NFR-RM-24, NFR-RM-35.

## ADR-007 Миграции отдельным заданием

- **Статус:** принято 2026-09-14; в Compose ещё не выполнено (K-04).
- **Контекст:** сервис миграций в Compose с `depends_on` не соответствует Kubernetes, где схему обновляет Job перед Deployment.
- **Решение:** golang-migrate запускается заданием: цель Taskfile локально, Job в Kubernetes; приложение в `/ready` проверяет версию схемы; роль приложения без DDL.
- **Последствия:** плюс - одинаковый порядок на стенде и в кластере, приложение не запускается на отставшей схеме; минус - локальный запуск требует отдельного шага. Связано с NFR-RM-16, NFR-RM-17, NFR-RM-21, FR-RM-31.

## ADR-008 Выгрузка `.xlsx` через заголовок `Accept` на операции чтения

- **Статус:** принято 2026-09-17; подтверждение - вопрос 13.
- **Контекст:** потребителям и администраторам нужна выгрузка отобранных записей; отдельный путь `/export` стал бы шестой операцией справочника.
- **Решение:** `GET /{catalog}` с `Accept` для `.xlsx` возвращает файл по тем же фильтрам и сортировке; предел объёма в конфигурации; коды и идентификаторы как текст.
- **Последствия:** плюс - пять операций сохраняются, фильтры едины; минус - нестандартное для некоторых клиентов согласование содержимого, длительные ответы на большом отборе (NFR-RM-43). Связано с FR-RM-40..43, NFR-RM-42..45.

## ADR-009 `PATCH` как JSON Merge Patch и постраничное чтение `limit`/`offset`

- **Статус:** принято 2026-09-14.
- **Контекст:** полное `PUT` перезаписывало бы поля, которых клиент не читал; курсорная пагинация избыточна для справочников в единицы тысяч записей, а интерфейсу нужен `total`.
- **Решение:** частичное изменение по RFC 7386, неизменяемые поля отклоняются 422; списки с `limit`, `offset`, `total`; чтение по коду - фильтр `code=` на списке.
- **Последствия:** плюс - меньше трафика и случайных перезаписей, простые клиенты; минус - при появлении справочников на сотни тысяч записей потребуется курсор как дополнительный параметр. Связано с FR-RM-06..08, NFR-RM-10, NFR-RM-20.

## ADR-010 Контракт прежде кода: OpenAPI и генерация oapi-codegen

- **Статус:** принято; реализовано в `main` (`task generate`, `pkg/api/v1`).
- **Контекст:** потребители и интерфейс интегрируются по контракту; ручное поддержание обработчиков и спецификации расходится.
- **Решение:** спецификация в `api/openapi/v1/` с разбиением на файлы; серверные интерфейсы и модели генерируются oapi-codegen; обработчики реализуют сгенерированные интерфейсы; контрактные тесты проверяют ответы по спецификации; совместимость `/v1` проверяется сравнением спецификаций в CI.
- **Последствия:** плюс - спецификация не расходится с кодом, схема записи каждого справочника публикуется автоматически; минус - зависимость от генератора, путь спецификации отличается от требований (K-03). Связано с NFR-RM-12, INT-RM-02, INT-RM-03.

## ADR-011 Способ переиспользования пяти обработчиков между справочниками

- **Статус:** предложено; решение до начала реализации среза 1 (вопрос 12).
- **Контекст:** NFR-RM-40 требует одинакового поведения обработчиков всех справочников, NFR-RM-41 - общего набора тестов без копирования. Варианты: обобщённый код по описанию справочника (тип записи, список столбцов, фильтры) или генерация кода на этапе `task generate` из спецификации.
- **Предлагаемое решение:** обобщённый сервисный слой и репозиторий, параметризованные описанием справочника (Go generics по типу записи плюс метаданные столбцов), при этом сгенерированные oapi-codegen интерфейсы реализуются тонкими адаптерами на справочник. Генерация кода откладывается до появления третьего справочника, если адаптеры окажутся однообразными.
- **Последствия при принятии:** плюс - один путь исполнения для всех справочников, общий набор тестов подключает справочник описанием; минус - обобщённый код сложнее читать, ограничения столбцов дублируются между миграцией и описанием для предварительной проверки.

## ADR-012 Заявка на справочник как issue и один pull request

- **Статус:** принято 2026-09-15, порядок уточнён 2026-09-17.
- **Контекст:** самообслуживания нет; состав справочников собирается у команд вручную.
- **Решение:** заявка - issue по шаблону (код, назначение, столбцы с ограничениями, признак арендаторского справочника, начальные данные); проверка по BR-RM-08; выпуск одним pull request с миграцией, обработчиками, OpenAPI и тестами; закрытие заявки со ссылкой на схему.
- **Последствия:** плюс - прозрачная очередь и трассируемость, единый формат; минус - время от заявки до справочника включает ревью и развёртывание. Связано с INT-RM-07..10, FR-RM-33.
