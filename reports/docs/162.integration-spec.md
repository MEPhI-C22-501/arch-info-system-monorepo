## 2. Аналитический контур: способ ETL

**Назначение.** Наполнять DWH историей из четырёх источников с лагом не более 1 часа (NFR-15).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Пакетный ETL по REST по расписанию | Подходит для опубликованных REST-контрактов; реальная доступность проверяется отдельно; первичная загрузка и сверка тем же кодом; простая повторяемость | Лаг равен интервалу; REST трекера без общего snapshot; удаления не видны без сверки |
| B. Потоковый ETL только по событиям | Минимальный лаг; удаления приходят событием | У Reference Manager событий нет, у трекера не согласованы; нет первичной загрузки; потеря при простое дольше срока хранения топика |
| C. Файловые выгрузки с manifest | Большие объёмы, единый срез | У Planning System есть неизменяемая REST-партия; файловый обмен остальных источников не согласован |
| D. Гибрид: пакет по REST раз в час + события там, где они есть + ежесуточная сверка | Лаг по событиям минимален; пакет закрывает источники без событий и первичную загрузку; сверка исправляет пропуски | Два пути загрузки; нужна идемпотентность обоих |

**Выбор:** D. **Обоснование:** он позволяет проектировать NFR-15 без зависимости от несогласованной Kafka трекера; выполнение порога требует доступов, согласованного расписания и сквозного прогона; события улучшают лаг, но не обязательны. **Ожидаемый результат:** DWH отстаёт не больше чем на час; повтор пакета или события не меняет показатели; ежесуточная сверка находит расхождения меньше 1%. **Критерий:** T-NFR-04, T-NFR-05, T-27. Решение — [ADR-004](145.architecture-decisions.md), [ADR-007](145.architecture-decisions.md).

## 3. Оперативный контур: откуда читать

**Назначение.** Показывать текущее состояние с лагом в минуты, не нагружая источники и аналитический контур.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Read-replica БД источников | Минимальный лаг; буквальное прочтение постановки | Нарушает владение данными: Planning System прямо запрещает чтение чужой БД; Reports зависит от внутренней схемы чужих БД; Infra не планирует реплики чужих БД |
| B. Прямые REST-запросы к источникам при каждом открытии дашборда | Данные свежие | Нагрузка на источники растёт с числом пользователей; недоступность источника ломает дашборд; нарушает NFR-20 |
| C. Собственная оперативная витрина из событий и частого REST + её read-replica | Владение не нарушено; дашборды не зависят от доступности источника; есть read-replica и разделение чтения и записи | Лаг до 15 минут для трекера без Kafka; ещё один путь наполнения |

**Выбор:** C. **Обоснование:** сохраняет границы модулей; соответствие трактовке read-replica требует Q-REP-01 и не считается подтверждённым. **Ожидаемый результат:** оперативные дашборды строятся ≤ 3 с при любом состоянии источников; лаг — по NFR-04. **Критерий:** T-30, T-NFR-17. Решение — [ADR-002](145.architecture-decisions.md). **Открыто:** Q-REP-01 — подтверждение толкования преподавателем.

## 4. Task Tracker: REST или Kafka

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Только REST-опрос | Есть сейчас; простой | Лаг; удалённые элементы REST не возвращает; нагрузка опросом |
| B. Только Kafka | Малый лаг; tombstone удаления | Нет первичной загрузки; Kafka не в локальном релизе трекера |
| C. Kafka для изменений + REST для первичной загрузки и сверки | Предложен самим трекером (DEC-TT-02); закрывает недостатки обоих | Возможны дубли — нужна дедупликация |

**Выбор:** C, до принятия DEC-TT-02 — A с опросом каждые 60 секунд и ежесуточной сверкой удалений. **Ожидаемый результат:** после DEC-TT-02 лаг ≤ 5 минут, до — ≤ 15 минут. **Правила:** часы только из `TimeLogged`; `eventId` в одной транзакции с витриной.

## 5. Planning System: проекция и партия

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Только оперативная проекция | Свежие данные по проекту | Нет согласованного среза для истории; по проекту за раз |
| B. Только неизменяемая партия | Согласованный срез, manifest, повтор страниц | Лаг до часа для оперативного дашборда |
| C. Проекция для оперативного контура + партия для DWH | Каждый контур получает подходящую форму данных; так предлагает сам Planning System (INT-05, INT-08) | Два контракта |

**Выбор:** C. **Ожидаемый результат:** план-факт в DWH согласован внутри одной версии плана; оперативный дашборд показывает прогноз с лагом ≤ 5 минут. **Открыто:** D-05 — TTL 24 часа и ежечасное расписание вместо ежедневного предложения владельца; явные архивы/tombstone; D-07 — методика стоимости. Контракт строк: `entityType`, `entityId`, `data`, manifest `counts`, `schemaVersion=1.0.0`; детали — [130](130.api-contracts.md#5-входящие-контракты).

## 6. Reference Manager: способ получения справочников

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. События изменений | Малый лаг | Владелец отказался от событий, решение согласовано |
| B. `Get` по каждому сотруднику при формировании отчёта | Всегда свежие | Нагрузка, зависимость отчётов от доступности справочников |
| C. Полная выгрузка `List` с `allowDeleted=true`, `pageSize` ≤ 100, `pageToken`/`nextPageToken` раз в час в размерности SCD2 | Контракт владельца; история изменений в DWH | Лаг до часа |

**Выбор:** C по текущему контракту владельца. Кадровые API реализованы; `id` числовой, `is_deleted` и `revision` сохраняются. `username` не равен Keycloak `sub`; связь — Q-REP-16. **Результат:** изменения подразделения отражаются в отчётах с историей не позже чем через час.

## 7. QA System: события и REST

**Выбор:** события `dev.qa.*` для оперативного контура и фактов переходов + пять REST-ресурсов `/reports/{test-cases,test-plans,test-runs,test-results,defects}` с `updatedSince` раз в час для полноты. Альтернатива «только REST» отвергнута: теряются промежуточные переходы дефекта, а без них не считается reopened rate по периоду. **Результат:** результат кейса виден ≤ 2 минут; reopened rate считается по переходам.

## 8. Выгрузки: где хранить файл и как отдавать

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Файл в БД | Транзакционность | Рост БД и реплики |
| B. MinIO и предподписанная ссылка | Разгрузка сервиса | Ссылку можно переслать; права после выдачи не проверяются |
| C. MinIO и скачивание через API с проверкой прав | Права проверяются при каждом скачивании; ссылка без токена бесполезна | Трафик через сервис |

**Выбор:** C — [ADR-010](145.architecture-decisions.md). **Результат:** FR-EXP-04 выполняется, потерявший права пользователь получает `403`.

## 10. Стек контура загрузки и представления

### 10.1. Задание ETL

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Python 3.12 + psycopg, задания Job/CronJob | Транзакции PostgreSQL, простая контейнеризация, совпадает с моделью Infra | Проверки страниц, повторы, журнал и расписание принадлежат Reports | Выбран для пилота; общий стек — Q-REP-15 |
| Airflow | Оркестрация и интерфейс | Отдельная платформа и сопровождение Infra | Отложен |
| Kafka Connect | Удобен для поддерживаемых коннекторов | Не заменяет REST-партии и проверки manifest | Не выбран для первичного ETL |

Назначение P-01 — проверить путь HTTP → проверка владельческого контракта →
staging → атомарная загрузка → checkpoint. Критерии: 6 синтетических трудозатрат,
11,25 часа; повтор сохраняет 6 строк, исправление меняет существующую строку,
потерянная страница/поле/дубликат/ошибка SQL отклоняют всю загрузку и сохраняют
прежний checkpoint. В пилоте выполняются полные сканы REST; watermark хранится
для наблюдаемости, но ещё не используется как универсальный `updatedSince`.
Наблюдаемые версии справочников SCD2 и цельные суточные снимки уже реализованы;
целевая звезда и типизированные преобразования остальных фактов остаются следующей итерацией.
Решения — ADR-004/007, проверки — [пилоты](../pilots/README.md).

### 10.2. Инструмент отчётов

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Apache Superset | OAuth/OIDC, дашборды, серверный RLS | Отдельная БД метаданных; безопасность BI проверяется отдельно от API | Выбран для P-02 |
| Metabase | Простой старт | Ограничения бесплатного встраивания и разграничения | Отложен |
| Собственные графики | Полный контроль | Дополнительная разработка и повтор реализации BI | Не выбран для пилота |

P-02 подключается к SQL API Cube, а не прямо к DWH. Служебная SQL-учётная запись
BI доступна только внутри сети; роль Gamma видит только разрешённый dataset,
RLS сравнивает `user_id` с проверенным UUID `sub`. SQL Lab и выдача доступа к БД
участникам запрещены. Критерий приёмки: два участника видят 3,75 и 7,50 часа,
администратор — 11,25; смена роли, чужой фильтр и прямой запрос не обходят RLS.
Локальный браузерный прогон Superset с Keycloak выполнен: суммы совпали,
пользователи изолированы, SQL Lab запрещён, вход без роли отклонён.
[Протокол](../pilots/artifacts/bi-verification.json). Отзыв роли для нового входа и отказ по exp сеанса проверены локально.
Локальная ротация ключей проверена для API, Cube и Superset.
Мгновенный back-channel logout и общий стенд принимаются отдельно. Решение — ADR-005/012.

### 10.3. Движок куба

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| Cube Core | Меры, измерения, drill-down, предагрегации, SQL/REST | Дополнительный сервис и Cubestore; требуется нагрузочная проверка | Выбран для P-03 |
| Материализованные представления PostgreSQL | Меньше компонентов | Нет отдельного семантического API для BI | Резервный вариант |
| Mondrian / MDX | Классическая OLAP-модель | Другой протокол и больше интеграционных настроек | Не выбран |

Мера M-01, разрезы проект/пользователь/месяц, детализация до записи; дневная
предагрегация содержит пользовательское измерение, чтобы фильтр не терялся.
Критерий: совпадение 11,25 часа с эталоном, запрет чужих строк и p95 ≤ 3 с на
миллионе трудозатрат при 20 клиентах. Локальные unit-тесты фильтра не являются
этим замером. Решение — ADR-006/013; схема — [150](150.component-diagram.md),
ресурсы — [160](160.integration-plan.md), развёртывание — [165](165.deployment-diagram.md).


## 11. Локальная проверка куба

Нативный прогон Cube/PostgreSQL на синтетических данных подтвердил сумму,
пользовательский фильтр, SQL dataset для Superset, детализацию и физическую
предагрегацию. На миллионе строк: 20 клиентов, 100 запросов, прогретый кэш,
p95 0,0180 с. Версии, аппаратные параметры, точные хеши и ограничения —
[результат](../pilots/artifacts/cube-benchmark.json). Вход и RLS в самом
Superset проверены отдельно в контейнерах. Холодный режим, Cubestore и общий
стенд остаются открытыми; локальный кэш — memory одного процесса.


Эталон ETL Infra в `infra-local-stand` написан на Python и демонстрирует загрузку
в SQLite с checkpoint после строки. Reports использует тот же язык, но
PostgreSQL и checkpoint после всей проверенной партии: это необходимо для
атомарности manifest/staging. Поэтому совпадение языка не объявляет Q-REP-15
закрытым; гранулярность checkpoint и общий рабочий пример ещё согласуются.
