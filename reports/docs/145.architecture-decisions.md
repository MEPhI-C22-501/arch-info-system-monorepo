**ADR-001. Два контура: оперативный и аналитический**

- Контекст: постановка требует операционные отчёты на актуальных данных и аналитические — на истории через ETL и кубы. Vision описывал один контур (K-01). Требования контуров противоречат друг другу: оперативный — минуты лага и текущее состояние, аналитический — история, SCD2, тяжёлые агрегаты.
- Решение: два контура с разными хранилищами и путями наполнения ([020, раздел 2](020.system-context.md#2-два-контура)); каждый отчёт отнесён к контуру; R-03, R-04, R-08 имеют оба представления — «сейчас» и «за период».
- Последствия: (+) оперативные дашборды не ждут ETL, аналитика не мешает оперативным запросам; (+) соответствие постановке; (−) два пути наполнения и два места, где может разойтись число; (−) нужно объяснять пользователю, почему «сейчас» и «вчера» считаются по-разному — закрыто подписью контура в каталоге. Связь: NFR-04, NFR-15.

**ADR-002. Оперативный контур — собственная оперативная витрина и её read-replica**

- Контекст: замечания требуют строить оперативные отчёты «из read-реплики». Ни один источник реплику своей БД не предоставляет, а Planning System прямо пишет, что общая инфраструктура не даёт права читать чужую БД; vision Reports (FR-DAT-01) — то же. Источники дают оперативное чтение через REST и события.
- Решение: Reports ведёт собственную оперативную витрину `ops`, наполняемую событиями (QA сразу, Task Tracker после DEC-TT-02) и опросом REST раз в 5 минут. Для витрины поднимается потоковая read-replica PostgreSQL; оперативные дашборды и тяжёлые запросы читают реплику. Реплики БД источников отвергнуты ([162](162.integration-spec.md)).
- Последствия: (+) есть read-replica и разделение чтения и записи, как требует постановка; (+) не нарушается владение данными и не появляется зависимость от схем чужих БД; (−) лаг больше, чем у реплики источника: до 15 минут при опросе REST; (−) толкование «read-replica» требует подтверждения преподавателем — Q-REP-01. Если преподаватель потребует реплику БД источника, нужны согласие владельца, отдельная учётная запись только для чтения и план Infra. Связь: NFR-04, NFR-07.

**ADR-003. DWH на PostgreSQL, схема «звезда», SCD2**

- Контекст: объём NFR-03 — до 36 млн строк снимков в год; Infra поддерживает PostgreSQL, отдельного аналитического движка в стеке Infra нет; соседи используют PostgreSQL.
- Решение: DWH — схема `dwh` в БД Reports на PostgreSQL той мажорной версии, что в матрице Infra; «звезда» из [120](120.data-model.md); SCD2 для сотрудников, проектов, задач, эпиков; секционирование больших фактов по месяцу.
- Альтернативы: ClickHouse — быстрее на больших агрегатах, но ещё один сервис для Infra и нет транзакций для идемпотентной загрузки; DuckDB — нет многопользовательского доступа.
- Последствия: (+) одна СУБД для всех схем Reports, транзакционная загрузка, знакомый стек; (+) реплика — штатное средство; (−) на объёмах сильно больше NFR-03 агрегаты станут медленными — компенсируется предагрегациями ADR-006; (−) ClickHouse можно добавить позже как хранилище предагрегаций Cube без изменения модели. Связь: NFR-01, NFR-03.

**ADR-004. ETL — собственные задания на Python в CronJob, без отдельной ETL-платформы**

- Контекст: Infra прямо пишет, что ETL не требует отдельной платформы: код ETL принадлежит потребителю, Infra даёт Job и CronJob, расписание и доступы. Пример ETL у Infra должен совпадать по стеку с нашим (замечания, этап 2). Источники — REST с разной пагинацией и Kafka.
- Решение: задания ETL — Python 3.12: `httpx` для REST, `psycopg` для загрузки, SQL-трансформации из staging в `dwh`; по одному CronJob на источник. Потребитель Kafka — отдельный процесс того же образа (Deployment) на `confluent-kafka`. Общий код — библиотека `reports-etl` в модуле.
- Альтернативы: Apache Airflow — удобная оркестрация и интерфейс, но тяжёлый сервис, который Infra не планирует; dbt — хорош для трансформаций, но добавляет инструмент ради десятка SQL-моделей; Kafka Connect — не покрывает REST-источники и staging-проверки.
- Последствия: (+) минимум новых сервисов, совпадение с моделью Infra; (+) один язык с сервисом отчётов (ADR-011); (−) повторы, журнал пакетов и мониторинг делаем сами — это `etl.batch` и `etl.freshness`; (−) нет графического DAG — зависимости заданий простые и описаны в [155](155.sequence-diagrams.md). Связь: NFR-16, NFR-20, Q-REP-15.

**ADR-005. BI — Apache Superset**

- Контекст: нужны дашборды, drill-down, вход через Keycloak, фильтрация строк по правам, встраивание в веб-интерфейс.
- Решение: Apache Superset: OIDC через Keycloak, row-level security, встраивание дашбордов с гостевым токеном, подключение к Cube через SQL API.
- Альтернативы: Metabase — проще, но RLS и встраивание с ограничениями доступны в платной редакции; Grafana — сильна для метрик, слаба для бизнес-отчётов и выгрузок; собственные графики — дольше и без исследования кубов.
- Последствия: (+) готовые дашборды и Explore для аналитика (UC-05); (+) открытая лицензия; (−) ещё один сервис с собственной БД метаданных; (−) RLS настраивается отдельно от API — правила генерируются из `app.user_scope` одним заданием, чтобы не расходились. Связь: NFR-17, FR-DASH-01.

**ADR-006. OLAP — Cube как семантический слой с предагрегациями**

- Контекст: замечания требуют кубы OLAP; NFR-01 и NFR-17 — 3 секунды; FR-CALC-01 — единые формулы.
- Решение: Cube (open source) поверх `dwh`: кубы, меры и измерения из [120, раздел 6](120.data-model.md#6-кубы-семантического-слоя); предагрегации по частым срезам обновляются после каждой загрузки (UC-15); Superset и сервис отчётов обращаются к Cube через SQL API и REST API.
- Альтернативы: Mondrian или Saiku — классический MDX, но проекты мало развиваются; материализованные представления PostgreSQL — нет единого слоя мер и drill-down; Apache Kylin — требует Hadoop-окружения.
- Последствия: (+) одно место описания мер (ADR-013); (+) контекст безопасности Cube режет данные по области пользователя; (−) ещё один сервис и хранилище предагрегаций; (−) пользователь видит данные на момент последнего обновления предагрегаций — это `dataAsOf` аналитического контура. Связь: NFR-01, NFR-17, FR-OLAP-01.

**ADR-007. Инкрементальная загрузка через staging с checkpoint и ежесуточной сверкой**

- Контекст: Task Tracker отдаёт страницы без общего snapshot (DEC-TT-06); Planning System — неизменяемую партию; Reference Manager — коллекции целиком; QA — `updatedSince`. Повтор пакета не должен дублировать данные.
- Решение: пакет пишет в `stg`; проверка числа строк, уникальности ID, совпадения с manifest; загрузка `stg → dwh` одной транзакцией через upsert по естественному ключу; checkpoint сдвигается только после `LOADED`; раз в сутки — сверка числа и ID за окно и догрузка.
- Последствия: (+) повтор безопасен, частичный пакет не попадает в DWH; (+) расхождения из-за отсутствия snapshot исправляются сверкой; (−) DWH может отставать на один интервал, если пакет отклонён. Связь: NFR-05, NFR-08, FR-DWH-03.

**ADR-008. История для отчётов по динамике — факты переходов и ежедневные снимки**

- Контекст: R-05, R-09, R-10 считаются по истории (FR-CALC-07); источники хранят текущее состояние и историю в разной форме; события QA живут в топике 7 суток.
- Решение: переходы статусов задач и дефектов — отдельные факты (`fact_status_transition`, `fact_defect_transition`); состояние задач и дефектов на конец дня — периодические снимки; история Task Tracker до запуска Reports загружается из `/reports/history`.
- Последствия: (+) любой день и любой переход доступны для отчёта; (+) R-10 не требует пересчёта истории; (−) снимки растут быстро — секционирование по месяцу; (−) история переходов QA до подключения Reports недоступна, если QA её не отдаёт по REST. Связь: NFR-13.

**ADR-009. Идемпотентность — журнал `eventId` в одной транзакции с витриной**

- Контекст: все источники гарантируют только at-least-once; дубли возможны.
- Решение: `etl.processed_event` с ключом `eventId`; вставка и изменение витрины — одна транзакция; смещение Kafka фиксируется после коммита ([140, раздел 4](140.event-schema.md#4-обработка-потребляемых-событий)).
- Последствия: (+) повторная доставка не меняет показатели (FR-DAT-03); (−) журнал растёт — очистка старше 30 суток, больше срока хранения топиков. Связь: NFR-19.

**ADR-010. Выгрузки в MinIO, скачивание только через API Reports**

- Контекст: файл должен храниться ограниченное время и быть доступен только по защищённой ссылке (FR-EXP-04); Infra выделила бакет `arch-dev-reports`, публичный доступ запрещён.
- Решение: файл пишется в MinIO под ключом `exports/{exportId}`; скачивание — `GET /api/v1/exports/{exportId}/file`, сервис проверяет владельца и права и передаёт поток; предподписанные ссылки не выдаются; истёкшие объекты удаляет задание по `expires_at`.
- Последствия: (+) потерявший права пользователь не скачает файл; (+) ссылку нельзя переслать постороннему; (−) трафик идёт через сервис — допустимо для объёмов NFR-02. Связь: NFR-09.

**ADR-011. Сервис отчётов — Python и FastAPI, декларативный каталог; веб-интерфейс — React и TypeScript**

- Контекст: NFR-12 — новый отчёт без изменения ядра; QA System выбрала Python и FastAPI, Task Tracker — React и TypeScript.
- Решение: сервис отчётов на FastAPI; отчёт описывается в `app.report_definition`: параметры, разрезы, меры Cube, контур; сервис строит запрос к Cube или к `ops` по описанию. Веб-интерфейс — React и TypeScript, дашборды Superset встраиваются.
- Последствия: (+) новый отчёт — описание и меры, без кода (NFR-12); (+) OpenAPI генерируется из моделей; (−) сложные отчёты (R-02 с дефицитом) требуют специальных мер в Cube. Связь: NFR-12.

**ADR-012. Keycloak OIDC в API и BI; область данных фильтруется на сервере**

- Контекст: FR-SEC-01…03; права нельзя проверять скрытием интерфейса.
- Решение: клиент `reports` в Keycloak с ролями RL-01…RL-08; API проверяет JWT по JWKS; Superset входит через OIDC; область данных из `app.user_scope` применяется в API условием запроса, в Cube — контекстом безопасности, в Superset — RLS.
- Последствия: (+) один источник правды о правах — `app.user_scope`; (−) область обновляется с лагом загрузки справочников и плана — до 1 часа после перевода сотрудника. Связь: NFR-09.

**ADR-013. Показатели определяются только в семантическом слое**

- Контекст: FR-CALC-01 — одинаковые формулы во всех отчётах; замечание П.5 — формул нигде нет.
- Решение: формулы M-01…M-20 из [075, раздел 4](075.nfr.md#4-спецификация-показателей) реализуются только мерами Cube; отчёты, дашборды и выгрузки ссылаются на меры; вычисляемые поля в Superset для бизнес-показателей запрещены.
- Последствия: (+) R-06 и R-01 считают часы одинаково; (+) формулы тестируются один раз (T-12…T-17); (−) аналитик не может быстро добавить свою формулу в BI — только через описание меры. Связь: NFR-06, NFR-12.

**ADR-014. Дефекты для отчётов — из QA System**

- Контекст: дефект ведётся в QA System со статусами тестирования, серьёзностью и `REOPENED`; в Task Tracker создаётся «Ошибка» через `POST /bugs` со своим статусом. Считать по обоим — двойной учёт.
- Решение: R-05, R-08, R-09 считаются по дефектам QA System; «Ошибка» трекера связывается с дефектом по `BugCreatedFromTesting` и используется только для перехода к задаче; ошибки трекера без дефекта QA показываются отдельной категорией «зарегистрированы вне QA System».
- Последствия: (+) есть серьёзность и reopened rate; (−) ошибки, заведённые разработчиками напрямую в трекере, не попадают в R-09 — требует подтверждения Q-REP-07.

**ADR-015. Прогноз — Planning System; расчёт Reports по темпу только сверочный**

- Контекст: FR-CALC-04 vision требует прогноз по темпу; Planning System владеет прогнозом и методикой (ADR-011 у Planning, D-07); принцип vision — не дублировать бизнес-правила источников.
- Решение: основной прогноз и отклонение бюджета в R-06 — значения Planning System с `quality`; Reports дополнительно показывает сверочный прогноз по темпу (M-08) с подписью «сверочный» и допущением.
- Последствия: (+) нет двух «официальных» дат; (+) FR-CALC-04 выполняется в части сверки; (−) расхождение двух прогнозов нужно объяснять — подсказка на плитке. Связь: Q-REP-06, K-09.
