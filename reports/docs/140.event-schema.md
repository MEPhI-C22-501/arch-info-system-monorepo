## 1. Публикуемые события Reports

Каждой строке раздела 1 каталога [135](135.event-catalog.md) соответствует одна JSON Schema (draft 2020-12) и один пример.

### Оболочка

Оболочка совпадает с оболочкой событий [Planning System](../../planning-system/docs/140.event-schema.md): так потребитель разбирает события разных издателей одинаково.

| Поле | Тип | Обязательно | Пример | Смысл |
| --- | --- | --- | --- | --- |
| `eventId` | string, uuid | Да | `3c6f2b10-…` | Уникальный идентификатор; ключ дедупликации у потребителя |
| `eventType` | string, const | Да | `ReportExportReady` | Имя события |
| `occurredAt` | string, date-time, UTC | Да | `2026-10-05T08:41:12Z` | Момент факта |
| `producer` | string, const `Reports` | Да | `Reports` | Издатель |
| `schemaVersion` | string, semver | Да | `1.0.0` | Версия схемы |
| `correlationId` | string | Да | `0a9d7c1e-…` | Связь с запросом или запуском подписки |
| `recipientSub` | string | Да | `5f2c8e7a-…` | `sub` получателя в Keycloak |
| `payload` | object | Да | — | Данные события |

### `ReportExportReady.payload`

| Поле | Тип | Обязательно | Пример | Смысл |
| --- | --- | --- | --- | --- |
| `exportId` | uuid | Да | `b7e1c3d5-…` | Задание выгрузки |
| `reportId` | string `R-01`…`R-11` или `CUBE` | Да | `R-01` | Что выгружено |
| `format` | `xlsx` или `csv` | Да | `xlsx` | Формат файла |
| `rowCount` | integer ≥ 0 | Да | `48210` | Строк в файле |
| `expiresAt` | date-time | Да | `2026-10-08T08:41:12Z` | Когда файл будет удалён |
| `downloadPath` | string | Да | `/api/v1/exports/…/file` | Путь API; скачивание требует токен и проверяет права |

### `ScheduledReportReady.payload`

| Поле | Тип | Обязательно | Пример | Смысл |
| --- | --- | --- | --- | --- |
| `subscriptionId` | uuid | Да | `e1f2a3b4-…` | Подписка |
| `snapshotId` | uuid | Да | `f0e1d2c3-…` | Снимок отчёта |
| `reportId` | string `R-01`…`R-11` | Да | `R-06` | Отчёт |
| `dataAsOf` | date-time | Да | `2026-10-05T05:00:00Z` | Наиболее раннее время актуальности источников отчёта |
| `viewPath` | string | Да | `/snapshots/…` | Путь в веб-интерфейсе; требует входа |

**Чего в событиях нет и не будет:** значений показателей, имён сотрудников, названий проектов, ссылок без проверки прав. Событие только сообщает, что результат готов; данные получатель читает через API с проверкой прав.

## 2. Партиционирование

| Топик | Ключ | Обоснование |
| --- | --- | --- |
| `dev.reports.delivery.v1` | `recipientSub` | Уведомления одного получателя приходят по порядку: «выгрузка готова» не обгонит более раннее. Распределение по 3 партициям равномерное: получателей сотни |

## 3. Версионирование и совместимость

- Версия схемы — semver в поле `schemaVersion` и в `$id`.
- **Минорная** версия — только добавление необязательных полей; совместимость backward и forward. Потребители обязаны игнорировать незнакомые поля; поэтому в самих схемах `additionalProperties: false` действует для издателя, а потребителю рекомендуется проверять по схеме своей версии без строгого запрета лишних полей.
- **Мажорная** версия — удаление или переименование поля, смена типа. Публикуется в новый топик `dev.reports.delivery.v2`; старый поддерживается до перехода всех подписчиков, не меньше одной итерации.
- Изменение схемы согласуется с подписчиками до выпуска.

## 4. Обработка потребляемых событий

Схемы потребляемых событий принадлежат издателям: [Task Tracker](../../task-tracker/docs/block-g-api-and-events/event-schemas.json) и [140 Task Tracker](../../task-tracker/docs/block-g-api-and-events/140.event-schema.md), [QA System](../../qa/docs/140.event-schema.md), [Planning System](../../planning-system/docs/contracts/events/). Reports проверяет входящее событие по схеме издателя той мажорной версии, которую поддерживает.

### Правила идемпотентной обработки

1. Прочитать событие; если `eventType` не из [135](135.event-catalog.md) — зафиксировать смещение, ничего не делать.
2. Открыть транзакцию. `INSERT INTO etl.processed_event (event_id, …) ON CONFLICT DO NOTHING`. Если строка не вставилась — событие уже обработано: закрыть транзакцию, зафиксировать смещение.
3. Применить изменение к `ops` и `dwh`, только если `sourceRevision` (или `occurredAt`, если ревизии нет) новее сохранённого.
4. Закрыть транзакцию, затем зафиксировать смещение Kafka. Падение после закрытия транзакции, но до фиксации смещения приводит к повторной доставке, которая отбрасывается на шаге 2.

### Особые правила по источникам

| Источник | Правило | Почему |
| --- | --- | --- |
| Task Tracker | Часы — только из `TimeLogged` и `/reports/time-logs`; `WorkItemFieldsChanged` с полем фактических часов не суммируется | Трекер описывает одно изменение общим и уточняющим событием ([135 трекера](../../task-tracker/docs/block-g-api-and-events/135.event-catalog.md)) |
| Task Tracker | `NotificationCreated` не учитывается | Техническое событие, не изменение факта |
| Task Tracker | `WorkItemHardDeleted` помечает удаление, строки не удаляются | История отчётов за прошлые периоды не должна меняться |
| QA System | Для `fact_test_result` хранится последний результат кейса в прогоне; после `TestRunCompleted` изменения прогона не принимаются | Результат можно менять только в `IN_PROGRESS` ([050 QA](../../qa/docs/050.entities.md)) |
| QA System | Переход `DefectChanged` в `REOPENED` пишется отдельной строкой `fact_defect_transition` с `is_reopen = true` | Основа M-17 |
| Planning System | События — только сигнал перечитать; данные берутся из партии или проекции | Planning System так и описывает свои события ([135 Planning](../../planning-system/docs/135.event-catalog.md)) |
