# 010 — Глоссарий (Ubiquitous Language)

> Формат — см. [состав документов](documents-composition.md), документ 010.
> Источник — [vision, раздел 1.4](vision.md#14-термины). Сверено с глоссариями
> [Task Tracker](../../task-tracker/docs/block-a-context-and-scope/010.glossary.md),
> [Planning System](../../planning-system/docs/010.glossary.md),
> [Reference Manager](../../reference-manager/documents/010.glossary.md) и
> [QA System](../../qa/docs/010.glossary.md).

Общепрограммные термины («пользователь», «роль», «API») не включены. В скобках после термина — имя, под которым он встречается в модели данных, API и событиях.

## 1. Название подсистемы

Единое написание во всём комплекте — **Reports**. Так подсистему называют Planning System («Reports — единое название подсистемы отчётности»), QA System и Infra. В документах Task Tracker она названа «сервис отчётности» с синонимом Reporting; это одна и та же подсистема.

## 2. Контуры отчётности

| Термин | Определение | Контекст | Синонимы |
| --- | --- | --- | --- |
| Оперативный контур | Часть подсистемы, которая показывает текущее состояние работ с задержкой в минуты: открытые задачи, назначения, идущие прогоны, открытые дефекты. Строится на оперативной витрине и читается через read-replica | Оперативные дашборды | Operational reporting |
| Аналитический контур | Часть подсистемы, которая хранит историю и строит показатели за периоды: план-факт, динамику, качество итераций. Строится на DWH, наполняемом ETL, и кубах OLAP | Аналитические отчёты, кубы | Analytical reporting |
| Оперативная витрина (`ops`) | Собственная схема БД Reports с текущим состоянием сущностей источников. Обновляется событиями и частым опросом REST | Оперативный контур | Operational store |
| Read-replica | Реплика БД только для чтения, которая получает изменения основной БД потоковой репликацией. Оперативные дашборды читают из неё, не нагружая основную БД. Reports реплицирует только собственную оперативную витрину — см. [ADR-002](145.architecture-decisions.md) | Оперативный контур | Реплика чтения |
| Хранилище данных (DWH, `dwh`) | Собственная схема БД Reports со схемой «звезда»: факты и размерности с историей. Источник аналитических отчётов и кубов | Аналитический контур | Аналитическое хранилище, аналитическая витрина (Planning System, Reference Manager) |
| Дашборд | Экран из нескольких связанных показателей и графиков с общими фильтрами. Оперативный дашборд читает оперативную витрину, аналитический — DWH или куб | BI | Панель |
| Отчёт | Именованный набор показателей с параметрами, разрезами и формой представления; R-01…R-11 по каталогу [vision](vision.md#4-каталог-отчётов) | Оба контура | Report |
| Витрина отчётности | Общее название данных Reports, по которым строятся отчёты: оперативная витрина и DWH вместе | Оба контура | — |

## 3. Хранилище и OLAP

| Термин | Определение | Контекст | Синонимы |
| --- | --- | --- | --- |
| Факт | Таблица измеряемых событий или состояний с заданной гранулярностью: запись трудозатрат, результат кейса, состояние задачи на день | DWH | Fact table |
| Размерность | Таблица признаков, по которым группируются и фильтруются факты: дата, сотрудник, проект, итерация, статус | DWH | Измерение, dimension |
| Гранулярность | Что именно описывает одна строка факта, например «одна задача в один день» | DWH | Grain |
| Медленно меняющаяся размерность (SCD2) | Размерность, в которой изменение признака не перезаписывает строку, а закрывает её (`valid_to`) и создаёт новую. Нужна, чтобы отчёт за прошлый период показывал подразделение и проект на тот момент | DWH | Slowly changing dimension, тип 2 |
| Суррогатный ключ (`*_key`) | Целочисленный ключ строки размерности внутри DWH. Не совпадает с идентификатором источника | DWH | — |
| Естественный ключ (`*_id`) | Идентификатор сущности у владельца: `employees/…` у Reference Manager, UUID проекта у Planning System, ID задачи у Task Tracker | DWH, ETL | Business key |
| Периодический снимок | Факт, в который раз в сутки записывается состояние каждой сущности: так считаются остатки и динамика за любой день | DWH | Periodic snapshot |
| Куб (OLAP) | Многомерная модель над DWH: меры, измерения и иерархии, по которым пользователь режет и детализирует данные без написания запросов | Аналитический контур | OLAP cube |
| Мера | Агрегируемое значение куба: сумма часов, количество дефектов, pass rate | Куб | Measure |
| Предагрегация | Заранее рассчитанный итог куба по частым сочетаниям измерений; ускоряет ответ | Куб | Pre-aggregation, rollup |
| Drill-down | Переход от итогового значения к более детальному уровню и далее к исходным записям | Куб, отчёт | Детализация |
| Семантический слой | Единое описание мер и измерений, из которого считают все отчёты и дашборды. Гарантирует одинаковые формулы (FR-CALC-01) | Аналитический контур | Semantic layer |

## 4. Загрузка данных

| Термин | Определение | Контекст | Синонимы |
| --- | --- | --- | --- |
| ETL | Извлечение данных у источника, преобразование и загрузка в DWH. Код ETL принадлежит Reports, расписание и доступы даёт Infra ([vision Infra, раздел 2](../../infra/vision.md)) | Аналитический контур | Extract–Transform–Load |
| Задание ETL | Отдельный запуск загрузки по одному источнику: Kubernetes Job или CronJob | ETL | ETL job, ETL-воркер |
| Staging (`stg`) | Схема БД для сырых данных пакета до проверки и загрузки в DWH | ETL | Промежуточная зона |
| Пакет (`batch`) | Набор данных одной загрузки с идентификатором, числом строк и контрольной суммой. У Planning System — неизменяемая партия экспорта с manifest | ETL | Batch, партия |
| Manifest | Описание пакета у источника: состав, число строк, срок хранения. Есть у пакетов Planning System | ETL | — |
| Checkpoint | Отметка, до которой данные источника успешно загружены; следующий запуск начинает с неё | ETL | Контрольная точка |
| Watermark | Значение отбора «изменено после», по которому выполняется инкрементальная загрузка, например `updatedSince` у QA System | ETL | Водяной знак |
| Инкрементальная загрузка | Загрузка только изменений после watermark | ETL | Incremental load |
| Полная загрузка | Чтение всех данных источника, в том числе удалённых (`show_deleted` у Reference Manager) | ETL | Full load, bootstrap |
| Сверка | Сравнение числа и идентификаторов записей DWH с источником и исправление расхождений | ETL | Reconciliation |
| Идемпотентная обработка | Повторная доставка события или повторный пакет не меняют показатели. Обработанные `eventId` хранятся в одной транзакции с изменением витрины | ETL, события | — |
| Tombstone | Признак удаления записи у источника, который нужно отразить в DWH, а не пропустить | ETL | Маркер удаления |

## 5. Актуальность данных

| Термин | Определение | Контекст | Синонимы |
| --- | --- | --- | --- |
| Лаг витрины | Время от изменения данных у источника до появления изменения в отчёте. Измеряется отдельно по каждому источнику и контуру | Оба контура | Задержка данных |
| Время актуальности (`dataAsOf`) | Момент, по состоянию на который данные источника гарантированно учтены. Показывается в каждом отчёте. Имя совпадает с полем выдачи Planning System | Оба контура | Data as of |
| Устаревшие данные | Состояние, при котором лаг превысил порог из [075](075.nfr.md). Отчёт формируется, но с предупреждением (FR-DAT-06) | Оба контура | Stale |
| Качество данных (`quality`) | Признак полноты входов расчёта у Planning System: `FULL` или `PARTIAL`. Reports показывает его рядом с прогнозом и не превращает `PARTIAL` в число | Прогнозы | — |

## 6. Отчёты и показатели

| Термин | Определение | Контекст | Синонимы |
| --- | --- | --- | --- |
| Параметр отчёта | Значение, которое задаёт пользователь: период, проект, итерация, сотрудник | Отчёт | Фильтр |
| Разрез | Признак группировки показателей: сотрудник, проект, итерация, эпик, период | Отчёт, куб | Измерение отчёта |
| Показатель | Значение, рассчитанное по правилу из [спецификации показателей](075.nfr.md#4-спецификация-показателей) | Отчёт | Метрика |
| Представление | Сохранённый набор параметров и разрезов отчёта (FR-RPT-10) | Отчёт | Saved view |
| Регламентный отчёт | Отчёт, который формируется по расписанию на фиксированных параметрах и доставляется подписчикам | Отчёт | Подписка |
| Задание выгрузки | Асинхронное формирование файла отчёта; живёт по жизненному циклу из [050](050.entities.md) | Выгрузка | Export job |
| Снимок отчёта | Сохранённый результат регламентного отчёта или выгрузки с параметрами и `dataAsOf` | Выгрузка | Report snapshot |
| План-факт | Сопоставление плановых часов и сроков Planning System с фактом Task Tracker | R-06 | Plan vs actual |
| Темп | Средние фактические часы в неделю за окно расчёта (по умолчанию 4 недели) | R-06 | Скорость |
| Ёмкость | Доступные часы сотрудника за период по плановой доступности Planning System | R-02, R-06 | Capacity |
| Дефицит | Требуемые часы по роли минус назначенные за тот же период | R-02 | Нехватка ресурсов |
| Pass rate | Доля пройденных кейсов среди выполненных: `PASSED / (PASSED + FAILED)` | R-07, R-09 | Процент прохождения |
| Defect density | Число дефектов, отнесённое к базе нормирования; база по умолчанию — 10 завершённых задач, см. Q-REP-12 в [020](020.system-context.md#6-открытые-договорённости) | R-09 | Плотность дефектов |
| Reopened rate | Доля дефектов, хотя бы раз перешедших в `REOPENED`, среди закрытых за период | R-09 | Доля переоткрытых |
| База нормирования | Величина, на которую делится показатель, чтобы его можно было сравнивать между итерациями | R-09 | Нормировочная база |
| Cycle time | Время от первого перехода задачи в рабочий статус до завершения | R-10 | Время цикла |
| Lead time | Время от создания задачи до завершения | R-10 | Время выполнения |
| Throughput | Количество задач, завершённых за неделю | R-10 | Пропускная способность |
| «Не задано» | Отдельная категория для пустых значений: нет оценки, исполнителя, итерации. Не равна нулю (FR-CALC-06) | Все отчёты | — |
