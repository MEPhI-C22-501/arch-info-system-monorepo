КОРОТКО (что уже хорошо и что нет)
--------------------------------------------------------------------------------
Хорошо:
- в отличие от многих модулей, комплект документов почти полный: блоки A–I
  написаны (010–165), отсутствует только один документ — 162;
- 161 относительная ссылка внутри документации — все живые, битых нет;
- статусы в 095 честные: где решение не принято, стоит partial/missing,
  а не «covered»;
- 115 подтверждается реальным прототипом в frontend/prototype/;
- машиночитаемые артефакты есть и валидны: openapi.yaml (OpenAPI 3.1) и
  event-schemas.json (16 схем событий) разбираются без ошибок.

Чего не хватает (главное):
1. Нет документа 162 (спецификация интеграционного решения) — последний
   пробел в комплекте.
2. Не описана интеграция с подсистемой планирования (плановые рамки внутрь,
   факт исполнения наружу). Это единственная связь, которая по матрице обмена
   должна быть двусторонней, а в документации её нет вообще.
3. Отсутствуют три из четырёх видов интеграции, принятых в проекте:
   очереди сообщений (сознательно не используются), обмен файлами через
   объектное хранилище (вложения хранятся «где-то», хранилище не названо)
   и пакетная выгрузка в аналитическое хранилище.
4. Единый вход через Keycloak не зафиксирован: провайдер идентификации везде
   описан как «кандидат, решение открыто».
5. Не назван владелец справочников: в соседней папке репозитория есть модуль
   справочников с готовыми требованиями, а вы запрашиваете «сервис
   справочников» без имени и без ссылки на его контракт.
6. Часть документов неполные по содержанию: openapi.yaml описывает 8 ресурсов
   вместо перечисленных в 130; NFR-008 без порогов; в 110 у трёх экранов нет
   всех состояний; спецификации есть лишь у 7 из 19 вариантов использования.
7. Расхождение в именах событий между 040 (русские имена) и 135/140
   (латинские) — трассировка между документами ломается.
8. Техническая часть не начата: кода, сборки, контейнеров, CI/CD и тестов нет
   (в репозитории есть только прототип интерфейса).

РАЗДЕЛ 1. ЧТО НУЖНО СОЗДАТЬ И ДОПОЛНИТЬ
--------------------------------------------------------------------------------
П. 1. 162.integration-spec.md — спецификация интеграционного решения
--------------------------------------------------------------------------------
Единственный отсутствующий документ комплекта. По каждой интеграции должно
быть:
- название и назначение;
- схема взаимодействия;
- рассмотренные варианты (например, синхронный API против событий против
  пакетной выгрузки файлов);
- «+» и «−» каждого варианта;
- выбранный вариант и обоснование выбора;
- ожидаемый результат и критерий проверки;
- ссылки на связанные документы (130, 135, 140, 145, 160).
Материал у вас уже есть и лежит не на своём месте: обоснование «почему REST,
а не события» — это ADR-004 в 145, а обоснование по каждому обмену должно
быть в 162. Перенесите туда разбор вариантов, оставив в 145 решение и его
последствия.

--------------------------------------------------------------------------------
П. 2. openapi.yaml — дописать до полноты, описанной в 130
--------------------------------------------------------------------------------
В 130.api-contracts.md перечислен состав эндпоинтов (список в таблице, строка
59 и далее), а в самом openapi.yaml описано только 8 ресурсов:
/bugs, /reports/work-items, /reports/iterations, /reports/time-logs,
/work-items/{id}/attachments, /work-items/{id}/attachments/{attachmentId},
/exports/work-items, /imports/work-items.
Чего в спецификации нет, хотя оно перечислено в 130:
- POST/GET /work-items (создание и список с фильтрами и пагинацией);
- GET/PATCH/DELETE /work-items/{id} (карточка, изменение, жёсткое удаление);
- POST /work-items/{id}/comments;
- POST /work-items/{id}/time-logs;
- GET /work-items/{id}/history;
- /iterations, /iterations/{id}/activate, /iterations/{id}/complete;
- /notifications;
- /admin/statuses и /admin/priorities.
Дополнительно: у части операций в спецификации нет схем ответов и кодов
ошибок (например, /reports/iterations, /reports/time-logs, /exports/work-items
описаны одной строкой). Требование проекта — по каждому эндпоинту метод, путь,
параметры, тело, коды ошибок, минимум один успешный и один ошибочный пример.

П. 3. 060.use-cases.md — спецификации не для всех ключевых сценариев
--------------------------------------------------------------------------------
В документе 19 вариантов использования, а спецификации (актор, предусловие,
постусловие, основной и альтернативный поток) написаны только для семи:
UC-1, UC-3, UC-8, UC-11, UC-15, UC-16, UC-19.
Добавьте спецификации хотя бы для: UC-2 (назначение исполнителя),
UC-4 (декомпозиция), UC-5/UC-6 (комментарии и вложения), UC-7 (регистрация

статусов и прав), UC-14 (уведомления), UC-17/UC-18 (чтение для отчётности,
синхронизация справочников). Если какой-то сценарий сознательно оставлен без
спецификации — напишите это явно, чтобы не выглядело пропуском.

П. 4. 075.nfr.md — NFR-008 без измеримых порогов
--------------------------------------------------------------------------------
Сейчас: «Время отклика, пропускная способность, объём данных, доступность,
RPO/RTO — порогов пока нет, требование остаётся missing».
Требование проекта: для каждого нефункционального требования — измеримая
метрика и пороговое значение. Определите и запишите числа: время отклика
типового экрана и типовой операции, ожидаемое число пользователей и рабочих
элементов, целевую доступность, допустимые RPO/RTO, поведение при
перегрузке. Если численные значения требуют согласования — укажите, с кем
и до какого момента, но не оставляйте требование без метрики.

П. 5. 110.ui-ux.md — не у всех экранов есть все состояния

По требованию каждый ключевой экран описывается со структурой,

Сейчас:
- «Карточка рабочего элемента» (строка 15): есть loading и error, нет empty;
- «Уведомления» (строка 17): есть только empty, нет loading и error;
- «Админ-панель» (строка 18): есть только error, нет loading и empty.
Допишите недостающие состояния — они же нужны для приёмки (пользователь
должен различать «нет данных», «грузится» и «ошибка»).

--------------------------------------------------------------------------------
П. 6. 155.sequence-diagrams.md — расширить набор сценариев
--------------------------------------------------------------------------------
Сейчас 4 сценария: изменение статуса, создание ошибки сервисом тестирования,
чтение данных отчётностью, синхронизация справочника.
Не хватает сценариев, которые уже описаны в других документах и должны иметь
диаграмму: запуск итерации с фиксацией базового плана; завершение итерации с

создание и получение уведомления; импорт Excel с отклонением некорректных
строк. По каждому — участники, сообщения, тайм-ауты, обработка ошибок, как
это сделано в существующих четырёх.

П. 7. Журнал проверки прототипа — сделать воспроизводимым
--------------------------------------------------------------------------------
В 115 и в frontend/prototype/README.md заявлено, что прототип прогнан через
headless Chrome (Playwright) по перечисленным сценариям и «без единой ошибки
в консоли». Сам прогон воспроизвести нельзя: в репозитории нет ни скрипта
прогона, ни сохранённого отчёта.
Что сделать: положить рядом с прототипом скрипт прогона (например,
playwright-тест или чек-лист с командами) и краткий отчёт — какие сценарии
проверены, на какой версии, с каким результатом. Иначе утверждение о проверке
остаётся непроверяемым, и при сдаче его придётся повторять вручную.

П. 5. Владение проектами и эпиками не согласовано
--------------------------------------------------------------------------------
010.glossary.md (строка 12) и 050/120 описывают Проект и Эпик как типы рабочих
элементов, которыми владеет Task Tracker: они хранятся в вашей таблице
WORK_ITEM и создаются в вашем интерфейсе.
При этом в матрице обмена данными между подсистемами проекты — мастер-данные
модуля планирования: он передаёт проекты, структуру и сроки в трекер, а
получает обратно факт исполнения. Модуль планирования уже зафиксировал это
как открытый вопрос и ждёт согласования (владение проектами и эпиками,
сопоставление идентификаторов, API приёма планов).
Что сделать: определить и записать в 020 §«владение данными» и в 145, кто
мастер проекта и эпика, по какому идентификатору они связываются с
задачами, что происходит с существующими задачами при удалении проекта.
Это же решение закрывает FR-010 и INT-03 в 095.

РАЗДЕЛ 3. НЕЗАКРЫТЫЕ ИНТЕГРАЦИИ (это нужно решить, а не дописать)
================================================================================
П. 1. Подсистема планирования — отсутствует полностью (критично)
--------------------------------------------------------------------------------
В 020.system-context.md, 030.actors.md и на всех диаграммах внешними системами
указаны только: провайдер идентификации, сервис тестирования, сервис
отчётности, сервис справочников и Infra. Подсистемы планирования нет.
По матрице обмена данных эта связь у Task Tracker единственная двусторонняя:
- получаете: проекты, структуру работ, сроки, назначения и плановые рамки;
- отдаёте: фактические часы, статусы задач, историю — то, из чего
  планирование считает прогноз остатка и бюджетные корректировки.
Смежный модуль уже описал эту связь со своей стороны и ждёт от вас
согласования контракта (владение проектами и эпиками, сопоставление
идентификаторов, приём планов, получение факта, повторная доставка, сигнал
удаления задачи).
Что сделать:
- добавить подсистему планирования в 020 §3 и в 030 как актора с указанием,
  что вы принимаете и что отдаёте;
- добавить интеграцию в 130 (API приёма плановых рамок и API/события отдачи
  факта), 155 (сценарии публикации плана и пересчёта факта), 160 (веха и
  ответственные), 162 (обоснование выбора способа);
- добавить требование и тест в 095 (сейчас в матрице нет ни одного пункта про
  планирование — это видно по списку FR-001…FR-015).

--------------------------------------------------------------------------------
П. 2. Подсистема тестирования и качества названа родовым термином
--------------------------------------------------------------------------------
Вы описываете «сервис тестирования» как безымянный внешний сервис, который
создаёт ошибки. В проекте это отдельный модуль — «Управление тестированием и
качеством», у него свои требования, и он уже описал взаимодействие с вами:
он создаёт в трекере задачи-ошибки, ссылается по идентификаторам на задачи,
итерации, проекты и эпики, а также рассчитывает читать ваши итерации и вехи.
Что сделать:
- назвать контрагента его реальным именем (или явно сослаться на его
  документы) в 020, 030, 130, 155, 160;
- убедиться, что API для чтения покрывает его потребности, а не только
  потребности отчётности: сейчас read-only API в 130 описан как «для сервиса
  отчётности», хотя итерации и задачи нужны и модулю тестирования;
- согласовать правило преобразования серьёзности дефекта в приоритет
  (оно вынесено в открытые вопросы — закройте с командой тестирования).

--------------------------------------------------------------------------------
П. 3. Очереди сообщений: решение принято, но требует согласования
--------------------------------------------------------------------------------
135.event-catalog.md (строка 6) фиксирует: Task Tracker не публикует события
во внешнюю шину, обмен с отчётностью — синхронный read-only REST;
145 (ADR-004, ADR-007) это обосновывает.
Решение само по себе нормальное и оформлено как ADR, но в проекте очереди —
один из четырёх обязательных видов интеграции, и события трекера (изменение
задачи, статуса, трудозатраты) — естественный источник для аналитики.
Что сделать: вынести этот вопрос на согласование с архитектором и командой
инфраструктуры, зафиксировать результат письменно (остаётся REST — так и
напишите «согласовано с архитектором, дата»; добавляется шина — заводите
топики, retry и очередь необработанных сообщений).
Важно: пока вопрос не закрыт, 090 (эпик E-9) и 160 не должны выглядеть
окончательно решёнными.

--------------------------------------------------------------------------------
П. 4. Обмен файлами и пакетная выгрузка в аналитическое хранилище — нет
--------------------------------------------------------------------------------
Ни в одном документе модуля нет:
- объектного хранилища для файлов (см. раздел 2, п. 7) — хотя вложения есть
  в требованиях, модели данных, API и UI;
- пакетной выгрузки данных в аналитическое хранилище отчётности: в матрице
  обмена от трекера к отчётности идут задачи, трекинг времени и статусы, а
  сейчас этот поток описан только как синхронный REST-опрос.
Что сделать: определить, участвует ли модуль в пакетной выгрузке (и в каком
виде: выгрузка в хранилище против read-only API), согласовать с командой
отчётности и записать результат в 020, 145, 160, 162. Без этого интеграция
«трекер → отчётность» считается закрытой только формально.

--------------------------------------------------------------------------------
П. 5. Владелец справочников не назван
--------------------------------------------------------------------------------
020 (строка 45) и 030: «Сервис справочников — источник пользователей, команд и
подразделений», владелец «не подтверждён»; 010 (строка 42) ссылается на модуль
справочников, но отмечает, что он «не подтверждён как владелец».
При этом в репозитории есть модуль справочников с готовыми требованиями, где
описаны справочники сотрудников и оргструктуры.
Что сделать: указать конкретного владельца, согласовать с ним контракт
выдачи (стабильный идентификатор, отображаемое имя, признак активности,
версия снимка, поведение при увольнении), закрыть FR-014 в 095 и убрать
формулировку «владелец не подтверждён» из 160.
