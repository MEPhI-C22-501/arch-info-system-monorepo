# Состав документов курсового проекта

> Что должно быть в каждом документе и зачем он нужен.
> Документы хранятся в папке `documents/`, нумерация 010–165,
> сгруппированы по блокам A–I.

---

## Блок A. Контекст и границы системы

### 010 — Глоссарий (Ubiquitous Language) — `010.glossary.md`

**Назначение:** Установить единую терминологию предметной области для всей команды. Избежать разночтений в названиях сущностей, процессов, ролей.

**Что должно быть:**
- Таблица с колонками: термин, определение, контекст / модуль ERP, синонимы (если есть)
- Термины из **предметной области модуля** (не общепрограммные — «пользователь», «роль», «CRUD» не должны составлять 80 % списка)
- Ссылки на смежные термины из Glossary смежных модулей (после согласования)

---

### 020 — System Context — `020.system-context.md`

**Назначение:** Определить границы системы — что входит в модуль, а что остаётся за его пределами. Показать внешние системы и акторов.

**Что должно быть:**
- Контекстная диаграмма (C4 Context level / Mermaid)
- Описание каждой внешней системы: название, роль, тип интеграции
- Список акторов (люди и внешние системы) с кратким описанием

---

### 030 — Actors — `030.actors.md`

**Назначение:** Зафиксировать всех участников взаимодействия с модулем — людей и внешние системы.

**Что должно быть:**
- Таблица: актор, описание, основные цели / функции в системе (колонки могут варьироваться; минимум — роль + описание)
- Для людей: должность / роль в предметной области, какие действия выполняет в системе
- Для внешних систем: название, протокол, сценарий интеграции

---

## Блок B. Анализ предметной области

### 040 — Event Storming — `040.event-storming.md`

**Назначение:** Смоделировать бизнес-процессы модуля через доменные события и команды. Это основа для выделения сущностей и агрегатов.

**Что должно быть:**
- Карта событий: доменные события (past-tense), команды, агрегаты, внешние системы
- Можно в виде таблицы или Mermaid-диаграммы
- События упорядочены по времени / процессу

---

### 050 — Entities + Lifecycle — `050.entities.md`

**Назначение:** Выделить ключевые сущности предметной области (Aggregates) и описать их статусную модель.

**Что должно быть:**
- Список агрегатов / сущностей: название, атрибуты (имя, тип, ограничения), связи с другими сущностями (FK, тип связи)
- Статусная модель (Lifecycle): диаграмма состояний и переходов (Mermaid stateDiagram)
- Для каждого статуса: описание, триггер перехода

---

### 060 — Use Cases — `060.use-cases.md`

**Назначение:** Описать функциональные требования через варианты использования. Связать акторов и сущности.

**Что должно быть:**
- Use Case диаграмма (Mermaid usecaseDiagram): акторы, варианты использования, связи include/extend
- Спецификации ключевых use cases: актор, пред-/постусловия, основной flow (шаги), альтернативные flow
- Рекомендуется нумеровать use cases (UC-1, UC-2…) и привязывать к ним user stories

---

## Блок C. Требования и роли

### 070 — RBAC (Role-Based Access Control) — `070.role-matrix.md`

**Назначение:** Определить, какие роли есть в системе и какие права доступа у каждой роли к сущностям / операциям.

**Что должно быть:**
- Матрица ролей и прав: строки = роли, столбцы = действия / сущности, ячейки = разрешено/запрещено
- Уровни доступа: create / read / update / delete / execute
- Соответствие ролей акторам из `030.actors.md`
---

### 075 — NFR (Non-Functional Requirements) — `075.nfr.md`

**Назначение:** Зафиксировать нефункциональные требования — ограничения и атрибуты качества, которым должна удовлетворять система.

**Что должно быть:**
- Категории NFR: производительность (время отклика, пропускная способность), безопасность, надёжность, масштабируемость, сопровождаемость
- Для каждого требования — измеримая метрика и пороговое значение
- Связь с архитектурными решениями (ADR) и сценариями тестирования

---

### 080 — User Stories — `080.{actor}-user-stories.md`

**Назначение:** Описать потребности пользователей в удобном для разработки формате. Это основной источник функциональных требований.

**Что должно быть:**
- User stories в формате: *As a \<actor\>, I want \<function\> so that \<value\>*
- Acceptance Criteria в формате Given-When-Then (GWT) — несколько сценариев на одну историю
- Группировка по ролям / акторам (удобнее, чем по функциям)
- Связанные use case из `060.use-cases.md` и роль из `070.role-matrix.md`
- Файлов может быть несколько — по одному на актора (например, `080.manager-user-stories.md`)

---

### 090 — Epics / Features — `090.features-epics.md`

**Назначение:** Сгруппировать user stories в крупные функциональные блоки (epics) для планирования разработки и приоритизации.

**Что должно быть:**
- Список эпиков: название, описание, приоритет (MoSCoW / числовой)
- Связанные user stories для каждого эпика
- Связь с вехами M4–M5 (какой эпик в какой итерации реализуется)

---

## Блок D. Верификация

### 095 — Traceability Matrix — `095.requirements-check.md`

**Назначение:** Проверить полноту покрытия — каждое требование должно быть связано с user story, документом и тестом.

**Что должно быть:**
- Матрица: ID требования, описание, тип (ФТ / НФТ / интеграционное), источник (Vision / NFR), артефакты (какие документы cover), элемент бэклога / user story, статус (covered / partial / missing)
- Разделение на функциональные и нефункциональные требования
- Вывод: есть ли пропуски, какие требования не покрыты
- Рекомендуется автоматизированная проверка при помощи AI (см. «Сопроводительные артефакты» в course-project.md)

---

## Блок E. Проектирование интерфейсов

### 110 — UI/UX прототип — `110.ui-ux.md`

**Назначение:** Визуализировать интерфейсы модуля до начала разработки — согласовать расположение элементов, поток экранов.

**Что должно быть:**
- Основные принципы UI/UX: консистентность, обратная связь, предсказуемость, минимизация когнитивной нагрузки, accessibility
- Описание каждого ключевого экрана: структура (панели, зоны), функциональные элементы, состояния (loading / empty / error)
- Описание навигации между экранами
- Контекстное управление: какие элементы интерфейса видны / скрыты в зависимости от роли / прав пользователя
- Привязка к user stories / use cases — какой экран закрывает какую историю
- UX-особенности: автосохранение, предпросмотр, подтверждение действий

---

### 115 — Live-прототип — `115.live-prototype.md`

**Назначение:** Интерактивное представление UI/UX для проверки гипотез и сценариев взаимодействия до начала кодирования.

**Что должно быть:**
- Описание прототипа: какие экраны, связки между ними, сценарии
- Ссылка на HTML-файлы прототипа (или описание, где они лежат)
- Рекомендация: вместо отдельных HTML — один index.html с навигацией по экранам

---

## Блок F. Проектирование данных

### 120 — Data Model — `120.data-model.md`

**Назначение:** Спроектировать структуру данных модуля — сущности, атрибуты, связи. Это основа для генерации DDL и API-контрактов.

**Что должно быть:**
- ER-диаграмма (Mermaid erDiagram) — все сущности, атрибуты, первичные и внешние ключи, связи
- Детальное описание каждой таблицы: столбец, тип, ограничения (NOT NULL, UNIQUE, FK), описание семантики поля
- Индексы (PRIMARY KEY, UNIQUE, композитные и частичные индексы для фильтрации не-удалённых записей)
- Связи между сущностями (один-ко-многим, многие-ко-многим, каскадное удаление)
- Примечания по бизнес-логике, валидации, soft-delete
- Согласование с Entity / Aggregate из `050.entities.md`

---

## Блок G. API и события

### 130 — API Contracts — `130.api-contracts.md`

**Назначение:** Специфицировать контракты синхронного взаимодействия (REST / gRPC) между модулями и внешними системами.

**Что должно быть:**
- OpenAPI-спецификация (swagger.yaml / .json) — включается как ссылка или встраивается
- Описание эндпоинтов: метод, путь, параметры, тело запроса / ответа, коды ошибок
- Примеры запросов и ответов (хотя бы 1 успешный + 1 ошибочный)
- Версионирование контракта (semver)

---

### 135 — Event Catalog — `135.event-catalog.md`

**Назначение:** Перечень доменных событий (Kafka) — кто публикует, кто потребляет, при каких условиях.

**Что должно быть:**
- Таблица: событие (имя), издатель (модуль), подписчики (модули), триггер (условие публикации), приоритет / критичность
- Краткое описание бизнес-смысла каждого события

---

### 140 — Event Schema — `140.event-schema.md`

**Назначение:** Спецификация структуры каждого события — поля, типы, partition key.

**Что должно быть:**
- Для каждого события из Event Catalog: JSON Schema или Avro Schema
- Описание полей: имя, тип, обязательность, пример, семантика
- Партицирование: partition key и обоснование
- Версионирование схемы (совместимость — backward / forward)

---

## Блок H. Архитектура и логика

### 145 — ADR — `145.architecture-decisions.md`

**Назначение:** Фиксировать значимые архитектурные решения, их контекст и последствия. Предотвращает повторное обсуждение одного и того же.

**Что должно быть:**
- ADR по шаблону: *Контекст → Решение → Последствия (positive + negative)*
- Каждое решение — отдельный раздел (можно нумеровать ADR-001, ADR-002…)
- Решения должны быть связаны с NFR и выявленными trade-off'ами

---

### 146 — Logic Scheme — `146.logic-scheme.md`

**Назначение:** Показать логическую архитектуру системы — потоки данных, ключевые компоненты и их логические связи (без привязки к физическому развёртыванию).

**Что должно быть:**
- Диаграмма логической схемы (Mermaid)
- Описание потоков данных между компонентами
- Какие компоненты синхронные, какие асинхронные (Kafka)
- Границы модуля и его внешние зависимости

---

### 150 — Component Diagram — `150.component-diagram.md`

**Назначение:** Обзорная архитектура модуля — из каких компонентов состоит система и как они связаны (C4 Component level).

**Что должно быть:**
- Компонентная диаграмма (C4 Component / Mermaid)
- Описание каждого компонента: название, технология, ответственность
- Интерфейсы между компонентами (REST / gRPC / Kafka / БД)
- Связь с ADR и логической схемой

---

## Блок I. Интеграции и развёртывание

### 155 — Sequence-диаграммы — `155.sequence-diagrams.md`

**Назначение:** Детализировать интеграционные сценарии — показать порядок сообщений между модулями, внешними системами и пользователем.

**Что должно быть:**
- Sequence-диаграммы (Mermaid sequenceDiagram) для ключевых сценариев интеграции
- Для каждого сценария: участники (модули / системы), сообщения, тайм-ауты, обработка ошибок
- Привязка к use cases / user stories и API Contracts

---

### 160 — Integration Plan — `160.integration-plan.md`

**Назначение:** План стыковки модуля с другими модулями и инфраструктурой — порядок, сроки, ответственные.

**Что должно быть:**
- Список интеграций: с кем / чем стыкуется, тип (REST / Kafka / БД), протокол
- Порядок реализации интеграций — последовательность шагов
- Сроки / привязка к вехам (И-M1… И-M5)
- Ответственные со стороны модуля и со стороны инфраструктуры
- Критерии готовности каждой интеграции

---

### 165 — Deployment Diagram — `165.deployment-diagram.md`

**Назначение:** Физическое развёртывание системы — серверы, контейнеры, сети, окружения.

**Что должно быть:**
- Deployment diagram (Mermaid deployment diagram / C4 Deployment)
- Описание узлов: физические / виртуальные машины, контейнеры (Docker), оркестрация
- Описание окружений: dev / staging / production
- Связь с Component Diagram — каждый компонент маппится на узел развёртывания
