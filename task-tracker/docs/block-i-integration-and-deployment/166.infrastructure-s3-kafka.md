# 166 — Подключение Task Tracker к S3 и Kafka

Инструкция и заявка команде Infra для кода ветки `codex/task-tracker-review-2026-11-01`. Владелец приложения — команда модуля учёта работ; владелец брокера, хранилища, сетей и выдачи секретов — Infra. Согласование бизнес-событий с Reports/Planning ведётся отдельно по [162](162.integration-spec.md).

## 1. Что требуется подготовить

| Ресурс | Требование |
|---|---|
| S3 | Приватный бакет `arch-dev-task-tracker`, отдельные ключи, PutObject/GetObject/DeleteObject |
| Kafka | Топик `task-tracker.events.v1`, principal `task_tracker`, запись и получение метаданных топика, идемпотентная публикация |
| Сеть | Backend достигает S3 API и всех адресов брокеров из Kafka metadata |
| Доверие TLS | Доверенный Java CA для HTTPS S3; отдельный Kafka truststore, доступный backend только для чтения |
| Развёртывание | Переменные передаются именно в backend; файлы сертификатов монтируются в его контейнер |
| Хранение | Бакет и данные Kafka переживают пересоздание контейнеров; резервные копии БД и бакета согласованы |

Применить миграции backend через Liquibase, включая `002-review`; вручную создавать таблицы не нужно. Доступ к этим таблицам внешним сервисам не выдаётся. Frontend не получает S3/Kafka-ключи и не подключается к этим сервисам напрямую.

Инфраструктурный bootstrap уже создаёт нужные имена: [Kafka](../../../infra/scripts/kafka-converge.sh), [MinIO](../../../infra/scripts/minio-converge.sh). Наличие ресурсов не означает готовность приложения: ниже перечислены дополнительные условия совместимости.

## 2. S3 / MinIO

### Ресурсы и права

Создать бакет `arch-dev-task-tracker`, закрыть анонимное чтение и запись. Приложение не создаёт бакет. Префикс объектов — `attachments/`; ключ содержит UUID вложения и дополнительный UUID, перезапись существующего объекта не нужна.

Выдать backend отдельную учётную запись. В текущем bootstrap Infra это `task-tracker`, пароль берётся из `S3_TASK_TRACKER_SECRET`. В приложение передаются `S3_ACCESS_KEY=task-tracker` и соответствующий секрет как `S3_SECRET_KEY` — имя bootstrap-переменной самим приложением не читается.

Минимальная объектная политика приложения:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
    "Resource": ["arn:aws:s3:::arch-dev-task-tracker/attachments/*"]
  }]
}
```

ListBucket/CreateBucket и административные операции не нужны коду приложения; их выполняет Infra при подготовке и проверке. Текущая политика Infra `task-tracker.json` разрешает `s3:*` только на своём бакете — она функционально подходит, но шире минимально необходимой. Не выдавать права на соседние бакеты. Object Lock/retention, запрещающий DeleteObject, с текущей очисткой несовместим.

### Конфигурация backend

| Переменная | Значение / смысл |
|---|---|
| `S3_ENDPOINT` | URL API, например `http://minio:9000` внутри локальной общей сети; для защищённого стенда — выданный HTTPS URL. Не URL консоли `9001` и не путь бакета |
| `S3_BUCKET` | `arch-dev-task-tracker` — также значение по умолчанию |
| `S3_ACCESS_KEY` | Отдельный access key приложения |
| `S3_SECRET_KEY` | Секрет этой учётной записи |

Текущий клиент использует path-style addressing и регион `us-east-1` фиксированно; переменные `S3_REGION`, `AWS_REGION` и `S3_PATH_STYLE` им не читаются. Endpoint должен принимать подпись для `us-east-1`. Временные STS-ключи с session token пока не поддерживаются.

При HTTPS сертификат должен соответствовать DNS endpoint и быть доверенным JVM. Для частного CA Infra готовит Java truststore и подключает его через стандартные JVM-настройки, например `JAVA_TOOL_OPTIONS` с `-Djavax.net.ssl.trustStore=/run/certs/s3-ca.jks`. Пароль/путь выдаются средствами управления секретами. Не отключать проверку TLS. Kafka truststore сам по себе доверие HTTPS S3 не настраивает.

Пустой `S3_ENDPOINT` оставляет новые вложения в bytea-режиме. Установка endpoint **автоматически запускает перенос старых вложений**: раз в 30 секунд до 10 записей, загрузка → скачивание → SHA-256 → очистка bytea в БД. Перед первым включением сделать согласованную резервную копию БД. После переноса отключение S3 не возвращает файлы в bytea: для чтения требуется доступ к бакету.

Резервации незавершённых загрузок находятся в `object_cleanup`; уборщик выполняется раз в минуту, незавершённая загрузка доступна для очистки через час. Удаление вложения или карточки ставит объект в очередь удаления. Не назначать бакету автоматическое удаление действующих `attachments/*` по возрасту: срок жизни объектов определяется ссылками из БД.

## 3. Kafka

### Совместимость аутентификации: необходимо решить до включения

В [текущем bootstrap Infra](../../../infra/scripts/kafka-init.sh) включён **PLAIN** поверх SASL_SSL. В `Outbox.java` приложения при заданном JAAS жёстко выбран **SCRAM-SHA-512**. Только передачей переменных окружения переключить приложение на PLAIN сейчас нельзя: переменная `KAFKA_SASL_MECHANISM` не поддерживается.

Для подключения без изменения приложения Infra должна добавить SCRAM-SHA-512 на доступный приложению SASL_SSL listener и создать соответствующие SCRAM credentials principal `task_tracker`. Настроить механизм на listener и зарегистрировать SCRAM credential в метаданных Kafka — одной строки пользователя в PLAIN JAAS недостаточно. Существующий PLAIN для других клиентов сохранить.

Если Infra оставляет только PLAIN, команда Task Tracker сначала должна выпустить поддержку выбора механизма в клиенте. До этого подключение к общему брокеру считать заблокированным; не выдавать PLAIN JAAS как рабочую настройку текущего SCRAM-клиента.

### Топик и ACL

| Параметр | Значение |
|---|---|
| Topic | `task-tracker.events.v1` — сейчас фиксирован в коде |
| Partitions | 3, как в bootstrap Infra |
| Retention | `604800000` ms, 7 суток, как в bootstrap Infra |
| `max.message.bytes` | `1048576`, как в bootstrap Infra; большие снимки итераций проверяются отдельно |
| Replication factor | 1 в текущем dev-стенде; для многоброкерного стенда значение и min ISR определяет Infra |
| Producer principal | `User:task_tracker` |
| Key / value | UTF-8 строка aggregate ID / JSON envelope события |
| Доставка | `acks=all`, `enable.idempotence=true`; нет `transactional.id`, нет Kafka-транзакций |

Выдать `Write` и `Describe` на топик. Для выдачи producer ID проверить разрешение InitProducerId. Ниже приведён вариант с явным `IdempotentWrite` на кластер. В современных Kafka авторизация может пройти через topic-level Write при отсутствии этого cluster ACL; поэтому отсутствие IdempotentWrite в текущем bootstrap само по себе не доказывает неисправность. Infra может сохранить более узкую политику, если реальная идемпотентная отправка под `task_tracker` подтверждена. Правило fallback описано в [таблице авторизации Apache Kafka](https://github.com/apache/kafka/blob/trunk/docs/security/authorization-and-acls.md).

Команды для администратора Kafka в окружении Infra (с существующим защищённым `admin.properties`):

```sh
/opt/kafka/bin/kafka-acls.sh --bootstrap-server kafka:9092 \
  --command-config /var/lib/kafka/config/admin.properties \
  --add --allow-principal User:task_tracker \
  --topic task-tracker.events.v1 --operation Write --operation Describe

/opt/kafka/bin/kafka-acls.sh --bootstrap-server kafka:9092 \
  --command-config /var/lib/kafka/config/admin.properties \
  --add --allow-principal User:task_tracker --cluster --operation IdempotentWrite
```

Task Tracker не требует Read, consumer group ACL или Create на топики. Предварительное создание топика остаётся обязанностью Infra. Для Reports/Planning bootstrap уже задаёт чтение и группы `reports-task-tracker` / `planning-task-tracker`; выдача их секретов производится самим потребителям.

### Конфигурация backend

| Переменная | Значение / смысл |
|---|---|
| `KAFKA_BOOTSTRAP_SERVERS` | Список `host:port` через запятую, доступный из backend, например `kafka:9092` |
| `KAFKA_SECURITY_PROTOCOL` | `SASL_SSL` для общего стенда; по умолчанию в коде `PLAINTEXT`, поэтому задать явно |
| `KAFKA_SASL_JAAS_CONFIG` | `org.apache.kafka.common.security.scram.ScramLoginModule required username="task_tracker" password="<secret>";` |
| `KAFKA_SSL_TRUSTSTORE_LOCATION` | Путь **внутри backend-контейнера**, например `/run/certs/kafka-ca.jks` |
| `KAFKA_SSL_TRUSTSTORE_PASSWORD` | Пароль этого truststore |

Полный JAAS передаётся одним значением секрета. Ключи `KAFKA_TASK_TRACKER_PASSWORD` и `KAFKA_SSL_PASSWORD` принадлежат bootstrap Infra; backend напрямую их не читает.

Код не задаёт `ssl.truststore.type`; передать JKS truststore, чтобы не зависеть от автоматического определения PKCS12 конкретной JVM. Infra сейчас создаёт `kafka.truststore.p12`: подготовить для приложения отдельный JKS с публичным CA/сертификатом. Не копировать broker keystore с приватным ключом и не монтировать весь каталог `/var/lib/kafka/config` с admin credentials.

Монтировать truststore read-only; он должен читаться UID backend. Все broker DNS из `advertised.listeners` должны разрешаться из его сети и присутствовать в SAN сертификатов. `localhost:29092` из metadata внутри backend-контейнера указывает на сам backend и не подходит. Существующий INTERNAL listener `kafka:9092` соответствует общей Compose-сети.

Клиент отправляет не более 20 доступных событий за проход, пауза между проходами 5 секунд; отказ повторяется через 30 секунд, после пяти неуспешных попыток событие становится DEAD. DEAD блокирует последующие события агрегата. После исправления подключения администратор приложения выполняет `POST /api/v1/admin/outbox/{id}/retry`; просмотр — `GET /api/v1/admin/outbox` с правом `access.admin`. Это пользовательская административная роль трекера, а не Kafka admin.

Отдельный Kafka DLQ приложением не используется: недоставленные события остаются в PostgreSQL. Дополнительный `.dlq` topic/ACL сейчас не требуется. Пустой bootstrap отключает отправку, но события продолжают накапливаться в outbox. Автоматическая очистка SENT пока не реализована — срок хранения/обслуживание таблицы согласовать с командой приложения; не удалять PENDING/DEAD.

## 4. Подключение к общему развёртыванию

Просто добавить эти переменные в корневой `.env` недостаточно: секция `task-tracker-backend` общего Compose должна явно передавать их в контейнер и монтировать truststore. Изменения выполняет Infra; локальный `task-tracker/compose.integrations.yaml` не заменяет защищённую общую среду.

Пример дополнительного Compose-файла, подключаемого **после** общих файлов. `${...:?}` требует выдачи значения; реальные секреты не коммитить. Путь source для сертификата задаётся относительно первого Compose-файла либо абсолютным путём.

```yaml
services:
  task-tracker-backend:
    environment:
      S3_ENDPOINT: ${S3_ENDPOINT:?required}
      S3_BUCKET: arch-dev-task-tracker
      S3_ACCESS_KEY: ${S3_ACCESS_KEY:?required}
      S3_SECRET_KEY: ${S3_SECRET_KEY:?required}
      KAFKA_BOOTSTRAP_SERVERS: ${KAFKA_BOOTSTRAP_SERVERS:?required}
      KAFKA_SECURITY_PROTOCOL: SASL_SSL
      KAFKA_SASL_JAAS_CONFIG: ${KAFKA_SASL_JAAS_CONFIG:?required}
      KAFKA_SSL_TRUSTSTORE_LOCATION: /run/certs/kafka-ca.jks
      KAFKA_SSL_TRUSTSTORE_PASSWORD: ${KAFKA_SSL_TRUSTSTORE_PASSWORD:?required}
    volumes:
      - type: bind
        source: ${TASK_TRACKER_KAFKA_TRUSTSTORE_FILE:?required}
        target: /run/certs/kafka-ca.jks
        read_only: true
```

При частном CA S3 отдельно добавить truststore JVM из раздела 2. Не перезаписывать другие JVM-параметры при добавлении `JAVA_TOOL_OPTIONS`.

Backend должен находиться в сети с Kafka и MinIO; наружу публиковать их порты для работы трекера не требуется. Для Kubernetes передать те же переменные через Secret/ConfigMap и read-only volume. Конфигурация клиентов читается при старте: после смены endpoint/секретов/truststore перезапустить backend.

## 5. Что Infra передаёт команде приложения

- Окружение, DNS/порты S3 и Kafka, сетевые ограничения, порядок подключения override.
- Подтверждение приватного бакета, имени principal/access key и выданных прав.
- Секрет S3, полный SCRAM JAAS, Kafka truststore и его пароль — через менеджер секретов; ссылки на секреты вместо значений в issue/PR.
- Подтверждение SCRAM listener, IdempotentWrite ACL, topic parameters и сертификатов SAN.
- Для HTTPS S3 — CA и способ доверия JVM; для обоих сервисов — срок действия сертификатов и порядок ротации.
- Политики backup/restore бакета и БД, хранения Kafka, ответственного за эксплуатационные ошибки и дату совместной проверки.

## 6. Приёмка подключения

Проводить на выделенных тестовых карточках и ресурсах. `GET /actuator/health` сам по себе не подтверждает доступ к S3/Kafka: отдельных health indicators этих зависимостей пока нет.

### S3

1. Через UI/API загрузить небольшое вложение, скачать, сверить содержимое. В БД у нового вложения заполнены `object_key` и `sha256`, `content` — NULL.
2. Проверить, что анонимное скачивание объекта и доступ ключом соседней команды запрещены. Пользователь без прав на карточку не скачивает вложение через API.
3. Удалить вложение или тестовую карточку: появляется запись `object_cleanup`, после прохода уборщика объект отсутствует. Учесть минутный интервал.
4. На выделенной старой bytea-записи дождаться миграции и проверить скачивание и SHA-256 после очистки bytea. При отказе S3 старое содержимое не должно теряться.
5. Проверить повторное создание backend-контейнера: действующее вложение остаётся доступным из бакета.

### Kafka

1. Создать/изменить тестовую задачу. Авторизованный потребитель Reports/Planning получает событие из `task-tracker.events.v1` с ожидаемым aggregate ID; соответствующая строка outbox становится SENT.
2. Проверить metadata и отправку именно из сети backend с его SCRAM-учётной записью; успешный запрос административной учёткой эту проверку не заменяет.
3. На отдельном тестовом экземпляре прервать доступ к брокеру, выполнить изменение задачи: бизнес-данные и PENDING сохраняются. Восстановить доступ и дождаться SENT; после DEAD выполнить admin retry.
4. Подтвердить дедупликацию по eventId у потребителя: DB и Kafka не образуют общую транзакцию, повторная доставка допустима даже при `enable.idempotence=true`.
5. Зафиксировать фактический размер событий снимков итераций. Лимит топика — 1 MiB; если снимок превышает согласованный предел, он уйдёт в DEAD. Увеличение broker/topic/client limits требует совместного изменения, одной настройки топика недостаточно.

Текущий исполняемый набор eventType и статус draft описаны в [135](../block-g-api-and-events/135.event-catalog.md) и [140](../block-g-api-and-events/140.event-schema.md). Создание топика не является согласованием бизнес-контракта.

### Диагностика

| Признак | Что проверить |
|---|---|
| Kafka authentication failure | На брокере включён SCRAM-SHA-512, есть SCRAM credentials, JAAS использует ScramLoginModule |
| Topic/cluster authorization failure | Write/Describe топика и IdempotentWrite кластера для task_tracker |
| SSL handshake / hostname mismatch | Truststore доступен JVM, пароль/формат верны, SAN совпадает с advertised DNS |
| Bootstrap достигается, отправка висит | Все адреса из metadata доступны из backend; нет контейнерного localhost вместо broker DNS |
| S3 SignatureDoesNotMatch / AccessDenied | Ключ, секрет, region us-east-1, policy на attachments/*, path-style endpoint и часы узлов |
| S3 работает администратору, но не трекеру | Проверить именно сервисные ключи backend, не root credentials |
| Объекты не очищаются | Право DeleteObject, нет Object Lock, worker работает, after_at наступил, объект не связан с действующим вложением |
| Outbox остаётся PENDING | Bootstrap не пуст, broker доступен, нет более раннего PENDING/DEAD того же агрегата |
| Событие DEAD после восстановления | Выполнить admin retry; автоматического сброса DEAD нет |

Итог приёмки оформить ссылкой на прогон/логи без секретов, датой и участниками от Infra и Task Tracker. Проверенный локальный PLAINTEXT Kafka и S3-совместимый Moto из тестов не заменяют проверку общего SASL_SSL/MinIO-стенда.
