## Keycloak

Назначение — единая идентификация людей и сервисов. Схема: браузер → Authorization Code + PKCE → Keycloak → JWT → API; API использует JWKS, issuer, exp и audience.

| Вариант | Плюсы | Минусы |
|---|---|---|
| Keycloak OIDC + локальная проверка JWT | Принято в проекте, единый вход, нет своего пароля, нет сетевого запроса на каждую операцию | Изменение доступа требует учёта срока жизни JWT |
| Introspection на каждый запрос | Проверка актуального состояния токена | Зависимость каждой операции от IdP |
| Своя аутентификация | Полный локальный контроль | Дублирование инфраструктуры и нарушение общей архитектуры |

Выбрана локальная проверка JWT и серверные права. Проверка: неверный issuer/audience/exp даёт 401; недостаточная роль — 403. Локальный допуск хранит права на трекер, не HR-профиль.

## Planning System

Назначение — получить план и вернуть факт. Схема: Planning → PUT версии проекта → транзакция проекции/аудита/outbox → REST facts и Kafka → Planning.

REST проще проверять и явно подтверждает применение версии; Kafka удобна для доставки изменений, но требует обработки дублей; Excel годится для ручной работы и не заменяет интеграцию планирования. Выбраны REST для команд плана и факта, Kafka для изменений. `version` — положительное целое; одинаковая версия с одинаковым JSON идемпотентна, иной JSON/устаревшая версия — 409. План — upsert-пакет: отсутствие задачи в новом пакете не удаляет её. Явное retirement сохраняет фактические данные. Сопоставление существующего элемента только через localWorkItemId; привязка неизменяема.

Ожидаемый результат: проект/эпик имеют одного мастера, задача и факт остаются в трекере. Проверка: повтор, stale/conflict, ошибка любого элемента откатывает пакет, retirement сохраняет время и историю. Арифметический `remainingHours = plannedHours − actualHours`, включая отрицательные значения, не выдаётся за прогноз будущих часов Planning System.

## Reports: события и ETL

REST-опрос прост и позволяет bootstrap, но имеет лаг и не хранит удалённые элементы. Kafka уменьшает лаг и передаёт tombstone, но требует брокера, ключей, повторов и идемпотентного потребителя. Файловый snapshot позволяет большие пакеты, но требует manifest, checksum и согласования моментального среза.

Выбраны Kafka через transactional outbox и REST для первичного/пакетного чтения и сверки. Отправка после commit; подтверждение Kafka и отметка БД не составляют общую транзакцию, поэтому возможны дубли. DEAD в БД блокирует следующие события агрегата; после исправления администратор повторяет отправку. Копия в Kafka DLQ отправляется по возможности, DB dead-letter остаётся источником восстановления при отказе брокера. Потребитель хранит обработанные eventId в одной транзакции с витриной, не суммирует часы по WorkItemFieldsChanged и TimeLogged дважды.

ETL выполняет Reports: извлечь все страницы, преобразовать в staging, сверить ID/количество, затем атомарно заменить или upsert витрину. REST-страницы согласованы внутри одного запроса, но весь многостраничный обход не обещает единого snapshot; сверять изменения по событиям и повторным проходом. Проверка: первичная загрузка, повтор без двойного учёта, пропавшая страница не завершает пакет, удаление получено событием.

## Reference Manager

Предполагаемый единый snapshot отвергнут: поставщик описывает отдельные коллекции. Kafka отвергнута для этой связи по текущему контракту Reference Manager. Выбрано постраничное REST-чтение `/v1/employees` и `/v1/org_units` (`pageSize`/`pageToken`, без total — `reference-manager/documents/130.api-contracts.md`), параметр фильтра удалённых называется у поставщика `allowDeleted`, не `show_deleted`. `org_units.kind` (`DEPARTMENT`/`TEAM`) уже реализован и совпадает с нашей проекцией команда/подразделение. Поле `account_user_id` для связи сотрудника с JWT `sub` у поставщика пока не реализовано — это целевое поле из его FR-RM-53..58, а не текущий контракт; до его появления проекция не может надёжно сопоставить сотрудника с subject'ом токена. Жизненный цикл сотрудника у поставщика — `employment_state` (`EMPLOYED`/`DISMISSED`, меняется через `POST /v1/employees/{id}/dismiss`) и отдельный общий признак `is_deleted`; значения `PENDING`/`ENABLED`/`DISABLED` относятся к другой, также пока не реализованной оси `account_state` (состояние Keycloak-аккаунта), а не к самому сотруднику — наша прежняя формулировка «сотрудник PENDING» смешивала эти три разные вещи. Версия кэша — локальный hash проекции, не версия snapshot поставщика. Данные salaries/absences не запрашиваются этим адаптером.

Все страницы загружаются до замены кэша; timeout 6 секунд на вызов, connect 3 секунды, до 3 попыток для сети/5xx/429. Сбой оставляет последнюю успешную проекцию. Проверка: вторая страница, ошибка промежуточной страницы, циклический page token, дубли sub, увольнение, fallback. Согласованность страниц поставщика остаётся предметом DEC-TT-03.

## QA

REST создаёт дефект с непосредственным подтверждением; очередь потребовала бы отдельного статуса запроса и сверки; ручной перенос теряет связь с источником. Выбран защищённый POST bugs, дедупликация (externalSource, externalDefectId), настраиваемая таблица severity→priority и read-only API. Проверка: 201 при создании, 200 при повторе, 401/403/422 при ошибках. Потребность QA в вехах и проектных ссылках фиксируется в DEC-TT-04, не объявляется закрытой наличием API итераций.

## MinIO

Хранение bytea даёт транзакционность БД, но увеличивает её объём и не соответствует принятому файловому обмену. Локальный диск прост, но привязывает экземпляр к файловой системе. Выбран MinIO/S3: приватный бакет, immutable key по UUID вложения, метаданные/SHA-256 в БД, скачивание через проверяющий права API; публичные ссылки не выдаются. Лимит 10 MiB по умолчанию, MIME allowlist конфигурируется.

Перед upload создаётся устойчивая reservation очистки. При commit объект остаётся; при rollback/crash удаляется фоновым worker после окна 1 час. Удаление вложения/hard delete ставит объект в очередь очистки в транзакции. Legacy bytea читается до фонового переноса; очищается только после чтения объекта и совпадения SHA-256. Сетевые операции не входят в транзакцию S3+БД. Проверка: upload/download, запрет чужого доступа, отказ S3, rollback upload, миграция и повторяемая очистка.

## Уточнение выбора на 12.10.2026

Контрольные даты реестра — внутренние даты повторной проверки Task Tracker, а не обещания контрагентов. Ответы и ссылки на письменные решения ещё не получены; по истечении даты ответственные фиксируют результат или переносят срок с причиной. DEC-TT-02 подписывают архитектор и Infra с потребителями; до подписания Kafka остаётся целевым предложением.

Для текущего локального релиза выбран временный REST-опрос: Reports читает все страницы `/api/v1/reports/{work-items,iterations,time-logs,statuses,history}` каждые 5 минут (интервал подтверждён документами Reports: `reports/docs/vision.md`, `075.nfr.md` NFR-04.2, `146.logic-scheme.md` — не 60 секунд, как было написано здесь ранее), QA — разрешённые GET задач, комментариев и итераций из [130](../block-g-api-and-events/130.api-contracts.md) каждые 60 секунд (подтверждено `qa/docs/vision.md`). Интервалы у двух потребителей разные, не общий «тот же интервал». Цикл выполняет потребитель, не Task Tracker; сервисная роль Reports не даёт доступа к обычным GET, для QA требуется отдельно согласованная учётная запись чтения без ролей testing-service/reports-service, с локальным допуском (у QA это открытый пункт `Q-09`, пока не выдано). Плановая задержка — до интервала потребителя плюс длительность обхода при исправной сети; измерений и гарантии SLO пока нет. Пропущенный цикл увеличивает лаг. Для удалений требуется полная сверка ID; история удалённой задачи не сохраняется этим способом. Реализация опроса у соседей подтверждена документами обеих команд; совместный прогон — нет. Опрос не закрывает требование очередей.
