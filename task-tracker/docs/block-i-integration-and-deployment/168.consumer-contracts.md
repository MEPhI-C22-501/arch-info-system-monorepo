# Контракты Task Tracker для соседних команд

Срез на 23.11.2026. Пути ниже начинаются с `/api/v1`. Схемы запросов и ответов опубликованы в [OpenAPI](../block-g-api-and-events/openapi.yaml), типы сообщений — в [каталоге событий](../block-g-api-and-events/135.event-catalog.md#исполняемый-срез-после-разбора-01112026).

## Planning System

Роль `planning-service` в аудиенсе `task-tracker` проверяется в `PlanningController`. Источником плана для явно привязанных проектов, эпиков и задач служит Planning System. Локальные элементы создаёт Task Tracker. `PUT /planning/projects/{externalId}` принимает целое положительное число `version` для всей публикации. Повтор того же документа с той же версией возвращает `already-applied`. Старая версия или другой документ с той же версией дают 409. Для привязки ранее созданной карточки передайте её UUID как `localWorkItemId`. Привязка постоянна и проверяется по `externalId` в рамках проекта.

На стороне Task Tracker UUID проекта подходит для `externalId` в пути, `versionNumber` передаётся в `version`, имя в `title`, даты в `startDate` и `dueDate` формата ISO date. Эпик передаётся в `epics[]` с его `logicalItemId` в `externalId`. Для `tasks[]` принимается одна карточка и один `assigneeId` на элемент. Правило сопоставления FEATURE и сведения нескольких назначений к одному исполнителю остаётся в [#145](https://github.com/MEPhI-C22-501/arch-info-system-monorepo/issues/145).

`GET /planning/projects/{externalId}/facts` возвращает страницы факта по локальному дереву привязанного проекта с теми же полями, что `/reports/work-items`. В проекцию могут входить локальные дочерние элементы, поэтому потребитель сопоставляет записи по возвращённому `id`. `assigneeId` — Keycloak `sub`. Для анализа факта используются абсолютные `actualHours` и `plannedHours`, а `remainingHours` равно `plannedHours - actualHours` и может быть отрицательным. При агрегации используйте один уровень дерева, так как родитель включает факт дочерних элементов.

`WorkItem.version` начинается с 0 и увеличивается при изменениях карточки. `WorkItemFieldsChanged.payload.version` — версия карточки после изменения. Изменение дочернего элемента может изменить агрегированные часы родителя без увеличения его версии. При сверке факта заменяйте актуальными значениями и родительские агрегаты. `TimeLogged` сообщает о созданной записи по `timeLogId` и содержит её часы. Для пересчёта абсолютного факта перечитайте REST, а для учёта отдельных записей применяйте каждую запись один раз по ID. Версия публикации отделена от версий карточек.

`DELETE /planning/projects/{externalId}?version=N` снимает публикацию. Используйте версию выше текущей. Повтор снятия с той же версией идемпотентен. Карточки, история и привязки сохраняются, факт остаётся доступным. Отсутствие элемента в следующей публикации также сохраняет его. Физическое удаление допускается для непривязанного элемента по правилам Task Tracker и публикует `WorkItemHardDeleted` с `workItemId` в payload и в `aggregateId`. В REST удалённой карточки нет. Сверяйте удаление по полному обходу в той же области данных.

Встречное подтверждение владельца проекта/эпика, маппинга и формата событий требуется от Planning System. Их реестр уже ссылается на наш OpenAPI и фиксирует различия. Совместный прогон приёмника остаётся открытым. [Реестр Planning System](../../../planning-system/docs/integration-agreements.md#task-tracker-d-01)

## Reports

Основной интерфейс загрузки — REST под ролью `reports-service`. Пакетный ETL по REST согласован 10.11.2026 (Q-REP-03). `POST /exports/work-items` формирует XLSX для пользователей Task Tracker и требует пользовательских прав. [Решение Reports](../../../reports/docs/162.integration-spec.md#1-реестр-согласований)

| GET | Поля записи | Фильтры |
|---|---|---|
| `/reports/work-items` | `id,type,title,description,statusId,version,assigneeId,dueDate,plannedHours,actualHours,remainingHours,iterationId,parentId,priorityId,severity,children,projectId,status,updatedAt` | `projectId,iterationId,type,assigneeId,status,periodFrom,periodTo`. Период по `updatedAt`, включительно |
| `/reports/time-logs` | `id,workItemId,userId,loggedDate,hours` | Те же фильтры. Период по `loggedDate`, `assigneeId` здесь означает автора записи |
| `/reports/iterations` | `id,name,startDate,endDate,state,baseline,result` | `periodFrom,periodTo`. Интервалы должны пересекаться |
| `/reports/history` | `id,workItemId,actorId,occurredAt,changedFields,oldValues,newValues` | `periodFrom,periodTo` по времени записи, включая обе даты |
| `/reports/statuses` | `id,name,boardOrder,category,active` | Массив без пагинации |

Типовая страница имеет поля `items,page,pageSize,total,totalPages`. Нумерация с 1, по умолчанию 100 записей, максимум 500. Один запрос использует согласованный срез, границы страниц могут сдвинуться между запросами. Обходите все страницы, загружайте промежуточный набор по `id` и публикуйте его после успеха всей загрузки. Повтор чтения должен обновлять строку по ключу. По частичному набору нельзя вывести удаление. Восстановление после пропуска цикла проверяется полной сверкой с источником.

Kafka дополняет REST для оперативных обновлений. Ключ агрегации — `aggregateId`, ключ повторной доставки — `eventId`. Сохраните обработанный `eventId` и изменения проекции в одной транзакции потребителя. ID Kafka-партиции и offset относятся к транспорту. Пропуски и удаления сверяются полным чтением. Подключение и ACL на общем стенде требуют совместной проверки.

## QA и дефекты

`POST /bugs` под ролью `testing-service` принимает `externalSource,externalDefectId,title,description,severity`, хотя бы одно из `environment,build` и хотя бы одно из `testRunUrl,testCaseUrl`. Допустимы `critical,high,medium,low`. Выставляется начальный приоритет по справочнику `severity_priority`. Ответ 201 содержит `id,status,workItemUrl`, повтор по той же паре внешних идентификаторов возвращает 200 и прежнюю карточку. Kafka публикует обычное `WorkItemCreated` с `type=BUG` и парой внешних идентификаторов. Отдельное право `qa-tracker-reader` даёт чтение карточки и комментариев по известному ID. [Контракт QA](../../../qa/docs/130.api-contracts.md)

## Reference Manager и общий доступ

`DirectoryService` получает токен `client_credentials` для `tracker-directory` и передаёт его в `GET /v1/profiles?includeInactive=true` и `GET /v1/org_units/?allowDeleted=true`. Infra выдаёт этому клиенту audience `reference-manager` и роль `reference-reader`. Проекция использует `profiles.userId` как Keycloak `sub`, исключает технические записи, считает профиль активным при `EMPLOYED`, `ENABLED` и `isActive=true`. `orgUnitId` и цепочка `parent_id` дают команду и подразделение. При сбое страницы остаётся предыдущий кэш.

Исходящий клиент `tracker-planning` с `S-03` объявлен в общем realm Infra. Task Tracker использует входящую роль `planning-service` для REST и Kafka для публикации изменений. На 23.11.2026 запрошенное ревью требует решения Infra и Planning System об удалении `tracker-planning` и выданных ему прав, если исходящие вызовы остаются вне утверждённого обмена.
