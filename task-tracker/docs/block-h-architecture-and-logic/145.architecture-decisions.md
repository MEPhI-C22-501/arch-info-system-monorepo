# 145 — ADR

> Формат — см. [`../documents-composition.md`](../documents-composition.md#145--adr-145architecture-decisionsmd).
> Связаны с [075 NFR](../block-c-requirements-and-roles/075.nfr.md) и [146 Logic Scheme](146.logic-scheme.md).

**ADR-001. Единая таблица рабочих элементов с дискриминатором типа**
- Контекст: пять типов (Проект/Эпик/Задача/Ошибка/Подзадача) образуют одну иерархию с общими атрибутами и процессами (статус, приоритет, история, уведомления).
- Решение: хранить все типы в одной таблице `WORK_ITEM` с полем `type` и self-referencing `parent_id`, а не в отдельных таблицах на тип.
- Последствия: (+) один набор запросов для бэклога/доски/истории независимо от типа, проще каскадные операции; (−) часть колонок неприменима к некоторым типам (например, `planned_hours` не вводится для `Проект`/`Эпик` напрямую), требуется валидация на уровне приложения.

**ADR-002. Уведомления — только встроенные, без внешнего канала на первом этапе**
- Контекст: vision.md требует уведомление при любом изменении, но не упоминает email/push.
- Решение: реализовать уведомления как внутреннюю сущность приложения (список в UI), без интеграции с внешними каналами доставки в первой версии.
- Последствия: (+) не требует дополнительной инфраструктуры и согласования с Infra; (−) пользователь должен зайти в систему, чтобы увидеть уведомление.

**ADR-003 (предлагается, требует согласования auth-модели). Проверка прав — на каждый запрос, на сервере**
- Контекст: NFR-003 ([075](../block-c-requirements-and-roles/075.nfr.md)) требует, чтобы права не определялись только интерфейсом.
- Решение: каждый API-запрос проверяет токен выбранного провайдера идентификации и разрешение по роли независимо от клиента. OIDC/Keycloak рассматривается как кандидат, но не считается утверждённым системными требованиями.
- Последствия: (+) устраняет обход через прямые вызовы API; (−) требует единого модуля авторизации и согласования локальной проверки JWT либо introspection; конкретная задержка зависит от выбранной схемы.

**ADR-004. Интеграция с сервисом отчётности — синхронный read-only REST, без Kafka**
- Контекст: vision.md фиксирует только API для чтения сервисом отчётности; публикация событий в шину не описана.
- Решение: реализовать `GET /api/v1/reports/...` с фильтрами и пагинацией; не публиковать события во внешнюю Kafka на этом этапе.
- Последствия: (+) меньше инфраструктурных зависимостей для первой версии; (−) актуальность данных на стороне сервиса отчётности ограничена частотой опроса, а не близка к реальному времени.

**ADR-005. Жёсткое удаление — отдельная защищённая операция**
- Контекст: vision.md различает архивирование (сохранение данных) и жёсткое удаление (безвозвратное).
- Решение: жёсткое удаление — отдельный эндпоинт с обязательным подтверждением, доступный только роли с явным правом, блокируется при наличии дочерних элементов.
- Последствия: (+) снижает риск случайной потери данных; (−) требует отдельного UI-потока подтверждения и отдельной проверки прав.

**ADR-006. Кэш пользовательских/оргданных с периодической синхронизацией**
- Контекст: сервис справочников может быть временно недоступен; система не должна блокировать чтение существующих задач.
- Решение: хранить локальный кэш (внешний ID, имя, команда, подразделение, активность, время синхронизации), обновляемый по расписанию и вручную администратором.
- Последствия: (+) устойчивость к недоступности внешнего сервиса; (−) возможна временная рассинхронизация данных об оргструктуре.

**ADR-007. Изменение, аудит и внутреннее уведомление — одна транзакция**
- Контекст: NFR-001/002/004 требуют, чтобы аудит и уведомление существовали только для успешного изменения и не терялись при штатной работе. Последовательные независимые записи оставляют окно частичного успеха.
- Решение: изменение агрегата, запись аудита и запись внутреннего уведомления выполняются в одной транзакции БД. Внутреннее доменное событие обрабатывается до commit; внешней Kafka в текущей архитектуре нет. Для hard delete уведомление хранит snapshot ID/наименования и nullable FK `ON DELETE SET NULL`.
- Последствия: (+) атомарность и отсутствие окна потери; (+) не требуется брокер; (−) транзакция становится шире, обработчики не должны выполнять сетевые вызовы и обязаны оставаться короткими.

**Трассировка NFR:** ADR-001 поддерживает NFR-001/005; ADR-002 и ADR-007 — NFR-004; ADR-003 — NFR-003; ADR-004/006 — NFR-001/006; ADR-005 — NFR-005. Эксплуатационные решения для NFR-008 намеренно не приняты до определения измеримых порогов.
