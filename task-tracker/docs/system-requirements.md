> Документ синхронизирован с [`vision.md`](vision.md) — vision.md является приоритетным
> источником продуктового направления; здесь фиксируются точные поля, ограничения, бизнес-правила
> и критерии приёмки, следующие из этого видения. Расширенный, структурированный по формату
> [`documents-composition.md`](documents-composition.md) разбор (глоссарий, use cases, RBAC,
> data model, API-контракты и т.д.) — в подпапках `block-a-context-and-scope/` … `block-i-integration-and-deployment/`.

## 1. Общая информация

### 1.2. Цель системы

Система должна предоставлять команде единое пространство, в котором можно:
- регистрировать и декомпозировать рабочие элементы — проекты, эпики, задачи, ошибки и подзадачи;
- планировать сроки и трудоёмкость работ;
- назначать ответственных;
- управлять приоритетами и статусами;
- планировать доступную ёмкость участников и итерации, контролировать их выполнение;
- отслеживать фактически затраченное и оставшееся время;
- вести обсуждение и совместную работу через комментарии, вложения и историю изменений;
- получать уведомления об изменениях, затрагивающих назначенные рабочие элементы;
- интегрироваться с сервисом тестирования, сервисом отчётности и сервисом справочников через API;
- обмениваться данными через файлы Excel.

### 1.3. Границы системы

В состав системы входят:

- бэклог рабочих элементов;
- канбан-доска;
- карточка рабочего элемента, комментарии и вложения;
- иерархия рабочих элементов (`Проект → Эпик → Задача или Ошибка → Подзадача`);
- история изменений с diff-просмотром;
- учёт трудозатрат и планирование доступной ёмкости участников;
- управление итерациями;
- встроенные уведомления;
- жёсткое удаление рабочих элементов;
- API для создания ошибок сервисом тестирования, для чтения данных сервисом отчётности и для
  синхронизации с сервисом справочников (пользователи, команды, подразделения);
- импорт и экспорт данных в формате Excel.

Обмен через Excel — это ручной, пользовательский способ переноса и пакетного редактирования
данных; он не заменяется и не конфликтует с API-интеграциями сервисов тестирования, отчётности
и справочников (см. разделы 4.14–4.17), которые обслуживают автоматический обмен между
системами.

## 2. Термины

| Термин | Определение |
| --- | --- |
| Рабочий элемент | Общее название единицы работы одного из пяти типов: Проект, Эпик, Задача, Ошибка, Подзадача. |
| Проект | Верхнеуровневая инициатива, объединяющая эпики и задачи общей целью. |
| Эпик | Крупный блок работ внутри проекта, декомпозируется на задачи и ошибки. |
| Задача | Самостоятельная единица плановой работы с исполнителем, сроками и трудоёмкостью. |
| Ошибка | Вид рабочего элемента, описывающий дефект или некорректное поведение; может создаваться сервисом тестирования через API. |
| Подзадача | Часть задачи или ошибки, выделенная для отдельного выполнения и контроля. |
| Бэклог | Общий упорядоченный список рабочих элементов, зарегистрированных в системе. |
| Итерация | Ограниченный период выполнения работ с датами, состоянием и составом рабочих элементов. |
| Базовый план итерации | Состав задач и суммарная плановая трудоёмкость, зафиксированные при переводе итерации в состояние «Активна». |
| Ёмкость участника | Доступное время участника в часах на период итерации. |
| Плановая трудоёмкость | Оценка времени, необходимого для выполнения исполнимого рабочего элемента. |
| Фактическая трудоёмкость | Время, фактически затраченное на выполнение элемента; сумма записей трудозатрат. |
| Оставшееся время | Расчётное количество часов, которое осталось затратить: `актуальный план − факт`. |
| Дочерний элемент | Элемент, созданный в рамках декомпозиции другого, родительского элемента. |
| История изменений (аудит) | Хронологическая последовательность записей об изменениях карточки: автор или источник, дата, изменённые поля, старые и новые значения. |
| Вложение | Файл, прикреплённый к рабочему элементу. |
| Уведомление | Встроенное сообщение пользователю о событии, затрагивающем назначенный ему рабочий элемент. |
| Жёсткое удаление | Безвозвратное физическое удаление рабочего элемента и всех зависимых данных. |
| Архивирование | Перевод рабочего элемента в завершающий статус без удаления данных. |

## 3. Пользователи и роли

Предварительно выделяются следующие роли:

| Роль | Основные возможности |
| --- | --- |
| Участник команды | Просмотр назначенных рабочих элементов, изменение их статуса на канбан-доске, комментирование, работа с вложениями, регистрация фактических трудозатрат, просмотр своих уведомлений. |
| Руководитель / планировщик | Ведение бэклога, декомпозиция рабочих элементов, назначение исполнителей, управление приоритетами, планирование ёмкости участников, планирование и контроль итераций. |
| Администратор | Управление статусами, типами рабочих элементов, пользователями и правами доступа; ручной запуск синхронизации с сервисом справочников; жёсткое удаление рабочих элементов. |

Внешние системы — сервис тестирования, сервис отчётности и сервис справочников — взаимодействуют
с Task Tracker через API как отдельные сервисные клиенты, а не через пользовательский интерфейс;
их права ограничены конкретными операциями (см. разделы 4.14–4.17).

## 4. Функциональные требования

### 4.1. Управление бэклогом

- Система должна хранить единый бэклог рабочих элементов.
- Пользователь с соответствующими правами должен иметь возможность создать, просмотреть, изменить, архивировать и безвозвратно (жёстко) удалить рабочий элемент.
- Система должна поддерживать пять типов рабочих элементов: «Проект», «Эпик», «Задача», «Ошибка» и «Подзадача».
- Для каждого рабочего элемента система должна хранить уникальный идентификатор.
- Пользователь должен иметь возможность отбирать и сортировать рабочие элементы как минимум по типу, статусу, приоритету, исполнителю и итерации.
- Пользователь должен иметь возможность открыть карточку рабочего элемента из бэклога.

### 4.2. Карточка рабочего элемента

- Карточка рабочего элемента должна содержать следующие поля:
  - идентификатор;
  - наименование;
  - описание (в виде markdown);
  - тип рабочего элемента;
  - статус;
  - приоритет;
  - исполнитель;
  - дата начала;
  - срок выполнения;
  - плановая трудоёмкость в часах (для исполнимых элементов нижнего уровня — вводится, для родительских — рассчитывается, см. 4.9);
  - фактическая трудоёмкость в часах;
  - оставшееся время в часах;
  - итерация;
  - родительский элемент, если он существует;
  - комментарии;
  - вложения;
  - история изменений.

- Наименование должно быть обязательным для заполнения.
- Плановая и фактическая трудоёмкость не должны принимать отрицательные значения.
- Срок выполнения не должен быть раньше даты начала.
- Пользователь должен иметь возможность назначить на рабочий элемент одного ответственного исполнителя.
- Система должна сохранять изменения карточки и фиксировать их в истории (см. 4.8).

### 4.3. Иерархия и декомпозиция рабочих элементов

- Пользователь должен иметь возможность создать дочерний элемент для существующего рабочего элемента.
- Базовая иерархия строится как `Проект → Эпик → Задача или Ошибка → Подзадача`.
- Система должна отображать родительский элемент и список его непосредственных дочерних элементов.
- Дочерний элемент должен иметь собственные статус, исполнителя, сроки и трудоёмкость.
- Система не должна допускать циклических связей в иерархии рабочих элементов; родительский и дочерний элемент не могут быть одним и тем же элементом.

### 4.4. Статусы и канбан-доска

- Система должна отображать рабочие элементы на канбан-доске.
- Каждому статусу должна соответствовать колонка канбан-доски.
- Пользователь должен иметь возможность изменить статус элемента путём его перемещения между колонками.
- После перемещения система должна сохранить новый статус, отобразить элемент в соответствующей колонке, зафиксировать изменение в истории (4.8) и создать уведомление исполнителю (4.11).
- Администратор должен иметь возможность создавать, переименовывать, упорядочивать и деактивировать статусы.
- Канбан-доска должна поддерживать фильтрацию как минимум по исполнителю, приоритету и итерации.

### 4.5. Приоритеты

- Каждому рабочему элементу должен назначаться приоритет.
- Пользователь с соответствующими правами должен иметь возможность изменить приоритет.
- Система должна позволять сортировать и фильтровать рабочие элементы по приоритету.
- Перечень значений приоритета должен быть единым для всех рабочих элементов.

### 4.6. Комментарии

- Пользователь должен иметь возможность добавить текстовый комментарий к рабочему элементу.
- Для каждого комментария система должна отображать автора, дату и время создания.
- Комментарии должны отображаться в карточке в хронологическом порядке.
- Правила изменения и удаления комментариев должны определяться правами пользователя.

### 4.7. Вложения

- Пользователь должен иметь возможность прикрепить файл к рабочему элементу.
- Пользователь должен иметь возможность просмотреть список вложений и скачать любое из них.
- Пользователь с соответствующими правами должен иметь возможность удалить вложение.
- Добавление и удаление вложения должно фиксироваться в истории изменений (4.8) и порождать уведомление (4.11).

### 4.8. История изменений (аудит)

- После каждого успешного изменения карточки система должна добавлять запись в историю изменений.
- Запись истории должна показывать автора изменения либо внешний источник (для изменений через API), дату и время, изменённые поля, предыдущие и новые значения.
- Пользователь должен иметь возможность открыть запись истории в формате diff — с визуальным выделением добавленных, удалённых и изменённых значений.
- История доступна пользователям, имеющим право на просмотр рабочего элемента, и не изменяется вместе с текущими значениями карточки.

### 4.9. Учёт трудоёмкости и планирование ёмкости

- Плановая трудоёмкость задаётся в часах для исполнимых элементов нижнего уровня: задач и ошибок без дочерних элементов, а также подзадач.
- Для проекта, эпика и родительской задачи система должна рассчитывать плановую, фактическую и оставшуюся трудоёмкость как сумму показателей дочерних исполнимых элементов; собственная оценка родителя в сумму не включается.
- Пользователь должен иметь возможность регистрировать фактически затраченное время отдельными записями с датой, количеством часов и автором.
- Фактическая трудоёмкость рабочего элемента должна рассчитываться как сумма всех зарегистрированных записей.
- Система должна рассчитывать оставшееся время по формуле: `актуальный план − фактическая трудоёмкость`.
- Если фактическая трудоёмкость превышает план, система должна показывать перерасход часов, а не скрывать его.
- Плановая, фактическая и оставшаяся трудоёмкость должны отображаться в карточке рабочего элемента.
- Руководитель должен иметь возможность задать доступную ёмкость каждого участника в часах на период итерации.
- При отборе и назначении задач в итерацию система должна сравнивать сумму оценок с личной и общей ёмкостью, показывать свободный резерв или перегрузку и предупреждать о задачах без оценки либо исполнителя — до запуска итерации.

### 4.10. Управление итерациями

- Пользователь с соответствующими правами должен иметь возможность создать, просмотреть, изменить и завершить итерацию.
- Для итерации должны храниться наименование, описание, дата начала, дата окончания и состояние.
- Система должна поддерживать как минимум состояния итерации «Запланирована», «Активна» и «Завершена».
- Пользователь должен иметь возможность включать рабочие элементы из бэклога в итерацию и исключать их из неё.
- Один рабочий элемент не должен одновременно входить более чем в одну незавершённую итерацию.
- При переводе итерации в состояние «Активна» система должна зафиксировать базовый план: исходный состав и плановую трудоёмкость. Последующие изменения оценки сохраняются в истории и не подменяют базовые показатели.
- Система должна отображать для итерации:
  - перечень входящих рабочих элементов;
  - количество элементов по статусам;
  - суммарную плановую, фактическую и оставшуюся трудоёмкость;
  - загрузку исполнителей относительно их ёмкости;
  - долю завершённых элементов.
- При завершении итерации система должна сохранить сравнение базового плана с фактом по элементам, исполнителям и итерации в целом.
- Незавершённые элементы завершённой итерации должны оставаться в бэклоге и быть доступными для последующего планирования.

### 4.11. Уведомления

- После любого успешного изменения рабочего элемента система должна создать встроенное уведомление для текущего исполнителя, если он назначен. К изменениям относятся: обновление полей или статуса, добавление комментария, вложения или трудозатрат, изменение связей, удаление элемента.
- При назначении или переназначении исполнителя отдельное уведомление получает новый исполнитель.
- Уведомление должно содержать идентификатор и наименование рабочего элемента, краткое описание изменения, автора, дату и время, а для существующего элемента — ссылку на его карточку.
- Пользователь должен видеть список своих уведомлений и иметь возможность отметить их прочитанными.
- Неуспешная операция не должна создавать уведомление.

### 4.12. Жёсткое удаление

- Пользователь с соответствующим правом может безвозвратно удалить рабочий элемент после явного подтверждения.
- Рабочий элемент и принадлежащие ему комментарии, вложения, записи трудозатрат и история изменений физически удаляются и не могут быть восстановлены через интерфейс или API.
- Если у элемента есть дочерние элементы, жёсткое удаление блокируется до их удаления или переноса.
- Операция должна выполняться атомарно и не должна оставлять нарушенных ссылок или зависимых данных.

### 4.13. Импорт и экспорт Excel

- Пользователь с соответствующими правами должен иметь возможность экспортировать рабочие элементы в файл формата `.xlsx`.
- Экспорт должен включать все поля карточки, необходимые для последующего восстановления данных посредством импорта, включая тип рабочего элемента, иерархию (родительский элемент) и итерацию.
- В экспорт должны включаться уникальные идентификаторы рабочих элементов и связанные справочные значения (статус, приоритет, исполнитель).
- Пользователь должен иметь возможность импортировать ранее экспортированный системой файл `.xlsx`.
- При импорте система должна создавать новые рабочие элементы и обновлять существующие по их уникальным идентификаторам.
- Перед применением импорта система должна проверить структуру файла, обязательные поля, форматы значений и ссылки на связанные сущности.
- При наличии ошибок система не должна частично применять некорректные строки без явного уведомления пользователя.
- После импорта система должна показать количество созданных, обновлённых и отклонённых записей, а также перечень ошибок.
- Экспортированный файл без изменений должен быть пригоден для обратного импорта без потери поддерживаемых данных.

### 4.14. Интеграция с сервисом тестирования

- Система должна предоставлять защищённую операцию API для создания рабочего элемента типа «Ошибка» по результатам тестирования.
- Запрос должен передавать как минимум: внешний идентификатор дефекта, наименование, описание, серьёзность, сведения об окружении или сборке, ссылку на тестовый запуск либо тест-кейс.
- Серьёзность должна преобразовываться в приоритет по согласованному правилу; статус новой ошибки определяется настройками процесса.
- Повторный запрос с теми же идентификаторами источника и дефекта не должен создавать дубликат — система должна вернуть ссылку на ранее созданную ошибку.
- Успешный ответ должен содержать внутренний идентификатор и ссылку на созданную (или ранее зарегистрированную) ошибку.
- Ошибки доступа, валидации и сопоставления справочных значений должны возвращаться вызывающему сервису в структурированном виде.
- В истории карточки должны фиксироваться внешний источник и исходный идентификатор дефекта.

### 4.15. Интеграция с сервисом отчётности

- Система должна предоставлять защищённое API только для чтения, через которое сервис отчётности получает данные о проектах, эпиках, задачах, итерациях, статусах и трудозатратах.
- API должно поддерживать фильтры по периоду, проекту, итерации, типу, статусу и исполнителю, а для больших выборок — пагинацию.
- В ответах должны использоваться стабильные идентификаторы, однозначные даты и время, согласованные единицы измерения.
- Данные должны быть достаточны для расчёта числа элементов по статусам, плановой, фактической и оставшейся трудоёмкости, доли завершённых элементов, просрочек и перерасхода.
- Сервис отчётности не должен получать данные, не необходимые для построения отчётов.

### 4.16. Интеграция с сервисом справочников

- Система должна обращаться к API сервиса справочников и получать сведения о пользователях, командах и подразделениях: стабильный внешний идентификатор, отображаемое наименование, признак активности.
- Внешние справочные значения используются при назначении исполнителей, фильтрации и формировании отчётности; изменять их средствами Task Tracker нельзя.
- Синхронизация должна выполняться периодически и может быть запущена администратором вручную.
- Последняя успешно полученная версия справочника должна кэшироваться, чтобы временная недоступность сервиса не блокировала чтение существующих рабочих элементов.
- Неактивные или исчезнувшие значения должны сохраняться в уже созданных элементах, но быть недоступны для новых назначений.
- Ошибки синхронизации должны быть видимы администратору.

### 4.17. Общие требования к API

- Все интеграции должны проходить аутентификацию и авторизацию от имени отдельного сервисного клиента и использовать защищённый транспорт.
- Контракты API должны документироваться в OpenAPI, версионироваться и сохранять обратную совместимость в пределах версии.
- Запросы и ответы должны использовать единый формат ошибок и идентификатор корреляции для трассировки.
- Изменяющие операции должны выполняться атомарно; повторяемые запросы должны быть идемпотентными там, где возможна повторная доставка.
- Для исходящих запросов должны задаваться тайм-ауты и ограниченные повторы; сбой внешнего сервиса не должен приводить к повреждению локальных данных.

## 5. Основные бизнес-правила

- Каждый рабочий элемент в любой момент времени имеет ровно один статус, один тип и один приоритет.
- Иерархия строится как `Проект → Эпик → Задача или Ошибка → Подзадача`; родительский и дочерний элемент не могут быть одним и тем же элементом, циклические связи запрещены.
- Плановая, фактическая и оставшаяся трудоёмкость родительского элемента рассчитываются как сумма показателей дочерних исполнимых элементов, без двойного учёта собственной оценки родителя.
- Оценка трудоёмкости вводится только для исполнимых элементов нижнего уровня (задачи и ошибки без дочерних элементов, подзадачи).
- Исполнитель может отсутствовать у элемента, находящегося в бэклоге, если иное не определено правилами процесса.
- Завершение рабочего элемента не удаляет его из системы; удаляет только явное жёсткое удаление (4.12).
- Значения времени хранятся и отображаются в часах.
- Оставшееся время вычисляется автоматически и не вводится пользователем вручную; отрицательный остаток отображается как перерасход, а не обнуляется.
- Один рабочий элемент не может одновременно входить более чем в одну незавершённую итерацию.
- Базовый план итерации фиксируется при переводе итерации в состояние «Активна» и не подменяется последующими изменениями оценок.
- Удаление пользователя, статуса, приоритета или итерации не должно приводить к потере связанных рабочих элементов.
- Жёсткое удаление элемента с дочерними элементами запрещено до их удаления или переноса.
- Повторный запрос сервиса тестирования с тем же внешним идентификатором дефекта не создаёт дубликат.
- Уведомление создаётся только при успешном завершении операции.

## 6. Пользовательские сценарии

### 6.1. Недельное планирование

1. Руководитель создаёт новую итерацию и задаёт её сроки.
2. Руководитель задаёт доступную ёмкость участников на период итерации.
3. Руководитель просматривает и при необходимости фильтрует бэклог.
4. Руководитель уточняет приоритеты, сроки и плановую трудоёмкость рабочих элементов.
5. Руководитель назначает исполнителей и включает выбранные элементы в итерацию.
6. Система показывает суммарную нагрузку по каждому участнику и предупреждает о перегрузке.
7. Руководитель переводит итерацию в активное состояние — система фиксирует базовый план.

### 6.2. Выполнение задачи

1. Исполнитель получает уведомление о назначении и открывает задачу.
2. Исполнитель переводит её в рабочий статус.
3. Исполнитель регистрирует затраченное время, при необходимости добавляет комментарии и вложения.
4. Система пересчитывает фактическое и оставшееся время и создаёт уведомления об изменениях.
5. После выполнения исполнитель переводит задачу в завершающий статус.

### 6.3. Декомпозиция

1. Пользователь открывает крупный рабочий элемент (проект, эпик или задачу).
2. Пользователь создаёт один или несколько дочерних элементов.
3. Пользователь задаёт для них исполнителей, сроки и оценки.
4. Система отображает созданные элементы в иерархии родительского элемента и в бэклоге, пересчитывает суммарную трудоёмкость родителя.

### 6.4. Контроль итерации

1. Руководитель открывает активную итерацию.
2. Система показывает распределение элементов по статусам, показатели трудоёмкости и загрузку исполнителей.
3. Руководитель выявляет просроченные элементы и элементы с перерасходом времени.
4. По окончании периода руководитель завершает итерацию; система сохраняет сравнение базового плана с фактом.
5. Незавершённые элементы возвращаются в доступный для планирования бэклог.

### 6.5. Автоматическая регистрация ошибки сервисом тестирования

1. Сервис тестирования обнаруживает дефект и вызывает API создания ошибки с внешним идентификатором дефекта и его характеристиками.
2. Система проверяет обязательные поля и отсутствие дубликата по внешнему идентификатору.
3. Система создаёт рабочий элемент типа «Ошибка», преобразует серьёзность в приоритет и фиксирует источник в истории.
4. Система возвращает сервису тестирования внутренний идентификатор созданной ошибки.
5. При повторном запросе с тем же внешним идентификатором система возвращает ссылку на уже созданную ошибку без дублирования.

### 6.6. Просмотр истории изменений

1. Пользователь открывает карточку рабочего элемента с историей изменений.
2. Пользователь переходит в блок истории и выбирает интересующую запись.
3. Система показывает предыдущие и новые значения полей в формате diff.

### 6.7. Обмен данными через Excel

1. Пользователь экспортирует рабочие элементы в файл `.xlsx`.
2. Пользователь изменяет допустимые значения в файле.
3. Пользователь загружает файл обратно в систему.
4. Система проверяет файл и показывает результат проверки.
5. При успешной проверке система создаёт или обновляет рабочие элементы и формирует отчёт об импорте.

## 7. Требования к интерфейсу

### 7.1. Страница бэклога

Страница должна содержать:

- таблицу или список рабочих элементов;
- основные поля: идентификатор, наименование, тип, статус, приоритет, исполнитель, срок, плановые, фактические и оставшиеся часы, итерация;
- элементы фильтрации и сортировки, включая фильтр по типу;
- действие создания рабочего элемента;
- действия импорта и экспорта Excel;
- действие жёсткого удаления (для пользователей с соответствующим правом, с подтверждением);
- переход к карточке выбранного элемента.

### 7.2. Канбан-доска

Страница должна содержать:

- колонки, соответствующие активным статусам;
- карточки рабочих элементов в колонках;
- возможность перемещения карточек между колонками;
- фильтры по исполнителю, приоритету и итерации;
- краткие сведения на карточке: идентификатор, наименование, тип, исполнитель, приоритет, срок и оставшиеся часы.

### 7.3. Карточка рабочего элемента

Страница должна содержать:

- все поля карточки;
- блок родительского и дочерних элементов;
- блок вложений с возможностью загрузки, просмотра, скачивания и удаления;
- историю зарегистрированных трудозатрат и форму добавления трудозатрат;
- список комментариев и форму нового комментария;
- историю изменений карточки с возможностью просмотра записи в формате diff;
- действия сохранения изменений, смены статуса и жёсткого удаления (при наличии права).

### 7.4. Страница итерации

Страница должна содержать:

- реквизиты и состояние итерации;
- список включённых рабочих элементов;
- ёмкость участников и текущую загрузку относительно неё;
- показатели плановой, фактической и оставшейся трудоёмкости;
- количество и долю завершённых элементов;
- распределение элементов по статусам;
- сравнение базового плана с фактом (после завершения итерации);
- действия добавления и исключения элементов, запуска и завершения итерации.

### 7.5. Уведомления

Страница должна содержать:

- список уведомлений пользователя, отсортированный по дате;
- признак «прочитано / не прочитано» и действие отметки как прочитанного;
- переход из уведомления в связанную карточку рабочего элемента.

### 7.6. Админ-панель

Страница должна содержать:

- управление статусами (создание, переименование, порядок, деактивация);
- управление типами рабочих элементов и правами ролей;
- ручной запуск синхронизации с сервисом справочников и отображение времени последней успешной синхронизации;
- журнал ошибок синхронизации.

## 8. Требования к данным

Система должна хранить как минимум следующие сущности и связи:

| Сущность | Основные данные и связи |
|---|---|
| Рабочий элемент | Поля карточки; тип (Проект/Эпик/Задача/Ошибка/Подзадача); связь со статусом, приоритетом, исполнителем, итерацией и родительским элементом; для внешне созданных ошибок — источник и внешний идентификатор дефекта. |
| Пользователь | Внешний идентификатор, отображаемое имя, команда, подразделение, признак активности — кэшируется из сервиса справочников, не редактируется в Task Tracker. |
| Статус | Идентификатор, наименование, порядок на доске и признак активности. |
| Приоритет | Идентификатор, наименование, порядок и признак активности. |
| Итерация | Наименование, описание, даты, состояние, базовый план (снимок состава и оценок на момент активации), связанные рабочие элементы. |
| Ёмкость участника | Итерация, внешний идентификатор пользователя, доступные часы. |
| Запись трудозатрат | Рабочий элемент, пользователь, дата, количество часов, необязательный комментарий. |
| Комментарий | Рабочий элемент, автор, текст, дата и время создания. |
| Вложение | Рабочий элемент, имя файла, размер, тип содержимого, ссылка на хранилище, кем и когда загружено. |
| Запись истории (аудит) | Рабочий элемент, автор или внешний источник, дата и время, изменённые поля, предыдущие и новые значения. |
| Уведомление | Получатель, связанный рабочий элемент (опционально), текст, дата создания, отметка о прочтении. |

## 9. Нефункциональные требования

- Операции изменения данных должны сохранять целостность и возвращать понятные ошибки.
- Для каждого изменения карточки должны фиксироваться автор или внешний источник, дата и время, изменённые поля, предыдущие и новые значения.
- Авторизация операций должна контролироваться на сервере в соответствии с ролью пользователя; система не должна полагаться только на скрытие элементов интерфейса.
- Уведомление должно создаваться только после успешного изменения и не должно теряться при штатной работе системы.
- Жёсткое удаление должно выполняться атомарно и не оставлять нарушенных ссылок или зависимых данных.
- Интеграционные операции должны быть наблюдаемыми: система фиксирует результат, длительность и идентификатор запроса, без записи секретов в журнал.
- Даты и время должны отображаться в согласованном часовом поясе и однозначном формате.
- Файлы экспорта Excel должны открываться в актуальных версиях Microsoft Excel и совместимых табличных редакторах.
- Требования к производительности, доступности, объёму данных, резервному копированию и восстановлению должны быть определены до ввода системы в эксплуатацию.

## 10. Критерии приёмки

Система может считаться соответствующей исходным пожеланиям, если одновременно выполняются следующие условия:

1. Пользователь может создать рабочий элемент любого из пяти типов со всеми обязательными атрибутами и увидеть его в бэклоге.
2. Рабочий элемент можно назначить исполнителю, приоритизировать, оценить в часах и привязать к итерации; для проекта/эпика/родительской задачи трудоёмкость рассчитывается как сумма по дочерним элементам.
3. Рабочий элемент отображается на канбан-доске и меняет статус при перемещении между колонками.
4. Для рабочего элемента можно создать дочерний элемент, добавить комментарий и вложение, зарегистрировать фактические трудозатраты.
5. Система корректно показывает плановые, фактические и оставшиеся часы, включая перерасход, и учитывает ёмкость участников при планировании итерации.
6. Пользователь может сформировать итерацию с базовым планом, контролировать её показатели и завершить без потери незавершённых элементов, получив сравнение плана с фактом.
7. Каждое изменение карточки фиксируется в истории и может быть просмотрено в формате diff.
8. При любом изменении рабочего элемента исполнитель получает встроенное уведомление; список уведомлений доступен и может быть отмечен прочитанным.
9. Пользователь с правом может безвозвратно удалить рабочий элемент без дочерних элементов; при их наличии удаление блокируется.
10. Сервис тестирования может создать ошибку через API без дублирования при повторном запросе; сервис отчётности может прочитать данные о задачах, итерациях и трудозатратах через защищённое API с фильтрами и пагинацией.
11. Рабочие элементы можно экспортировать в `.xlsx`, а полученный файл — импортировать обратно без потери поддерживаемых данных.
12. Некорректный файл импорта не приводит к незаметной частичной порче данных и сопровождается отчётом об ошибках.

## 11. Вопросы, требующие согласования

1. Точная модель авторизации и права каждой роли, включая право на жёсткое удаление и на просмотр истории чужих рабочих элементов.
2. Исходный набор статусов рабочих элементов и допустимые переходы между ними.
3. Исходный набор приоритетов.
4. Точное правило преобразования серьёзности дефекта в приоритет при создании ошибки сервисом тестирования.
5. Правила аутентификации сервисных клиентов, лимиты запросов, объёмы выборок и сроки хранения интеграционных журналов.
6. Нужно ли учитывать трудозатраты дробно, например с шагом 0,25 часа?
7. Требуются ли поиск, ограничения незавершённой работы (WIP) и иные показатели процесса сверх встроенных в итерацию (детальная аналитика делегирована сервису отчётности)?
8. Каковы ожидаемые число пользователей, количество рабочих элементов и требования к скорости работы?
9. Какие требования предъявляются к развёртыванию, резервному копированию, доступности и защите данных?
10. Какие поля и связанные данные должны переноситься через Excel: комментарии, трудозатраты, иерархия, итерации, вложения и справочники?
11. Как разрешать конфликты, если один и тот же рабочий элемент был изменён и в системе, и в экспортированном файле?
