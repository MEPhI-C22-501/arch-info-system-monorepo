# Решения для локального релиза Task Tracker

Этот документ фиксирует трактовку открытых вопросов раздела 11 [системных требований](system-requirements.md). Исходные критерии приёмки в разделе 10 сохраняются.

- Идентификация — Keycloak OIDC/JWKS с проверкой issuer и audience `task-tracker`; для людей дополнительно необходим локальный допуск. Стартовая матрица ролей задана в `070.role-matrix.md` и доступна администратору для изменения. Проверки исполняются на сервере.
- Исходные статусы: «Бэклог», «В работе», «На проверке», «Завершена», «Архивирована». Переход между любыми активными статусами допустим при разрешении `item.status`; категория завершения влияет на показатель готовности итерации. Администратор настраивает справочник и видимость колонок.
- Приоритеты: критический, высокий, средний, низкий. Одноимённое сопоставление серьёзности дефекта с приоритетом — начальная конфигурация; её можно изменить через `/admin/severity-mapping`.
- Часы хранятся с точностью до сотых. Отрицательный остаток показывает перерасход. План проекта, эпика и родительской задачи вычисляется по листовым потомкам; запись времени допускается только на листе.
- Excel переносит поля карточки, родителя и привязку к итерации. Комментарии, учёт времени и вложения не редактируются через таблицу. Версия защищает от устаревшего файла; весь импорт откатывается при любой ошибке.
- Справочник пользователей, команд и подразделений читается через версионированный snapshot-адаптер. До согласования реального API в локальном окружении используются только явно обозначенные демонстрационные пользователи.
- Сервис тестирования вызывает защищённый идемпотентный `POST /bugs`; сервис отчётности читает `GET /reports/*`. Загрузка данных в сервис отчётности, Planning System и Kafka не входит в этот локальный релиз; для них в документации нет согласованного внешнего контракта.
- Локальный релиз предназначен для разработки. Перед production необходимы отдельно согласованные SLO, лимиты, резервное копирование, секреты, нагрузочные и end-to-end испытания.
