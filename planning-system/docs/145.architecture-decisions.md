# 145 — Журнал архитектурных решений

Редакция 1.0, 05.10.2026. Проектирование; все ADR **предложены** командой
Planning System и требуют ревью. Дата принятия и ссылка на согласование добавляются
после решения владельца. Факт публикации документа не меняет статус ADR.
Исходные карточки ADR-C-01…07 перенесены сюда как ADR-001…007.

<a id="adr-001"></a>

## ADR-001 — Keycloak и серверные права

**Контекст:** NFR-02/03/16; роли интерфейса не защищают прямой API-запрос.
**Решение:** OIDC Authorization Code + PKCE для браузера, bearer access token для
API; проверка подписи, issuer, audience, exp через JWKS. Затем проверка операции,
области проекта/ресурса и поля по [070](070.role-matrix.md). Service accounts
имеют отдельные scopes. Пароли пользователей в Planning System не хранятся.
**Положительные последствия:** единая идентичность, проверяемые отказы 401/403.
**Отрицательные последствия:** зависимость от доступности входа и ротации ключей;
кэш JWKS не разрешает принимать неизвестную подпись. Привязка sub не равна роли НСИ.
**Альтернатива:** локальные аккаунты отвергнуты как дублирование Keycloak.

<a id="adr-002"></a>

## ADR-002 — API и расчётный worker

**Контекст:** NFR-01/09/15, пересчёт не должен удерживать HTTP-запрос.
**Решение:** API сохраняет задание и отвечает 202 с operationId; worker берёт
задание с lease из PostgreSQL, считает по фиксированному inputSnapshot и сохраняет
неизменяемый результат. Уникален ключ versionId + contentRevision + inputHash.
**Положительные последствия:** повторяемость расчёта, масштабирование API.
**Отрицательные последствия:** ожидание и устаревание результата видны пользователю;
lease, повтор и дедупликация результата требуют тестов. Ответ 202 не означает успех.
**Альтернатива:** синхронный расчёт проще, но связывает HTTP-тайм-аут с размером плана.

<a id="adr-003"></a>

## ADR-003 — Транзакционные инварианты

**Контекст:** NFR-04/05/14; два клиента могут утвердить разные редакции.
**Решение:** If-Match/revision, блокировка строки Project при активации, один ACTIVE
через частичный UNIQUE; содержимое после APPROVED неизменно. Аудит и outbox
записываются в транзакции бизнес-изменения; доставка выполняется после commit.
**Положительные последствия:** нет плана без аудита/намерения публикации.
**Отрицательные последствия:** конфликт 409/412 требует перечитать данные;
растёт объём исторических версий. Проверки циклов/горизонтов нужны сверх SQL FK.
**Альтернатива:** last-write-wins теряет решения и отвергнута.

<a id="adr-004"></a>

## ADR-004 — Надёжный обмен

**Контекст:** NFR-06/10/11; Kafka и HTTP допускают повтор и неизвестный результат.
**Решение:** outbox, inbox с UNIQUE(producer,eventId), абсолютные часы и
sourceRevision. Commit проекции и inbox предшествует подтверждению offset.
После сбоя между commit и ack повтор не меняет факт. Политика повторов и DLQ —
[140](140.event-schema.md); ручной повтор сохраняет eventId/idempotencyKey.
**Положительные последствия:** один бизнес-эффект при at-least-once.
**Отрицательные последствия:** нужны хранение ключей, мониторинг DLQ и сверка;
это не общая exactly-once транзакция с чужим сервисом.
**Альтернатива:** прямая отправка перед commit может опубликовать откатившийся план.

<a id="adr-005"></a>

## ADR-005 — Восстановление стенда

**Контекст:** NFR-07/08; одиночные PostgreSQL/Kafka/S3 не являются HA-кластером.
**Решение:** совместно с Infra резервировать БД и объекты; восстанавливать на
отдельной среде, сверять baseline, ключи объектов, inbox/outbox и доступы.
**Положительные последствия:** измеряемые RPO/RTO и контроль связности.
**Отрицательные последствия:** окно простоя, хранение копий и процедура восстановления;
предложенные в 075 пороги остаются неподтверждёнными до испытания.
**Альтернатива:** кластерная HA выходит за доказанный объём учебного стенда.

<a id="adr-006"></a>

## ADR-006 — Понятные состояния UI

**Контекст:** NFR-12; ноль, отсутствие входа и ошибка имеют разный смысл.
**Решение:** русский интерфейс, состояния loading/empty/error/stale/PARTIAL,
видимая revision и дата среза, подтверждение активации/архивации; см. [110](110.ui-ux.md).
**Положительные последствия:** пользователь понимает последствия решения.
**Отрицательные последствия:** каждый экран требует проверки состояний и клавиатуры.
**Альтернатива:** пустая таблица при сетевой ошибке вводит в заблуждение.

<a id="adr-007"></a>

## ADR-007 — Приватные вложения в S3

**Контекст:** NFR-13; БД и файловое хранилище не имеют общей транзакции.
**Решение:** отдельный бакет Infra, случайный objectKey; UPLOADING → AVAILABLE
только после проверки длины, фактического MIME и SHA-256. Выдача после RBAC;
DELETE_PENDING → DELETED после подтверждения S3. Предложенные 20 MiB и пять минут
для ссылки из 075 согласуются до реализации; секреты не передаются браузеру.
**Положительные последствия:** непроверенный объект не читается, БД не хранит blobs.
**Отрицательные последствия:** уборка зависших загрузок, повторы и затраты хранения.
**Альтернативы:** публичный бакет нарушает права; blobs в БД усложняют резервирование.

<a id="adr-008"></a>

## ADR-008 — Способ интеграции каждой связи

**Контекст:** смежные сервисы имеют разные гарантии и владельцев данных.
**Решение:** единая матрица обмена — [020 §3](020.system-context.md#3-единая-матрица-обмена).
Keycloak — OIDC/JWKS; Reference Manager — REST без событий НСИ; S3 — объектный API;
Task Tracker — HTTP-публикация и событийный факт с REST-сверкой; QA — REST-чтение
рамок и ссылки на итерации; Reports — оперативный REST и пакетный ETL;
уведомления — Kafka request/receipt. Обоснования альтернатив — [162](162.integration-spec.md).
**Положительные последствия:** транспорт соответствует синхронности потребности.
**Отрицательные последствия:** несколько адаптеров, отдельные контракты и мониторинг.
Внешняя Kafka Task Tracker и поставщик уведомлений ещё не подтверждены.

<a id="adr-009"></a>

## ADR-009 — Версии контрактов

**Контекст:** NFR-10, потребители обновляются независимо.
**Решение:** HTTP /api/v1 и semver 1.0.0 в спецификации; optional-поля и новые
операции — minor, исправление описания — patch. Удаление, изменение типа/смысла,
добавление обязательного входа — major с согласованием Task Tracker, Reports, QA.
Kafka: новый major — новый топик; старый и новый живут до подтверждения миграции.
**Положительные последствия:** контракты проверяются до выпуска.
**Отрицательные последствия:** период двойной поддержки; нельзя считать любое
добавление поля совместимым. Семантическую совместимость не докажет один валидатор.

<a id="adr-010"></a>

## ADR-010 — Кадровый источник и расчётные ставки

**Контекст:** [Reference Manager, требования](../../reference-manager/documents/system-requirements.md)
от 02.10 уже включают HR; [контракт](../../reference-manager/documents/130.api-contracts.md)
описывает employees, org_units, positions, assignments, salaries, absences.
**Решение:** ФИО/должность/подразделение/оклады/отсутствия — мастер Reference Manager.
employeeId = стабильное resource name employees/…, связь с Keycloak sub —
account_user_id в профиле; поиск по имени/email запрещён. Для стоимости нужен
hr-reader у адаптера и отдельный cost.read у потребителя. Оклад не считается
часовой ставкой: выбранная методика преобразования и норма часов входят в срез.
Календарные нормы, часовой пояс и почасовые расчётные ставки ведёт уполномоченный
ресурсный руководитель в Planning System как плановые предпосылки до появления
согласованного календарного источника. Они не изменяют HR-мастер.
**Положительные последствия:** источник личности определён; доступность воспроизводима.
**Отрицательные последствия:** обновление кэша и расхождения ручных предпосылок;
без подтверждённых норм/ставок результат PARTIAL. D-03 сохраняет только вопросы
календаря и проверки реального API; D-07 — методику стоимости.

<a id="adr-011"></a>

## ADR-011 — Прогноз и бюджет

**Контекст:** FR-10/NFR-15, арифметический остаток задачи не является ETC.
**Решение:** оценка до завершения по листьям из отдельного согласованного поля
Task Tracker либо явной оценки планировщика. Источник и автор входят в inputSnapshot.
Даты — размещение остатка в подтверждённом календаре с FS-зависимостями;
стоимость = фактические часы × датированная ставка + будущие часы × ставка,
только при полном покрытии часов ставками одной валюты. Корректировка = стоимость
− baselineBudget; конвертация валют вне первой методики. Если нет датированного
факта для ставки, неизвестны часы/валюта/норма, денежный итог null.
**Контрольный пример (синтетический):** факт 12 ч, ETC 8 ч, согласованная ставка
1 000 RUB/ч для всего периода, baseline 18 000 RUB → 20 ч, 20 000 RUB,
корректировка +2 000 RUB. При мощности 4 ч/рабочий день ETC занимает два
рабочих дня; выходные и зависимости сдвигают дату. Без ставки сохраняются часы,
стоимость null и PARTIAL. Из 20−12=8 совпадение с ETC не выводится автоматически.
**Положительные последствия:** проверяемый результат и объяснимые пропуски.
**Отрицательные последствия:** оценки требуют актуализации; D-07 остаётся до
принятия методики, входов и порога существенности владельцем продукта.

<a id="adr-012"></a>

## ADR-012 — Срезы для ETL и QA

**Контекст:** Reports нужна воспроизводимая загрузка, QA — рамки релиза.
**Решение:** Reports забирает неизменяемый export batch через постраничный API;
checkpoint только после staging → validate → merge всей партии. QA получает
release/iteration projection с projectId, planVersionId, logicalItemId и source.
Релиз — новый тип PlanItem RELEASE; итерация — проекция Task Tracker, связанная
с релизом, не второй мастер итераций. QA может читать её непосредственно из TT;
через Planning System передаётся явная ссылка с sourceRevision и dataAsOf.
**Положительные последствия:** повтор загрузки безопасен; не создаётся второй
источник итераций. **Отрицательные последствия:** нужны объём хранения batch,
ACL денежных полей и D-09 о маршруте итераций; до согласования контракт предложен.

<a id="adr-013"></a>

## ADR-013 — Технологическая граница реализации

**Контекст:** пока есть проектные документы и HTML-прототип.
**Решение:** предложить TypeScript для API/worker, PostgreSQL для транзакций,
статический web UI, Kafka/S3/Keycloak Infra. Конкретные библиотеки, версии и
digest фиксируются командой до сборки; схема компонентов — [150](150.component-diagram.md).
**Положительные последствия:** один язык бизнес-расчётов и контрактных фикстур.
**Отрицательные последствия:** стек ещё требует выбора библиотек и тестирования;
наличие прототипа не подтверждает готовность сервера или контейнеров.
