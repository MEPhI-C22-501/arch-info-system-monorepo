# 162 — Спецификация интеграционного решения

Редакция 1.0, 05.10.2026. Предложение к межкомандному согласованию.
Состав, направления и данные — единая [матрица 020](020.system-context.md#3-единая-матрица-обмена),
порядок и владельцы — [160](160.integration-plan.md). Здесь — выбор способа.

## INT-01 — Единый вход

Схема: браузер → Keycloak → токен → API → локальная проверка JWKS + RBAC.
Выбран OIDC: стандартная сессия и ротация ключей, зависимость от входа сохраняется.
Синхронная introspection на каждый запрос даёт быстрый отзыв, но добавляет сетевую
зависимость; локальные пароли создают второй реестр и исключены. Проверка:
невалидный issuer/audience/exp и чужая область отклоняются. ADR-001, T-INT-01.

## INT-02 — НСИ и кадровые входы

Схема: sync adapter → REST Reference Manager → кэш с name/etag → плановый срез.
REST поддерживается поставщиком и позволяет сверить все страницы/удалённые записи.
Kafka могла бы уменьшить задержку, но поставщик не публикует события; XLSX теряет
автоматическую актуальность и остаётся средством ручной работы у владельца.
employeeId хранит resource name, subject — account_user_id. Salary не становится
почасовой ставкой без методики. Проверка: деактивация/отсутствие, повтор страницы,
смена назначения на дату, чужие HR-поля; действующая baseline остаётся читаемой.
ADR-008/010, T-INT-02. Плановые нормы календаря принадлежат Planning System.

## INT-03 — План и факт Task Tracker

Схема: ACTIVE → Publication → HTTPS приёмник TT → receipt; TT → Kafka → inbox
→ TaskSnapshot → Forecast; после пропуска — авторизованная REST-сверка.
HTTP даёт адресный результат приёма версии. Kafka отделяет жизненный цикл задач
от расчёта; требует согласованных producer/consumer и DLQ. Только polling проще
на старте, но задерживает реакцию и требует полного удаления/tombstone протокола.
Общая БД исключена границей владения. Контракт TT-приёмника в [130](130.api-contracts.md)
является предложением, не уже существующим endpoint. Внутренние WorkItem-события
TT сами по себе не появляются в Kafka. Без D-01 реальная интеграция blocked.
Критерий: одна публикация/один учёт часов при десяти повторах, старый sourceRevision
не откатывает проекцию, явное удаление запускает сверку. ADR-004/008/011, T-INT-03.

## INT-04 — Оповещения

Схема: бизнес-причина → NotificationRequested → Kafka → поставщик →
NotificationDelivered → inbox. Выбран асинхронный канал: ожидание внешней доставки
не блокирует активацию. HTTP даёт синхронный ack приёма, но тоже требует отдельного
receipt доставки; прямой SMTP связывает модуль с каналом и дублирует инфраструктуру.
Kafka ack не равен DELIVERED. До назначения поставщика D-04 остаётся блокировкой.
Критерий: поздний receipt и ручной retry не создают второго сообщения.
ADR-004/008, [140](140.event-schema.md), T-INT-04.

## INT-05/08 — Reports и аналитическое хранилище

Оперативное чтение: Reports → REST projection → текущий разрешённый срез.
ETL: Reports → создать batch → страницы неизменяемого batch → staging Reports
→ проверки количества/уникальности → merge → checkpoint batchId.
Один REST-запрос к постоянно меняющемуся списку не гарантирует целостную выгрузку;
Kafka удобна для сигнала обновления, но не заменяет начальную загрузку/сверку.
S3-файлы экономят HTTP-запросы на больших объёмах, но требуют отдельного lifecycle
и ACL; первая версия использует batch REST, после замера объёма может перейти на S3.
Полный snapshot выбран до определения надёжного watermark изменений. Удаления
передаются tombstone/ARCHIVED, не угадываются по одной странице. При истечении batch
потребитель начинает новую партию; частичный staging не становится витриной.
Критерий: сбой на второй странице и повтор не удваивают часы, нет смеси версий
и денежных полей без cost.read. ADR-009/012, [130](130.api-contracts.md), T-INT-05/08.

## INT-06 — Вложения

Схема: авторизованный API → UPLOADING → S3 upload → проверка → AVAILABLE.
Выбран S3: потоковые файлы и независимый storage, сложнее согласование БД/объекта.
Blobs PostgreSQL дают одну транзакцию, но увеличивают БД и резервные копии;
локальный диск не подходит нескольким экземплярам API.
Критерий: размер/тип/хеш проверены, чужой objectKey недоступен; timeout не открывает
неполный объект, повтор удаления безопасен. ADR-007, T-INT-06.

## INT-07 — QA System

Схема: QA → GET release-context(projectId, planVersionId) → релизы, вехи,
эпики/фичи и ссылки на итерации источника Task Tracker. Читается только выбранная
утверждённая версия, со временем среза и качеством; ACTIVE определяется явно.
REST выбран для адресного получения нужной версии. Kafka PlanActivated может
инвалидировать кэш, но не заменяет выбор исторической версии. Общая таблица QA/PS
нарушила бы независимость модулей. Новая итерация в Planning System не создаётся.
Если TT-проекция недоступна, iterations=null, quality=PARTIAL и причина, а не []
как ложный признак отсутствия итераций. Маршрут итераций — D-09.
Критерий: QA связывает тест-план с устойчивым релизным ID, новая версия не меняет
старую привязку; чужой проект и неподтверждённый черновик отклонены.
ADR-012, [130](130.api-contracts.md), [135](135.event-catalog.md), T-INT-07.
