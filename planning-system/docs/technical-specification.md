# Техническое задание: Planning System

**Редакция:** 1.0
**Статус:** финальная
**Дата:** 17.09.2026

Документ составлен по структуре ГОСТ 34.602-2020. Видение продукта приведено в
[Vision](vision.md), техническая структура - в [архитектуре](architecture.md).

## 1. Общие сведения

Planning System - автоматизированная система портфельного, ресурсного и календарного
планирования проектов. Разработчик - команда Planning System. Сроки реализации
определяются планом команды.

## 2. Цели и назначение

Система предназначена для годового и скользящего планирования, обоснования
потребности в людях, управления сроками и формирования единого прогноза оставшегося
времени и бюджетных корректировок.

Цели: единая версия плана, раннее выявление дефицита людей, прозрачные последствия
переносов и автоматическое обновление прогноза по факту из Task Tracker.

## 3. Объект автоматизации

Автоматизируются процессы PMO, руководителей проектов и ресурсных руководителей:
создание проектов, декомпозиция, оценка, распределение сотрудников, календарное
планирование, утверждение версий и перепланирование.

Planning System хранит проекты и передает их в Task Tracker. Task Tracker хранит
задачи и возвращает данные об их исполнении.

## 4. Требования к системе

### 4.1. Состав

1. портфель и проекты;
2. декомпозиция и календарное планирование;
3. ресурсы и доступность;
4. версии, базовые линии и сценарии;
5. прогноз и бюджетные корректировки;
6. вложения и оповещения;
7. интеграции, отчеты и администрирование.

### 4.2. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Создавать и хранить проекты, программы и приоритеты |
| FR-02 | Формировать годовой и скользящий планы |
| FR-03 | Декомпозировать проекты на этапы, вехи, эпики и фичи |
| FR-04 | Оценивать часы и потребность по ролям и грейдам |
| FR-05 | Вести доступность и назначения сотрудников по периодам |
| FR-06 | Выявлять перегрузку, простой и дефицит ресурсов |
| FR-07 | Управлять датами, зависимостями и Гантом по проектам и людям |
| FR-08 | Создавать сценарии и показывать последствия сдвигов |
| FR-09 | Хранить неизменяемые утвержденные версии и базовые линии |
| FR-10 | Формировать единый прогноз оставшегося времени и бюджетных корректировок |
| FR-11 | Публиковать проекты, структуру, сроки и назначения в Task Tracker |
| FR-12 | Получать из Task Tracker события задач, статусы, историю и фактические часы |
| FR-13 | Прикреплять файлы к проекту, версии плана и сценарию; скачивать и удалять их по правам |
| FR-14 | Оповещать о создании и изменении связанных задач, конфликтах ресурсов и решениях по плану |
| FR-15 | Формировать отчеты по срокам, загрузке и отклонениям |

### 4.3. Бизнес-правила

- проект создается и изменяется в Planning System;
- задача и ее история создаются и изменяются в Task Tracker;
- обмен задачами выполняется через API и события, без файлового обмена;
- утвержденная версия плана неизменна; исправление создает новую версию;
- сценарий не меняет активный план до утверждения;
- назначение сверх доступной мощности отображается как конфликт;
- повторная доставка события не создает дубликат;
- вложение связано с автором, временем загрузки и объектом-владельцем.

### 4.4. Нефункциональные требования

- русский веб-интерфейс;
- аутентификация выполняется готовым Keycloak по OIDC/OAuth 2.0;
- отдельный сервис аутентификации не разрабатывается;
- доступ управляется ролями и областью проектов;
- критичные изменения аудируются;
- типовой экран открывается не более чем за 3 секунды;
- пересчет типового проекта выполняется не более чем за 10 секунд;
- ошибки внешних систем не повреждают последнюю утвержденную версию;
- вложения проверяются по размеру и допустимому типу;
- API версионируется, интеграционные операции идемпотентны.

### 4.5. Интеграции первой версии

| Система | Planning System получает | Planning System передает | Способ |
|---|---|---|---|
| Keycloak | идентификатор, профиль, роли и группы пользователя | стандартный запрос аутентификации | OIDC/OAuth 2.0 |
| Reference Manager | роли, грейды, календари и классификаторы | запросы по стабильным кодам | REST API / события |
| Task Tracker | события задач, статусы, история, комментарии и фактические часы | проекты, декомпозицию, сроки, назначения, прогноз остатка и бюджетные корректировки | REST API / события |
| Notification Service | результат доставки | запрос оповещения и шаблонные параметры | REST API / события |
| Reporting | - | версии плана, прогноз, загрузку и отклонения | REST API / события |
| Object Storage | файл и метаданные | загрузку, чтение и удаление вложений | S3-совместимый API |

Keycloak используется как готовый инфраструктурный компонент. Planning System не
хранит пароли и не реализует собственный процесс входа. Интеграции с Keycloak,
Reference Manager, Task Tracker, Notification Service и Object Storage входят в
первую версию.

### 4.6. Оповещения

Оповещения создаются при:

- создании или изменении связанной задачи;
- изменении срока, оценки или фактической трудоемкости;
- появлении ресурсного конфликта;
- отправке версии на согласование, возврате или утверждении;
- завершении пересчета прогноза с существенным отклонением.

Пользователь получает уведомление внутри приложения и через доступный канал
Notification Service. Повтор события не должен создавать повторное оповещение.

## 5. Состав работ

1. модель данных и контракты интеграций;
2. проекты, декомпозиция и версии;
3. ресурсы, календарь, Гант и сценарии;
4. скользящий прогноз и бюджетные корректировки;
5. Keycloak, справочники, Task Tracker, вложения и оповещения;
6. испытания, документация и демонстрация.

## 6. Порядок разработки

Разработка ведется итерациями в монорепозитории. API описывается в OpenAPI, события
- схемами сообщений, архитектурные решения - ADR. Изменения проходят review и
автоматические тесты.

## 7. Контроль и приемка

Приемка подтверждает, что пользователь может создать проект, сформировать годовой и
скользящий планы, распределить людей, увидеть Гант, сравнить сценарии, утвердить
версию, прикрепить файл, опубликовать проект в Task Tracker, получить события задач,
пересчитать прогноз и получить оповещение.

## 8. Подготовка к вводу

Необходимо настроить realm и clients в Keycloak, роли и грейды в Reference Manager,
доступы к Task Tracker, Notification Service и Object Storage, а также подготовить
демонстрационные проекты, сотрудников и календари.

## 9. Документирование

Комплект включает Vision, ТЗ, C4/UML-диаграммы, OpenAPI, схемы событий, руководство
пользователя и инструкцию запуска.
