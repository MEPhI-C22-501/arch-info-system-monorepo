# Техническое задание: Planning System

**Редакция:** 0.2, концептуальная  
**Дата:** 15.09.2026  
**Статус:** на согласование

Краткое ТЗ составлено по структуре ГОСТ 34.602-2020. Детализация продукта и процессов
приведена в [Vision](vision.md), архитектура - в [отдельном документе](architecture.md).

## 1. Общие сведения

Полное наименование: «Автоматизированная подсистема портфельного, ресурсного,
календарного и финансового планирования проектов Planning System».

- разработчик: команда Planning System (Борисова, Миндзяк, Смирнов);
- основание: описание подсистем проекта и ГОСТ 34.602-2020;
- плановый срок первой версии: уточняется после оценки;
- источник финансирования разработки: уточняется.

Planning System входит в `arch-info-system-monorepo` и взаимодействует с Task
Tracker, Keycloak, Reference Manager, финансовым и отчетным контурами.

## 2. Цели и назначение

Система предназначена для ежегодного и скользящего планирования проектов с учетом
сроков, людей и финансирования.

Цели:

- сформировать единую утвержденную версию портфеля;
- обосновывать потребность в ролях, грейдах и часах;
- выявлять перегрузку и дефицит ресурсов;
- контролировать сроки и последствия переносов;
- сопоставлять лимит, план, факт, прогноз и остаток бюджета;
- уменьшить ручное сведение данных Planning System и Task Tracker.

## 3. Характеристика объекта автоматизации

Автоматизируются процессы PMO, руководителей проектов, ресурсных руководителей и
финансовых контролеров: от выбора проектов до декомпозиции, распределения людей,
утверждения бюджета и перепланирования по факту.

Task Tracker является оперативным контуром: backlog, задачи, канбан, итерации,
статусы, исполнители, developer/tester, трудоемкость, история, тест-кейсы, прогоны и
дефекты. Planning System не дублирует эти функции, а использует их данные.

Система создается как учебная/демонстрационная; промышленный режим и масштаб
согласуются отдельно.

## 4. Требования к системе

### 4.1. Состав

1. портфель и годовые планы;
2. декомпозиция проектов;
3. ресурсное планирование;
4. календарь и диаграммы Ганта;
5. сценарии и версии;
6. финансовое планирование;
7. согласования и аудит;
8. интеграции, отчеты и администрирование.

### 4.2. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Вести инициативы, проекты, приоритеты и версии годового плана |
| FR-02 | Декомпозировать проект на этапы, вехи, эпики и фичи |
| FR-03 | Оценивать трудоемкость и потребность по ролям и грейдам |
| FR-04 | Вести доступность сотрудников и назначения по периодам |
| FR-05 | Показывать перегрузку, простой и дефицит ресурсов |
| FR-06 | Управлять датами, зависимостями и Гантом по проектам и людям |
| FR-07 | Создавать сценарии «что если» и показывать последствия сдвигов |
| FR-08 | Хранить неизменяемые утвержденные версии и базовые линии |
| FR-09 | Вести источники финансирования, лимиты, бюджет, факт, прогноз и остаток |
| FR-10 | Получать из Task Tracker задачи, итерации, статусы, историю, часы и комментарии |
| FR-11 | Учитывать тестовые прогоны и дефекты при прогнозе готовности |
| FR-12 | Передавать в Task Tracker сроки, назначения, остаток времени и бюджетные корректировки |
| FR-13 | Согласовывать ресурсную и финансовую части плана, сохранять решения |
| FR-14 | Формировать отчеты и экспорт по срокам, людям и бюджету |

### 4.3. Основные бизнес-правила

- утвержденный план изменяется только созданием новой версии;
- сценарий не влияет на активный план до утверждения;
- назначение сверх доступной мощности всегда отображается как конфликт;
- план с превышением финансирования нельзя утвердить без зафиксированного решения;
- факт имеет внешний ID, источник и дату актуальности;
- повторный импорт не создает дубликаты;
- Task Tracker владеет задачей и ее историей, Planning System - планом и прогнозом.

### 4.4. Нефункциональные требования

- русский веб-интерфейс;
- аутентификация через Keycloak по OIDC/OAuth 2.0;
- ролевая авторизация и аудит критичных изменений;
- типовой экран открывается не более чем за 3 секунды;
- пересчет типового проекта выполняется не более чем за 10 секунд;
- ошибки интеграции не повреждают последнюю утвержденную версию;
- API версионируется, операции импорта идемпотентны;
- резервное копирование должно позволять восстановить согласованные планы;
- специальный промышленный SLA в первой версии не устанавливается.

### 4.5. Требования к интеграциям

| Система | Назначение интеграции |
|---|---|
| Keycloak | аутентификация пользователей и получение групп |
| Reference Manager | роли, грейды, валюты, статьи затрат и другие классификаторы |
| Task Tracker | двусторонний обмен плановыми рамками, задачами, итерациями, статусами, историей и трудозатратами |
| Контур тестирования | получение состояния тест-планов, прогонов и дефектов через Task Tracker |
| TFS | только косвенно через Task Tracker; прямой обмен не требуется |
| Финансовая система | лимиты, обязательства, факт и согласованные корректировки |
| Reporting | передача план-факта, загрузки и финансовых показателей |

Интеграции выполняются через REST API и события; для начальной загрузки допускаются
CSV/XLSX. Каждая запись должна содержать внешний ID, источник и время изменения.

### 4.6. Виды обеспечения

- данные хранятся в реляционной СУБД, финансовые значения - вместе с валютой;
- даты и ставки в утвержденных версиях сохраняются исторически;
- API документируется в OpenAPI;
- интерфейс использует единый глоссарий и справочники;
- специальные требования к метрологическому обеспечению отсутствуют;
- эксплуатационные регламенты и матрица доступа утверждаются до приемки.

## 5. Состав и содержание работ

1. уточнение Vision, ролей и интеграционных контрактов;
2. проектирование модели данных и интерфейсов;
3. реализация портфеля, декомпозиции и версий;
4. реализация ресурсов, календаря и Ганта;
5. реализация финансирования и интеграций;
6. отчеты, испытания, документация и демонстрация.

Сроки этапов устанавливаются после оценки командой.

## 6. Порядок разработки

Разработка ведется итерациями в монорепозитории. Архитектурные решения фиксируются
в ADR, интерфейсы - в OpenAPI и схемах событий. Изменения проходят code review,
автоматические тесты и демонстрацию владельцу продукта.

## 7. Контроль и приемка

Приемка включает функциональные, интеграционные и ролевые тесты. На демонстрационном
наборе необходимо:

1. создать годовой план и декомпозицию;
2. рассчитать потребность и распределить людей;
3. показать Гант и ресурсный конфликт;
4. сравнить два сценария;
5. проверить финансирование и утвердить базовую линию;
6. получить факт из Task Tracker и выполнить перепланирование;
7. подтвердить отсутствие дублей при повторном импорте.

Критические дефекты к моменту приемки должны отсутствовать.

## 8. Подготовка к вводу

Заказчик предоставляет Keycloak, справочники, тестовые проекты, сотрудников,
календари, финансовые лимиты и доступы к API. Назначаются владельцы данных и
проводится краткое ролевое обучение.

## 9. Документирование

Должны быть подготовлены: Vision, ТЗ, C4/UML-диаграммы, модель данных, OpenAPI,
схемы событий, инструкция запуска, руководство пользователя и сценарии испытаний.
Документы хранятся вместе с исходным кодом.
