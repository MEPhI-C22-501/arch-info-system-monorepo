# 160 — План интеграции

Редакция 1.0, 05.10.2026. Этапы: **проектирование → планирование разработки →
разработка → тестирование**. Сроки заданы контрольными выходами этапов;
календарные даты назначает руководитель проекта, они не выдумываются в документации.
Полная матрица данных/протоколов — [020 §3](020.system-context.md#3-единая-матрица-обмена).

## Порядок стыковки и приёмка

Для каждой строки: на проектировании согласовать [130](130.api-contracts.md),
[135](135.event-catalog.md)/[140](140.event-schema.md); при планировании разработки
назначить исполнителей, доступы и фикстуры; на разработке выполнить adapter +
контрактную заглушку, затем реальный сервис; на тестировании — соответствующий
T-INT из [095](095.requirements-check.md). Заглушка имеет отдельный verdict.

из открытого реестра 020 только после подтверждения владельцев со ссылкой на PR
или протокол; результат реального теста фиксируется отдельно.

## Переход к эксплуатации

До тестирования Infra выдаёт endpoint/JWKS/ACL/bucket без секретов в Git;
Planning System предоставляет image digest, health/readiness и миграции.
Перед приёмкой выполнить потерю связи, повтор, DLQ replay, восстановление БД/S3,
security checklist и minikube smoke из [165](165.deployment-diagram.md).
Протокол: commit, версии схем, среда, входы, ожидаемое/фактическое, логи,
passed/failed/blocked и ответственные. Отсутствующий сервис = blocked.

## Конфигурация интеграций и отключение заглушек

Адреса example.invalid в контрактах — примеры. Реальные адреса подставляет
ответственный PS в конфигурации среды после выдачи владельцем; секреты — через
Secret/.env вне Git. Заглушка отключается для конкретной связи после выполнения
её входных условий и контрактного smoke; приёмочный T-INT затем выполняется с
реальным сервисом. Ошибка реального сервиса не включает mock автоматически.

| Связь | Кто выдаёт адрес/доступ | Кто настраивает PS | Срок и условие замены |
| --- | --- | --- | --- |
| INT-01 | Infra: issuer, JWKS, audience, web client, redirect URI | Владелец API/доступа | До защищённого CRUD на общем стенде; PKCE + JWT smoke; AUTH_MODE=oidc |
| INT-02 | Reference Manager: HR_BASE_URL, версия; Infra: service account | Владелец HR adapter | До реального ресурсного расчёта; все страницы и переименование; D-02/03 |
| INT-03 | Task Tracker: TT_BASE_URL и mapping; Infra: Kafka/ACL | Владелец публикации/факта | После D-01, до общего план-факта; TT_MAPPING_APPROVED=true только после ответа |
| INT-04 | Infra + назначенный Notification Service: broker/topic/receipt | Владелец notification adapter | После D-04, до приёмки уведомлений; реальная доставка |
| INT-05 | PS выдаёт адрес своего API, Infra — reports.read client | Владелец проекций + Reports | После D-05, до оперативного дашборда; cost.read отрицательный кейс |
| INT-06 | Infra: S3_ENDPOINT, бакет и минимальные ACL | Владелец вложений | До показа реальных вложений; STORAGE_MODE=s3, upload/download/delete smoke |
| INT-07 | PS выдаёт API, Infra — qa.read client; QA/TT выбирают итерации | Владелец QA-проекции | После D-09, до привязки реального тест-плана; историческая версия и PARTIAL |
| INT-08 | PS выдаёт batch API, Infra — расписание/ETL client | Владелец exports + Reports | После D-05, до первой загрузки; поля, TTL, повтор и сверка manifest |

Коллектор телеметрии выдаёт Infra; ответственный за выпуск задаёт endpoint и
протокол до общего стенда. Локальные stdout/health не считаются подключением
коллектора. Календарный график зависимостей — [рабочий план](../work-plan.md),
датированные ответы — [реестр](integration-agreements.md).
