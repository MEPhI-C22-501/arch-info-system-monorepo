# 030 — Акторы Planning System

**Блок A.** Редакция 1.1 от 24.09.2026, к ревью команды.
Основания: [Vision §2](vision.md#2-пользователи), [ТЗ §4](technical-specification.md),
[контекст](020.system-context.md). Идентификаторы используются в [Use Cases](060.use-cases.md).

## 1. Люди

| ID | Актор, должность / роль | Основные цели и действия | Граница ответственности | Use Cases |
| --- | --- | --- | --- | --- |
| H-01 | Руководитель портфеля / руководитель проектного офиса | Выбирает состав портфеля, задаёт приоритеты, сравнивает варианты, утверждает либо возвращает план, вводит утверждённую версию в действие | Решения в доступном портфеле; не подменяет ввод факта исполнителями | UC-01, UC-05, UC-06, UC-07, UC-11 |
| H-02 | Планировщик / специалист PMO | Формирует годовой и скользящий планы, создаёт версии, собирает оценки, строит Гант, выявляет конфликты, сравнивает сценарии и отправляет их на согласование | Не получает право окончательного утверждения только из факта подготовки плана | UC-01–UC-07, UC-09, UC-11 |
| H-03 | Руководитель проекта | Ведёт проект, этапы/вехи/эпики/фичи, оценки и зависимости, анализирует факт и прогноз, инициирует перепланирование, прикладывает обоснования | Работает в своих проектах; утверждение возможно только по отдельному делегированию D-06 | UC-01, UC-02, UC-04–UC-06, UC-08, UC-09, UC-11 |
| H-04 | Ресурсный руководитель / руководитель подразделения | Подтверждает доступность сотрудников, проверяет роли и грейды, предлагает и подтверждает назначения, устраняет перегрузку и дефицит | Область своих ресурсов и назначений; не утверждает весь портфель | UC-03, UC-04, UC-06, UC-11 |
| H-05 | Участник команды / исполнитель | Просматривает свои назначения, календарь, допустимые вложения и оповещения; видит изменение плановых сроков | Факт, статусы и комментарии к задачам вводит в Task Tracker; денежные данные и чужая загрузка не доступны автоматически | UC-09 (чтение), UC-10, UC-11 (собственные данные) |
| H-06 | Администратор Planning System | Настраивает доступ и интеграции в пределах модуля, контролирует ошибки обмена, повторяет неуспешные операции, управляет конфигурацией расчёта | Не создаёт собственный сервис входа, не редактирует чужие НСИ и не получает бизнес-право утверждения плана автоматически | UC-12, UC-07 (повтор доставки) |

Один человек может совмещать роли. Решение определяется не должностью в таблице,
а проверенными полномочиями и областью проекта/ресурса. Точная RBAC-матрица
относится к блоку C. Здесь заданы бизнес-акторы, а не окончательные названия ролей
Keycloak. Проектная роль «разработчик» из НСИ также не равна роли доступа H-05.

Фраза исходного Vision «администратор настраивает справочники» уточняется границей:
администратор модуля выбирает и проверяет используемые справочники, а изменения
общих записей выполняет команда Reference Manager по своим правам.

## 2. Внешние системы

| ID | Системный актор | Протокол | Цель / сценарий взаимодействия | Use Cases и статус |
| --- | --- | --- | --- | --- |
| S-01 | Keycloak | OIDC/OAuth 2.0, JWKS, HTTPS | Аутентифицирует пользователей, предоставляет идентичность и сведения о доступе; Planning System проверяет токен и свои права | UC-12, предпосылка всех пользовательских UC; готовый инфраструктурный компонент |
| S-02 | Reference Manager | REST по HTTPS | Отдаёт проектные роли, грейды, валюты и другие согласованные НСИ по стабильным кодам | UC-02, UC-03, UC-12; события НСИ не предполагаются, D-02/D-03 |
| S-03 | Task Tracker | Целевые REST API и события через согласованный транспорт | Принимает проекты и активные плановые рамки; передаёт изменения задач и трудозатрат для обновления проекций и прогноза | UC-07, UC-08; двусторонний контракт открыт, D-01 |
| S-04 | Notification Service | Целевые REST API / события | Принимает запросы уведомлений и возвращает результат доставки; повтор по одному ID не создаёт новый запрос | UC-10; поставщик, каналы и схема подтверждения открыты, D-04 |
| S-05 | Object Storage / MinIO | S3-совместимый API по HTTPS | Хранит и выдаёт вложения по ключу, подтверждает загрузку/удаление | UC-09; конфигурация бакета и лимитов определяется совместно с Infra |
| S-06 | Reports / Reporting | REST по HTTPS; события после согласования | Читает планы, baseline, ресурсы, прогноз и отклонения для собственных отчётов | UC-11; форма проекций и периодичность открыты, D-05 |

Брокер сообщений, PostgreSQL и фоновые работники не выделяются бизнес-акторами:
они реализуют обмен и хранение, но не формулируют самостоятельных целей в
предметной области. Фоновый запуск — инициатор системного шага внутри UC,
а не новый внешний участник.

## 3. Ответственность за сквозной процесс

Планировщик готовит вариант, руководитель проекта отвечает за его содержание,
ресурсный руководитель подтверждает назначения, уполномоченный руководитель
принимает решение. После активации система публикует плановые рамки в Task Tracker.
Полученный факт обновляет прогноз и может вызвать новый сценарий, но не утверждает
и не активирует план автоматически.

Круг обязательных согласующих, возможность делегирования и действия при их
отсутствии — проектные уточнения D-06/D-08 из
[020](020.system-context.md#6-открытые-договорённости), а не уже внедрённый регламент.
