# 155 — Последовательности ключевых сценариев

Редакция 1.0, 05.10.2026. Проект взаимодействий. Методы и схемы —
[130](130.api-contracts.md), события — [135](135.event-catalog.md)/[140](140.event-schema.md).
HTTP connect/request timeout 3/10 с и retry 1/5/30/120/300 с — предложенные
настройки ADR-004, не измеренный SLA. Все ответы об ошибке сохраняют correlationId.

## SEQ-01 — Годовое планирование и утверждение

UC-01/02/03/06, US-PL-01/02, US-RM-01/02, US-PO-02.
Операции createProject, saveDraft, submitReview, recordDecision.

```mermaid
sequenceDiagram
  actor P as Планировщик
  participant A as Planning API
  participant DB as PostgreSQL
  actor R as Ресурсный руководитель
  actor H as Финальный согласующий
  P->>A: createProject / Idempotency-Key
  A->>DB: TX Project + первый DRAFT + audit
  DB-->>A: commit
  A-->>P: 201 + revision
  P->>A: saveDraft / If-Match
  A->>DB: Проверить дерево, даты, часы и revision
  alt Неверные входы или чужая revision
    A-->>P: 422 или 412, без частичной записи
  else Черновик сохранён
    A-->>P: 200 + новая revision
    R->>A: Подтвердить доступность и назначения
    P->>A: submitReview
    A->>DB: TX freeze contentRevision + reviewRound + reviewers
    A-->>P: ON_REVIEW
    H->>A: recordDecision / round / contentRevision
    alt RETURN с причиной
      A->>DB: TX решение + DRAFT + audit
      A-->>P: Требуется доработка и новый раунд
    else Все обязательные APPROVE
      A->>DB: TX решение + APPROVED + baseline
      A-->>H: Утверждено, ещё не активно
    end
  end
```

После HTTP timeout клиент перечитывает объект/повторяет с тем же ключом;
не создаёт новое решение. 412 требует сравнить изменения. Если внешние входы
устарели, submit/approve блокируется до проверки; сетевой сбой не отменяет baseline.

## SEQ-02 — Активация и подтверждение Task Tracker

UC-07/12, US-PO-03, US-AD-02. activatePlan, getPublication,
acceptPlanningVersion (предложение приёмника TT), publicationReceipt.

```mermaid
sequenceDiagram
  actor H as Руководитель
  participant A as Planning API
  participant DB as PostgreSQL
  participant W as Integration Worker
  participant T as Task Tracker
  H->>A: activatePlan / projectRevision / If-Match
  A->>DB: TX lock Project, прежняя SUPERSEDED, новая ACTIVE
  A->>DB: В той же TX Publication + outbox + audit
  DB-->>A: commit
  A-->>H: ACTIVE, доставка PENDING
  W->>DB: Получить актуальную Publication
  W->>T: PUT версии / Idempotency-Key
  alt Приём подтверждён
    T-->>W: 200 APPLIED + receipt
    W->>DB: SUCCEEDED с receipt
  else Тайм-аут с неизвестным результатом
    W->>DB: FAILED / unknown, ключ сохранён
    W->>T: Повтор той же версии и ключа после сверки
    T-->>W: Тот же receipt, без нового объекта
    W->>DB: SUCCEEDED
  end
```

Перед каждой новой попыткой проверяется текущая ACTIVE; SUPERSEDED_BEFORE_DELIVERY
блокирует отправку старой версии. Поздний receipt старой публикации только закрывает
её запись доставки, не активирует старую версию. После исчерпания retry — разбор
R-06. План остаётся активным локально даже при недоступности TT.

## SEQ-03 — Факт и единый прогноз

UC-08/11, US-PM-02, US-PO-04. TaskCreated/Changed/TimeLogged/Deleted,
calculateForecast, getOperation, getForecast.

```mermaid
sequenceDiagram
  participant T as Task Tracker
  participant K as Kafka
  participant W as Inbox Worker
  participant DB as PostgreSQL
  participant F as Forecast Worker
  T->>K: Абсолютный срез, sourceRevision, eventId
  K->>W: at-least-once доставка
  W->>W: Проверить schema, producer, projectId
  alt Повтор eventId или старая revision
    W->>DB: Проверить inbox/hash, не менять часы
    W-->>K: ack
  else Новая допустимая редакция
    W->>DB: TX inbox + TaskSnapshot + calculation job
    DB-->>W: commit
    W-->>K: ack после commit
    F->>DB: Зафиксировать inputSnapshot и lease
    F->>F: ETC, календарь, стоимость и качество
    F->>DB: TX ForecastSnapshot + outbox
  end
```

Неверная схема/неизвестный проект — DLQ; offset после durable DLQ ack. Сбой worker
до commit оставляет сообщение для повтора, после commit ловится inbox. Нет ставки
или ETC — PARTIAL, а не ноль. Сбой расчёта повторяет тот же inputHash; два работника
не сохраняют два результата. API расчёта возвращает 202, UI опрашивает operation.

## SEQ-04 — Перепланирование через сценарий

UC-05/06/07, US-PL-04, US-PM-04. createVersion, saveDraft,
calculateForecast, далее SEQ-01/02.

```mermaid
sequenceDiagram
  actor P as Планировщик
  participant A as Planning API
  participant DB as PostgreSQL
  participant F as Forecast Worker
  P->>A: createVersion / kind SCENARIO / baseVersionId
  A->>DB: TX копия с новыми id и прежними logicalItemId
  A-->>P: DRAFT сценария, исходная ACTIVE неизменна
  P->>A: saveDraft / If-Match
  A->>DB: Проверить и сохранить только сценарий
  P->>A: calculateForecast
  A-->>P: 202 operationId
  F->>DB: Общий срез факта, отдельные результаты вариантов
  P->>A: getOperation / getForecast
  A-->>P: Разницы сроков, нагрузки и качества
  P->>A: submitReview выбранного сценария
  Note over A,DB: Решения и активация как SEQ-01/02, без обхода review
```

Timeout создания повторяется с тем же ключом. Сравнение разных dataAsOf помечается
несопоставимым, требуется новый расчёт. Параллельная активация другого сценария
вызывает 412/409, не перезапись выбранной baseline.

## SEQ-05 — Вложение

UC-09, US-PM-03. uploadAttachment, getAttachment,
downloadAttachment, deleteAttachment; ADR-007.

```mermaid
sequenceDiagram
  actor P as Пользователь
  participant A as Attachment API
  participant DB as PostgreSQL
  participant S as Object Storage
  P->>A: Multipart файл + владелец + Idempotency-Key
  A->>A: RBAC, состояние владельца, лимит
  A->>DB: UPLOADING + устойчивый objectKey
  A->>S: Поток байтов
  alt Upload завершён и тип/размер/хеш верны
    S-->>A: Подтверждение объекта
    A->>DB: AVAILABLE + checksum + audit
    A-->>P: 201 AVAILABLE
  else Тайм-аут или неверный файл
    A->>DB: UPLOAD_FAILED
    A-->>P: Ошибка, чтение запрещено
  end
  P->>A: DELETE / If-Match
  A->>DB: DELETE_PENDING
  A->>S: Delete objectKey
  S-->>A: Удалён или уже отсутствует
  A->>DB: DELETED
```

При обрыве upload повторная попытка использует прежний ключ после проверки
частичного объекта; статус 201 выставляется только после верификации. Повтор delete
безопасен, timeout оставляет DELETE_PENDING для worker. Для утверждённой версии
загрузка/удаление запрещены, обоснование прикладывается к проекту или новому DRAFT.

## SEQ-06 — Оповещение и подтверждение доставки

UC-10/12, US-TM-02, US-AD-02. NotificationRequested/Delivered по 140.

```mermaid
sequenceDiagram
  participant P as Бизнес-политика
  participant DB as PostgreSQL
  participant W as Outbox Worker
  participant K as Kafka
  participant N as Notification Service
  P->>DB: TX Notification + outbox, UNIQUE причины/адресата/канала
  W->>K: NotificationRequested
  K-->>W: Broker ack
  W->>DB: Отправлено, не DELIVERED
  K->>N: Запрос с устойчивым notificationId
  N->>N: Дедупликация и доставка каналу
  N->>K: NotificationDelivered + deliveryReceipt
  K->>W: Подтверждение
  W->>DB: TX inbox + DELIVERED по тому же notificationId
  W-->>K: ack
```

Предложенный timeout receipt — 60 с: FAILED с неизвестным результатом; сверка
перед повтором. Позднее подтверждение переводит ту же запись в DELIVERED.
Исчерпание retry — DLQ, ручной replay сохраняет ID. Поставщик ещё не назначен D-04;
диаграмма не доказывает существование внешнего канала.
