# 140 — Схемы и доставка событий

Редакция 1.0, 05.10.2026. JSON Schema draft 2020-12, контракт 1.0.0.
Генератор: [build-contracts.mjs](../scripts/build-contracts.mjs).
Каждая схема самостоятельна; каждый example — синтетическая фикстура.

## Envelope и совместимость

Обязательны eventId (UUID), eventType, occurredAt (RFC3339 UTC), producer,
schemaVersion, correlationId (UUID), projectId и payload. Первые шесть полей
также передаются Kafka headers как UTF-8 строки; header обязан совпасть с JSON.
Ключ внешнего сообщения = projectId: порядок одной проектной линии находится
в одной partition одного топика. Между топиками порядка нет: получатель использует
sourceRevision/versionNumber и сверку. Для внутренних событий projectId может
быть null; их aggregateId выбирает портфель/ресурс.

Новые необязательные поля — minor; удаление/обязательное поле/смена типа, enum
или смысла — major с новым топиком. Схемы закрыты additionalProperties=false:
consumer проверяет по **схеме указанной версии**, а не по старой схеме; до minor
производителя consumers получают новую схему и тестируются на игнорирование
новых optional-полей. Backward: новый consumer читает старое сообщение; forward
обеспечивается таким порядком rollout и tolerant DTO, автоматически не обещается.
Изменение const schemaVersion согласуется вместе со схемой.

## Политика отказов (предлагаемые настройки)

HTTP: connect timeout 3 с, request timeout 10 с; 408/429/5xx повторяются с
Retry-After либо 1/5/30/120/300 с + jitter до 20%. Пять повторов после первой
попытки; 400/401/403/422 требуют исправления, автоматический цикл не запускается.
Kafka: retry с тем же расписанием; после шести неудачных обработок — DLQ
<исходный-топик>.dlq, с original envelope, reason, attempts и first/lastFailureAt.
Неверная схема сразу в DLQ; offset фиксируется только после durable DLQ ack.
Ошибка самого DLQ не позволяет потерять исходное сообщение: partition приостанавливается.

Inbox UNIQUE(producer,eventId), payload hash; тот же ID с иными данными — ошибка.
Проекция и inbox commit вместе, затем ack. Устаревший sourceRevision фиксируется
как проигнорированный, часы не прибавляются. Неизвестный проект — карантин/DLQ,
не создание проекта. Поздний receipt не меняет ACTIVE и не дублирует доставку.
Replay только после устранения причины, с тем же eventId, роль R-06 и аудит;
неактуальная публикация не отправляется заново. Retention inbox/outbox/DLQ и
число partitions согласуются с Infra до выпуска; до этого чистка ключей запрещена.
Уведомление без receipt через предложенные 60 с помечается FAILED/unknown;
поздний receipt допускается. Значения — параметры для согласования D-01/D-04.
