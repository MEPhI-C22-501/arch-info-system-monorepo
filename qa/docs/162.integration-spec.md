## 1. Task Tracker: создание «Ошибки»

**Назначение.** Дефект из QA System должен появиться в бэклоге команды-владельца подсистемы как задача вида «Ошибка» без ручного переноса (FR-DEF-06).

**Схема.** Defect Service → таблица исходящих → Outbox Relay → Task Tracker Client → `POST /api/v1/bugs` → идентификатор и ссылка задачи сохраняются в дефекте ([SD-04](155.sequence-diagrams.md#sd-04-создание-ошибки-в-task-tracker)).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. REST `POST /bugs` через таблицу исходящих** — выбран | Немедленное подтверждение и идентификатор задачи; идемпотентность по `(externalSource, externalDefectId)` у Task Tracker; недоступность трекера не мешает записи результата | Задержка до 30 секунд; нужна таблица исходящих и повторы |
| B. Синхронный вызов в транзакции записи результата | Проще: нет очереди | Недоступный Task Tracker ломает запись результата; сетевой вызов внутри транзакции |
| C. Событие в Kafka, Task Tracker создаёт задачу сам | Слабая связность | Task Tracker такого потребителя не описывает; нужен отдельный статус приёма и сверка |
| D. Ручной перенос тестировщиком | Нет интеграции | Теряется связь дефекта с задачей; противоречит ключевой возможности vision |

**Обоснование.** Вариант A — единственный, у которого есть контракт и код у Task Tracker, и он не связывает доступность двух систем.

**Ожидаемый результат и проверка.** `201` при создании, `200` при повторе без дубликата; `401`, `403`, `422` — синхронизация `FAILED` с причиной; при отключённом Task Tracker дефект сохранён и досылается после восстановления (T-FR-30, T-NFR-11).

## 2. Task Tracker: статусы, приоритет и комментарии

**Назначение.** Дефект должен узнавать, что разработчик взял «Ошибку» в работу и исправил её, без ручного ввода (FR-DEF-06, FR-DEF-07).

**Схема.** Scheduler → Tracker Sync → `GET /api/v1/work-items/{id}` и `/comments` раз в 60 секунд → маппинг → Defect Service ([SD-08](155.sequence-diagrams.md#sd-08-синхронизация-статуса-и-комментариев-ошибки-с-task-tracker)).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Опрос REST раз в 60 секунд** — выбран сейчас | Работает с существующим API Task Tracker; Task Tracker сам выбрал этот механизм для потребителей до решения о Kafka ([его 162](../../task-tracker/docs/block-i-integration-and-deployment/162.integration-spec.md#уточнение-выбора-на-12102026)); повтор чтения безопасен | Задержка до 60 секунд плюс цикл; нагрузка растёт с числом открытых дефектов; нужна учётная запись чтения (Q-09) |
| B. События Kafka `task-tracker.events.v1` — целевой | Малая задержка, нет лишних запросов | Task Tracker не публикует события наружу до DEC-TT-02; нужен bootstrap и сверка |
| C. Webhook от Task Tracker в QA System | Мгновенно | Task Tracker такого механизма не описывает; QA System пришлось бы принимать запись от соседа |
| D. Ручной ввод статусов QA-лидом | Не зависит от соседа | Статус отстаёт и расходится; оставлен только как резерв |

**Обоснование.** A — доступно сейчас и согласуется с решением владельца данных. Переход на B меняет только транспорт: дедупликация через `inbox_event` и применение по маппингу остаются теми же.

**Ожидаемый результат и проверка.** Смена статуса «Ошибки» отражается в дефекте не позже 2 минут; повторное чтение без изменений — 0 записей истории (T-NFR-04); несопоставленный статус — предупреждение администратору; `401` и `403` опроса видны в «Состоянии интеграций».

## 3. Владение статусами: QA-статусы при владении задачей у учёта работ

**Назначение.** Один дефект живёт в двух системах. Нужно, чтобы у каждого статуса был один владелец и одна точка изменения.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. QA System — мастер всего, Task Tracker — зеркало | Полный жизненный цикл в одном месте | Разработчик меняет статус не в своём инструменте; Task Tracker не принимает внешнюю смену статуса |
| B. Task Tracker — мастер всего, QA System — зеркало | Один инструмент у разработчиков | В Task Tracker нет статусов «Ready for Test» и «Reopened»; reopened rate не посчитать; перепроверка выпадает из QA System |
| **C. Раздельное владение и таблица маппинга** — выбран | Статусы разработки ставит разработчик в Task Tracker, статусы тестирования — тестировщик в QA System; набор статусов Task Tracker может меняться без выпуска QA System | Закрытие и переоткрытие в Task Tracker пока ручные; возможны временные расхождения — их показывает флаг `tracker_mismatch` |

**Обоснование.** C совпадает с решением Reference Manager (статусы задач — Task Tracker, серьёзность — QA System) и Reports (статусы тестирования — QA System, их Q-REP-07). Таблица маппинга — [vision 4.4](vision.md#44-жизненный-цикл-дефекта), кто что меняет — [070, раздел 5а](070.role-matrix.md#5а-справочники-значений-и-статусы-кто-что-меняет).

**Ожидаемый результат и проверка.** Полный цикл New → Open → In Progress → Fixed → Ready for Test → Closed / Reopened проходит с источниками `QA` и `TRACKER` в истории; попытка сопоставить статус Task Tracker со статусом тестирования отклоняется (T-FR-29, US-AD-04).

## 4. Planning System: релизы, вехи, эпики

**Назначение.** Привязать тест-план к релизу и вехе; группировать кейсы по эпикам и фичам (FR-TP-05, FR-TP-06, FR-TC-07).

**Схема.** Directory Service → `GET /api/v1/projects/{projectId}/release-context` → `planning_item_cache`; событие `PlanActivated` — сигнал перечитать ([SD-07](155.sequence-diagrams.md#sd-07-привязка-плана-к-релизу-вехе-и-итерации)).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. REST `release-context` с кэшем** — выбран | Контракт предложен владельцем ([их 162, INT-07](../../planning-system/docs/162.integration-spec.md#int-07--qa-system)); адресно читается нужная утверждённая версия | Без событий кэш обновляется по расписанию |
| B. Только события Kafka | Изменения приходят сами | Нельзя выбрать историческую версию плана; нет первичной загрузки |
| C. Свой справочник релизов в QA System | Нет зависимости | Второй владелец релиза — именно то, от чего предостерегает замечание |
| D. Релиз строкой без владельца | Просто | Ссылки не проверяются; отчёт по релизу у Reports не строится |

**Ожидаемый результат и проверка.** План привязан к релизу по `logicalItemId`; новая версия плана не меняет привязку; черновик и чужой проект не читаются; недоступность Planning System не блокирует сохранение плана.

## 5. Reference Manager: сотрудники и оргструктура

**Назначение.** Источник людей для назначения тестировщиков и ответственного за план (FR-RUN-02, FR-TP-03).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. REST `/v1/employees`, `/v1/org_units` с кэшем, связь по `account_user_id`** — выбран | Владелец HR-профилей с 2026-10-02 — Reference Manager; QA — его потребитель I-12; кэш переживает недоступность | Пока коллекции не реализованы, назначение работает на ручном списке |
| B. Только Keycloak (пользователи realm) | Уже есть | Нет ФИО, подразделения и признака увольнения; Admin API Keycloak не для потребителей |
| C. Свой список тестировщиков в QA System | Нет зависимости | Копия кадровых данных; расходится с источником |

**Ожидаемый результат и проверка.** Кандидаты на назначение — только активные сотрудники с учётной записью; уволенный сохраняется в старых записях; при недоступности Reference Manager используется кэш с датой актуальности (US-QL-04, US-AD-03).

## 6. Reports: оперативный и аналитический контур

**Назначение.** По матрице обмена в хранилище отчётности попадают тест-кейсы, прогоны, дефекты и метрики качества (FR-DAT-03).

**Схема.** Оперативный контур — события `dev.qa.*` → потребитель Reports; аналитический — задание ETL Reports раз в час → `GET /api/v1/reports/{test-cases, test-plans, test-runs, test-results, defects}?updatedSince=…` → хранилище ([SD-05](155.sequence-diagrams.md#sd-05-передача-данных-в-reports)).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. События и REST раз в час** — выбран вместе с Reports | Малый лаг для оперативных отчётов; полнота и первичная загрузка — тем же REST; переходы дефекта не теряются | Два канала поддерживаются одновременно |
| B. Только REST | Один канал | Промежуточные переходы дефекта теряются — не посчитать reopened rate за период ([их 162, раздел 7](../../reports/docs/162.integration-spec.md#7-qa-system-события-и-rest)) |
| C. Пакетные файлы с manifest в MinIO | Единый срез для больших объёмов | Объём учебного проекта этого не требует; новый контракт и хранилище |
| D. QA System считает метрики и выгружает их | Reports проще | Метрика считается в двух местах и расходится |

**Обоснование.** Совпадает с выбором Reports; пакетная выгрузка файлами QA System не нужна, это записано явно в [vision 8.4](vision.md#84-участие-в-аналитическом-контуре-reports).

**Ожидаемый результат и проверка.** Результат кейса в витрине Reports не позже 2 минут; дубль события отброшен; пять ресурсов читаются постранично, повтор страницы даёт те же строки; без роли — `403`.

## 7. Keycloak

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. OIDC, локальная проверка JWT по JWKS, клиентские роли** — выбран | Принято в проекте; нет сетевого вызова на запрос | Отзыв роли действует после истечения токена |
| B. Introspection на каждый запрос | Актуальное состояние токена | Каждая операция зависит от Keycloak |
| C. Своя аутентификация | Полный контроль | Дублирует инфраструктуру и нарушает общую архитектуру |

**Проверка.** Неверные `iss`, `aud`, истёкший токен — `401`; нет роли — `403`; секрет `qa-executor` не попадает в журналы (T-NFR-06).

## 8. MinIO: вложения и журналы

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Бакет `arch-dev-qa`, метаданные в БД, выдача после проверки прав** — выбран | Отдельный бакет команды по правилам Infra; БД не раздувается | Нет общей транзакции объекта и строки — нужна очистка «сирот» |
| B. Файлы в БД (`bytea`) | Транзакционность | Рост БД, противоречит файловому обмену Infra |
| C. Локальный диск контейнера | Просто | Привязка к узлу, потеря при пересоздании |

**Проверка.** Свой объект пишется и читается, чужой бакет — отказ; файл больше 10 МиБ — `413`; SVG и HTML — `422` (T-FR-05, T-NFR-19).

## 9. Kafka: публикация событий

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Таблица исходящих и фоновая отправка, at-least-once** — выбран | Нет потерь и «призрачных» событий; брокер может быть недоступен | Возможны дубли — потребитель отбрасывает по `eventId` |
| B. Отправка прямо из обработчика запроса | Меньше кода | Событие для отменённой транзакции или потеря при сбое |
| C. Отдельный топик ошибок | Стандартный приём | Не нужен издателю: очередь повторов — сама таблица исходящих |

**Проверка.** Отключение брокера — события копятся и уходят после восстановления, потерь 0 (T-NFR-11).

## 10. Пайплайн и способы запуска прогонов: ручные против автоматических

**Назначение.** Определить, кто запускает прогоны и как QA System работает приёмочным контуром ([vision 4.6](vision.md#46-приёмка-стенда)).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Только ручной запуск | Полный контроль QA-лида | Сломанный стенд замечают поздно |
| B. Только автоматический запуск из пайплайна | Быстрая обратная связь | Ручные кейсы (TC-TT-02, TC-INF-02) и кейсы без API не проверяются; нет решения о приёмке |
| C. Пайплайн блокирует выпуск при любом провале | Строгий контроль | Пока у соседей мало API, много «Пропущен» и ложных блокировок; откат развёртывания — не решение QA |
| **D. Комбинация: «Smoke» из пайплайна и по расписанию; «Приёмка стенда» вручную с вердиктом** — выбран | Каждое развёртывание проверяется автоматически; веха принимается явным решением; ручные кейсы учтены | Красный «Smoke» не откатывает развёртывание; нужен шаг в общем workflow (Q-08) |

**Ожидаемый результат и проверка.** Повторный вызов с тем же ключом идемпотентности не создаёт второй прогон; повторный запуск идущего набора — `409`; при `RED` шаг пайплайна красный со ссылкой на прогон; вердикт «принят» невозможен при провалах и незакрытых Blocker и Critical ([SD-09](155.sequence-diagrams.md#sd-09-приёмка-стенда-smoke-из-пайплайна-и-25-приёмочных-кейсов)).

## 11. Тестируемые подсистемы

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Публичные API под служебной записью `qa-executor`, данные с префиксом** — выбран | Проверяется то, что видит клиент; минимальные права | Зависит от появления API соседей |
| B. Прямой доступ к БД подсистем | Быстрая подготовка данных | Нарушает FR-DAT-01 и изоляцию; проверяет не то, что видит клиент |
| C. Браузерные проверки интерфейсов | Ближе к пользователю | Отдельная инфраструктура; вне первой версии (ADR-013) |

**Проверка.** Набор проходит в любом порядке (T-NFR-02); недоступная подсистема даёт «Заблокирован» или «Провален» с причиной (T-NFR-03).
