## 1. Спецификация

Машиночитаемый контракт — [`../api/openapi/v1/openapi.yaml`](../api/openapi/v1/openapi.yaml), OpenAPI 3.1, версия `0.3.0-draft`. Изменения `0.2.0` относительно `0.1.0` — совместимые: поля привязки к релизу, `lastResult`, `smokeVerdict` и `verdict`, копия полей «Ошибки», заголовок `Idempotency-Key`, ресурс `test-cases` в `/reports/*`. Изменения `0.3.0` относительно `0.2.0` — тоже совместимые: пути `/templates`, `/suites`, `/admin/classifiers`, `/admin/environments`; фильтр `suiteId` списка кейсов; необязательное поле `version` в `TestCaseInput`; поля `currentVersion`, `createdBy`, `createdAt` кейса. Спецификация — источник истины: реализация проверяется против неё контрактным тестом `qa/backend/tests/test_openapi_contract.py` (NFR-13) — каждая реализованная операция есть в спецификации, версии и поля общих схем совпадают.

**Версионирование.** Мажорная версия — в пути (`/api/v1`). В её пределах допускаются только совместимые изменения: новые пути и необязательные поля. `info.version` следует semver: minor — новый путь или поле, patch — уточнение описаний; несовместимое изменение — `/api/v2`. Статус `draft` снимается после согласования с Task Tracker, Reports и Infra (Q-01, Q-06, Q-13 в [160](160.integration-plan.md#5-открытые-вопросы-и-ответственные)).

**Правила совместимости для потребителей.**

| Потребитель | Что использует | Гарантия в пределах `v1` | Как сообщаем об изменении |
| --- | --- | --- | --- |
| Reports | `/api/v1/reports/*`, события [140](140.event-schema.md) | Поля не удаляются и не меняют тип и смысл; новые поля необязательны, потребитель игнорирует неизвестные; значения перечислений серьёзности и статусов не меняются | Minor — запись в журнале изменений спецификации; major — `/api/v2` и параллельная работа `v1` не меньше одной вехи |
| Пайплайн (`qa-ci`) | `POST /runs`, `GET /runs/{id}` | Поля запроса `suiteName`, `environment`, `start`, заголовок `Idempotency-Key` и поля ответа `status`, `summary`, `smokeVerdict` стабильны; имя набора `Smoke` и коды окружений не меняются: API отклоняет переименование | Изменение workflow делает команда QA в том же pull request |
| Task Tracker | Ссылки `testRunUrl`, `testCaseUrl` в «Ошибке» | Адреса карточек прогона и кейса в интерфейсе не меняются | — |

## 2. Общие правила

| Правило | Значение |
| --- | --- |
| Аутентификация | `Authorization: Bearer <токен Keycloak>`; realm `arch-info-system`; роли клиента `qa-system` |
| Формат | `application/json`, UTF-8; время — RFC 3339 в UTC; даты — `YYYY-MM-DD` |
| Идентификаторы | `id` — UUID; `key` — читаемый ключ (`TC-RM-03`, `RUN-87`, `DEF-45`) |
| Списки | `page` с 1, `pageSize` 1…200, по умолчанию 50; ответ содержит `items`, `page`, `pageSize`, `totalPages` |
| Заголовки ответа | `X-Request-Id` в каждом ответе; он же `correlationId` в теле ошибки |
| Идемпотентность | Создание прогона из CI принимает заголовок `Idempotency-Key`; повтор с тем же ключом возвращает тот же прогон |
| Ошибки | Тело `{code, message, correlationId, errors[]}`; `errors[]` — перечень `{field, reason}` для ошибок проверки |

## 4. Примеры

### 4.1. Создание кейса, успех

```http
POST /api/v1/test-cases
Authorization: Bearer <token>
Content-Type: application/json

{
  "title": "Создание записи с занятым кодом отклоняется",
  "module": "RM",
  "priority": "HIGH",
  "severity": "MAJOR",
  "type": "NEGATIVE",
  "steps": [
    {"action": "Создать запись currencies/PLN", "expectedResult": "201, state ACTIVE"},
    {"action": "Удалить запись", "expectedResult": "200, state DELETED"},
    {"action": "Создать запись с тем же идентификатором", "expectedResult": "409 ALREADY_EXISTS"}
  ]
}
```

```http
HTTP/1.1 201 Created
X-Request-Id: 5f1c2a…

{"id": "0b6f…", "key": "TC-RM-03", "status": "DRAFT", "version": 1, "title": "Создание записи с занятым кодом отклоняется", "module": "RM", "priority": "HIGH", "severity": "MAJOR", "type": "NEGATIVE", "automated": false, "steps": [{"id": "a1…", "position": 1, "action": "Создать запись currencies/PLN", "expectedResult": "201, state ACTIVE"}]}
```

В примере ответа часть шагов опущена.

### 4.2. Создание кейса, ошибка проверки

```http
HTTP/1.1 422 Unprocessable Entity

{"code": "VALIDATION_FAILED", "message": "Тест-кейс не прошёл проверку", "correlationId": "5f1c2a…", "errors": [{"field": "title", "reason": "required"}, {"field": "steps[2].expectedResult", "reason": "required"}]}
```

### 4.3. Запуск набора из CI

```http
POST /api/v1/runs
Authorization: Bearer <токен клиента qa-ci>
Idempotency-Key: deploy-2d82b9e

{"suiteName": "Smoke", "environment": "staging", "start": true}
```

```http
HTTP/1.1 201 Created

{"id": "7d2e…", "key": "RUN-87", "suiteId": "c41a…", "environment": "staging", "status": "IN_PROGRESS", "trigger": "CI", "startedBy": "service-account-qa-ci", "smokeVerdict": null, "summary": {"total": 25, "passed": 0, "failed": 0, "blocked": 0, "notRun": 25, "skipped": 0}}
```

Набор уже исполняется на этом окружении:

```http
HTTP/1.1 409 Conflict

{"code": "SUITE_ALREADY_RUNNING", "message": "Набор Smoke уже выполняется на окружении staging: RUN-86", "correlationId": "9a41…", "errors": [{"field": "suiteName", "reason": "running:RUN-86"}]}
```

### 4.4. Запись результата с провалом шага

```http
PUT /api/v1/runs/7d2e…/results/31aa…

{"status": "FAILED", "steps": [{"stepId": "a1…", "status": "PASSED"}, {"stepId": "a2…", "status": "PASSED"}, {"stepId": "a3…", "status": "FAILED", "actualResult": "201 Created вместо 409"}]}
```

```http
HTTP/1.1 200 OK

{"id": "31aa…", "testCaseId": "0b6f…", "testCaseKey": "TC-RM-03", "caseVersion": 2, "status": "FAILED", "failedStepPosition": 3, "actualResult": "201 Created вместо 409", "defect": {"id": "e9c0…", "key": "DEF-45", "created": true}}
```

При повторном провале того же кейса в другом прогоне `defect.created` равно `false`: связан существующий дефект. Запись в завершённый прогон:

```http
HTTP/1.1 409 Conflict

{"code": "RUN_FINISHED", "message": "Прогон RUN-87 завершён, результаты не изменяются", "correlationId": "c0de…"}
```

### 4.5. Недопустимый переход дефекта

```http
POST /api/v1/defects/e9c0…/transitions

{"to": "CLOSED"}
```

```http
HTTP/1.1 409 Conflict

{"code": "INVALID_TRANSITION", "message": "Переход NEW → CLOSED недопустим", "correlationId": "77ab…", "errors": [{"field": "to", "reason": "allowed:OPEN"}]}
```

### 4.6. Вердикт приёмки стенда, отказ

```http
POST /api/v1/runs/7d2f…/verdict
Authorization: Bearer <токен QA-лида>

{"verdict": "ACCEPTED", "note": "Приёмка к демонстрации И-M3"}
```

```http
HTTP/1.1 409 Conflict

{"code": "ACCEPTANCE_CRITERIA_NOT_MET", "message": "Стенд не может быть принят: есть провалы и незакрытые дефекты Blocker", "correlationId": "41fe…", "errors": [{"field": "results", "reason": "failed:TC-TT-04"}, {"field": "defects", "reason": "open-blocker:DEF-51"}]}
```

Успешный вердикт возвращает `200` с прогоном, где `verdict = ACCEPTED`, `verdictBy`, `verdictAt` и `summary.unverified` — число кейсов «Пропущен» с причиной «проверка невозможна».

## 5. Соответствие ошибок

| Ситуация | HTTP | `code` |
| --- | --- | --- |
| Нет токена или он недействителен | 401 | `UNAUTHENTICATED` |
| Нет роли на операцию; чужой назначенный кейс | 403 | `PERMISSION_DENIED` |
| Объект не найден | 404 | `NOT_FOUND` |
| Недопустимый переход статуса кейса, набора, плана, прогона, дефекта; удаление кейса не в статусе «Черновик» | 409 | `INVALID_TRANSITION` |
| Кейс переводится в «Актуален» без шага с ожидаемым результатом | 409 | `CASE_NOT_READY` |
| Ручная смена статуса разработки при включённом опросе Task Tracker | 409 | `STATUS_OWNED_BY_TRACKER` |
| Вердикт: прогон не завершён, не приёмочный, уже имеет вердикт, критерии не выполнены | 409 | `RUN_NOT_COMPLETED`, `NOT_ACCEPTANCE_RUN`, `VERDICT_ALREADY_SET`, `ACCEPTANCE_CRITERIA_NOT_MET` |
| Изменение архивного кейса, закрытого плана, завершённого прогона | 409 | `CASE_ARCHIVED`, `PLAN_CLOSED`, `RUN_FINISHED` |
| Параллельное сохранение кейса | 409 | `VERSION_CONFLICT` |
| Набор уже исполняется на окружении | 409 | `SUITE_ALREADY_RUNNING` |
| Удаление кейса с результатами прогонов или дефектами; отключаемое значение используется | 409 | `CASE_HAS_RUNS`, `VALUE_IN_USE` |
| Некорректные поля, пустой состав прогона, ошибка импорта | 422 | `VALIDATION_FAILED`, `RUN_EMPTY`, `IMPORT_INVALID` |
| Файл больше предела | 413 | `PAYLOAD_TOO_LARGE` |
| Хранилище файлов или БД недоступны | 503 | `STORAGE_UNAVAILABLE`, `DATABASE_UNAVAILABLE` |
| Внутренняя ошибка | 500 | `INTERNAL` |

## 6. Исходящие контракты

### 6.1. Task Tracker: создание «Ошибки»

Контракт принадлежит Task Tracker: [`openapi.yaml`](../../task-tracker/docs/block-g-api-and-events/openapi.yaml), операция `post_bugs` (`POST /api/v1/bugs`). QA System использует его без изменений.

| Поле запроса | Откуда берётся |
| --- | --- |
| `externalSource` | Константа `qa-system` |
| `externalDefectId` | Ключ дефекта, например `DEF-45` |
| `title` | Заголовок дефекта |
| `description` | Шаги воспроизведения, ожидаемый и фактический результат, исходная серьёзность, предложенный приоритет, ключ кейса и номер шага |
| `severity` | Преобразование по Q-02: `BLOCKER`, `CRITICAL` → `critical`; `MAJOR` → `high`; `MINOR` → `medium`; `TRIVIAL` → `low` |
| `environment` | Код окружения прогона |
| `build` | Версия тестируемой подсистемы и commit SHA автотестов |
| `testRunUrl`, `testCaseUrl` | Ссылки на прогон и кейс в интерфейсе QA System |

| Ответ Task Tracker | Действие QA System |
| --- | --- |
| `201 created`, `200 already-exists` | Сохранить `id` и `workItemUrl`, состояние `SYNCED` |
| `401`, `403`, `422` | Состояние `FAILED`, причина видна администратору; автоматических повторов нет |
| Тайм-аут, `5xx`, сеть | Повтор с нарастающей задержкой; запрос идемпотентен по паре (`externalSource`, `externalDefectId`) |

Тайм-аут вызова — 5 секунд. Приоритет «Ошибки» Task Tracker назначает сам по своей таблице `severity → priority` (`/admin/severity-mapping`).

### 6.1а. Task Tracker: чтение «Ошибки» опросом

Временный механизм, выбранный Task Tracker до решения о Kafka ([его 162](../../task-tracker/docs/block-i-integration-and-deployment/162.integration-spec.md#уточнение-выбора-на-12102026)). Вызовы — под отдельной учётной записью чтения `qa-tracker-reader` без ролей `testing-service` и `reports-service` (Q-09).

| Задача | Запрос | Период |
| --- | --- | --- |
| Список статусов для таблицы маппинга | `GET /api/v1/statuses` | Раз в час и по кнопке администратора |
| Статус, приоритет, исполнитель «Ошибки» | `GET /api/v1/work-items/{id}` для каждого дефекта в `SYNCED`, кроме `CLOSED` дольше 30 суток | Раз в 60 секунд |
| Комментарии | `GET /api/v1/work-items/{id}/comments` для тех же дефектов, если изменилось `updatedAt` задачи | Раз в 60 секунд |
| Итерации | `GET /api/v1/iterations` | Раз в час, если итерации не пришли в `release-context` Planning System |

Изменение применяется, только если `updatedAt` задачи больше `defect.tracker_updated_at`; комментарий — если его идентификатора ещё нет в `defect_comment.external_comment_id`. Тайм-аут вызова 5 секунд; при ошибке цикл пропускается и повторяется со следующим интервалом. Запись статусов и комментариев в Task Tracker контрактом не предусмотрена (Q-01).

### 6.4. Planning System: релизные рамки

Контракт принадлежит Planning System: [130](../../planning-system/docs/130.api-contracts.md), операция `getReleaseContext`, роль `qa.read` (их S-07). Описан, но не реализован (Q-04).

| Задача | Запрос |
| --- | --- |
| Релизы, вехи, эпики, фичи и проекция итераций утверждённой версии плана | `GET /api/v1/projects/{projectId}/release-context` и при необходимости `?planVersionId=` для исторической версии |

QA System сохраняет в `planning_item_cache` элементы с их `logicalItemId`, датами, родителем и ссылками на итерации Task Tracker, а также `dataAsOf` и `quality`. Черновик плана не читается. Если `iterations = null` и `quality = PARTIAL`, итерация вводится вручную. Событие `PlanActivated` (Kafka, предложено Planning System) — сигнал перечитать проект вне расписания.
