## SD-01. Создание прогона и ручное выполнение кейса

Связи: UC-09, UC-10; US-QL-04, US-TS-07; FR-RUN-01, FR-RUN-03, NFR-05.

```mermaid
sequenceDiagram
    actor QL as QA-лид
    actor TS as Тестировщик
    participant UI as SPA
    participant API as HTTP-слой
    participant RUN as Run Service
    participant DB as PostgreSQL

    QL->>UI: создать прогон из плана на окружении dev
    UI->>API: POST /runs {planId, environment}
    API->>API: проверить токен и роль
    API->>RUN: создать прогон
    RUN->>DB: BEGIN, прочитать состав плана и текущие версии кейсов
    alt план активен и состав не пуст
        RUN->>DB: вставить test_run и run_result со ссылкой на версию, COMMIT
        RUN-->>API: прогон CREATED
        API-->>UI: 201
    else план не активен или состав пуст
        RUN->>DB: ROLLBACK
        API-->>UI: 409 PLAN_NOT_ACTIVE или 422 RUN_EMPTY
    end
    QL->>UI: назначить тестировщика, запустить
    UI->>API: POST /runs/{id}/start
    API->>RUN: запустить
    RUN->>DB: статус IN_PROGRESS и событие TestRunStarted в исходящие
    TS->>UI: открыть назначенный кейс
    UI->>API: GET /test-cases/{id}?version=N
    API-->>UI: шаги зафиксированной версии
    TS->>UI: отметить шаги, записать фактический результат
    UI->>API: PUT /runs/{id}/results/{resultId}
    API->>RUN: записать результат
    alt прогон выполняется
        RUN->>DB: BEGIN, обновить run_result и step_result, событие в исходящие, COMMIT
        API-->>UI: 200, результат
    else прогон завершён
        API-->>UI: 409 RUN_FINISHED
    end
```

Тайм-аут запросов интерфейса — 10 секунд. При ошибке записи транзакция откатывается целиком: результата без события и события без результата не бывает.

## SD-02. Автоматический прогон по запросу CI

Связи: UC-12, UC-13; US-CI-01, US-AU-03, US-AU-04, US-EX-01; FR-RUN-08, FR-RUN-09, FR-RUN-10, NFR-03.

```mermaid
sequenceDiagram
    participant CI as GitHub Actions
    participant API as HTTP-слой
    participant RUN as Run Service
    participant DB as PostgreSQL
    participant EXE as Executor
    participant KC as Keycloak
    participant AT as Autotest Runner
    participant SUT as Тестируемая подсистема

    CI->>API: POST /runs {suiteName Smoke, environment dev, start true}
    API->>RUN: создать и запустить
    RUN->>DB: BEGIN, test_run, run_result, execution_job QUEUED
    alt набор не исполняется на этом окружении
        RUN->>DB: COMMIT
        API-->>CI: 201, прогон IN_PROGRESS
    else сработал уникальный индекс набора и окружения
        RUN->>DB: ROLLBACK
        API-->>CI: 409 SUITE_ALREADY_RUNNING
    end
    loop опрос очереди
        EXE->>DB: SELECT … FOR UPDATE SKIP LOCKED
    end
    DB-->>EXE: задание
    EXE->>DB: статус RUNNING, commit SHA автотестов
    EXE->>KC: client credentials qa-executor
    alt токен получен
        KC-->>EXE: служебный токен
        EXE->>AT: запустить автотесты по ключам кейсов
        loop каждый автоматизированный кейс
            AT->>SUT: шаги проверки
            alt ответ получен
                SUT-->>AT: ответ
            else подсистема недоступна
                AT-->>AT: результат BLOCKED с причиной
            end
        end
        AT-->>EXE: отчёт JUnit XML и журналы
        EXE->>RUN: записать результаты по кейсам
        RUN->>DB: run_result, события, дефекты по провалам (SD-03)
    else Keycloak недоступен
        EXE->>RUN: все кейсы задания BLOCKED, причина «нет служебного токена»
    end
    EXE->>DB: задание DONE
    opt в прогоне нет ручных кейсов
        RUN->>DB: прогон COMPLETED, событие TestRunCompleted
    end
    loop до завершения
        CI->>API: GET /runs/{id}
        API-->>CI: статус и счётчики
    end
```

Тайм-ауты: один HTTP-запрос автотеста — 10 секунд; задание — 10 минут (настройка окружения). Задание без отметки активности дольше тайм-аута переводится в `TIMED_OUT`, невыполненные кейсы — в «Провален» с причиной «тайм-аут». При сбое исполнителя задание возвращается в очередь не более двух раз; уже записанные результаты не перезаписываются.

## SD-03. Автоматическое создание дефекта и дедупликация

Связи: UC-15; US-TS-09; FR-DEF-02, FR-DEF-03, FR-DEF-04; ADR-006.

```mermaid
sequenceDiagram
    participant RUN as Run Service
    participant DEF as Defect Service
    participant DB as PostgreSQL

    RUN->>DB: BEGIN, обновить run_result статус FAILED
    RUN->>DEF: провал кейса: версия, упавший шаг, фактический результат
    DEF->>DB: найти незакрытый автодефект по кейсу
    alt не найден
        DEF->>DB: вставить defect NEW с полями из версии кейса и результата
        alt вставка успешна
            DEF->>DB: defect_run_link, defect_history, исходящие: DefectChanged и запрос «Ошибки»
        else уникальный индекс: дефект создан параллельно
            DEF->>DB: прочитать существующий, вставить defect_run_link и комментарий
        end
    else найден в статусе READY_FOR_TEST
        DEF->>DB: статус REOPENED, reopen_count + 1, история, defect_run_link, DefectChanged
    else найден в другом незакрытом статусе
        DEF->>DB: defect_run_link и комментарий с фактическим результатом
    end
    DEF-->>RUN: идентификатор дефекта и признак создания
    RUN->>DB: событие TestResultRecorded с defectId, COMMIT
```

Весь сценарий — одна транзакция БД без сетевых вызовов: запрос в Task Tracker только ставится в исходящие. Ошибка на любом шаге откатывает и результат, и дефект.

## SD-04. Создание «Ошибки» в Task Tracker

Связи: UC-18; US-DV-01, US-TT-01, US-AD-03; FR-DEF-06, NFR-11; ADR-007.

```mermaid
sequenceDiagram
    participant REL as Outbox Relay
    participant DB as PostgreSQL
    participant TTC as Task Tracker Client
    participant TT as Task Tracker
    actor AD as Администратор

    loop каждые несколько секунд
        REL->>DB: взять неотправленные сообщения TRACKER_BUG
    end
    REL->>TTC: создать «Ошибку» по дефекту DEF-45
    TTC->>TT: POST /api/v1/bugs {externalSource qa-system, externalDefectId DEF-45, …}
    alt 201 created или 200 already-exists
        TT-->>TTC: id, workItemUrl
        TTC-->>REL: успех
        REL->>DB: BEGIN, defect: tracker_work_item_id, SYNCED, история, DefectChanged TRACKER_LINKED, сообщение отправлено, COMMIT
    else тайм-аут 5 с, 5xx или ошибка сети
        TTC-->>REL: временная ошибка
        REL->>DB: attempts + 1, следующая попытка с нарастающей задержкой
    else 401, 403 или 422
        TT-->>TTC: структурированная ошибка, correlationId
        TTC-->>REL: постоянная ошибка
        REL->>DB: defect: FAILED, last_error
        Note over REL,AD: администратор видит сбой в состоянии интеграций и повторяет отправку — POST /defects/{id}/sync
    end
```

Повтор безопасен: Task Tracker не создаёт дубликат для той же пары (`externalSource`, `externalDefectId`). Задержка повторов растёт от 5 секунд до 10 минут; после 20 попыток состояние становится `FAILED`. Обратный поток статусов из Task Tracker — SD-08.

## SD-05. Передача данных в Reports

Связи: UC-20; US-RP-01; vision 8.3; ADR-007.

```mermaid
sequenceDiagram
    participant RUN as Run Service
    participant DB as PostgreSQL
    participant REL as Outbox Relay
    participant KF as Kafka
    participant REP as Reports
    participant API as HTTP-слой

    RUN->>DB: BEGIN, прогон COMPLETED, TestRunCompleted в исходящие, COMMIT
    REL->>DB: взять неотправленные KAFKA_EVENT
    REL->>KF: отправить в dev.qa.test-run.v1, ключ runId
    alt брокер подтвердил
        KF-->>REL: подтверждение
        REL->>DB: отметить отправленным
    else брокер недоступен
        REL->>DB: attempts + 1, повтор позже
    end
    KF-->>REP: событие
    REP->>REP: eventId уже обработан?
    alt нет
        REP->>REP: применить к витрине, запомнить eventId
    else да
        REP->>REP: пропустить
    end
    Note over REP,API: сверка по расписанию
    REP->>API: GET /reports/test-runs?updatedSince=…
    alt токен с ролью qa-reports-reader
        API-->>REP: страница прогонов
    else роли нет
        API-->>REP: 403
    end
```

Если отметка «отправлено» не записалась после успешной отправки, событие уйдёт повторно с тем же `eventId` — потребитель его отбросит.

## SD-06. Перепроверка и закрытие дефекта

Связи: UC-14, UC-17; US-TS-11, US-QL-05; FR-DEF-05, FR-RUN-07.

```mermaid
sequenceDiagram
    actor TS as Тестировщик
    participant API as HTTP-слой
    participant DEF as Defect Service
    participant RUN as Run Service
    participant DB as PostgreSQL

    Note over TS,DB: FIXED приходит из Task Tracker опросом (SD-08), при выключенном опросе QA-лид ставит его вручную
    TS->>API: POST /defects/{id}/transitions {to READY_FOR_TEST}
    API->>DEF: сменить статус
    alt переход допустим
        DEF->>DB: обновить, история, DefectChanged
        API-->>TS: 200
    else переход недопустим
        API-->>TS: 409 INVALID_TRANSITION, перечень допустимых
    end
    TS->>API: POST /runs/{id}/rerun
    API->>RUN: создать повторный прогон по FAILED и BLOCKED
    RUN->>DB: новый test_run с parent_run_id, результаты NOT_RUN
    TS->>API: PUT /runs/{newId}/results/{resultId}
    API->>RUN: записать результат
    RUN->>DEF: результат кейса с дефектом в READY_FOR_TEST
    alt кейс пройден
        DEF->>DB: статус CLOSED, closed_at, история, DefectChanged
    else кейс провален
        DEF->>DB: статус REOPENED, reopen_count + 1, история, DefectChanged
    end
```

## SD-07. Привязка плана к релизу, вехе и итерации

Связи: UC-07, UC-22; US-QL-02; FR-TP-05, FR-TP-06; ADR-015.

```mermaid
sequenceDiagram
    actor QL as QA-лид
    participant UI as SPA
    participant API as HTTP-слой
    participant DIR as Directory Service
    participant PLAN as Plan and Suite Service
    participant DB as PostgreSQL
    participant PS as Planning System

    QL->>UI: создать план, выбрать проект
    UI->>API: GET /directory/planning-items?projectId=P&type=RELEASE
    API->>DIR: релизы проекта
    DIR->>DB: planning_item_cache проекта
    alt кэш старше часа или пуст
        DIR->>PS: GET /api/v1/projects/P/release-context (тайм-аут 5 с)
        alt утверждённая версия есть
            PS-->>DIR: релизы, вехи, эпики, фичи, итерации, dataAsOf, quality
            DIR->>DB: обновить кэш
        else 404 или нет утверждённой версии
            PS-->>DIR: ошибка
            DIR-->>API: пусто, причина
        else тайм-аут или 5xx
            DIR-->>API: прежний кэш с датой актуальности
        end
    end
    API-->>UI: релизы и вехи, связанные итерации, dataAsOf
    QL->>UI: выбрать релиз R1, веху, итерацию
    UI->>API: POST /test-plans {scopeKind RELEASE, planningProjectId P, planningReleaseId R1, planningPlanVersionId V3, trackerIterationId I}
    API->>PLAN: создать план
    alt ссылки найдены в кэше
        PLAN->>DB: test_plan, refs_verified = true
    else релизы недоступны, ссылка введена вручную
        PLAN->>DB: test_plan, refs_verified = false
    end
    API-->>UI: 201, план DRAFT
    Note over DIR,PS: новая утверждённая версия плана V4 не меняет привязку: R1 ищется по logicalItemId
```

Тайм-аут обращения к Planning System — 5 секунд; при отказе сохранение плана не блокируется (NFR-11). Если `iterations = null` и `quality = PARTIAL`, итерация вводится вручную.

## SD-08. Синхронизация статуса и комментариев «Ошибки» с Task Tracker

Связи: UC-18, UC-24; US-DV-03, US-QL-06; FR-DEF-06, FR-DEF-07, FR-DEF-09, NFR-04; ADR-008.

```mermaid
sequenceDiagram
    participant SCH as Scheduler
    participant SYNC as Tracker Sync
    participant TTC as Task Tracker Client
    participant TT as Task Tracker
    participant DEF as Defect Service
    participant DB as PostgreSQL

    SCH->>SYNC: цикл опроса, раз в 60 с
    SYNC->>DB: дефекты SYNCED, кроме закрытых дольше 30 суток
    loop каждый дефект
        SYNC->>TTC: прочитать «Ошибку»
        TTC->>TT: GET /api/v1/work-items/{id} (тайм-аут 5 с)
        alt ответ получен
            TT-->>TTC: status, priority, assignee, updatedAt
            SYNC->>DB: ключ tracker:{id}:{updatedAt} есть в inbox_event?
            alt уже применено
                SYNC->>SYNC: пропустить
            else новое изменение
                SYNC->>DEF: применить изменение
                DEF->>DB: BEGIN, маппинг статуса Task Tracker
                alt статус сопоставлен и переход допустим
                    DEF->>DB: статус OPEN, IN_PROGRESS или FIXED, история с источником TRACKER, DefectChanged в исходящие
                else не сопоставлен или переход недопустим
                    DEF->>DB: статус не меняется, tracker_mismatch = true
                end
                DEF->>DB: копия статуса, приоритета, исполнителя, inbox_event APPLIED, COMMIT
                opt updatedAt изменился
                    TTC->>TT: GET /api/v1/work-items/{id}/comments
                    TT-->>TTC: комментарии
                    DEF->>DB: новые комментарии с источником TRACKER по external_comment_id
                end
            end
        else тайм-аут, 5xx или 401 и 403
            TTC-->>SYNC: ошибка
            SYNC->>DB: tracker_poll_state.last_error, дефект не меняется
        end
    end
    Note over DEF,DB: дефект CLOSED или REOPENED, а «Ошибка» в другом статусе — tracker_mismatch = true, список «требует действия в трекере»
```

Повторное чтение той же задачи без изменений не создаёт записей истории. Неприменённое изменение после 3 попыток остаётся в `inbox_event` со статусом `FAILED` и видно администратору. Запись статусов и комментариев в Task Tracker не выполняется: у него нет такого API (Q-01).

## SD-09. Приёмка стенда: «Smoke» из пайплайна и 25 приёмочных кейсов

Связи: UC-23, UC-12, UC-13; US-CI-01, US-QL-08, US-PM-03; FR-RUN-08, FR-RUN-11; ADR-017.

```mermaid
sequenceDiagram
    participant CI as Пайплайн
    actor QL as QA-лид
    actor TS as Тестировщик
    participant API as HTTP-слой
    participant RUN as Run Service
    participant ACC as Acceptance
    participant EXE as Executor
    participant DB as PostgreSQL

    Note over CI,DB: после каждого развёртывания staging
    CI->>API: POST /runs {suiteName Smoke, environment staging, start true}, Idempotency-Key = commit SHA
    alt ключ уже использован
        API-->>CI: 201, тот же прогон
    else новый запуск
        API->>RUN: создать и запустить
        RUN->>DB: прогон, задание QUEUED
        API-->>CI: 201, прогон IN_PROGRESS
    end
    EXE->>DB: взять задание, исполнить автотесты (SD-02), провалы — дефекты (SD-03)
    loop каждые 15 с, не дольше 15 минут
        CI->>API: GET /runs/{id}
        API-->>CI: status, summary, smokeVerdict
    end
    alt smokeVerdict GREEN
        CI->>CI: шаг зелёный, ссылка на прогон в итоге шага
    else smokeVerdict RED
        CI->>CI: шаг красный, ссылки на прогон и дефекты, отката нет
    else итог не получен за 15 минут
        CI->>CI: шаг красный «нет вердикта»
    end

    Note over QL,DB: перед демонстрацией вехи
    QL->>API: POST /runs {suiteId Приёмка стенда, environment staging, start true}
    API->>RUN: 25 кейсов: автоматические — исполнителю, ручные — тестировщикам
    TS->>API: PUT /runs/{id}/results/{resultId}, кейсы без API — SKIPPED с причиной
    RUN->>DB: прогон COMPLETED, TestRunCompleted
    QL->>API: POST /runs/{id}/verdict {ACCEPTED}
    API->>ACC: проверить критерии
    ACC->>DB: есть FAILED? есть незакрытые Blocker и Critical по кейсам набора?
    alt критерии выполнены
        ACC->>DB: verdict ACCEPTED, verdict_by, verdict_at, TestRunCompleted с вердиктом
        API-->>QL: 200, число непроверенных кейсов
    else есть провалы или открытые Blocker и Critical
        API-->>QL: 409 ACCEPTANCE_CRITERIA_NOT_MET с перечнем
        QL->>API: POST /runs/{id}/verdict {REJECTED}, затем повторный прогон упавших (UC-14)
    end
```

Красный «Smoke» не откатывает развёртывание: решение об откате принимают Infra и команда-владелец подсистемы, получившая «Ошибку». Красная «Приёмка стенда» блокирует демонстрацию вехи до повторного прогона и нового вердикта.
