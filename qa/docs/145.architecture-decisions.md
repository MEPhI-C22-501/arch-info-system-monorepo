**ADR-001. Стек: Python и FastAPI, PostgreSQL, React и TypeScript**

- Контекст: vision оставляет стек открытым (вопрос 5) и предлагает держать автотесты на одном стеке с системой. Автотесты — HTTP-проверки чужих API; для них стандартом де-факто является pytest. Соседи используют Go (Reference Manager) и Java (Task Tracker), общего стека в проекте нет.
- Решение: серверная часть и исполнитель — Python с FastAPI; хранилище — PostgreSQL той же мажорной версии, что у Infra; миграции — Alembic; интерфейс — React и TypeScript. OpenAPI — источник истины, проверяется контрактными тестами.
- Последствия: (+) один язык для системы, исполнителя и автотестов, исполнитель вызывает pytest как библиотеку; (+) FastAPI строит схему из тех же моделей, что проверяют запросы; (−) третий язык серверной части в монорепозитории, общие библиотеки соседей не переиспользуются; (−) производительность ниже Go и Java, для NFR-09 и NFR-10 достаточна.
- Связь: NFR-13, NFR-01.

**ADR-002. Модульный монолит и отдельный процесс исполнителя из того же образа**

- Контекст: в системе пять частей (vision 1.3). Автотесты выполняются минутами и не должны занимать обработчики запросов; при этом у команды нет ресурса сопровождать несколько сервисов.
- Решение: один код и один образ с двумя точками входа: `api` обслуживает запросы, `worker` исполняет задания, публикует исходящие сообщения и выполняет расписания. Модули внутри — кейсы, планы, прогоны, дефекты, вложения, интеграции — общаются вызовами в процессе и работают с одной БД.
- Последствия: (+) одна сборка, одна миграция, транзакция охватывает результат, дефект и исходящее сообщение; (+) исполнители масштабируются числом экземпляров `worker`; (−) модули связаны общей схемой БД, границы держатся дисциплиной и проверкой импортов; (−) выпуск API и исполнителя всегда совместный.
- Связь: NFR-08, NFR-10.

**ADR-003. Неизменяемые версии кейса; прогон ссылается на версию**

- Контекст: кейс живёт дольше планов и прогонов и постоянно правится. Старые результаты не должны «переписываться» после правки (NFR-05, FR-RUN-01).
- Решение: каждое сохранение создаёт строку `test_case_version` с собственными шагами; строки не изменяются. Результат прогона хранит ссылку на версию, результат шага — на шаг этой версии. Дефект хранит версию и шаг, на которых возник.
- Последствия: (+) исторический прогон и дефект всегда показывают шаги, которые реально выполнялись; (+) история изменений получается без отдельного журнала; (−) шаги дублируются между версиями, объём растёт с числом правок (учтено в NFR-10); (−) сравнение версий вычисляется при чтении.
- Связь: NFR-05, FR-TC-04, FR-RUN-01.

**ADR-004. Очередь заданий исполнителя в PostgreSQL**

- Контекст: исполнителю нужна очередь с гарантией «одно задание — один исполнитель», запретом параллельного запуска набора на окружении (FR-RUN-10) и обнаружением зависших заданий (NFR-03). Kafka в проекте есть, но выдаётся по заявке и не даёт отбора «возьми следующее и заблокируй».
- Решение: таблица `execution_job`; исполнитель берёт задание запросом `SELECT … FOR UPDATE SKIP LOCKED`. Запрет параллельного запуска — частичный уникальный индекс по (набор, окружение) для незавершённых заданий. Задание без отметки активности дольше тайм-аута переводится в `TIMED_OUT`, а его невыполненные кейсы — в «Провален».
- Последствия: (+) постановка задания атомарна с запуском прогона; (+) нет зависимости от брокера для основной функции; (−) опрос таблицы даёт задержку старта до нескольких секунд; (−) при тысячах заданий в минуту решение пришлось бы менять, для учебного объёма запас большой.
- Связь: NFR-01, NFR-03, NFR-10, FR-RUN-09, FR-RUN-10.

**ADR-005. Автотесты в `qa/autotests`, связь по ключу, результат в JUnit XML**

- Контекст: автотесты должны быть воспроизводимы (NFR-07) и связаны с кейсами (FR-TC-09). Vision предлагает этот вариант в вопросе 5.
- Решение: автотесты лежат в каталоге `qa/autotests` монорепозитория и входят в образ исполнителя. Ключ автотеста — идентификатор теста pytest. Исполнитель запускает тесты по ключам кейсов задания, читает отчёт JUnit XML и сопоставляет записи с кейсами. Прогон хранит commit SHA образа. Автотест получает адреса подсистем и служебный токен из окружения, создаёт данные с префиксом прогона и убирает их за собой.
- Последствия: (+) версия автотестов однозначно определяется коммитом; (+) формат отчёта стандартен, другой инструмент подключается без изменения исполнителя; (−) новый автотест требует пересборки образа исполнителя; (−) переименование теста рвёт связь — для этого есть список несвязанных ключей.
- Связь: NFR-02, NFR-07, FR-TC-09.

**ADR-006. Один незакрытый автодефект на кейс — частичным уникальным индексом**

- Контекст: после первого красного прогона стенда без дедупликации появятся десятки одинаковых дефектов (vision 4.3). Проверка «найти, потом создать» в коде не защищает от двух одновременных результатов.
- Решение: уникальный индекс по `test_case_id` для строк с `origin = 'AUTO'` и статусом, отличным от `CLOSED`. При нарушении система находит существующий дефект и добавляет связь с результатом. На ручные дефекты ограничение не действует.
- Последствия: (+) правило выполняется при любой конкуренции; (+) закрытый дефект не мешает завести новый; (−) два разных дефекта, найденных автотестом в одном кейсе, сливаются в один — различает их тестировщик вручную.
- Связь: FR-DEF-03.

**ADR-007. Таблица исходящих сообщений для Kafka и Task Tracker**

- Контекст: изменение в БД и публикация события или вызов Task Tracker не образуют общей транзакции. Недоступность соседа не должна останавливать тестирование (NFR-11); событие нельзя потерять и нельзя опубликовать для отменённого изменения.
- Решение: событие для Kafka и запрос создания «Ошибки» записываются строкой `outbox_message` в транзакции изменения. Процесс `worker` отправляет строки и отмечает успех; при ошибке повторяет с нарастающей задержкой. Идентификатор строки — `eventId` события. Входящие события дедуплицируются таблицей `inbox_event`.
- Последствия: (+) нет потерь и «призрачных» событий; (+) повтор запроса в Task Tracker безопасен: его API идемпотентен; (−) доставка at-least-once, потребитель обязан устранять дубли; (−) задержка публикации до 30 секунд; (−) таблицу нужно чистить.
- Связь: NFR-04, NFR-11, NFR-12.

**ADR-008. Раздельное владение статусами дефекта; ручной ввод статусов разработки до контракта**

- Контекст: vision делит статусы между QA System и Task Tracker и ждёт статусы разработки событием. Task Tracker даёт только создание «Ошибки» и событий наружу не публикует (Q-01).
- Решение: QA System — мастер QA-полей и статусов `NEW`, `READY_FOR_TEST`, `CLOSED`, `REOPENED`. Статусы `OPEN`, `IN_PROGRESS`, `FIXED` принадлежат Task Tracker; пока обратного потока нет, их вносит QA-лид, а история хранит источник `QA`. Приёмник изменений из Task Tracker реализуется за флагом конфигурации и включается после согласования контракта — событиями или опросом.
- Последствия: (+) жизненный цикл дефекта работает уже в M4 без зависимости от соседа; (+) переход на автоматический поток не меняет модель данных; (−) статус в QA System может отставать от Task Tracker; (−) FR-DEF-06 выполнено частично до согласования.
- Связь: FR-DEF-05, FR-DEF-06, NFR-04.

**ADR-009. Классификаторы серьёзности, приоритета и типов кейсов ведёт QA System**

- Контекст: vision предполагал получать классификаторы из Reference Manager. Reference Manager снял их из своего состава и закрепил серьёзность за QA System.
- Решение: значения хранятся в `classifier_value`, окружения — в `environment`; ведёт их администратор QA System. Набор серьёзности фиксирован кодом (Blocker…Trivial), потому что от него зависят преобразование для Task Tracker и отчёты; администратор меняет названия и отключает значения.
- Последствия: (+) нет зависимости от чужого выпуска ради пяти значений; (−) значения не общие для ERP: Reports получает их от нас в событиях; (−) расхождение со шкалой Task Tracker решается преобразованием (Q-02).
- Связь: INT-03, FR-DEF-08.

**ADR-010. Чужие объекты — внешние ссылки с кэшем, без внешних ключей**

- Контекст: итерации, вехи, эпики и сотрудники принадлежат другим подсистемам (FR-DAT-02). Их API частично не опубликованы, а доступность не гарантирована.
- Решение: идентификаторы хранятся строками без внешних ключей. Сотрудники и подразделения кэшируются в `employee_cache` с временем синхронизации; остальные ссылки вводятся вручную и помечаются непроверенными, пока нет источника. Запись со ссылкой сохраняется при недоступном источнике.
- Последствия: (+) работа не блокируется соседями; (+) удаление объекта у владельца не ломает наши данные; (−) возможны «висячие» ссылки и опечатки при ручном вводе; (−) отображаемые имена могут устареть до следующей синхронизации.
- Связь: NFR-11, FR-DAT-02, FR-TP-05.

**ADR-011. Keycloak OIDC, локальная проверка JWT, клиентские роли**

- Контекст: все обращения требуют действительного токена, права проверяет сервер (FR-SEC-01). Infra даёт Keycloak и не создаёт собственный сервис авторизации.
- Решение: API проверяет подпись, издателя, аудиторию и срок токена локально по ключам JWKS с кэшем. Права берутся из клиентских ролей `qa-system` в токене. Служебный клиент `qa-ci` и клиент Reports с ролью `qa-reports-reader` получают токен по client credentials. Исполнитель использует отдельный клиент `qa-executor`; его секрет передаётся через окружение и маскируется в журналах.
- Последствия: (+) нет обращения к Keycloak на каждый запрос; (+) роли выдаются в одном месте для всей ERP; (−) отзыв роли действует после истечения токена; (−) требуется заявка в Infra на клиентов и роли.
- Связь: NFR-06, FR-SEC-01, FR-SEC-02.

**ADR-012. Вложения в S3, метаданные в БД, выдача по ссылке с ограниченным сроком**

- Контекст: скриншоты и журналы автотестов не должны раздувать БД; Infra выделяет каждой команде отдельный бакет.
- Решение: файл принимает API, проверяет размер и тип и записывает в бакет `arch-dev-qa` под ключом `<вид владельца>/<идентификатор>/<uuid>`. В БД хранятся метаданные и контрольная сумма. Скачивание — перенаправление на подписанную ссылку со сроком 5 минут после проверки прав. До выделения бакета журналы автотестов хранятся в `run_result.log_text`.
- Последствия: (+) права на файл наследуются от владельца и проверяются сервером; (+) бакет не публичный; (−) запись объекта и строки метаданных не атомарна: «осиротевшие» объекты чистит фоновое задание; (−) эпик вложений зависит от Infra.
- Связь: FR-TC-05, FR-RUN-04, NFR-06.

**ADR-013. В первой версии только API-автотесты**

- Контекст: браузерные проверки требуют отдельной инфраструктуры и готовых интерфейсов соседей, которых пока нет (vision 1.4, 9).
- Решение: исполнитель запускает только HTTP-проверки публичных API. Кейсы, требующие интерфейса, остаются ручными (TC-TT-02, TC-INF-02).
- Последствия: (+) образ исполнителя лёгкий, прогон укладывается в NFR-01; (−) интерфейсы соседей автоматически не проверяются; (+) формат JUnit XML (ADR-005) позволит добавить браузерный инструмент позже без изменения модели.
- Связь: NFR-01, INT-09.
