## 1. Назначение и граница

QA System — система управления тестированием — хранит тест-кейсы, собирает их в планы, проводит ручные и автоматические прогоны и заводит дефекты по провалам. Вторая задача модуля — приёмочный контур проекта: стартовый набор из 25 кейсов проверяет соседние подсистемы на общем стенде ([vision 4.6](vision.md#46-приёмка-стенда)).

| Внутри QA System | За пределами модуля |
| --- | --- |
| Тест-кейсы, шаги, версии, шаблоны, импорт и экспорт | Задачи, итерации, канбан, статусы и приоритеты задач — Task Tracker |
| Наборы и тест-планы, их привязка к релизу, вехе и итерации | Проекты, релизы, вехи, эпики, фичи — Planning System |
| Прогоны, результаты кейсов и шагов, повторные прогоны, приёмка стенда | HR-профили сотрудников, подразделения — Reference Manager |
| Исполнитель автотестов и стартовый набор автотестов | Учётные записи, пароли, роли — Keycloak |
| Дефекты, их QA-поля, статусы тестирования, история и перепроверка | Задача «Ошибка», её статусы разработки и приоритет исправления — Task Tracker |
| Классификаторы серьёзности, приоритета кейса, типов кейсов, окружений; таблица маппинга статусов | Метрики качества, отчёты, аналитическое хранилище — Reports |
| Метаданные вложений и права на них | Файловые объекты — MinIO; брокер событий — Kafka; развёртывание и пайплайны — Infra |
| Сводки плана и прогона, вердикт приёмки | Нагрузочное тестирование и проверки через браузер — вне первой версии |

QA System не читает и не изменяет чужие базы данных. Единственная запись в чужие данные — создание задачи «Ошибка» через API Task Tracker.

При недоступности Task Tracker дефект сохраняется у нас с отметкой незавершённой синхронизации и досылается позже. При недоступности источника справочных данных работа продолжается на кэше с датой актуальности. Недоступность тестируемой подсистемы даёт результат «Провален» или «Заблокирован» с причиной.

### 3.1. Откуда берутся люди

Для назначения ответственного за план и тестировщиков на прогон и кейс (FR-TP-03, FR-RUN-02) нужны два источника, и у каждого свой владелец:

| Что нужно | Источник | Как используется |
| --- | --- | --- |
| Кто вошёл и что ему можно | Keycloak: `sub` токена и клиентские роли `qa-system` | Проверка прав на каждый запрос; автор записей и истории |
| Кого можно назначить и как его показать | Reference Manager: HR-профиль `employees` (ФИО, подразделение, состояние занятости, `account_user_id`) и `org_units` | Список кандидатов на назначение и отображаемые имена |
| Связь двух источников | `employees.account_user_id` = `sub` | Назначенный сотрудник находит свои кейсы после входа |

Кандидат на назначение — активный сотрудник с заполненным `account_user_id`. Уволенный сотрудник сохраняется в старых записях, но не предлагается для новых назначений. Модуль справочников классификаторы тестирования не ведёт, но сотрудников ведёт: эта граница закреплена Reference Manager 2026-10-02. Срок и ответственные интеграции — I-04 в [160](160.integration-plan.md).

### 3.2. Аналитический контур

Reports получает данные QA System двумя путями: события Kafka — для оперативных отчётов (не позже 2 минут), и задание ETL раз в час — постраничное чтение `/api/v1/reports/{test-cases, test-plans, test-runs, test-results, defects}` с `updatedSince` в аналитическое хранилище. Метрики качества считает Reports. Пакетных файлов QA System не формирует — см. [vision 8.4](vision.md#84-участие-в-аналитическом-контуре-reports) и [162](162.integration-spec.md).

### 3.3. Тестируемые подсистемы как объект проверки

Reference Manager, Task Tracker, Planning System, Reports и Infra — не только соседи по обмену, но и объект проверки: по каждой пять кейсов стартового набора. QA System обращается к ним только через публичные API под служебной учётной записью `qa-executor`, данные создаёт с префиксом прогона и убирает за собой. Провал кейса превращается в «Ошибку» у команды-владельца подсистемы.

## 4. Акторы

Люди: **H-01** QA-лид, **H-02** тестировщик, **H-03** автоматизатор, **H-04** разработчик, **H-05** руководитель проекта, **H-06** администратор. Системы: **S-01…S-09** из раздела 3 и **S-10** исполнитель автотестов. Цели и действия каждого — в [030](030.actors.md), права — в [070](070.role-matrix.md).

Infra — команда-поставщик окружения, а не самостоятельный бизнес-актор.
