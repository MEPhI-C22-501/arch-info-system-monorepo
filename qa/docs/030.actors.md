## 1. Люди

| ID | Актор | Роль в предметной области | Действия в системе | Роль доступа |
| --- | --- | --- | --- | --- |
| H-01 | QA-лид | Руководитель тестирования итерации или релиза | Ведёт тест-планы и наборы, назначает тестировщиков и сроки, запускает и завершает прогоны, создаёт повторные прогоны, смотрит сводку и решает, готова ли итерация; до согласования Q-01 вносит статусы разработки дефекта | R-04 `qa-lead` |
| H-02 | Тестировщик | Инженер по ручному тестированию | Пишет, копирует и архивирует кейсы, выполняет назначенные кейсы по шагам, запускает автотесты, заводит дефекты, перепроверяет исправления, закрывает и переоткрывает дефекты | R-02 `qa-tester` |
| H-03 | Автоматизатор | Инженер по автоматизации тестирования | Пишет автотесты в `qa/autotests`, указывает ключ автотеста в кейсе, разбирает несвязанные ключи и журналы, запускает автопрогоны | R-03 `qa-automation` |
| H-04 | Разработчик | Участник команды тестируемой подсистемы | Получает дефект как «Ошибку» в Task Tracker; в QA System читает дефект, шаги воспроизведения, журнал и прогон, оставляет комментарий | R-01 `qa-viewer` |
| H-05 | Руководитель проекта | Ответственный за сроки итерации или релиза | Смотрит состояние тестирования: сводку плана и прогона, открытые дефекты по серьёзности | R-01 `qa-viewer` |
| H-06 | Администратор | Участник команды QA, отвечающий за настройку | Ведёт шаблоны кейсов, классификаторы, окружения и расписания; смотрит состояние интеграций и запускает обновление кэша; бизнес-данные не редактирует | R-05 `qa-admin` |

Роли назначаются в Keycloak. Один человек может совмещать роли: права складываются.

## 2. Внешние системы

| ID | Актор | Протокол | Сценарий интеграции | Направление |
| --- | --- | --- | --- | --- |
| S-01 | Keycloak | OIDC, JWKS по HTTPS | Пользователь входит в Keycloak, QA System проверяет подпись, срок, издателя и роли токена; исполнитель получает служебный токен по client credentials | QA System → Keycloak |
| S-02 | Task Tracker | REST / JSON | QA System создаёт «Ошибку» по дефекту и сохраняет её идентификатор; обратный поток статусов и комментариев согласуется (Q-01) | QA System → Task Tracker; обратно — после согласования |
| S-03 | Planning System | REST / JSON | QA System читает проекты, вехи, эпики и фичи для группировки кейсов и привязки планов (Q-04) | QA System → Planning System |
| S-04 | Reference Manager | REST `/v1`, Google AIP | QA System постранично читает `employees` и `org_units`, держит кэш и находит сотрудника по `account_user_id` из токена | QA System → Reference Manager |
| S-05 | Reports | Kafka; REST read-only | Reports подписан на события прогонов и дефектов и сверяет витрину через `/api/v1/reports/*` под ролью R-07 | QA System → Kafka → Reports; Reports → QA System |
| S-06 | GitHub Actions | REST / JSON, служебный клиент `qa-ci` | После развёртывания стенда workflow запускает прогон набора и опрашивает его итог | CI → QA System |
| S-07 | MinIO | S3 API, Signature V4 | QA System кладёт вложения и журналы в бакет `arch-dev-qa` и выдаёт ссылки с ограниченным сроком | QA System ↔ MinIO |
| S-08 | Kafka | Kafka protocol, `SASL_SSL` | QA System публикует события из [135](135.event-catalog.md); доставка at-least-once | QA System → Kafka |
| S-09 | Тестируемые подсистемы | REST / JSON | Исполнитель выполняет шаги автотестов против публичных API под служебной записью `qa-executor` | QA System → подсистема |
