# 080 — User Stories: внешние сервисы

**US-CI-01.** As a сервис пайплайна, I want запустить «Smoke» после развёртывания и получить вердикт so that выпуск сопровождался проверкой стенда.
- GWT-1: Given у клиента `qa-ci` действительный токен, When workflow после развёртывания вызывает запуск набора «Smoke» на окружении `staging` с ключом идемпотентности, равным commit SHA, Then возвращается идентификатор прогона, а опрос статуса показывает ход и итог.
- GWT-2: Given прогон завершён, When workflow читает итог, Then получает число кейсов по статусам и вердикт `GREEN` или `RED`; при `RED` шаг пайплайна завершается ошибкой со ссылкой на прогон.
- GWT-3: Given набор уже исполняется на этом окружении, When workflow запускает его снова, Then получает `409` со ссылкой на идущий прогон.
- GWT-4: Given токен без роли `qa-ci`, When вызывается запуск, Then ответ `403`, прогон не создан.
- GWT-5: Given workflow перезапущен с тем же ключом идемпотентности, When вызывает запуск, Then получает тот же прогон, второй не создаётся.

*(→ UC-12, UC-23; FR-RUN-08, FR-RUN-10, FR-RUN-11; актор S-06, роль R-06)*

**US-EX-01.** As a исполнитель автотестов, I want обращаться к тестируемым подсистемам под отдельной служебной записью so that автотесты проверяли систему так же, как клиент, и не имели лишних прав.
- GWT-1: Given секрет клиента `qa-executor` задан в окружении, When исполнитель начинает задание, Then он получает токен по client credentials и передаёт его автотестам.
- GWT-2: Given автотест создаёт данные, When он завершается, Then созданные записи имеют уникальный префикс прогона и удалены или помечены удалёнными.
- GWT-3: Given Keycloak недоступен, When исполнитель начинает задание, Then кейсы получают «Заблокирован» с причиной, прогон не зависает.

*(→ UC-13; FR-SEC-02, NFR-02, NFR-03, NFR-06)*

**US-TT-01.** As a Task Tracker, I want получать дефекты QA System идемпотентным запросом so that в бэклоге не появлялись дубликаты.
- GWT-1: Given дефект `DEF-45` создан, When QA System вызывает `POST /api/v1/bugs` с `externalSource = qa-system` и `externalDefectId = DEF-45`, Then Task Tracker отвечает `201` с идентификатором задачи.
- GWT-2: Given тот же запрос повторён, When Task Tracker обрабатывает его, Then отвечает `200` со статусом `already-exists`, а QA System сохраняет тот же идентификатор.
- GWT-3: Given запрос отклонён с `422`, When QA System получает ответ, Then синхронизация переходит в `FAILED`, причина видна администратору, повторов без вмешательства нет.

*(→ UC-18; FR-DEF-06; актор S-02)*

**US-RP-01.** As a сервис отчётности, I want получать результаты тестирования событиями и сверять их запросом so that считать pass rate и reopened rate без догадок.
- GWT-1: Given прогон завершён, When QA System публикует `TestRunCompleted`, Then событие содержит идентификатор прогона, число кейсов по статусам и ссылку на итерацию или веху.
- GWT-2: Given дефект переоткрыт, When публикуется `DefectChanged`, Then событие содержит статус `REOPENED`, серьёзность и идентификатор задачи Task Tracker.
- GWT-3: Given одно событие доставлено дважды, When Reports сравнивает `eventId`, Then второе можно отбросить: идентификатор совпадает.
- GWT-4: Given токен клиента с ролью `qa-reports-reader`, When Reports запрашивает `/api/v1/reports/defects?updatedSince=…`, Then получает постраничный ответ; изменяющих операций по этому пути нет.
- GWT-5: Given задание ETL Reports запускается раз в час, When оно читает `/api/v1/reports/test-cases?updatedSince=…` и остальные четыре ресурса, Then получает все изменённые с прошлого запуска строки, а повтор страницы возвращает те же строки.
